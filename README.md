# prepare-dev

利用者の希望を具体例と図で確かめ、設計・実装・レビュー・形式証明を進めるための、skill と補助コマンドです。指摘や確認結果は、どの要求・設計・コードの、どの版についてのものかをたどれる形で残します。

作り直す前の中身は `main` ブランチにあります。

## 中身

| 場所 | 内容 |
|---|---|
| `skills/` | skill 八つ。入口は `prepare-dev` |
| `cmd/ppdev/` | skill から呼ぶ補助コマンド `ppdev` |
| `internal/` | 記録、起動の照合、検証、図の処理 |
| `model/` | 最初に証明まで通した動きの、ルールと証明 |
| `hooks/` | 担当の起動を実行環境で止めるための設定例 |
| `.ppdev/` | このリポジトリ自身の記録。git に入れる |

### skill

| skill | 役割 |
|---|---|
| `prepare-dev` | 進行。次の作業と担当を選び、起動を設定と照合する |
| `prepare-requirements` | 要件整理。希望を、具体例・受入条件・未決事項・保証要求にする |
| `prepare-design` | 設計、試作、本番の実装 |
| `prepare-review-spec` | 仕様レビュー。新しい文脈の確認役が読む |
| `prepare-review-code` | 実装レビュー。再現できた不具合だけを残す |
| `prepare-verify` | 形式化と検証 |
| `prepare-show` | 見せ方。画面の絵・具体例・流れの図を、HTML のページにして開く。図への指摘を受け取る |
| `prepare-setup` | 担当ごとのモデル・思考量・人数を、利用者に確認して設定の表に書く |

参考にした既存の skill と、変えたところは [skills/SOURCES.md](skills/SOURCES.md) にあります。

## 使い始める

```bash
go build -o bin/ppdev ./cmd/ppdev
```

できた `bin/ppdev` を、PATH の通った場所に置きます。

対象のプロジェクトで `ppdev init` を実行します。記録の置き場所（`.ppdev/`）ができ、skill が `.agents/skills` と `.claude/skills` に入ります。skill は `ppdev` の中に入っているので、このリポジトリを対象のプロジェクトに置く必要はありません。

`ppdev` を新しくしたら、もう一度 `ppdev init` を実行します。編集していない skill は新しい版に置き換わり、編集した skill はそのまま残ります。

依頼は `prepare-dev` の skill から始めます。AI は、依頼をどう理解したかを HTML のページ（`.ppdev/pages/`）にして開き、利用者が決めるまで、頼まれたものを作りません。ページの見た目は、`prepare-show` の skill に入っている雛形（`page.html`）で決まります。

別の担当（レビューや証明）を使うときは、担当ごとのモデル・思考量・人数が要ります。`prepare-setup` の skill が利用者に確認して、設定の表に書きます。表の書き方は pstack の設定の表と同じで、一行が一つの役割、モデルを並べた数が人数です。

```
設計: gpt-a, gpt-a
仕様レビュー: gpt-a, gpt-b, gpt-b
証明: gpt-b @xhigh

通常の思考量: high
```

思考量は、表の値が出発点です。pstack と同じく、いちばん難しい作業では一段上げ、判断の作業では一段、定型の作業では二段以上下げます。表に「思考量の調整: 固定」と書けば、上げ下げしません。

表を作るまで、別の担当は起動しません。担当を使わない作業に、表は要りません。

## 確かめ方

```bash
scripts/check.sh
```

検証器 Lean 4.35.0 が要ります（`model/lean-toolchain`）。

## 確かめてあること

`scripts/check.sh` で、次を確かめています。

- **ルールの証明**：`model/CancelRule.lean` の主張四つを Lean が受理する。未証明の穴はなく、頼る公理は Lean の標準のものだけ。わざと壊した変種四つは、どれも証明が通らなくなる。
- **コードとルールの一致**：実行二つ、長さ 4 までの出来事の並び 22,621 通りすべてで、コードの結果が、証明したモデルを実行した結果と一致する。
- **記録の決まり**：AI の提案は利用者の決定なしに採用されない。古い版への決定は今の版に当たらない。同じ旧版からの二つ目の変更は衝突になる。同じ要求を二度送っても一度しか当たらない。書き込みが途中で切れた行は確定しない。
- **指摘の決まり**：行番号から、どの記録のどの版への指摘かが決まる。決まらない指摘は別の記録に付かない。受入条件に関わる指摘は、書いた側の判断だけでは不採用にできない。
- **起動の照合**：設定の表に行のない役割、禁止した思考量、人数や総数の上限を超える要求、表にないモデルへの切り替えは通らない。思考量は、表の値から一段上までと、下げる方向なら、理由を付ければ通る。二段以上の引き上げと、理由のない変更は通らない。利用者の例外は、範囲の中でだけ使える。
- **設定の表**：一行が一つの役割、並べた数が人数、`@` で思考量、という書き方を読める。読めない行は、黙って捨てずに知らせる。
- **skill を入れる**：`ppdev init` が skill を二か所に入れる。編集した skill は上書きせずに知らせ、頼まれたときだけ、退避してから置き換える。
- **一連の作業**：要求、具体例、保証要求、形式条件、レビュー、形式証明、適合テスト、図、返答、変更後の確かめ直しを、実際のコマンドと実際の検証器で通す。

## まだ確かめていないこと

- **skill は、まだ一度しか実際に使われていない。** 2026-11-14 に、Codex で「ログイン画面をつくる」と頼んだところ、AI は何を作るかを確かめる前に画面を作り始め、担当の設定を三回続けて聞いた。原因は skill の文章で、「何を作るかを利用者が決めるまで、作らない」という決まりを一番上に置く形に直した。直した skill を、別の文脈の担当（Claude）に同じ依頼で試し、作らずに、具体例と図を見せて止まることを見た。
  同じ日に Codex で試し直すと、AI は作らずに止まったが、返事は具体例二つと、文字のままの図のコードだけだった。そこで、理解を HTML のページ（画面の絵、具体例、流れの図、決めてほしいこと）にして開く形に直し、`ppdev init` と `ppdev status` が最初に担当の設定を促していた案内も直した。この形を、別の文脈の担当（Claude）に同じ依頼で試し、ページが一枚できること（具体例四つ、流れの図一枚、案二つ）を画面で見た。ページを作るのに、およそ 9 分かかった。Codex では、この形を試していない。
- **実行環境での起動の停止を試していない。** `ppdev spawn gate` が止めることはテストしましたが、Claude Code のフックとして実際のセッションで働くことは試していません。フックを入れていない環境では、起動の制限は手順としての指示にとどまります。
- **証明が及ぶのはルールまで。** コードがルールどおりかは、試した並びの範囲でしか確かめていません。ルールが置いている前提と、扱っていない範囲は `model/CancelRule.lean` の冒頭にあります。
- **別の検査器による再検査をしていない。** 公理は、検証器と同じ実行の中で調べています。
- **使える検証器は Lean だけ。** ほかの検証器や、コードそのものの形式証明には対応していません。
- **担当が実際に何を読んだかは記録していない。** 記録するのは、渡したファイルの内容です。
- **記録の置き場所への直接の書き込みは止めていない。** 手順として ppdev だけを使う決まりです。
- **設定の表を AI が書き換えることは止めていない。** 利用者が変えると言ったときだけ書き換える、という手順としての決まりです。
