# 回答の適用

本仕様は、人間の回答を判断（decision）として確定する手順と、中断からの回復を定める。対象は runtime の永続状態であり、プロセス内の一時状態は含めない。中断後に残るのは永続状態だけだからである。

## 1. 永続状態

| 要素 | 内容 |
| - | - |
| `records` | 記録 id → 現在の版 `{rev, sha256}`。質問の対象になる要求・仕様など |
| `questions` | 質問 id → `{subjects, answers}`。`subjects` は作成時に写した対象の版の一覧 `[{id, rev, sha256}]` |
| `answers` | 回答 id → `{question, subjects_at_answer, stale, received, closed, applied_as}`。`applied_as` はファイル上の適用印で、確定の写し |
| `decisions` | 存在する decision ファイルの集合。各 decision は `{id, txid}` を持つ |
| `journal` | 追記のみの列。要素は `intent {txid, answer, decision_id, subjects}`、`commit {txid}`、`abort {txid}` |

導出する状態。

- `committed(a)`: `intent(tx, a)` と `commit(tx)` が存在する。
- `inflight`: `commit` も `abort` もない `intent` が存在する。
- `recovery_pending`: `inflight`、または abort 済み取引の仮 decision・仮適用印・未更新の stale 状態が残っている。`inflight = false` だけでは回復完了を意味しない。
- `public_decisions`: `decisions` のうち `txid` が commit 済みのもの。
- `pending`: 保存済みの回答のうち、`committed` でも `closed` でもないもの。`received` や `stale` は条件に含めない。

## 2. 操作

通常の操作は `recovery_pending = false` のときだけ受け付ける。回復が必要なときは先に `recover` を完了する。API の質問取得・未処理回答・SSE は journal から確定を判定し、未確定の `applied_as` を公開しない。質問全体に別の確定済み回答があっても、各回答を個別に判定する。

| 操作 | 前提 | 効果 |
| - | - | - |
| `create_question(q, subjects)` | 対象の記録が存在 | 対象の現在の版を写して質問を保存 |
| `edit(r)` | デーモン停止中、または操作と操作の間 | 記録 `r` の `rev` を 1 増やし `sha256` を変える（外部編集） |
| `save_answer(q, a)` | 質問が存在 | 回答を保存。対象のいずれかの現在の版が `q.subjects` と異なれば `stale = true` |
| `ack(a)` | 回答が存在 | `received = true`。`pending` には影響しない |
| `close(a)` | `¬committed(a)` | `closed = true` |
| `apply(a)` | 下記 | 下記 |
| `recover()` | なし | 下記 |

### 2.1 `apply(a)`

1. `committed(a)` なら、その `decision_id` を返して終わる（再試行は同じ結果）。
2. `closed(a)` なら拒否する。
3. `a.stale` であるか、`q.subjects` のいずれかが現在の版（`rev` と `sha256` の両方）と一致しなければ、`a.stale = true` にして拒否する。
4. 段階 a: `decision_id` を採番し、`intent {txid, a, decision_id, subjects = q.subjects}` を journal に追記する。
5. 段階 b: decision ファイル `{decision_id, txid}` を書く。
6. 段階 c: 回答に `applied_as = decision_id` を書く。
7. 段階 d: `commit {txid}` を journal に追記する。

段階 a の追記以降、どの段階の後でも中断（crash）が起こりうる。中断後は `inflight` となり、`recover` が完了するまで通常の操作は受け付けない。

### 2.2 `recover()`

`inflight` の `intent` について、

- `intent.subjects` のすべてが現在の版（`rev` と `sha256`）と一致すれば、同じ `decision_id` で段階 b、c、d のうち未完了のものを順に行う（ロールフォワード）。
- 一致しなければ (1) `abort {txid}` を追記、(2) 仮 decision ファイルを削除、(3) 回答の `applied_as` を外して `stale = true` を保存する。各書き込みの後に再中断できる。`abort` 後は `inflight = false` になるが、清掃が終わるまで `recovery_pending = true` とする。
- 起動時には abort 済み取引も走査し、残存する仮 decision と回答を再清掃する。既に済んだ書き込みは繰り返しても結果を変えない。再中断は保存状態をそのまま残し、次の起動も同じディスク状態から再開する。

確定済み（commit 済み）の取引は、その後に対象の版が変わっても abort しない。

## 3. 主張

| 主張 | 内容 |
| - | - |
| C1 | 任意の到達可能な状態で、各回答について commit 済みの `intent` は高々一つ。`public_decisions` の各要素は commit 済みの `intent` と一対一に対応する |
| C2 | commit 済みの各取引について、`intent.subjects` は質問の `subjects` と一致し、その回答は `stale` ではない。commit は、現在の版が `intent.subjects` と一致する状態でのみ起こる |
| C3 | 保存済み回答はすべての遷移で保持される。`recovery_pending = false` の状態で、(i) 保存済みの回答は存在し続ける、(ii) `applied_as` が付いている ⟺ `committed`、(iii) decision ファイルが存在する ⟺ その `txid` が commit 済み、(iv) `pending` はファイルから計算しても journal から計算しても同じ集合になる |
| C4 | 第4節の trace 形式で生成した操作列を TypeScript 実装に流したとき、各段階の観測結果がモデルと一致する |

C1 から C3 は操作単位の Lean モデルで証明する。C2 は `committed_safety` が状態と確定時の版照合をまとめ、C3 は `quiescent_with_answers` が回答保持と整合性をまとめる。モデルは `apply` の段階 a〜d と中断を含むが、`recover` の内部は一操作に抽象化している。その内部の取り消し清掃は C5 のモデルで別に扱う。操作単位のモデルの `inflight = false` は清掃完了後の状態に対応し、実ディスク上の清掃途中を含めない。

### C5: 回復途中の再中断

`model/PrepareDev/Spec/Recovery.lean` は、対象版が変わった未確定取引一件の abort 記録、decision の有無、適用印、stale 状態、保存した回答をモデルにする。`resume` は次の一つの保存段階、`crash` は保存状態を変えない中断。任意の有限な操作列で回答を保持し、続けて三回 resume すれば清掃が完了し、完了状態は再回復で変わらないことを `PrepareDev.Recovery.recovery_safe` で証明する。中断が永久に続く場合の進行は保証しない。段階は abort ログ、仮 decision の削除、回答 JSON の更新という三つの状態変更であり、補助的な index や record.remove ログの更新回数は数えない。

`lake exe prepare-model recovery` が生成する48本の trace（apply の三つの中断点 × 四操作の中断・再開の全組合せ）を `recovery.test.ts` で実装へ流す。各保存段階の後に中断し、実ファイルの状態、回答保持、回復待ち中の通常操作拒否、未確定印の非公開を比較する。モデル上の証明と、実装について実行した trace の範囲の適合テストを区別する。

### C6: 公開する確定状態と回復待ち

API の質問取得・未処理回答・通知は `apply.commit` を根拠に各回答の `applied_as` を組み立てる。保存途中の仮適用印は公開しない。通常の質問操作は清掃中も拒否する。`questions.test.ts` と `recovery.test.ts` の `[C6]` を同じ検証実行に含める。C6 は実装テストによる保証であり、C5 の Lean 定理が API や UI を証明するという意味ではない。

## 4. trace 形式（C4 用）

モデルの実行可能定義が操作列を列挙し、各段階の後の観測を JSON Lines で出力する。TypeScript 側は同じ操作を実装に対して行い、観測を比較する。

一行の形式。

```json
{"trace": 12, "step": 3, "action": {"type": "apply", "answer": "A1", "crash_after": "question"}, "observe": {"inflight": true, "pending": ["A1"], "committed": {}, "closed": [], "stale": [], "public_decisions": [], "result": "crashed"}}
```

`action.type` と引数。

| type | 引数 | 意味 |
| - | - | - |
| `create_question` | `question`, `subjects: [record]` | 2章の `create_question` |
| `edit` | `record` | 外部編集 |
| `save_answer` | `question`, `answer` | 回答の保存 |
| `ack` | `answer` | 受領 |
| `close` | `answer` | 終了 |
| `apply` | `answer`, `crash_after: null \| "intent" \| "decision" \| "question"` | 適用。`crash_after` があれば、その段階まで行って中断する |
| `recover` | なし | 回復 |

記録 id は `R1`、質問は `Q1`、回答は `A1`、decision は採番順に `D1`、`D2` … とする。実装側は自分の id 体系へ対応づける。

`observe` の項目。

| 項目 | 内容 |
| - | - |
| `inflight` | 進行中の取引があるか |
| `pending` | `pending` に含まれる回答 id の昇順一覧 |
| `committed` | 回答 id → decision id |
| `closed` | `closed` の回答 id の一覧 |
| `stale` | `stale` の回答 id の一覧 |
| `public_decisions` | 公開される decision id の一覧 |
| `result` | 直前の操作の結果。`ok`、`applied`、`already_applied`、`rejected_stale`、`rejected_closed`、`rejected_inflight`、`crashed`、`recovered_forward`、`recovered_abort`、`noop` |

操作列の生成は決定的で、同じ入力から同じ出力を得る。中断後は `edit` と `recover` だけを生成し、`recover` の後に通常の操作へ戻る。

### 2.2 デーモン起動の排他と書き手（DES-0001 §5.4 の性質 P1〜P7 の手順）

同じ root について、journal、index、記録を書くプロセス（書き手）は同時に一つでなければならない（SPEC-0001 の前提）。書き手は、`openRuntime` を始めてから、runtime を閉じる（停止の `Runtime.close`、または `openRuntime` の失敗の後始末）か強制終了されるまでの `serve` だけである。`init` は `Runtime.open` を呼ばず（`Store.initLayout` で設定の検査、ディレクトリ、追記で開いた空の journal を作るだけ）、書き手にならない（C29）。停止は書き込みを止めて runtime を閉じてから `daemon.json` を消す（C30）。以下は `serve` の起動手順である。

`L` は `<root>/.prepare-dev/daemon.lock`、`B` は `<root>/.prepare-dev/daemon.lock.break`（他人の古い `L` を消す権利の印）、`D` は `daemon.json`、`me` は自分の pid。`serve` は最初に `<root>/.prepare-dev/` を作る（既にあれば何もしない）。`X` は死んだ保持者と判定したときに読んだ `L` の内容、`Y` は死んだ保持者と判定したときに読んだ `B` の内容（どちらもバイト列）。内容が「読めない」とは、空、JSON でない、または `pid` が正の整数でないこと（`process.kill(0, 0)` や負の pid は成功してしまうため）。保持者が「生きている」とは §用語の「生存の判定」が真であること（`isAlive` が例外を投げたときも生きているとみなす）。

回数の数え方（一つの `serve` の中で通算し、やり直しても数え直さない。上限 `N` は `startInit` の引数で、既定 10）: `uL` は `L` を読んで読めなかった回数、`uB` は `B` を読んで読めなかった回数（どちらも今回の読みを含む）、`wB` は生きた `B` の保持者を見て `sleep` した回数。

| 起動 | `openRuntime` が失敗（応答 `{error: <メッセージ>}`） | `closeRuntime`（開いたところまでを閉じる）、`L` を消して終了 `failed`（コード 1。詳細に例外のメッセージ） |
| どこでも | 強制終了 | 作ったファイルが残る（`L`、`B` の保持者の pid は死んでいるので、後の `serve` が引き取る） |

**作成**: `L` と `B` は次の手順で作る。内容を一時ファイル `<作るファイル>.tmp.<me>` に上書きで書き（前の強制終了で残っていても上書きする）、`link(一時ファイル, 作るファイル)` で置き、一時ファイルを消す。`link` は作るファイルが既にあれば EEXIST で失敗するので、作成は排他的で、作られたファイルは最初から内容を持つ。`link` が EPERM か ENOTSUP で失敗するファイルシステム（ハードリンクを持たないもの）では、一時ファイルを消して `{flag: "wx"}` の書き込みに切り替える（作成直後に空が読めることがあり、それは「読めない」の規則で扱う）。「作れなかった」（false）は EEXIST だけで、それ以外の失敗は例外（`serve` は終了コード 1）。読めない `L` は、人が手で編集したか、ディスクが壊れたか、ハードリンクの無いファイルシステムで作成の途中に見えたものである。

不変条件:

- I1: 同じ root について、claim 済み（claim 済み、再確認、起動の状態）にある生きた `serve` は高々一つ。
- I2: 同じ root について、書き手は高々一つ。生きたデーモンが `D` にある間に `openRuntime` を始める `serve` は無い。
- I3: `L` を消すのは、`L` の保持者自身か、`B` を保持し、`B` の保持中に読み直した `L` が `X` と一致した `serve` だけ。`B` を消すのは、`B` の保持者自身か、`L` の保持者（保持者の死んだ `B` だけ）。

I1 と I3 は操作の回数についての帰納で成り立つ。ある時点まで I1 と I3 が成り立つとする。`L` は作成（排他的）でしか作られないので、claim 済みに入れるのは `L` が無い瞬間に作れた一つだけ。生きた保持者の `L` の内容はその保持者の pid を持ち、死んだ保持者の内容 `X` とは異なるので、`B` の保持者はそれを消さない。`B` も作成でしか作られず、保持者の死んだ `B` を消すのは `L` の保持者（その時点で I1 により一つ）だけなので、他人の `L` を消す操作は同時に一つしか進まず、読み直しから削除までの間に `L` が変わることはない。したがって次の操作の後も I1 と I3 が成り立つ。I2 は I1、claim 後の `D` の読み直し、停止の順序から従う: 稼働するデーモンは `D` を書いてから `L` を消し、停止では runtime を閉じて（書き手でなくなって）から `D` を消すので、`L` を消した後に claim した `serve` は生きた `D` を見て終わり、`D` が消えた後には書き手は残っていない。`openRuntime` が失敗した `serve` は runtime を閉じてから `L` を消すので、その後に claim した `serve` と書き手が重ならない。

すべての待ちに通算の上限があり、「読もうとしたら無かった」の輪は毎回他の `serve` の削除を要するので、どの `serve` も有限の操作で終わる（C27 (3)）。`stale-break-lock` は、`B` が実際に残っていて、その保持者が死んでいて、`L` も変わっていないときだけ起きる（読み直しで確かめる。C10 (j)）。保持者の死んだ `B` は、`L` の保持者がいればその保持者が消すので、残るのは `L` の保持者も `B` の保持者も死んだときだけで、そのときは人が消す。

死んだ保持者の `L` を `rename` や unlink で直列化せずに引き取る手順では I1 が成り立たない。その操作はその時点でそのパスにあるファイルに効くので、`serve` S1 と S2 が同じ死んだ `L` を読んだあと、S1 が引き取って `L` を作り直してから S2 が引き取ると、S2 は S1 の生きた `L` を奪って消し、両方が claim 済みになる。また、`D` を見てから `L` を作るまでの間に先行のデーモンが `D` を書いて `L` を消すと、claim 後に `D` を見ない手順では後の `serve` が二つ目の `Runtime.open` に進む。

**起動手順の形**（C10 と C27 が依存する）: 手順は、状態を明示した遷移関数として書く。状態は JSON で表せる値で、C27 はこの状態をそのまま重複判定の鍵に使う。

```text
type Op =
  | {op: "readDaemon"}                                    // → number | null（readLiveDaemon。生きたデーモンの pid か null）
  | {op: "isAlive", pid: number, at: string | null}       // → boolean（生存の判定。例外は true と同じに扱う）
  | {op: "createExclusive", path: string, data: string}   // → boolean（作成。false は EEXIST だけ）
  | {op: "read", path: string}                            // → string | null（無ければ null）
  | {op: "unlink", path: string}                          // → void（無ければ何もしない）
  | {op: "sleep", ms: number}                             // → void
  | {op: "openRuntime"}                                   // → {ok: true} | {error: string}（Runtime.open と HTTP の待ち受け。D は書かない）
  | {op: "closeRuntime"}                                  // → void（開いたところまでを閉じる。以後の書き込みは例外）
  | {op: "writeDaemon"}                                   // → void（D を原子的に書く）
type Outcome = "running" | "already-running" | "held" | "stale-break-lock" | "failed"
type StartState = { phase: string, x: string | null, y: string | null, uL: number, uB: number, wB: number, limit: number, ... }  // JSON
startInit(paths: {daemon, lock, breakLock}, me: number, now: () => string, opts?: {limit?: number, from?: "check" | "acquire"}): StartState
startNext(s: StartState, response: unknown): {state: StartState, op: Op} | {state: StartState, outcome: Outcome, detail: string | null}
runStart(s: StartState, effects): Promise<{outcome: Outcome, detail: string | null}>   // 実際の操作で進める駆動部。cmdServe が使う
claimDaemonLock(lockFile, {pid, isAlive?, sleep?, now?, bootTime?, fs?}): Promise<"claimed" | "held">
```

- `cmdServe` は `runStart` を使い、`Outcome` を終了コード（`running` は稼働を続ける、`already-running` と `held` は 0、`stale-break-lock` と `failed` は 1）に写し、`detail` があれば stderr に一行で出す。
- `claimDaemonLock` は本番の経路では使わない。C10 が、本番と同じ `startNext` の取得から claim 済みまでの部分を、差し替えた操作で確かめるための駆動部である。`startInit(paths, pid, now, {from: "acquire"})` で取得から始め（確認を飛ばす）、claim 済みの後の再確認の `readDaemon` を要求された時点で `claimed` を返して止まる（`B` の片付けは済んでいる）。パスは `lockFile` から導く: `breakLock` は `lockFile + ".break"`、`daemon` は同じディレクトリの `daemon.json`。`fs` は `{createExclusive(path, data): boolean, read(path): string | null, unlink(path): void}`。`stale-break-lock` は `RuntimeError("conflict", "<B の絶対パス>: stale break lock (pid N). Remove it after checking no prepare-dev serve is running.")` として投げる。
- `openRuntime` と `writeDaemon` を分けるため、`Server.listen()` は `{writeDaemonFile?: boolean}`（既定 true）を受け、`cmdServe` は false で待ち受けてから `writeDaemon` で `server.writeDaemonFile()` を呼ぶ。C12、C18 は既定のまま `listen()` して `D` を観測する。
- 既定の `isAlive(pid, at)` は、`at` が `bootTime`（`Date.now() − os.uptime()`）より前なら false、そうでなければ `process.kill(pid, 0)` が成功なら true、ESRCH と EPERM なら false。`readLiveDaemon(root)` は `D` を読み、pid が正の整数で、`isAlive(pid, started_at)` が真のときだけ返す。入口と `serve` は同じ `readLiveDaemon` を使う。
- lock と `B` の内容は `{"pid": <number>, "at": <ISO 8601 の文字列>}` の JSON。読む側は `pid` と `at` を使う。
- 入口（`ensureDaemon`）は lock の手順を知らない。`readLiveDaemon` で `D` を見て、生きていれば接続し、接続を拒否されたら（停止中）`D` が消えるか pid が死ぬまで待つ。`D` が無ければ `entryCommand()` で `serve` を起動し、子の終了か生きた `D` の出現を待つ。子が 0 以外で終われば `daemon.log` のパスを含むエラーで失敗する。子が 0 で終わったのに生きた `D` が無ければ、300 ms 置いて `serve` を起動し直す。全体で 15 秒を過ぎたら、`daemon.log` のパスと、`serve` が最後に stderr に出した一行を含むエラーで失敗する。
- MCP の入口は stdio を先に接続し、`ensureDaemon` を裏で始める。その失敗は捕まえて保持し、ツール呼び出しにそのエラーを返し、次のツール呼び出しで `ensureDaemon` からやり直す（C32）。接続を拒否されたら `D` を読み直して接続し直す。

### 3.2 検証で決まる前提（人の判断ではないが未確認）

H1、H8 と、ホストの道具の振る舞いは、フェーズ 0（§8。prepare-dev のコードは変えず、何も書かない探査用の MCP サーバを使う）で確かめる。結果は人が記録する: H1 と H8 は DIS-0001 の証拠欄に、ホストの道具の振る舞いと入口コマンドの形の測定は DIS-0001 に新しい仮説として足す。

- H1: ホストが入口を対象リポジトリ（またはそのサブディレクトリ）の cwd で起動する。偽のホストがあれば、そのホストでは G が成り立たず B に切り替える（REQ-0002 §シナリオ）。偽のホストが一つでもあれば、フェーズ 1 に進む前に「そのホストだけ B にするか、全体を B にするか」を質問にする。判断の時点はフェーズ 0 の終わり。
- H8: 対象＝道具リポジトリのとき、プロジェクト単位の登録が利用者単位の登録より優先される。偽なら dogfooding の worktree で編集中の checkout が動かないので、利用者単位の登録を一時的に外す運用になる。
- ホストの道具の振る舞い: ツールを一つも公開しない MCP サーバをホストがエラーとして表示しないこと、`claude mcp add -s user` と `codex mcp add` が同名の既存の登録を上書きするか失敗するか、`codex mcp add` が作った `[mcp_servers.prepare-dev]` に二行を足せば Codex がそれを時間切れの値として読むこと。
- 入口コマンドの形: `node --import <道具>/node_modules/tsx/dist/loader.mjs <入口ファイル>`（決定点 1d）が一プロセスで動くことと、その費用。

H7（G でも非対象プロジェクトで `prepare/` と `.prepare-dev/` を作らずに済む）は試す必要が無く、§5.3 の抑止で満たす。書き込む経路は `ensureDaemon`（`.prepare-dev/`、`daemon.log`）と `Runtime.open`（`prepare/`）の二つだけで、どちらも抑止の後ろにある（`packages/mcp/src/client.ts`、`packages/runtime/src/store.ts` の `ensureDirs`）。

### 3.3 本設計から人に聞く判断

質問にする基準は二つ。(a) §6 の決定点のうち、複数の案が残り、人が受け入れるトレードオフを含むもの。(b) §10 の矛盾候補のうち、記録の読み方しだいで矛盾になるもの。`new_decisions` に挙げただけで、他の案が要求や前段の前提に反して一つに決まるもの（決定点 2、3、4、8）は、報告に留めて質問にしない（`prepare-design` の手順 1「機械的な選択は自分で決める」）。決定点 4 の選択自体は機械的だが、それが REQ-0006 の読み方に依存するので、読み方だけを質問 5 にする。§10 の矛盾候補のうち、2 と 4 は条件を弱めない読み替えなので矛盾ではないと判断し、3 は決定点 6 の質問に含めた。

該当するのは次の五つで、レビューの修正を済ませてから質問として作る。質問の id は本記録の本文には書かず、質問側の `subjects`（質問が対象にした記録 id と版の一覧）から `trace` で引く。本文に書くと本記録の版が進み、その版を `subjects` に固定した質問の回答が `stale`（対象が質問の後に変わったので、保存はするが自動では反映しない回答。DEC-0001）になる。レビューの進め方とその経緯も同じ理由で本文に書かない（`REV-*` の指摘と処理、`status` の `open_findings` が持つ）。

1. 決定点 1: 利用者単位の登録に書く入口コマンドの形（絶対パスの `node` か、PATH の `node` か、`--import` で一プロセスにするか）。1b と 1d の可否はフェーズ 0 の実測で分かるので、回答はフェーズ 0 の結果を見てからでよい。
2. 決定点 5: dogfooding のプロジェクト登録を git 管理に入れるか。
3. 決定点 6: 案 G での同意の関門（利用者単位の対象一覧を置くか、`config.json` だけで起動するか、origin 制限を前提条件に前倒しするか）。
4. 決定点 7: `--migrate` が対象リポジトリ内の skills の絶対 symlink を消すか。
5. §10 矛盾候補 1: REQ-0006「固定の場所を前提にしない」の読み方。

§6 の各決定点の「判断」欄は次の語で書く。選んだ案の行は「採用（前提）」＝本設計がその案を前提に書かれており質問で確認する、「採用（機械的）」＝他の案が要求や前提に反し一つに決まるので質問にしない、のどちらか。未決の決定点（5、7）は両案とも「open」＝本設計は両案を書き分けており質問で決まる。選ばなかった案の行は「代替」＝質問で選ばれれば採る、「棄却」＝理由つきで採らない、のどちらか。frontmatter の `alternatives[].status` は、採用が `chosen`、open と代替が `open`、棄却が `rejected`。

frontmatter の `coverage` の値の根拠: `hypothesis` は人の判断待ちに対応する（architecture は決定点 1、5、6 と Q-0002 の判断 a、security は決定点 6、compatibility_migration は決定点 7 と Q-0003 m、prior_reconciliation は §10 の矛盾候補 1）。`unverified` は試せば分かるもの（integrations は §3.2 のホストの道具の振る舞いと H1、H8）。`decided` はそれ以外。

## 4. 利用シナリオ（CUJ）

### CUJ 1: 新しい機械で対象リポジトリを使い始める（REQ-0002 AC-1、AC-2、REQ-0003 AC-1、AC-4）

- Given: 道具リポジトリを任意の場所に clone し `pnpm install` 済み。対象リポジトリを clone 済み（`prepare/` と `.prepare-dev/config.json`、`.prepare-dev/.gitignore` が git に入っている）。利用者単位の MCP 登録と skills は未設定。
- When: 道具リポジトリで `pnpm cli init --root <対象>` を実行し、出力の `setup_commands`（`claude mcp add -s user ...`、`codex mcp add ...` と `~/.codex/config.toml` に足す二行、`pnpm --dir <道具> cli skills --user`）を実行する。ホストを対象リポジトリ（またはそのサブディレクトリ）で起動する。
- Then: 対象リポジトリには `init` 前後で git 差分が無い（`init` が書くものは既に git にあり、一時ファイルは `.prepare-dev/.gitignore` で除外される）。利用者単位の対象一覧（§5.3）に対象が登録される。ホストは cwd から対象を決めた入口に接続し、`status` が返る。`daemon.json` に道具リポジトリの位置が出る。

### CUJ 2: 無関係なプロジェクトでホストを起動する（REQ-0003 AC-2）

- Given: 利用者単位の登録が済んでいる。cwd は `init` していないディレクトリ（`.prepare-dev/config.json` が無い、または対象一覧に無い）。
- When: ホストが入口を `mcp` で起動する。
- Then: 入口は MCP の initialize に応答し、ツールを一つも公開せず、そのまま待つ。cwd に `prepare/` も `.prepare-dev/` も作られない。ホストのログ（stderr）に「対象ではない。`init` で対象にできる」という一行が出る。

### CUJ 3: 既存の絶対パス入りの登録を移行する（REQ-0002 AC-3、AC-4）

- Given: 旧 `init` が書いた `.mcp.json`、`.codex/config.toml` の `[mcp_servers.prepare-dev]` ブロック、`.agents/skills/*` の絶対 symlink がある対象リポジトリ。`.codex/config.toml` には利用者が書いた別の設定もある。
- When: `pnpm cli init --root <対象> --migrate` を実行する。途中で止めてもう一度実行する。
- Then: `.mcp.json` の `prepare-dev` 項目と TOML のそのブロック（旧 `init` の内容を含むものだけ）が消え、TOML の他の行は byte 単位で変わらない（`.mcp.json` は JSON として読み書きするので、他の項目は意味が変わらない）。出力の `removed` に消したものが列挙される。二回目の実行は何も消さず、結果は一回で完了した場合と同じ。

### CUJ 4: 道具リポジトリ自身で作業する（dogfooding。REQ-0003 AC-5）

- Given: 道具リポジトリの worktree を二つ持つ。利用者単位の登録は片方の checkout を指す。
- When: 各 worktree で `pnpm cli init`（`--root` は worktree）を実行し、ホストをその worktree で起動する。
- Then: `.mcp.json` と `.codex/config.toml` に `pnpm cli mcp --host <host>` のプロジェクト登録があり（決定点 5a なら git から、5b なら `init` が書く）、絶対パスを含まない。プロジェクト単位の登録が優先され（H8）、その worktree のソースが動く。`.agents/skills/*` は `../../skills/*` への相対 symlink。`status` の `tool.root` がその worktree を指す。

### CUJ 5: 道具リポジトリを移動した（REQ-0005 AC-2、AC-3、REQ-0006 AC-1）

- Given: 利用者単位の skills リンクと MCP 登録が旧い場所を指している。デーモンは止まっている。
- When: 新しい場所の道具リポジトリで `pnpm cli init --root <対象>` を実行し、出力の `setup_commands` を再実行する。ホストを対象で起動する。
- Then: `skills --user` は切れたリンクを skill 名つきで報告して張り直す。新しい場所から起動した入口がデーモンを立て、`GET /` が新しい場所の UI を返す。

### CUJ 6: 二つのホストが同時に入口を起動する（REQ-0003 AC-3、AC-6）

- Given: 対象リポジトリにデーモンが無い。
- When: Claude Code と Codex（または CLI）がほぼ同時に入口を起動する。
- Then: 二つの `serve` が起動しうるが、claim（§5.4）を取れた一つだけが `Runtime.open` に進み、もう一つは何も書かずに終了する。`daemon.json` は一つの生きているデーモンを指し、孤児プロセスは残らない。`serve` が起動に失敗した場合は原因が `.prepare-dev/daemon.log` に残り、どちらの入口も 15 秒待たずに失敗し（負けた側の入口も、lock も daemon.json も無いと分かった時点で失敗する）、再試行でも二つ目は立たない。

### CUJ 7: UI がビルドされていない（REQ-0006 AC-2）

- Given: `packages/ui/dist/index.html` が無い checkout からデーモンが立った。
- When: ブラウザで `/` を開き、`pnpm cli status` を実行する。
- Then: 簡易フォームが表示され、`status` に `ui: <探したパス> (missing)` が出る。`daemon.json` の `ui.path` に同じパスがある。

### 5.2 データ: `daemon.json` と `status`

`daemon.json`（`.prepare-dev/daemon.json`、デーモンが `listen()` で原子的に書く）に二項目を足す。既存項目は変えない。

```json
{
  "pid": 12345, "port": 50837, "url": "http://127.0.0.1:50837", "root": "/abs/target", "started_at": "...",
  "tool": { "root": "/abs/tool-repo" },
  "ui": { "path": "/abs/tool-repo/packages/ui/dist/index.html", "found": true }
}
```

- `tool.root` は `toolRepoRoot()`。段階 1 ではこの一項目だけ（REQ-0004「道具リポジトリの位置を一項目足す最小形」）。案 C、D で要る識別子は、そのとき任意項目として足す（本設計は名前を予約しない）。
- `ui.path` は探したパス、`ui.found` は起動時の存在。`GET /` は従来どおりリクエストごとに存在を見る（REQ-0006 の書きかけ HTML は防がない）。
- `tool`、`ui` が無い `daemon.json`（本変更前のデーモン）は読め、`status` に `tool: unknown` と出る。段階 1 では不一致として扱わない（REQ-0004 AC-4 は C、D のみ）。
- `DaemonInfo` 型は現在 `packages/mcp/src/client.ts` と `packages/runtime/src/server.ts` に同じ定義が二つあり、`readDaemonInfo` 関数も両方にある（runtime 側は export されるが誰も使っていない）。型は `packages/core/src/schemas.ts` に一つ置き、関数は mcp 側の `readLiveDaemon`（§5.1。生存の判定を入口と `serve` で共有する）一つにする。

`GET /api/status` は `StatusView` に `daemon: {pid, url, started_at, tool, ui}` を足す。`ui.found` は呼ばれた時点で存在を評価し直す。CLI の `status` の文字出力に三行を足す: `daemon: <url> (pid <pid>)`、`tool: <root>`、`ui: <path> (found|missing)`。

### 5.3 入口の root の決定と対象判定（REQ-0003、H7、同意の関門）

`rootOf()` の既定順（`--root` → `PREPARE_DEV_ROOT` → cwd）は保ち、三つ目を `findRoot(cwd)` にする: cwd から親へたどり、`.prepare-dev/config.json` を持つ最も近いディレクトリを root にする。ただし `.git`（ディレクトリかファイル。worktree では `.git` はファイル）を持つディレクトリより上にはたどらない。見つからなければ cwd を root にする（その root は非対象になる）。ホストを対象のサブディレクトリで開いてもツールが消えないようにし（決定点 8）、対象の中に置いた別の checkout（`.claude/worktrees/` などの worktree）が外側の対象の記録に黙ってつながらないようにするため。`--root` を明示しない呼び出しでは、求めた root について `isTarget(root)` を見る。

`isTarget(root)` は次の両方が成り立つとき真。

1. `<root>/.prepare-dev/config.json` がある。
2. 利用者単位の対象一覧（`<利用者単位のディレクトリ>/targets.json`。内容は `{"targets": ["<realpath>", ...]}`）に `realpath(root)` がある。`init` が登録する。利用者単位のディレクトリは環境変数 `PREPARE_DEV_USER_DIR` で差し替えられ、既定は `~/.prepare-dev`。テストと `scripts/e2e-crash.sh` は一時ディレクトリに向け、利用者の実ファイルを汚さない。

対象一覧の扱い: `targets.json` が無ければ一覧は空。読めない（JSON でない、`targets` が文字列の配列でない）ときは、すべての root を非対象と判定し、理由に一覧の絶対パスを含める（全セッションの入口が読むので、例外で落とさず、誤ってツールを公開する側にも倒さない）。`init` は一覧を一時ファイルと `rename` で原子的に書き、読めない一覧は上書きせずに終了コード 1 で失敗する（他の対象の登録を黙って失わない）。存在しなくなった項目を落とすのは、親ディレクトリはあるが root が無いときだけ（外付けのボリュームが外れているだけの項目は残す）。二つの `init` が同時に書くと片方の登録が失われうるが、`init` をもう一度実行すれば直る。

2 を置く理由（決定点 6a）: 利用者単位の登録では入口が全セッションで起動するので、1 だけだと「clone した見知らぬリポジトリに `config.json` があるだけでデーモンが自動で立つ」。デーモンの HTTP は無認証で `access-control-allow-origin: *` を返し（DIS-0001 §現状）、`/api/runs` は対象の `vitest` や `lake` を実行するので、起動の同意は利用者の明示の操作（`init`）に残す。現状のプロジェクト単位の登録ではホストが承認を求めていたのと同じ関門を、`init` に移す。

| 呼び出し | 非対象のとき |
| - | - |
| `mcp`（`--root` なし） | `McpServer` を `capabilities: {tools: {}}` を宣言し、ツールを一つも登録しない状態で stdio に接続し、ホストが stdio を閉じるまで待つ（Q-0003 s-wait）。宣言が無いと MCP SDK 1.32 は `tools/list` のハンドラを置かず Method not found を返す（`server/mcp.js`）。宣言すれば空の一覧を返す。stderr に `prepare-dev: <root> is not a prepare-dev target (<理由>); no tools published. to enable: pnpm --dir <道具> cli init --root <root>` を一行出す。理由は「`config.json` が無い」「対象一覧に無い」「対象一覧が読めない: <パス>」のどれか。`ensureDaemon` を呼ばないので `.prepare-dev/` も `prepare/` もできない。セッション中に `init` されても気付かない（次のセッションから有効）。MCP の `instructions` は空にする（全セッションの会話に載るため）。診断は、ホストの MCP 一覧（`claude mcp list`、`codex mcp list`）で接続状態とこの一行を見る |
| `status`、`q`、`record`、`verify`、`trace`、`bundle`、`ui`、`pending`、`stop`（`--root` なし） | `error: <root> is not a prepare-dev target (<理由>). to enable: pnpm --dir <道具> cli init --root <root>` を stderr に出し終了コード 2。何も作らない |
| `init` | 判定しない（`init` は root を対象にするための操作）。`.prepare-dev/config.json` と `prepare/` を作り、対象一覧に登録する |
| `skills` | root を使わないので判定しない（`init` の案内の `pnpm --dir <道具> cli skills --user` は道具リポジトリを cwd にして動き、道具リポジトリは対象一覧に無いことがある） |
| `serve`、または `--root` を明示したコマンド | 対象判定をしない（現状どおり）。`--root` の明示が同意に当たる。`mcp.test.ts` と `scripts/e2e-crash.sh` はこの経路 |

案内の `<道具>` は入口が `toolRepoRoot()` で知っている絶対パスで、そのまま実行できる形で出す（G では PATH に `prepare-dev` が無い）。`PREPARE_DEV_ROOT` だけが設定されている場合も「`--root` なし」として扱い、その root を判定する（REQ-0003 は「cwd」と書くが、既定順で求めた root に読み替える。§10）。

判定を置く場所は一箇所にする。`rootOf(args)` の直後に `targetRootOf(args)`（`--root` が無く `isTarget` が偽なら上の振る舞い）を置き、`init`、`serve`、`skills` 以外のすべてのコマンドがそれを通る。`mcp` も `targetRootOf` の結果（root と、対象か、理由）を `serveStdio` に渡すだけで、`packages/mcp` の側で判定し直さない。特に `ui` は現在 `client()` を通らず `ensureDaemon(rootOf(args))` を直接呼ぶので、個別に例外にしない。

設定の検証: `Store.loadConfig()` は `records_dir` を `path.resolve(root, records_dir)` に解決し、root の外を指す値（`../` など）を `invalid` として拒否する。現在は無検査で結合して `mkdir` と走査をしており（`store.ts`）、`config.json` の中身で root の外に書けた。自動起動の経路が増えるので塞ぐ。検査は字面だけで、git に symlink としてコミットされた `prepare` が root の外を指す場合は通る（限界。主な関門は決定点 6a の対象一覧）。

### 5.4 デーモンの起動、排他、停止（REQ-0003 AC-3、AC-6）

`Runtime.open` は `prepare/` の作成、index（`.prepare-dev/index.json`。記録の一覧と版のキャッシュ）の再構築、外部変更の走査に加えて回復処理（中断した回答適用の取引をロールフォワードまたは撤回する処理。SPEC-0001 §2.2）を行い、journal（`prepare/events.jsonl`）に追記する。動いているデーモンも journal、index、記録を書く。SPEC-0001 は「書き込むデーモンは一つ」を前提にしているので、同じ root について書き手は同時に一つでなければならない。本設計は次の性質でそれを守る（決定点 2a）。

| 性質 | 内容 |
| - | - |
| P1 | `serve` は `Runtime.open` の前に `.prepare-dev/daemon.lock` を claim し、`daemon.json` を書いた後に解放する |
| P2 | lock の作成は内容ごと原子的（内容を書いた一時ファイルを `link` で置く）。生きた書き手の lock が空や書きかけに見えることは無い。ハードリンクを持たないファイルシステムでは排他作成に切り替え、作成直後の空の読みは「読めない lock」の規則で扱う（SPEC-0002 §2.2） |
| P3 | 死んだ保持者の lock の引き取りは同時に一つしか進まず、判定に使った lock より新しい lock を消さない |
| P4 | claim の後に `daemon.json` を読み直し、生きたデーモンがあれば何もせずに lock を解放して終わる（先行のデーモンが `daemon.json` を書いて lock を消した直後に claim した場合） |
| P5 | 待ちはすべて回数に上限があり、`serve` は必ず終わる |
| P6 | 停止は、受付を止め、長い待ちを打ち切り、検証ジョブを止め、HTTP を閉じ、runtime を閉じてから `daemon.json` を消す。runtime を閉じた後の書き込みはすべて例外になるので、`daemon.json` が無いときに書き手は残っていない。停止全体に上限（10 秒）を置く |
| P7 | `init` は `Runtime.open` を呼ばない（§5.5）。journal、index、記録を書くのはデーモンだけ |

P3 と P4 が要る理由: 死んだ保持者の lock を `rename` や unlink で引き取ると、その操作はその時点でそのパスにあるファイルに効く。二つの `serve` が同じ死んだ lock を読んだあと、先の一方が引き取って lock を作り直すと、後の一方がその生きた lock を奪える（決定点 2 が 2b を棄てた理由と同じ競合）。また、`daemon.json` を見てから lock を作るまでの間に先行のデーモンが `daemon.json` を書いて lock を消すと、後の `serve` が二つ目の `Runtime.open` に進む。具体的な手順と、その検証（操作単位の状態探索）は SPEC-0002 §2.2 にあり、手順の選び方は人の判断を待っている。本設計はどの手順でも P1〜P7 を満たすことだけを求め、入口は手順の中身（lock に関わるファイルの名前や種類）を知らない。

生存の判定（`readLiveDaemon`。lock の保持者の判定も同じ規則）: pid が正の整数で、`process.kill(pid, 0)` が成功し、記録に書いた時刻（`daemon.json` の `started_at`、lock の `at`）が今回の OS の起動より後のとき生きているとみなす。EPERM は他の利用者のプロセス（`serve` は利用者自身のプロセスなので、保持者ではありえない）として死とみなす。時刻の条件は、再起動の後に残った記録の pid が起動時のシステムプロセスに再利用されていても、それを生きたデーモンと取り違えないためである。

`serve`（`cmdServe`）の順序:

1. `readLiveDaemon(root)` が生きているデーモンを返せば「already running」を stderr に出して終了コード 0 で終わる（現状は終了コード 1。入口が「子が 0 以外で終わった」を失敗とみなすので 0 にする）。
2. claim（SPEC-0002 §2.2）。他の生きた保持者がいれば「another daemon is starting」を stderr に出して終了コード 0 で終わる。
3. `readLiveDaemon(root)` をもう一度見て、生きていれば lock を解放して終了コード 0（P4）。
4. `Runtime.open(root)` と HTTP の待ち受け。
5. `daemon.json` を原子的に書く。
6. lock を消す。4〜5 で例外が出たら、開いた runtime を閉じ、lock を消して終了コード 1 で終わる（stderr は `daemon.log`）。強制終了で lock が残っても、保持者の pid が死んでいるので次の `serve` が引き取る。

停止（`Server.close()`。`stop` の SIGTERM で呼ばれる）の順序（P6）:

1. 新しい要求とジョブの受付を止める（新しい要求には 503 と `{"error": "stopping"}` を返す）。
2. 長い待ち（`/api/questions/:id/wait`、`/api/runs/:id/wait`、SSE）を打ち切り、待っていた要求に停止を示す応答を返す。エージェントは `question_wait` を待ち直す。
3. 実行中の検証ジョブの子プロセスを終わらせ、その決着を待つ（`Runs.stopAll()`。止めた実行の `RUN-*` は記録しない）。
4. HTTP を閉じる（残った接続は閉じる）。
5. runtime を閉じる（`Runtime.close()`: store を書き込み不能にする。以後の書き込みはすべて例外）。
6. `daemon.json` を消して終了する。

1〜6 に 10 秒の上限を置き、超えたら残りの接続とジョブを強制的に終わらせて 5、6 に進む。`stop` コマンドは SIGTERM を送ったあと、プロセスの終了を最大 15 秒待ってから「stopped」と出す（終わらなければ pid を含むエラー）。現在は `daemon.json` を先に消してから排出を待つので、その間に起動した `serve` が二つ目の書き手になりえた。停止中は `daemon.json` が生きた pid を指したままで、そのとき起動した `serve` は already running で終わる。

入口（`ensureDaemon(root)`）:

1. `readLiveDaemon(root)` が生きているデーモンを返せば接続する。接続を拒否されたら（停止中）、`daemon.json` が消えるか pid が死ぬまで待ってから 2 へ進む。
2. `entryCommand()` の `command` と `args` に `serve --root <root>` を続けて detached 起動する（cwd は現状どおり `toolRepoRoot()`、stdout/stderr は `.prepare-dev/daemon.log` に追記）。現在渡している環境変数 `PREPARE_DEV_DETACHED=1` は読む側が無いので、この変更で消す。
3. 子の終了か、生きた `daemon.json` の出現を待つ。`daemon.json` が現れれば接続する。子が 0 以外で終われば、`daemon.log` のパスを含むエラーを投げる。子が 0 で終わったのに生きた `daemon.json` が無ければ（別の `serve` が起動中だった）、300 ms 置いて 2 からやり直す。勝った側が立てば次の `serve` は already running で終わって `daemon.json` が見え、勝った側が失敗していれば次の `serve` が自分で claim して起動するか 0 以外で終わる。入口は lock の手順を知らずに済む。
4. 全体で 15 秒（現状値）を過ぎたら、`daemon.log` のパスと、`serve` が最後に stderr に出した一行（lock の保持者の pid を含む）を含むエラーを投げる（pid の再利用で lock が引き取れないときに、人が原因を辿れるようにする）。

MCP の入口（`serveStdio`）は、対象の場合も stdio を先に接続してツールを登録し、`ensureDaemon` は接続の直後に裏で始める。ツール呼び出しはその完了を待ち、失敗したらそのエラーを返す。裏の起動の失敗は捕まえて保持し（未処理の reject でプロセスを落とさない）、次のツール呼び出しで `ensureDaemon` からやり直す。接続を拒否されたら `daemon.json` を読み直して接続し直す（停止の後に別のポートで立ったデーモンにつなぐため）。MCP の initialize がデーモンの起動を待たないので、Q-0003 q の目標（initialize まで 1 秒）とホストの起動の時間切れ（Codex の `startup_timeout_sec`）にデーモンの冷起動が乗らない。CLI は従来どおり `ensureDaemon` を待ってから実行する。

同時に二つの入口が起動すると二つの `serve` が立ち上がるが、claim を取れなかった方は何も書かずに約 0.3 秒で終わる。その費用は、入口側で lock を取り合う案（決定点 2b）より小さい。

### 5.5 `init`（REQ-0002）

`init --root <root>` は次を行う。既存の「あるものは書かない」規則は保つ。

1. `.prepare-dev/config.json`（無ければ作る）と、`Store.initLayout(root)` で `prepare/` のディレクトリと空の journal（`prepare/events.jsonl`）を作る。`initLayout` は `loadConfig` を通して設定を検査し（`records_dir` の root 外を拒否する）、journal は追記で開いて作る（既にあれば中身を変えない。同時に起動したデーモンが追記した journal を空で上書きしない）。`Runtime.open` は呼ばない（現在は呼んでいる）。`Runtime.open` は回復処理、走査、index の書き込みを行うので、動いているデーモンと並行に呼ぶと二つ目の書き手になる（§5.4 の P7）。journal への追記と index はデーモンが起動時に行う。
2. `.prepare-dev/.gitignore`（無ければ作る）: 内容は `*`、`!.gitignore`、`!config.json`、`!reviews/`、`!reviews/**` の五行（許可リスト形式）。git 管理に入れるのは設定とレビュー資料で、`daemon.json`、lock に関わるファイル（名前は SPEC-0002 §2.2）、`daemon.log`、`index.json`、`tmp/`、`runs/` は除外される。レビュー資料（`reviews/` の bundle）は、レビュー役が読んだ版の唯一の写しなので残す（`buildBundle` は現在の版しか読めず、store は過去の版を持たない。`REV-*` の本文は bundle のパスを資料として引く）。許可リスト形式なら状態ファイルが増えても `init` と既存の対象を更新しなくて済む。現在は道具リポジトリ自身の root の `.gitignore` に項目が列挙されているだけで、他の対象では利用者任せだった。
3. 利用者単位の対象一覧（`PREPARE_DEV_USER_DIR`、既定 `~/.prepare-dev`、の `targets.json`）に `realpath(root)` を登録する（無ければ作る。既にあれば何もしない）。書き込みは `packages/runtime/src/targets.ts` の `registerTarget` が `writeFileAtomic`（一時ファイルと `rename`）で原子的に行う。同時に、親ディレクトリはあるが root が無くなった項目を落とす。一覧が読めないときは上書きせず、一覧の絶対パスを含むエラーで終了コード 1（§5.3）。
4. 出力の `setup_commands` に、利用者が手で行う登録を、この機械で解決した絶対パスで出す。絶対パスは利用者のホームの設定（`~/.claude.json`、`~/.codex/config.toml`）に入り、機械で一箇所になる。`<node>` は `init` を実行した `process.execPath`。

```text
claude mcp add -s user prepare-dev -- <node> <tool>/node_modules/tsx/dist/cli.mjs <tool>/packages/cli/src/index.ts mcp --host claude-code
codex mcp add prepare-dev -- <node> <tool>/node_modules/tsx/dist/cli.mjs <tool>/packages/cli/src/index.ts mcp --host codex
  （続けて ~/.codex/config.toml の [mcp_servers.prepare-dev] に次の二行を足す）
  startup_timeout_sec = 30
  tool_timeout_sec = 3600
pnpm --dir <tool> cli skills --user
```

`codex mcp add` には時間切れの値を設定する項目が無い（codex-cli 0.167.0 の `--help`。レビュー役が確認）。現在の `init` は `.codex/config.toml` に `startup_timeout_sec = 30` と `tool_timeout_sec = 3600` を書いており、これが落ちると Codex の既定値（文書によれば起動 10 秒、ツール 60 秒。未確認）になって、`question_wait`（人の回答が来るまで最大 1 時間ブロックする MCP のツール）の長い待ちが打ち切られる。そこで二行を足す手順を案内に含める。二行を足せば Codex がそれを読むことはフェーズ 0 で確かめる。登録をやり直すとき（Node の版や道具リポジトリの場所を変えたとき）に、同名の登録が上書きされるかは未確認（フェーズ 0）なので、出力には先に実行する `claude mcp remove -s user prepare-dev` と `codex mcp remove prepare-dev` も載せる。

5. 旧 `init` の痕跡（`.mcp.json` の `prepare-dev` 項目、`.codex/config.toml` の旧ブロック、`.agents/skills/*` の絶対 symlink）があれば、出力の `legacy` に列挙する。`--migrate` が無ければ消さない。
6. dogfooding（`root` が `toolRepoRoot()` と同じ）: 決定点 5a（推奨。登録ファイルと相対 symlink を git 管理に入れる）なら `init` は何も足さない。5b なら、`.mcp.json` に `{"type":"stdio","command":"pnpm","args":["cli","mcp","--host","claude-code"]}`、`.codex/config.toml` に `command = "pnpm"`、`args = ["cli", "mcp", "--host", "codex"]`、`startup_timeout_sec = 30`、`tool_timeout_sec = 3600` のブロック、`.agents/skills/<name> -> ../../skills/<name>`、`.claude/skills -> ../.agents/skills` を書く。どちらでも `--root` は書かない（cwd＝プロジェクト。H1）。`command: "pnpm"` は PATH に依存する（絶対パス無しの登録は PATH 依存と表裏。限界として §7 に書く）。案 B に切り替えるときは、この値を `command: "prepare-dev"`、`args: ["mcp", "--host", ...]` にする一箇所の変更で済む。

`--migrate`（m-option。`init` が書いたものだけを消し、1〜6 の前に行う）:

- `.mcp.json`: JSON として読み、`mcpServers["prepare-dev"]` を消して 2 スペース字下げで書き戻す（現在の `init` と同じ整形）。`mcpServers` が空になり他のキーも無ければファイルを消す。他の項目は意味が変わらない（byte 単位の同一は保証しない）。
- `.codex/config.toml`: `[mcp_servers.prepare-dev]` の行から、次の `[` で始まる行の直前（または EOF）までを一つのブロックとし、そのブロックに `node_modules/.bin/tsx` か `packages/cli/src/index.ts` を含む行があるとき（旧 `init` が書いた内容）だけ消す。直前の空行も一つ消す。他の行は byte 単位で変えない。利用者が自分で書いた同名ブロックは条件に合わないので残る。
- `.agents/skills/<name>`（`name` は道具リポジトリの `skills/` にある skill 名）が絶対パスへの symlink なら消す。実体のディレクトリと相対 symlink は消さない（決定点 7a。7b なら消さず `legacy` に残す）。
- 消したものを出力の `removed` に列挙する。無ければ何もしない。中断して再実行しても、残っているものだけが処理される（REQ-0002 AC-4）。

出力は `{root, written, removed, legacy, setup_commands, skills}`。`skills` は dogfooding で置いた相対 symlink の結果（§5.6 の表の `state`）で、決定点 5a では常に空。出力の詳しい形は SPEC-0002 §2.3。

### 5.6 skills（REQ-0005、b-link）

共通関数 `placeSkillLinks(destDir, linkTargetOf)`: 道具リポジトリの `skills/*/SKILL.md` を持つ各 `name` について `destDir/<name>` を次のように扱い、結果を `{name, state}` の一覧で返す。書き込まない検査モードは作らない（配置の結果を列挙すれば REQ-0005 の「検出して報告」を満たす）。

| `destDir/<name>` の状態 | 処理 | `state` |
| - | - | - |
| 無い | symlink を作る | `linked` |
| symlink、先が期待どおりで解決できる | 何もしない | `ok` |
| symlink、先が解決できない（切れたリンク） | 張り直す | `relinked` |
| symlink、先が期待と違う（移動した道具リポジトリなど） | 張り直す | `relinked` |
| 実体のディレクトリかファイル | 触らない（利用者のもの） | `kept` |

- `prepare-dev skills --user`（新設の明示の操作。REQ-0005）: `destDir` は `~/.agents/skills` と `~/.claude/skills`（`os.homedir()`。テストは `HOME` を差し替える）、リンク先は `<toolRepoRoot>/skills/<name>` の絶対パス。ディレクトリ自体は利用者の他の skills と共有なので、ディレクトリごとの symlink は作らない。`ok` 以外を skill 名つきで出力する（黙って飛ばさない）。
- dogfooding（決定点 5b のとき `init` が置く）: `destDir` は `<root>/.agents/skills`、リンク先は `../../skills/<name>` の相対パス。
- `init`（G）: 対象リポジトリに skills を置かない（REQ-0002 §シナリオ G）。
- コピー方式と印ファイル（REQ-0005 AC-4、AC-5）は b-link では使わないので作らない。

## 7. 非機能要求

- 安全性: 案 G は入口を全セッションで起動するので、デーモンの自動起動の条件を利用者の `init` を経た対象に限る（決定点 6a）。`records_dir` を root 内に制限する（字面の検査。symlink は限界、§5.3）。デーモンの HTTP（無認証、`access-control-allow-origin: *`）自体は変えず、別件のままにする（決定点 6c は質問）。非対象で待機する入口はネットワークを開かない。`--migrate` は旧 `init` が書いた項目だけを消す（REQ-0002 AC-3）。同じ root の書き手は一つ（§5.4 の P1〜P7）。`stop` は `readLiveDaemon` が生きていると判定した pid にだけ SIGTERM を送るので、再起動の後に残った `daemon.json` の pid を持つ無関係なプロセスを止めない。
- 性能（実測、Node 26.13、tsx 4.23、macOS、2026-11-08）: 入口は tsx のラッパーと、入口ファイルを実行する子の二プロセスで動く。対象で起動した入口（デーモンを除く）は、initialize の応答まで 576〜652 ms（三回）、RSS の和は約 170 MB（ラッパー約 60 MB、子約 111 MB）。費用の大半は Node と tsx のローダ自体で、runtime やプラグインの読み込みを遅延させても大きくは変わらない。費用は「セッション数 × 約 170 MB」で、10 セッションなら約 1.7 GB。これを受け入れるかが Q-0003 s（s-wait か s-exit か）の判断材料になる。決定点 1d（`--import` で一プロセス）が動けばラッパー分が消えるので、フェーズ 0 で測ってから Q-0003 s に答えるのがよい。待機中の入口は CPU を使わない。MCP の initialize はデーモンの起動を待たない（§5.4）ので、Q-0003 q の目標（1 秒）に冷起動は乗らない。停止は 10 秒以内に終わる（§5.4 の P6）。
- 互換性と移行: `daemon.json` の追加項目は任意で、旧デーモンの `daemon.json` も読める。利用者単位のディレクトリは `PREPARE_DEV_USER_DIR` で差し替えられ、テストと `scripts/e2e-crash.sh` は一時ディレクトリを使う（`init` を呼ぶ自動化が利用者の対象一覧を汚さない）。旧 `init` の登録は `--migrate` で消す。本変更の前に立てたデーモンは `pnpm cli stop` で止めるまで残る（REQ-0007 の現状どおり）。本変更の前に `init` した対象は対象一覧に無いので、`init` をもう一度実行するまでツールが出ない。`mcp.test.ts` と `scripts/e2e-crash.sh` は `--root` 明示の経路なので挙動は変わらない。利用者単位の登録は `node` と道具リポジトリの絶対パスを含むので、Node の版や checkout の場所を変えたら `init` の案内を再実行する（決定点 1 の欠点）。Codex のタイムアウトの二行も案内に含める（§5.5）。dogfooding の `command: "pnpm"` は PATH に依存する（絶対パス無しの登録は PATH 依存と表裏）。GUI 起動のホストで PATH に `pnpm` が無ければ、利用者単位の登録（別 checkout）が動く。ハードリンクを持たないファイルシステム（exFAT の外付けボリューム、多くの SMB 共有）にある対象では、lock の作成が排他作成に切り替わる（P2）。
- 切り戻し: コードは git revert。利用者単位の登録は `claude mcp remove -s user prepare-dev`、`codex mcp remove prepare-dev`（足した二行も同じ表にあるので一緒に消える。未確認）、skills リンクは `~/.agents/skills/<name>` と `~/.claude/skills/<name>` を消す。`~/.prepare-dev/targets.json` を消す。対象リポジトリ側には `init`（G）は `.prepare-dev/.gitignore` と空の journal 以外の新しいものを書いていない。

### 新しい決定（`new_decisions`。前段に無く、アーキテクチャ・外部インターフェース・依存に関わるもの）
