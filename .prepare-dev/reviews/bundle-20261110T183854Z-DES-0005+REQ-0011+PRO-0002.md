## 1. 概要と問題

REQ-0011 の「仕様のページ」を作る設計。prepare-dev を使うどのプロジェクトでも、AI が仕様から中身を生成して ppdev で登録し、判断画面のアプリがそれを描く。

今の判断画面のアプリは質問の画面一つで、図を描く部品も、仕様を試す画面も無い（ui/src）。人は 2026-11-10 に「ずとかもないし、ダイアグラムもない」と指摘した（DEC-0018）。中身は AI に生成させ（DEC-0019、DEC-0022）、形の定義は自前で作る（DEC-0023）。出発点は、DEC-0023 の判断に使ったデモの写し（PRO-0002）である。

```
AI が仕様を書き終える
  │ prepare-specify の references/spec-page.md を読む（書き方の説明。形の定義から書き出したもの）
  │ （AI が中身の JSON を書く）
  │ ppdev page put SPEC-xxxx --file page.json
  ▼
prepare-dev（デーモン）が検査する
  │ 形の検査（JSON Schema）、つながりの検査、仕様の版と主張の番号の検査
  │ 合わなければ、何も保存せずに、どこがどう合わないかを返す
  ▼
prepare/pages/SPEC-xxxx.json に保存し、画面に「page」の知らせを出す
  ▼
判断画面のアプリ /spec/SPEC-xxxx が描く
  仕様の版が変わっていたら「古い」と出す。形が読めなければ、そうと出して仕様の本文を出す
```

## 2. 目標と非目標

目標は REQ-0011 の AC-1〜AC-5 と、DEC-0025（約束していないことの欄をいつも出す）。

非目標（REQ-0011 の対象外と同じ）。

## 5. 技術計画

### 5.1 部品と、中身の形

部品は六つ。並ぶ順は決まっていて、AI は使う部品を選ぶだけ（同じ部品を二つ置かない。部品の中に部品を入れない）。形の細部は、PRO-0002 の schema.ts を出発点にし、この節のとおりに直す。

| 部品 | 必須か | 中身 |
| - | - | - |
| ページの頭 | 必須 | 題、何の話かの二〜三文 |
| 例の流れ | 必須 | 2〜5 コマ。コマごとに、誰が何をするか、見せる物（名前と一文）、選択肢（人が選ぶコマだけ）、補足。この仕様の話のコマは一つ |
| 困ることと約束 | 必須 | 困ること 1〜4 件（困ること、なぜ困るか）。約束 1〜3 個ずつ（通し番号、言い直した一文、主張の番号） |
| 流れの図と試す画面 | 任意 | 図 1〜3 枚と、場面 2〜8 個 |
| 理解の確認 | 任意 | 問い 1〜4 個（問い、選択肢、正解の位置、理由、指す場面） |
| 扱っていないこと | 必須（DEC-0025） | 仕様の前提、約束していないこと、約束に選ばなかった主張（番号と一文） |

流れの図と試す画面の形（PRO-0002 で中身を書いた AI が迷った所を、次のように決める）。

- 図は、箱を上から並べた一本道と、横への分かれ（終わり方の箱）で描く。箱は、始まり・確かめること・すること・終わり方の四種類。図を 3 枚まで持てるので、手順の流れと、起動し直した時の流れを分けて描ける。
- 場面は、図ごとに、通った箱の並びを持つ。止まった箱（そこで処理が途中で止まった箱）は、止まった時だけ持つ。
- 場面の中の出来事は、確かめた箱ごとの答えを「進んだ」「ここで分かれた」「やり終えた」「ここで止まった」の四つで持つ。
- 場面は、その場面がどの約束を見せるかを、約束の番号で持つ。試す画面を使う時は、困ることと約束の約束が、どれも一つ以上の場面に出る。
- 約束に選ぶ主張は、人がその仕様に頼ることを言う主張（例: 一つの回答が決定になるのは一度だけ）。実装と Lean の証明の一致や、テストの範囲だけを言う主張は、扱っていないことの「約束に選ばなかった主張」に入れる。
- 途中で起きることや入力で結果が分かれる決まりが無い仕様では、流れの図と試す画面を使わない。理解の確認は、場面を指さない問い（約束についての問い）だけで使ってよい。
- 誰が何をするかが仕様に書かれていない時は、AI は、仕様が指す要求の記録（§5.6）から取る。そこにも無ければ「だれかが」と書く。

### 5.2 一つの定義から出すもの

部品と中身の形は、zod で `ui/src/specpage/schema.ts` に一つだけ書く（DEC-0023）。項目ごとの説明、数の上限、選べる値も、ここに書く。

| 出すもの | 置き場所 | どうやって |
| - | - | - |
| 画面の型 | ui/src/specpage | schema.ts の型をそのまま使う |
| JSON Schema | ui/build/spec-page.schema.json | Vite のビルドで z.toJSONSchema から書き出す。assets.go で実行ファイルに埋め込む |
| AI への書き方の説明 | skills/prepare-specify/references/spec-page.md | 同じビルドで、部品の説明、JSON Schema、文の書き方の決まりから書き出す |
| 登録の時の検査 | internal/specpage | 埋め込んだ JSON Schema で形を検査し、§5.2 の残りを Go で検査する |

書き方の説明は、DEC-0011（検証プラグインの書き方は prepare-verify の references/ に置き、専用のコマンドを持たない）と同じく、手順書の references/ に置く。init が手順書と一緒に対象プロジェクトに入れ、status は手順書が古いことを示す（今の仕組み）。手順書が実行ファイルより古いと、説明と検査がずれ、登録が断られて誤りが返る。AI はその誤りで直せる。

二つの書き出しは build.json に載せ、internal/uibuild の検査で、ソースから作られたかを見る（今の index.html と同じ）。

形の検査には、Go のライブラリ github.com/santhosh-tekuri/jsonschema/v6（Apache-2.0、依存は golang.org/x/text だけ）を使う。JSON Schema では見られない、つながりの検査は Go で書く（internal/specpage/check.go。PRO-0002 の check.ts と同じ中身に、§5.1 で足したものを加える）。

- 例の流れの「この仕様の話」のコマが一つ
- 約束の番号が重ならない
- 図の箱の名前が重ならない、図が始まりで始まり終わり方で終わる、分かれる箱の行き先が終わり方
- 場面の通った箱が図にあり、図の上で進める順になっている、「ふつうの流れ」の場面が一つ
- 場面が指す約束の番号があり、約束がどれも一つ以上の場面に出る（試す画面を使う時）
- 問いの正解の位置が選択肢の数の中、問いが指す場面がある

仕様と照らす検査（約束と「約束に選ばなかった主張」が指す番号が、仕様の claims にある）も Go で書く。これは登録の時だけ行う（§5.3）。

ライブラリとつながりの検査の誤りは、どちらも core.Issue（path と message）にし、core.ValidationError で返す（frontmatter の検査と同じ）。

### 5.3 置き場所と状態

中身は `prepare/pages/<SPEC の id>.json` に一つずつ置く。記録の種類（Markdown の記録）にはしない（§6 の record-kind）。

```json
{
  "format": 1,
  "spec": { "id": "SPEC-0001", "rev": 15, "sha256": "…" },
  "generated": { "at": "2026-11-11T…", "from_rev": 15 },
  "page": { "title": "…", "lead": "…", "sections": [ … ] }
}
```

- 書くのはデーモンだけ（DES-0004 の書き手を一つにする決まり）。一時ファイルからの rename で書く。
- ジャーナルには書かない。ジャーナルに知らない種類の行があると、前の版の prepare-dev は起動しないからである（internal/core/types.go の行の種類の検査）。中身はジャーナルから戻す必要も無い（AI が生成し直せる）。
- 登録できるのは、今の仕様の版（rev と sha256）に結び付けた中身だけ。古い版に結び付けた中身は断る。そのため、遅れて届いた古い中身が、新しい中身を置き換えることは起きない。
- `generated.from_rev` は、中身を最後に生成した仕様の版。§5.6 の結び直しでは spec だけが進み、from_rev は変わらない。
- 状態は、無い・今の版・古い・読めないの四つ。
  - 古い: 中身の spec の版が、今の仕様の版と違う。
  - 読めない: format がこの prepare-dev の知らない値か、形の検査（JSON Schema）に合わない（手で書き換えたなど）。
  - 読む時は、format と形の検査だけを行う。仕様と照らす検査とつながりの検査は、登録の時だけ行う。
- format は、形を互換でなく変える時だけ上げる。互換の追加（任意の項目を足す）では上げない。読めない中身は、AI が生成し直す。

### 5.4 ppdev と API

| 操作 | CLI | API |
| - | - | - |
| 登録する | `ppdev page put SPEC-xxxx --file page.json` | `PUT /api/pages/:spec` |
| 今の版に結び直す | `ppdev page rebind SPEC-xxxx` | `POST /api/pages/:spec/rebind` |
| 見る | `ppdev page get SPEC-xxxx` | `GET /api/pages/:spec`（状態、中身、仕様の題・版・claims の文を返す） |

- 書き方の説明を出すコマンドと API は持たない（§5.2）。
- 断る時は、今の API と同じく `{error, message, details}` で返し、検査の誤りは `details.issues` に入れる（internal/server の writeError）。CLI は今と同じく誤りを出して終わる。
- 登録と結び直しは、判断画面のアプリからはできない（REQ-0011 の制約）。回答の API と逆に、判断画面の Origin からの要求を断る。
- 中身を登録したら、ストアの Emitter で名前付きの知らせ「page」（spec の id）を SSE に流す（今の「question」「run」「job」と同じ）。

### 5.5 判断画面のアプリ

- 経路 `/spec/:id` を足す。サーバーは、`/` と `/q/:id` と同じく、この経路でも UI の HTML を返す。
- 質問の画面の「対象の記録」（SubjectRecords）で、種類が spec の記録に「仕様のページを開く」を出す。
- 部品は、PRO-0002 の parts.tsx を移し、§5.1 の形に合わせて直す。文字は React の文字として出し、HTML として解釈しない（dangerouslySetInnerHTML を使わない）。Markdown も使わない。
- 約束の横には、主張の番号と、今の仕様の claims の文を出す。中身が古い時は、ページの上に「古い」が出ている。
- 知らせ「page」で、開いている仕様の中身が変わったら、黙って替えずに「新しい中身がある」と出し、押すと読み込み直す。接続が戻った時は、今と同じく取り直す。

### 5.6 いつ、誰が生成するか

- AI が、prepare-specify の手順の中で生成する。仕様を書いてレビューを終え、人に確定を頼む質問を作る前に、references/spec-page.md を読み、中身を書いて `ppdev page put` する。
- 仕様の決まりを変えた時（DEC-0016 の区別）は、人に確定を頼み直す前に生成し直す。
- 仕様の決まりを変えない修正（誤字、言い換え、名前の置き換え）では、生成し直さずに `ppdev page rebind` で今の版に結び直す。結び直しは、仕様と照らす検査をもう一度行い、合えば spec の版だけを進める。合わなければ（主張の番号が消えたなど）断り、AI は生成し直す。
- 生成の入力は、仕様の記録の全体（本文と claims）と、仕様が specifies で指す要求の記録。困ることの理由や、誰が何をするかは、要求に書かれていることが多いため。
- 登録が断られたら、AI は返った誤りを直して出し直す。3 回断られたら止めて、誤りの一覧を人への報告に書く。
- これを prepare-specify の SKILL.md に書く。

### 5.7 生成した中身の確かめ方（DEC-0021。人に聞く）

| 案 | すること | 拾えるもの | 拾えないもの |
| - | - | - | - |
| A | 登録の時の機械の検査（§5.2）と、人がページを見ることだけ | 形の誤り、無い主張を指すこと、図と場面のつながりの誤り | 例や答えが仕様と食い違うこと |
| B（推奨） | A に加えて、生成した時に、経緯を知らないレビュー役に、仕様と中身だけを読ませて食い違いを挙げさせる。結果は REV に残し、食い違いは直してから人に確定を頼む。結び直しでは回さない | A ＋ 答えや約束の言い直しが仕様と食い違うこと（読んで分かる範囲） | 読み手も見落とす食い違い |
| C | B に加えて、Lean の証明がある仕様では、試す画面の答えを Lean で出した結果と突き合わせるテストを足す | B ＋ Lean の証明がある仕様の、場面の答えの誤り | Lean の証明が無い仕様の答えの誤り |

推奨は B。A では、人は仕様と食い違うページを見ても気付けない。C は、場面の言葉を Lean の操作に対応させる表を仕様ごとに書く必要があり、今 Lean の証明がある仕様は SPEC-0001 だけなので、手間に見合わない。B のレビュー役は、生成した時（新しく作った時と、決まりを変えた時）だけ回し、決まりを変えない修正の結び直しでは回さない（DEC-0016）。

## 7. 非機能要求

- 安全性: 中身は AI が書く。画面は文字を文字として出し、HTML もプログラムも実行しない（REQ-0011 の制約）。登録と結び直しは判断画面の Origin から受けない。

- 切り戻し: 仕様のページは今の機能から独立している。経路と操作を外し、`prepare/pages/` を消せば元に戻る。

## 要求

prepare-dev を使うどのプロジェクトでも、人は、判断画面のアプリで、仕様一つについて「仕様のページ」を見られる。ページの中身は、AI がその仕様の本文から生成する（DEC-0019、DEC-0022）。

ページに出すものは、決めた部品の一覧から選ぶ。最初の一覧は次の五つ。

| 部品 | 人が見るもの |
| - | - |
| 例の流れ | 仕様が扱う場面を、具体的な一件で順に見せる |
| 困ることと約束 | 仕様が無いと何が困るかと、仕様の約束。約束ごとに、元になった仕様の主張を示す |
| 流れの図と試す画面 | 人が場面（途中で起きることや入力の組み合わせ）を選ぶと、仕様の答え（何を確かめ、どう終わり、後に何が残るか）が、流れの図の上で通った道と並んで出る |
| 理解の確認 | 問いに答えると、正誤と理由が出る。問いが扱う場面を、試す画面で開ける |
| 扱っていないこと | 仕様の前提、仕様が約束していないこと、約束に選ばなかった主張 |

試す画面の答えをどう出すか（AI が場面ごとに前もって中身に書くか、prepare-dev に入れた決まった作りが中身のデータから求めるか）と、人が選べる場面の範囲は、設計で決める（§設計で決めること）。どちらの場合も、中身に書かれたプログラムは実行しない（§制約）。

どの部品を使うかは、中身を書く AI が仕様を読んで決める。例の流れ、困ることと約束、扱っていないことは、どの仕様でも使う。途中で起きることや入力によって結果が分かれる決まりが仕様に無い時に、流れの図、試す画面、理解の確認をどうするかは、設計で決める（§設計で決めること）。部品は一つずつ選んで、上から順に並べる。同じ部品を二つ置いたり、部品の中に部品を入れたりはしない。

部品ごとに、中身の形（欄、型、数の上限、欄ごとの説明）を一つの定義に決める。AI への書き方の説明、登録する時の検査、画面の描画は、その定義から出す（DEC-0023）。

```
仕様 ──（AI が本文を読み、決めた形で中身を書く）──→ ppdev で登録する
         登録する時に検査する。合わなければ、何も保存せずに理由を返す（AI が直して出し直す）
         中身は、どの版の仕様から作ったかを持つ
     ──→ 判断画面のアプリが描く
         仕様が変わったら「古い」と出る。AI が生成し直す
```

## 根拠

人が 2026-11-10 のチャットで指摘した。「全然pdd-kitのスピリットを感じないんだよね」「ずとかもないし、ダイアグラムもない」「Run a login against the spec　みたいなのもない」。PDD Kit は、prepare-dev が参考にした既存の仕組みである（REC-0001）。今の判断画面のアプリは質問の画面一つで、図を描く部品も、仕様を試す画面も無い（ui/src）。

SPEC-0001 の試作を作り、三つ目の版で「いいんじゃない大枠は」と言われた（DEC-0018）。その後、人は、仕様一つのための画面ではなく道具として作ると決めた。

- 「ここはあくまでtoolなんだからどの仕様じゃなくてもだめだろ」「AIに生成させるしかないとおもうが」（DEC-0019）
- 「仕様からgenerateしないと」（DEC-0022）
- 生成させるものの形は、先に決める。「ある程度決めないと困るぞ」（2026-11-10 のチャット）
- 形の定義は自前で作る（DEC-0023）

デモで確かめたこと（DEC-0023）: 別の AI に、仕様の本文と書き方の説明だけを読ませ、決めた形で中身を書かせた。SPEC-0001 と SPEC-0003 の両方で、一回で検査に合い、画面に描けた。

問題の整理（DIS）は書いていない。この人については、問題が、人の指摘と試作への感想で具体的に分かっているためである。prepare-dev を使うほかの人に同じ問題があるかは、確かめていない。

## シナリオ

通常の場合。

- S1: AI が仕様を書き終え、ページの中身を生成して登録する。検査に合い、保存される。
- S2: 人がその仕様のページを開く。部品が出る。
- S3: 人が、試す画面で場面を選ぶ。仕様の答えと、図の上で通った道が出る。理解の確認の問いに答えると、正誤と理由が出る。

例外の場合。

- X1: AI が登録しようとした中身が、決めた形に合わない（欄が無い、数が上限を超える、図に無い箱を指す）。登録は断られ、何も保存されず、どこがどう合わないかが AI に返る。
- X2: 中身がまだ無い仕様のページを、人が開く。中身が無いことが分かり、仕様の本文は読める。
- X3: 中身を作った後で、仕様が変わった。人がそのページを開くと、中身が前の版の仕様から作られたことが分かる。
- X4（中断と再試行）: ページを開いている間に、prepare-dev との接続が切れた。接続が戻ると、人が操作し直さなくても、ページは今の中身を取り直す。

## 受入条件

- AC-1: 次の二つの仕様について、AI が仕様の本文から生成した中身が登録の検査に合い、仕様のページに五つの部品が出る（S1〜S3）。二つとも、途中で起きることや入力で結果が分かれる決まりを持つ。
  - SPEC-0001（回答の適用）: 手順が進んで状態が変わっていく仕様。Lean の証明がある。
  - SPEC-0003（検証入力の追跡と実行記録の対応）: 検証の結果がいつまで証拠になるかを、入力に対して判定する仕様。Lean の証明は無い（主張は Go のテストで確かめる）。対象は仕様の全体。
  - この二つを選んだのは、種類が違い、デモで使ったからである。どちらも、このリポジトリの中で書かれた仕様で、このリポジトリの外の仕様では確かめていない。
- AC-2: 決めた形に合わない中身は、登録が断られ、何も保存されず、どの欄がどう合わないかが返る（X1）。
- AC-3: 仕様のページに、中身がどの版の仕様から作られたかと、今の版と違うかが出る（X3）。
- AC-4: 中身が無い時はそうと分かり、仕様の本文は読める（X2）。接続が戻ると取り直す（X4）。
- AC-5: 中身の文は、仕様の内部の言葉と記録の番号を、説明なしに使わない。会話の経緯を知らない読み手に中身の文だけを読ませ、「何の話か」と「約束が無いと何が困るか」を言い直せることを、確認記録に残す。約束に付ける元の主張は、仕様の文を示すもので、ここで言う中身の文には入らない（元の主張が仕様と同じであることの確かめ方は、§設計で決めること）。

## 制約

- 配るのは実行ファイル一つのままにする（REQ-0010）。
- 中身に書かれたプログラムや HTML を、画面で実行しない。中身は AI が書き、質問に答える画面と同じ所に出る。そこでプログラムが動くと、AI の書いたものが、人の代わりに質問に答えられてしまう。
- 画面から、仕様やページの中身を書き換えない。

## 対象外

- わざと間違いを入れた場合に、どの約束が破れるかを見せる機能。後で足す（DEC-0020）。
- AI が部品を自由に組み合わせること、画面に少しずつ出すこと（DEC-0023）。
- 理解の確認の答えを保存すること。
- 表示の速さの数値目標。

## 設計で決めること

- 部品ごとの中身の形の細部。デモで、中身を書いた AI が迷った所がある。
  - 流れの図は、一本道と横への分かれしか描けない。流れが二つある仕様や、落ちた後に起動し直す時の入口を置けない。
  - 場面の中で、途中で止まった所の示し方と、確かめた答えの示し方（はい・いいえ・やり終えた・止まった）の意味が決まっていない。
  - 仕様の主張のうち、どれを約束に選ぶかの基準が無い。
- 試す画面の答えをどう出すか。AI が場面ごとに前もって中身に書くか、prepare-dev に入れた決まった作りが中身のデータ（起きることや入力ごとの効果、分かれ道の表など）から求めるか。前者は、人が選べるのが AI の書いた場面だけになる。後者は、人が選んだどの組み合わせにも答えられるが、仕様の決まりをそのデータで書き切れる場合に限る（状態で答えが変わる仕様では、書き切れるかを確かめていない）。SPEC-0001 の試作は、その仕様の Lean の証明を JavaScript に手で写したもので、どちらの案でもない。どの組み合わせも試せることに価値があったことの根拠にはなる。
- 途中で起きることや入力によって結果が分かれる決まりが仕様に無い時に、流れの図、試す画面、理解の確認をどうするか（流れの図は一本道でも描ける。理解の確認は、約束についての問いなら場面が無くても作れる）。
- 人が選べる場面の範囲。最低限入れる場面（ページに出す仕様が扱う例外の場合それぞれ、など）を決めるか。
- 中身をどこに置くか（記録の一種にするか）。
- いつ、誰が生成するか（手順書のどこに書くか）。生成の入力を仕様の本文だけにするか。登録が断られた時の出し直しを、何回で止めて人に知らせるか。
- 人がどこからページを開くか。
- 生成した中身が仕様と食い違っていないことを、どう確かめるか。案を作って人に聞く（DEC-0021）。この中に、約束に付ける元の主張の扱いも入る。中身が主張を番号で指して、画面が仕様から文を出すなら、確かめるのは主張が仕様にあることと、どの版の仕様から文を出すか（仕様は番号を変えずに文を書き直すので、今の版から出すと、古い中身の約束の隣に新しい文が並ぶ）。中身が主張の文を写すなら、文が仕様と同じであることも確かめる。Lean の証明がある仕様では、試す画面の結果を Lean と照らせる。
- 部品の形の定義が prepare-dev の版で変わった時に、前に登録した中身をどうするか（DEC-0019）。その時に人に何が見えるか。
- ページを開いている間に中身が登録し直された時と、前の版の仕様から作った中身が後から登録された時に、どうするか。
- このリポジトリの外の仕様と、結果が分かれる決まりの無い仕様で、どう確かめるか。
- 人が質問に答えた時に見ていた中身の版を、回答や決定に残すか。

## 優先度

should と置いた。設計を始めることは人が決めた（DEC-0018）が、作るかどうかは、設計を人が確認した後に決まる。

## 観点の対応

- users・rationale: prepare-dev を使うプロジェクトで、仕様を確かめて確定する人のための要求（DEC-0019）。根拠は上のとおり。この人以外の利用者に必要かは、確かめていないので、users は hypothesis とする。
- scenarios_normal・scenarios_exception: S1〜S3 と X1〜X4。
- terms・data: 上の用語。中身は、どの版の仕様から作ったかを持つ。形の細部は設計で決める。
- states・rules: 中身の状態は、無い・ある・古いの三つ。合わない中身は登録しない（X1）。登録した後に部品の形の定義が変わった中身の扱いは、設計で決める（§設計で決めること）。
- quality・constraints: 読みやすさは AC-5 で確かめる。制約は上の三つ。
- priority: should（仮）。作るかどうかは設計の確認の後に人が決めるので、hypothesis とする。
- acceptance: AC-1〜AC-5。

coverage の decided は、観点の扱いが決まっているという意味で、検証済みという意味ではない。

## DEC-0016 — 確定した記録を後から変える時、AI のレビューは決まりを変えた時だけ回す

kind: decision · rev 1 · status accepted · sha256 b873a94adae94ada626d237529492f9b69e69b7474da29f4b99050915c31651e

```yaml
links:
  rationale_for:
    - PRO-0001
question: Q-0039
answer: ANS-0039-1
txid: 0b1ba4d6e2e3857d
chosen: rule-change-only
alternatives:
  - どの修正でも、変えた箇所を見る
  - 今のまま（どの修正でも、関連する記録の全文を見る）
reviewed:
  - id: PRO-0001
    rev: 1
    sha256: dd350699f4b711b12faf9f7057aa5e9cb83937c4f62647b5fe05af5c38254157
```

## 決定

確定した（accepted の）記録を後から変える時、AI のレビューは次のように回す。

| 修正の種類 | 例 | レビュー |
| - | - | - |
| 決まりを変えない | 誤字を直す。言い換える。ファイルの場所や名前を置き換える | 回さない。検証（RUN）と手の確認だけで合否を決める。報告に、変えた箇所を示す |
| 決まりを変える | 「パスワードは 2 桁」を「3 桁と記号」に変える | 変えた決まりと、それに関わる箇所だけをレビュー役に見せる |

決まりを変える修正では、次のようにする。

- レビュー役が見るのは、変えた決まりが頼まれたことに合うかと、ほかの決まりと食い違わないかである。
- 重い指摘を直したら、一度だけ確かめ直す。
- 変えていない箇所への指摘は、直さず一覧に残す。
- 変えた決まりは、人が見て確定し直す。

新しく書いた記録を人が確定するまでのレビューは、この決定では変えない。

この決定を記録した時点では、手順書（skills）と具体化案（PRO-0001 の 5.1 節）は書き換えていない。

## 代替案

- どの修正でも、変えた箇所を見る（決まりを変えない修正でも、変えた行とその前後をレビュー役に一回見せる）: 採らない。
- 今のまま（どの修正でも、関連する記録の全文をレビュー役が読み、重い指摘は直すか人に聞くまで先へ進めない）: 採らない。

## 理由

人が判断画面（Q-0039）で「決まりを変えた時だけ見る」を選んだ。

始まりは、2026-11-10 のチャットでの指摘である。「毎回多少の修正でも長すぎてきつい」「すすむにつれ重箱つつくことになってないか？」「仕様を確定して、その仕様に対してのみじゃないのか？」。直前の作業（docs/ の記録を prepare/ に移す）では、記録の変更が +46 −29 行だったのに対して、レビュー役が 1,500〜1,800 行の束を四回読み、重い指摘が 45 件出た。

先に出した質問（Q-0037）は「確定の後は回さない」とだけ書いていて、「パスワード2桁 -> 3桁+記号としたときに、レビューしないってこと？」と聞かれた。そこで、決まりを変えない修正と変える修正を分けた。

受け入れた欠点は、言い換えのつもりで意味が変わっていた場合を、レビューでは拾えないことである。報告に変えた箇所を示すので、人が見て気付くことになる。

- AI が、判断画面のアプリに「仕様を見るページ」を足す設計の文書を書く。

## 代替案

- 別の仕様でもう一つ試してから決める（ほかの仕様で同じ形の試しの画面を作り、この形が通じるかを見る）: 採らない。
- 試作のまま置く（本体には入れない）: 採らない。

## 理由

人が判断画面（Q-0041）で「本体に入れる設計を始める」を選んだ。記述欄には何も書かれていない。

始まりは、2026-11-10 のチャットでの指摘である。「全然pdd-kitのスピリットを感じないんだよね」「ずとかもないし、ダイアグラムもない」「Run a login against the spec　みたいなのもない」。引き継ぎ記録（REC-0001）が PDD Kit から取り入れると書いたのは工程の流れだけで、人への見せ方は、取り入れるものとして書かれていなかった。

「試作を作る」と言われて、SPEC-0001 を題材に、例、流れの図、起きることを選んで試す画面、理解の確認を一枚にした試作を作った。試作は本体の外にあり、リポジトリには入れていない。三回作り直し、そのたびに次の感想があった。

- 一版目: 「UI的にはそういう方向だけど、回答の適用を試すがよくわからんでなにをしてるのかがわからんかった」
- 二版目: 「UIは別にいいんだけど説明とかいいまわしとか文言がわかりづらすぎる」
- 三版目: 「いいんじゃない大枠は」

試作で分かったことは、次の四つである。

## 実行時の流れ

CLI は root の `.prepare-dev/daemon.json` を読み、書かれた URL の `/api/identity` に問い合わせて、動いているデーモンの version と build を自分のものと比べる。デーモンは HTTP を始めてから daemon.json を書くので、lease が取られていて daemon.json が無い間は起動中である。

| 状況 | CLI の振る舞い |
| --- | --- |
| daemon.json がなく、lease も空いている | 同じ実行ファイルを `serve --root <root>` で起動し、端末から切り離す（新しいセッション）。起動したものが応答せずに終わったら、待たずに daemon.log の最後の行（起動できなかった理由）を示して終える。別の起動に lease を取られたときは、その相手が応答するのを待つ |
| デーモンが応答し、version と build が同じ | 接続する。置き場所が違う同じ build の写しも接続する |
| デーモンが応答し、version か build が違う | 接続しない。相手の version・build・場所・pid と、`prepare-dev stop --root <root>` で止めてから再実行することを示して終える |
| デーモンが停止を受け付けた後で、まだ終わっていない | identity にだけ答え、ほかの要求は 409 で拒む。CLI はその誤りを示して終える（止まってから再実行する） |
| daemon.json はあるが応答せず、lease が空いている | 強制終了したデーモンの残りとみなし、daemon.json を消して起動する。ただし daemon.json を TypeScript 版が書いていて、その版の lease がまだ取られているときは、引き継がずに止め方を示して終える（移行期の対策。§TypeScript 版からの移行） |
| lease が取られているが応答がない（daemon.json の有無によらない） | 起動中かもしれないので、時間（既定 15 秒）まで待つ。それでも応答しなければ、lease ファイルに書かれた pid を示して終える（そのプロセスを止めて再実行する） |

デーモンは、lease を取ってから記録を開き（走査と回復を済ませる）、127.0.0.1 の空いているポートで HTTP を始め、daemon.json（pid、ポート、URL、root、起動時刻、version と build と場所、停止用のトークン）を書く。lease はプロセスの終了とともに OS が外す。停止は `prepare-dev stop` が daemon.json のトークンで `/api/shutdown` を呼ぶ。検証ジョブの実行中は拒否する。デーモンは止めるまでプロジェクトごとに一つ残る。

デーモンを置く理由は三つある。人が回答している間も判断画面をいつでも開けること、回答や検証の完了を画面とエージェントの待機（`q wait`、`verify wait`）へ届けること、検証を非同期に走らせて結果を同じ書き手が記録すること。CLI がその都度ファイルロックを取って直接書く形では、画面と待機のために結局どこかで HTTP を出し続ける必要がある（代替案 no-daemon）。

## 書き手を一つにする

lease が守るのは、一つの root の永続状態（記録、質問、RUN、ジャーナル）を開くプロセスが一つだけであること。ID の採番と回答の適用は、メモリ上の索引とジャーナルを一つの書き手が持つ前提で作っている（SPEC-0001 の前提）。lease のファイルは root の中にあるので、root をどのパスで指してもロックは同じファイルに掛かる。lease を取れない `serve` は記録を開く前に終わる（CLI が lease を確かめるために一瞬ロックするので、取得は 1 秒だけ再試行する）。

lease のファイルを動作中に消されると（`git clean`、`git stash -u` など）、次の CLI は lease が空いていると見て二つ目のデーモンを起動できてしまう。これを防ぐため、デーモンはすべての操作の前に、lease のパスが自分のロックしているファイルと同じものかを確かめ、違えば何も書かずに 503 を返し、2 秒以内に終わる。`init` は `.prepare-dev/.gitignore` に daemon.json・daemon.log・lease などを書き、これらが消されたりコミットされたりしにくくする。

保証は作業コピーごとである。ブランチや worktree の作業コピーはそれぞれのデーモンを持ち、同じ基準から別々に ID を採番するので、記録を書く作業コピーは一つにする（配布物の README と prepare-dev skill に書く）。二つの作業コピーで書いた prepare/ をマージすると、同じ番号の記録とジャーナルが衝突する。これは普通のコンフリクトとして、マージのときに人が直す（DEC-0008）。prepare-dev は自動でまとめず、直し方の手順も持たない。代わりに、直した結果を黙って書き進めないための検査を持つ。

- ジャーナルに衝突の印が残っている: デーモンは起動せず、CLI が待たずにその理由（daemon.log の最後の行）を示す。
- 直した結果に矛盾がある（同じ記録・質問・回答の二度の作成、同じ decision の二つの取引、一つの回答の二つの確定、別の作業コピーで判断に反映した回答や decision が残っている）: デーモンは起動するが、回復も含めて何も書かず、status の problems に示す。
- ブランチの切り替え・stash・reset・pull で Git がジャーナルを置き換えた: 動いているデーモンは、操作の前にジャーナルが開いたときと同じファイル・同じ長さかを確かめ、違えば何も書かずに止まる。次のコマンドが今のジャーナルで起動し直す。

別の名前のファイルが同じ ID を持つ場合（手で写したときなど）は、二つ目を problems に示してどちらも書き換えない。

## データの形式

記録の Markdown（YAML の frontmatter）、質問と RUN の JSON（2 文字の字下げ）、ジャーナル（JSON Lines）の形式は TypeScript 版から変えない。読むだけではファイルを書かないので、記録ファイルの sha256（版として質問・判断・レビュー・RUN が参照する）は、内容を変えない限り変わらず、版の切り替えでファイルが書き換わることもない。

書き方（YAML の引用と順序、JSON の並び）まで TypeScript 版と同じにするのは、runtime が書き直すファイル、つまり記録（`record put` と外部編集の検出）と質問（回答・受領・終了・適用）の差分を、変えた項目だけにするためである。記録は Git に入れて差分で読む。RUN は完了時に一度書くだけ、ジャーナルは追記だけで書き直さないので、書き方の一致は求めず、読んで欠ける項目がないこと（API と回復が使う）だけを求める。

基準は TypeScript 版の最後のコミット（342bc64）が書いたファイルの写し（internal/core/testdata/ts-342bc64）で、テストは写しの記録と質問を読み直して書き出してもバイト列が変わらないこと（`cancelled` の無い古い質問に `cancelled: null` が加わるのは TypeScript 版と同じ）、RUN とジャーナルの行は読んで書き出しても欠ける項目がないこと（書き方は問わない）を確かめる（SPEC-0004 D1）。YAML の書き出しは npm の yaml パッケージに合わせて自前で実装した。書く前に読み戻し、内容が一致しなければ書かない。YAML 1.1 の読み手が改行とみなす文字（U+2028、U+2029、U+0085）と制御文字は、二重引用符の中でエスケープする。

## HTTP API

経路は標準の ServeMux で振り分ける。判断画面と CLI が使う経路は次のとおり。

| 経路 | 用途 |
| --- | --- |
| `GET /api/identity` | pid、root、起動時刻、version・build・場所 |
| `POST /api/shutdown` | 停止（daemon.json のトークンが必要） |
| `GET /api/status` | 未処理の回答、回答待ちの質問、未対処の指摘、主張の今の結果を決める RUN（今の仕様が挙げる主張とプラグインの組ごとに最も新しい RUN）のうち当てはまるものと当てはまらないもの、ほかの RUN の数、記録されなかった検証、問題（次の init が skills にすることは、CLI の status が足す） |
| `GET/POST /api/records`、`GET/PUT /api/records/:id` | 記録の一覧・作成・取得・更新（更新は読んだ版が必要） |
| `GET/POST /api/questions`、`GET /api/questions/:id`、`GET /api/pending` | 質問の一覧・作成・取得、未処理の回答 |
| `POST /api/questions/:id/answers` | 回答（判断画面からだけ） |
| `GET /api/questions/:id/wait` | 回答を待つ |
| `POST /api/questions/:id/answers/:aid/ack`、`.../apply`、`.../close`、`POST /api/questions/:id/cancel` | 受領、判断への適用、終了、取り消し |
| `GET/POST /api/runs`、`GET /api/runs/:id`、`GET /api/runs/:id/wait` | 検証の一覧・開始・取得・待機 |
| `GET /api/trace/:id`、`GET /api/bundle`、`GET /api/plugins` | trace、レビュー資料、プラグイン一覧 |
| `GET /events` | 変更の通知（SSE） |
| `GET /`、`GET /q/:id` | 判断画面 |

Host が `127.0.0.1:<port>` か `localhost:<port>` でない要求と、Origin が自分以外の要求は 403 で拒否する。回答は判断画面の人のものなので、Origin を持たない要求（ブラウザ以外）も拒否し、CLI に回答の操作を置かない。これで防ぐのは、エージェントが手順どおりに CLI で回答することと、ほかのサイトのページからの要求である。同じ利用者のプロセスが Origin を付けて送ることは防がない（受け入れた残りのリスク）。loopback の API に認証は無いので、一人の利用者のホストを前提にする。エラーは `{error, message, details}` の形で返し、500 は daemon.log にも書く。

## CLI

コマンドは `init`、`status`、`ui`、`pending`、`record create|get|put|list`、`q create|list|show|wait|pending|ack|apply|close|cancel`、`verify run|wait|get|list`、`trace`、`bundle`、`serve`、`stop`、`version`。`mcp` と `q answer` は無い。出力は JSON で、`status` は既定で文章（`--json` で JSON）。エージェントが読む `verify` と `trace` は、入力ファイルの一覧を件数に、不一致と実行したテストの一覧を先頭の 5 件と残りの数に縮め、`verify list` は実行ごとの要約にする。`--json` で全体を出す。

## init と skills

`init` は `.prepare-dev/config.json` と `.prepare-dev/.gitignore` がなければ作り（あれば変えない）、skills を `.agents/skills` と `.claude/skills` にコピーし（`--skills-dir` で変更、`--no-skills` で省略）、デーモンを起動する。MCP の設定は書かない。

skills のコピーは、入れた skill の digest を `.prepare-dev/skills.json` に残す。次の `init` では、無い skill を入れ（利用者が消したものも入れ直す）、同じ内容なら何もせず、前に入れたときのまま編集されていない skill は新しい版に置き換える。それ以外の違い（利用者の編集、別の方法で置いたもの）は残して conflicts に示す。`--replace-skills` を付けると、違う skill のディレクトリを `.prepare-dev/skills-backup/<時刻>/` に移してから置き換える。skill の場所にあるシンボリックリンクとファイル、root の外・シンボリックリンク・ディレクトリでない配置先は、`--replace-skills` でも触らずに conflicts に示す。

init はその回の配置先（既定の二つか、`--skills-dir` で指定したもの）を skills.json に残す（`--no-skills` は変えない。0.3.0 より前の skills.json では、入れた skill の配置先をそれとみなす）。CLI の status は、その配置先に対して init を書き込まずに動かし、次の init がすることを示す。入れるもの（この build にあって配置先に無いもの）、置き換えるもの（init が入れて編集されていない、この build と違うもの）、残すもの（編集されたもの、init が入れていないもの。`--replace-skills` で退避して置き換わる）、手で直すもの（シンボリックリンク、ファイル、root の外。`--replace-skills` でも触らない）。比べるのは CLI で、デーモンの `/api/status` には入れない（デーモンは同じ build なので結果は同じで、記録の problems に skills のことが混ざらない）。skills.json が無ければ（init で入れていない、`--no-skills`）示さず、読めなければその誤りを示す。

## 判断画面のビルド

ui/ の `pnpm build` が build/index.html、画面に入れた npm パッケージのライセンス（build/THIRD_PARTY_NOTICES.txt）、build/build.json を書く。build.json には、ビルドの元にしたソースの digest と、出力の二つのファイルの sha256 が入る。ソースは ui 直下の index.html・package.json・pnpm-lock.yaml・tsconfig.json・vite.config.ts と、src/ の下のファイル（テストと、`.` で始まる名前を除く）である。Go のテスト（SPEC-0004 B1）とリリースのスクリプトは、今のソースの digest と出力の sha256 を build.json と照合し、ソースを変えてビルドし直していないときも、出力を手で書き換えたときも失敗する。この範囲は、ビルド（ui/vite.config.ts）と Go（internal/uibuild）の二か所に同じ一覧として書き、src/ の外にビルドの入力を足すときは両方を直す。二つの計算が食い違えば B1 が失敗して分かる。Node.js（pnpm・Vite）は画面を直す人だけが使い、prepare-dev のビルドと利用には要らない。

## 検証プラグイン

- lean4: `lake env lean --src-deps` を再帰的に使って入力を集め、`lake build` と `#check`・`#print axioms` で確かめる。Lean はモジュールの名前で import を読むので、ファイルが増えても結果は変わらず、ディレクトリの一覧は記録しない。
- vitest: テスト・追加実装・Vitest の設定から、esbuild のバンドルと同じ規則で import をたどり、esbuild が読み込むファイルを入力にする。拡張子の無い import は Vite の既定の順で探す。node_modules の中のパッケージは manifest と lockfile で代表し、型だけの import は実行時に読まれないので入力にしない。import が読むファイルのディレクトリ（その段だけ）と、impl_files のパターンが探すディレクトリの一覧を記録する（SPEC-0003 V1）。
- gotest: go list が報告するテストのビルドに使うファイル、実行するパッケージの testdata、テストが実行中にビルドするパッケージ（`input_packages`）、そのほかに読むファイル（`impl_files`、`**` を使えるパターン）を入力にし、パッケージ・埋め込み・testdata・パターンのディレクトリの一覧を記録して、`go test -json -count=1` で、テストのキャッシュを使わずに実行する（SPEC-0003 V3。集めるファイルの種類は SPEC-0003 だけに書く）。デーモン自身の環境の `PREPARE_DEV_` で始まる変数はテストに渡さない（ほかの環境変数はデーモンのものが渡る）。テストは RUN ごとのディレクトリ（`PREPARE_DEV_BOUNDS_DIR`）に、流した件数や検査した実行ファイルを書いて scope.bounds に残せる。

runtime は、入力の内容の変更・削除と同じく、記録したディレクトリの一覧が変われば証拠を当てはまらないものにする。どのプラグインも、検証器の有無を project_dir で調べ（elan が project_dir の lean-toolchain の版を選ぶ）、使った道具の場所を RUN の `tool.extra` に残す。検証はデーモンが動かすので、道具の探し方（PATH に `~/.elan/bin`・`~/.cargo/bin`・`~/.local/bin` を足す）と環境変数は、デーモンを起動した CLI のものが使われ続ける。デーモンは検証の道具を別のプロセスグループで動かし、timeout_ms を超えたらグループごと止めて RUN を timeout にする（Go のテストが macOS で確かめる）。デーモンを止めても、動いている道具は止めない（停止の API は検証中の停止を拒む。pid を止めて終わらせたときは道具が残りうり、その RUN は runs_incomplete に残る）。

## 工程の外の記録

工程の記録（DIS・REQ・DEC・DES・SPEC・REV）と検証の結果（RUN）のほかに、工程の外で残すものには記録の種類 record（REC-*）と proposal（PRO-*）を使う。どちらも runtime を通して書く。

- record: 確認記録（用語）と、貼り付けられた引き継ぎの文書の原文のように、工程の外で起きたことの記録。
- proposal: 工程の外で作った案（工程に入る前の具体化案など）。採ったものは工程の記録に引き継ぎ、置き換わったら superseded にする。

### すべての対象プロジェクトに入る規則

skills（prepare-dev の共通規則と、prepare-specify・prepare-verify の手順）が、すべての対象プロジェクトのエージェントに次を求める。このリポジトリも対象プロジェクトの一つとして従う。人が決めたのは、工程の外の記録を REC・PRO として runtime を通して書き、docs/ などに書かないことと、それをすべての対象プロジェクトに求めること（DEC-0013）で、確認記録の向き、checked、報告とやり直しの条件、添付の細目は、設計者がそれを具体化したもの。

- 工程の記録を runtime の外のファイル（docs/ など）に書かない。
- 書き込みが止まっている間は、確かめたことを人への報告に書き、直った後に確認記録にする。書き込みが止まっているのは、runtime が「Nothing is written until …」の誤りで書き込みを拒む間（マージしたジャーナルの矛盾と、回復できない取引（用語）。status の problems にもその理由が出る）と、デーモンが起動しない間（ジャーナルに衝突の印があるときなど）である。status の problems には書き込みを止めないもの（読めない記録のファイル、同じ ID の二つ目のファイル、どの取引も使っていない読めない質問のファイル）も出るので、problems があることだけで記録を控えない。
- 確認記録は、確かめた SPEC・REQ・DES を自分の links.related_to から指し、確かめられる側は、自分を確かめた確認記録を links にも本文にも書かない。確かめられる側の版が進むと、その版を控えたもの（SPEC と REQ なら主張の RUN。どの記録でも、それを対象にした質問と、それを見た判断）が今の版に当てはまらなくなるので、確認を足すたびにそれらを取り直すことにならないようにするため（DES の版は RUN には控えられないが、質問と判断には控えられる）。どの確認記録が何を確かめたかは trace で引く（trace は links を両方向にたどる）。
- 手の確認は人かエージェントが行い、誰が行ったかを本文に書く。確認は一回ごとに新しい確認記録にし、前の確認記録に新しい確認を書き足さない。書いたことの誤りや足りない links は直してよく、直したことを本文か note に書く。
- frontmatter の checked には、確かめたものを後から特定できる値を書く。commit（確かめたものを作ったソースのコミット）と、成果物や配布物を確かめたなら artifacts（ものごとに name と sha256。実行ファイルと、それを含む tar.gz は別の項目）。確認は、変更の無い作業コピー（コミットした後）から作ったもので行う。変更のある作業コピーから作ったものを確かめたときは、commit の代わりに base_commit と dirty: true を書き、後から同じものを作れないことを本文に書く。
- 手の確認を求める仕様は、確認ごとに、何を確かめるかと、やり直しの条件（どの場所を変えたら、その確認をやり直すか）を書く。やり直しの条件は仕様か設計に書く。
- prepare-verify の報告では、手の確認ごとに、それを含む最も新しい確認記録の checked.commit から今の作業コピーまで（コミットしていない変更と、追跡していないファイルを含む）の変更が、やり直しの条件に当たるかを示す。dirty: true の確認記録と、commit も dirty も持たない確認記録（この決まりより前に書いたもの）は、確かめたものと今のものを比べられないので、当たるものとして扱う。検証の工程は、手の確認ごとに、やり直しの条件が仕様か設計に書かれていて、当たる変更の無い確認記録があって終わる。当たるものは、変更をコミットした後に、そのコミットから作ったもので確認をやり直す。やり直さずに終えるなら、人に聞いて判断（DEC）にする。
- 確認記録の添付（画像、出力の JSON）は `<records_dir>/records/<id>/` に置く（records_dir は既定で prepare）。runtime は添付を読まず、記録の版にも含めないので、本文にそれぞれの sha256 を書き、添付を変えたら本文の sha256 も直す。

### このリポジトリでのやり直しの条件

このリポジトリの手の確認（SPEC-0004 §受入範囲 の五つ: 配布物の e2e、Linux のコンテナでの実行、TypeScript 版との共存と戻し方、ブラウザでの操作、REQ-0010 P4 の一連の利用。それに SPEC-0003 §検証 の、実際の Vitest での確認）は、確認記録の checked の commit の後に次の場所を変えたらやり直す。何を確かめるかは、それぞれの仕様に書く。skills と判断画面の埋め込みは、checkout からビルドした e2e（RUN）が確かめるので、配布物を手で確かめ直すのは、ビルドとリリース、デーモンの起動と識別と停止、TypeScript 版が読むもの、判断画面の操作に関わる変更だけでよい。

| 変えた場所 | やり直す確認 |
| --- | --- |
| scripts/release/、cmd/prepare-dev、assets.go の埋め込みの指定 | 配布物の e2e |
| internal/daemon/ と、internal/cli/cli.go の cmdServe（起動、識別、lease、停止のシグナル、TypeScript 版の検出） | 配布物の e2e、Linux のコンテナでの実行、TypeScript 版との共存と戻し方 |
| internal/server/ の daemon.json と /api/identity、internal/core の ToolIdentity と RUN・ジャーナルの型、internal/store のジャーナルと RUN の書き方（TypeScript 版が読むもの） | TypeScript 版との共存と戻し方 |
| ui/src/ と ui/build/、internal/server/（回答の API と配信） | 配布物で、判断画面をブラウザで操作する |
| internal/plugin/vitest が実行ごとに加える reporter、ui/package.json の vitest の版 | 実際の Vitest で、レポートと reporter の出力の形を確かめ直す（SPEC-0003 §検証） |

REQ-0010 P4 の一連の利用は、Vitest の行を除く、上の表のどれかに当たる変更でやり直す。検証の道具の起動と時間切れ（internal/plugin/plugin.go の Exec）は、Go のテスト（TestExecTimeoutStopsTheProcessGroup。主張の証拠ではない）が macOS で確かめるので、手の確認には入れない。やり直す確認は、変更をコミットした後に、そのコミットから作ったもので行い、新しい確認記録にする。済むまで、prepare-verify の報告では未解決として示す。

## 配布と開発

`go run ./scripts/release -version <v>` で macOS と Linux（arm64・amd64）向けの実行ファイルを作り、README と第三者ライセンスとともに tar.gz にまとめ、sha256 を `dist/artifact.json` に残す。画面のビルドが build.json と合わなければ作らない。パッケージ管理サービスへの公開はしない。配布物そのものは、展開した実行ファイルを `PREPARE_DEV_E2E_BINARY` に渡して e2e テストで確かめる。

開発中は checkout で `go run ./cmd/prepare-dev` を使う。ソースを変えると build が変わるので、前のデーモンを `prepare-dev stop` で止めてから使う。

このリポジトリ自身の記録も、§工程の外の記録 のとおりに prepare/ に置く。記録でないものは、それを使う場所か人が決めた場所に置く。配布物の README の元は scripts/release に、構想の段階で参照した資料の一覧は docs/references.md に置く（DEC-0012）。検証プラグインごとの主張の書き方（guidance）を skills に置くこと（DEC-0011）と、記録の規則をすべての対象プロジェクトに求めること（DEC-0013）も、人が判断画面で選んだ。

検証プラグインごとの主張の書き方（guidance）は、エージェントが仕様と検証の工程で読むものなので、prepare-verify の skill の references/ に置き、skills と一緒に配る。プラグインの規則を説明するので prepare-verify に置き、prepare-specify は同じ親ディレクトリの prepare-verify/references/ を読む（init はすべての skill を並べて入れる）。

更新するときは、デーモンを `prepare-dev stop` で止め、実行ファイルを入れ替え、`prepare-dev init` を実行し直す。init が skills と guidance を新しい版にし、編集した skill は残して status に示す。プラグインの版（`prepare-dev version --json` の plugins）が変わった版では、前の版で取った RUN が当てはまらなくなるので、実装を変えていなくても verify run をやり直す（0.3.0 では三つとも変わる）。config.json に、入れた実行ファイルが持たないプラグインの名前があれば外す。配布物の README（scripts/release/distribution-readme.md）にも同じ手順を書く。0.2.0 の skills は `prepare-dev guidance` を実行するよう書いており、0.3.0 の実行ファイルはそれを持たないので、init を実行し直すまで書き方を読めない。

## TypeScript 版からの移行

TypeScript の本体（packages/ の core・runtime・mcp・cli、plugins/、scripts の build.mjs・pack.mjs、ルートの package.json・pnpm・tsconfig・vitest の設定）を消し、画面を packages/ui から ui/ に移す。実プロセスの強制終了からの回復を確かめていた scripts/e2e-crash.sh は Go の e2e テストに移す。このリポジトリの `.mcp.json` と `.codex/config.toml` の登録を消す（DEC-0007）。

切り替えるときは、TypeScript 版のデーモンを `prepare-dev stop` で止め（停止の API は同じ）、エージェントの MCP 設定から `prepare-dev mcp` を消し、`prepare-dev init --replace-skills` で skills を置き換える。戻すときは Go 版のデーモンを止め、commit 342bc64 の checkout で `pnpm install` と `pnpm ui:build` を実行して TypeScript 版を使う。TypeScript 版は Go 版の書いた記録をそのまま読み、Go 版で増えたもの（gotest の RUN、RUN の listings、skills.json）は使わない。

移行期の対策として、止め忘れた相手のデーモンを検出する。TypeScript 版の lease は root から決めた TCP のポートで、Go 版の flock とは互いを排除しない。そこで Go 版は daemon.json と `/api/identity` の識別に TypeScript 版が必須とする root（実行ファイルのディレクトリ）と mode（`package`）も書き、TypeScript 版の CLI が Go 版のデーモンを別の build として拒むようにする。逆向きは、Go 版の CLI と `serve` が TypeScript 版の書いた daemon.json を見つけ、その版の lease のポートが取られていれば、引き継がずに止め方を示す。この検出は相手の daemon.json があるときしか働かない（相手が lease を取ってから daemon.json を書くまでの間、daemon.json が消された後、手で起動した TypeScript 版の `serve`）。そのため、移行中は二つの版を同じ root で同時に使わないことを手順とする。これらは TypeScript 版を使うプロジェクトを切り替え終えるまでの対策で、TypeScript 版を使うプロジェクトが残っていないことを確かめてから外す（版の番号には結びつけない）。外す前に、所有者に、ほかの機械で TypeScript 版を使っていないかと、戻す予定が無いかを聞く（調べて分からない事実なので）。外すものは、相手の daemon.json と lease のポートの検出（internal/daemon）と、その CLI と serve からの呼び出し、識別の root と mode、その e2e、SPEC-0004 の P3 と assumptions の該当部分。コードでは、internal/daemon の「the TypeScript version」の区切りと、ToolIdentity と cmdServe の注記が目印になる（記録の形式の互換についての同じ語の注記は外すものではない）。

移行は、TypeScript の本体が残っていないこと、SPEC-0001・SPEC-0003・SPEC-0004 の主張の RUN が今の版に当てはまること、配布物を別の場所と Linux で動かした確認と版の共存の確認が確認記録に残っていることで完了とした（85477c7 としてコミットする前に、342bc64 と未コミットの変更から作った build で確かめた）。その後の変更で手の確認をやり直す条件は §工程の外の記録 に書く。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 自前の YAML 書き出しが npm の yaml と違う書き方をする | TypeScript 版の写しで往復のバイト一致を確かめ、書く前に読み戻して違えば書かない |
| 埋め込む画面のビルドがソースとずれる、または手で書き換えられる | build.json のソースの digest と出力の sha256 を、テストとリリースで照合する |
| 強制終了したデーモンの daemon.json が残る | lease が空いていれば古いものとして消す。pid は使わない |
