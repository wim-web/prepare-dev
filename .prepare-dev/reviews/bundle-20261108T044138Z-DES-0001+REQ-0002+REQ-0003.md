## 1. 概要と問題

prepare-dev の入口（CLI と MCP）とデーモンを、対象リポジトリに機械固有の絶対パスを書かずに起動できるようにする。DIS-0001 の根の問題は、`init` が道具リポジトリの `tsx`、入口ソース、対象の `--root`、skills の symlink 先という四つの絶対パスを対象リポジトリに書き出し、ホストと入口がそれに頼っていることにある。本設計は Q-0002 の推奨（段階 1 を案 G＝利用者単位の MCP 登録で。skills はリンク。PATH 依存の備えは H1 の後）と Q-0003 の推奨を前提に、REQ-0002〜REQ-0007 を満たす最小の変更を定める。REQ-0008（段階 2）は扱わないが、妨げない構造にする。用語は DIS-0001 の「用語」に従う。

## 2. 目標と非目標

目標（優先度は REQ の `priority`）:

- REQ-0002（must）: 対象リポジトリの git 共有ファイルに絶対パスを書かない。既存の絶対パス入りの登録を移行できる。
- REQ-0003（must）: 入口は自分の位置と対象リポジトリを設定ファイルなしで決め、対象外の場所では副作用を出さない。同時起動でもデーモンは一つ。
- REQ-0005（must）: skills が解決でき、切れたリンクを検出して報告・張り直す。
- REQ-0006（must）: デーモンは自分の checkout 内の UI を配信し、無ければ探したパスとともにそれと分かる。
- REQ-0004（should）: `daemon.json` と `status` に道具リポジトリの位置と実行経路を出す（段階 1 の最小形）。
- REQ-0007（should）: `pnpm cli` と `pnpm test` は常にソースを見る。`mcp.test.ts` と `scripts/e2e-crash.sh` が新しい起動経路で通る。

非目標:

- REQ-0008（could）: 配布物だけで動く段階 2。Q-0002 で a-2d が選ばれない限り着手しない（Q-0003 p8-could）。本設計は `daemon.json` の項目名と起動経路を段階 2 でも使える形にするだけで、束ねる作業は含めない。
- DIS-0001 の非目標（npm 公開、Windows、複数版共存、検証ツールの配布、UI の見た目、skills の内容、HTTP の認証と origin 制限）。
- 案 B（起動シム）の実装。Q-0002 c-defer により、H1 が偽のホストが見つかるまで作らない。切り替え時の差分は §6 に書く。
- 再ビルド後の古いデーモンの検出（REQ-0004 AC-2〜AC-4 は案 C、D のみ）。

## 4. 利用シナリオ（CUJ）

### CUJ 1: 新しい機械で対象リポジトリを使い始める（REQ-0002 AC-1、AC-2、REQ-0003 AC-1、AC-4）

- Given: 道具リポジトリを任意の場所に clone し `pnpm install` 済み。対象リポジトリを clone 済み（`prepare/` と `.prepare-dev/config.json` が git に入っている）。利用者単位の MCP 登録と skills は未設定。
- When: 道具リポジトリで `pnpm cli init --root <対象>` を実行し、出力に示された二つの登録コマンド（`claude mcp add -s user ...`、`codex mcp add ...`）と `pnpm cli skills --user` をそのまま実行する。ホストを対象リポジトリで起動する。
- Then: 対象リポジトリには `init` 前後で git 差分が無い（`prepare/`、`config.json` は既にある）。ホストは cwd から対象を決めた入口に接続し、`status` が返る。`daemon.json` に道具リポジトリの位置が出る。

### CUJ 2: 無関係なプロジェクトでホストを起動する（REQ-0003 AC-2）

- Given: 利用者単位の登録が済んでいる。cwd に `.prepare-dev/config.json` が無い。
- When: ホストが入口を `mcp` で起動する。
- Then: 入口は MCP の initialize に応答し、ツールを一つも公開せず、そのまま待つ。cwd に `prepare/` も `.prepare-dev/` も作られない。ホストのログ（stderr）に「対象ではない。`init` で対象にできる」という一行が出る。

### CUJ 3: 既存の絶対パス入りの登録を移行する（REQ-0002 AC-3、AC-4）

- Given: 旧 `init` が書いた `.mcp.json`、`.codex/config.toml` の `[mcp_servers.prepare-dev]` ブロック、`.agents/skills/*` の絶対 symlink がある対象リポジトリ。`.codex/config.toml` には利用者が書いた別の設定もある。
- When: `pnpm cli init --root <対象> --migrate` を実行する。途中で止めてもう一度実行する。
- Then: `.mcp.json` の `prepare-dev` 項目と TOML のそのブロックだけが消え、他の設定は byte 単位で変わらない。出力に消したものが列挙される。二回目の実行は何も消さず、結果は一回で完了した場合と同じ。

### CUJ 4: 道具リポジトリ自身で作業する（dogfooding。REQ-0003 AC-5）

- Given: 道具リポジトリの worktree を二つ持つ。利用者単位の登録は片方の checkout を指す。
- When: 各 worktree で `pnpm cli init`（`--root` は worktree。`--register project` が既定で選ばれる）を実行し、ホストをその worktree で起動する。
- Then: `.mcp.json` と `.codex/config.toml` に `pnpm cli mcp --host <host>` の登録が書かれ、絶対パスを含まない。プロジェクト単位の登録が優先され（H8）、その worktree のソースが動く。`.agents/skills/*` は `../../skills/*` への相対 symlink になる。`status` の `tool.root` がその worktree を指す。

### CUJ 5: 道具リポジトリを移動した（REQ-0005 AC-2、AC-3、REQ-0006 AC-1）

- Given: 利用者単位の skills リンクと MCP 登録が旧い場所を指している。デーモンは止まっている。
- When: 新しい場所の道具リポジトリで `pnpm cli skills --user` を実行し、`init` の出力にある登録コマンドを再実行する。ホストを対象で起動する。
- Then: `skills --user` は切れたリンクを skill 名つきで報告して張り直す。新しい場所から起動した入口がデーモンを立て、`GET /` が新しい場所の UI を返す。

### CUJ 6: 二つのホストが同時に入口を起動する（REQ-0003 AC-3、AC-6）

- Given: 対象リポジトリにデーモンが無い。
- When: Claude Code と Codex（または CLI）がほぼ同時に入口を起動する。
- Then: 一方だけがデーモンを立て、他方はそれに接続する。`daemon.json` は一つの生きているデーモンを指し、孤児プロセスは残らない。起動に失敗した場合は原因が `.prepare-dev/daemon.log` に残り、再試行で二つ目は立たない。

### CUJ 7: UI がビルドされていない（REQ-0006 AC-2）

- Given: `packages/ui/dist/index.html` が無い checkout からデーモンが立った。
- When: ブラウザで `/` を開き、`pnpm cli status` を実行する。
- Then: 簡易フォームが表示され、`status` に `ui: <探したパス> (missing)` が出る。`daemon.json` の `ui.path` に同じパスがある。

## 5. 技術計画

### 5.1 構成と責務

変更は入口（`packages/cli`、`packages/mcp`）とデーモンの HTTP 層（`packages/runtime/src/server.ts`）に閉じる。記録の保存（`store.ts`）、質問と回答、検証ジョブには触れない。

ホスト（Claude Code / Codex）
  利用者単位の MCP 登録: <道具>/node_modules/.bin/tsx <道具>/packages/cli/src/index.ts mcp --host <host>
  cwd = 対象リポジトリ（H1）
        │ stdio
        ▼
入口 packages/cli/src/index.ts ──▶ packages/mcp (ApiClient, ensureDaemon, isTarget, selfCommand)
  rootOf(): --root → PREPARE_DEV_ROOT → cwd
  isTarget(root): <root>/.prepare-dev/config.json がある
  非対象かつ --root なし → mcp: ツールなしで待機 / CLI: エラー終了（何も作らない）

### 5.2 データ: `daemon.json` と `status`

`daemon.json`（`.prepare-dev/daemon.json`、デーモンが `listen()` で原子的に書く）に二項目を足す。既存項目は変えない。

```json
{
  "pid": 12345, "port": 50837, "url": "http://127.0.0.1:50837", "root": "/abs/target", "started_at": "...",
  "tool": { "root": "/abs/tool-repo", "entry": "/abs/tool-repo/packages/cli/src/index.ts", "mode": "source" },
  "ui": { "path": "/abs/tool-repo/packages/ui/dist/index.html", "found": true }
}
```

- `tool.root` は `toolRepoRoot()`、`tool.entry` は `process.argv[1]`、`tool.mode` は段階 1 では常に `"source"`（段階 2 の束ねた物は `"bundle"` を使い、内容ハッシュを `tool.hash` として足す。REQ-0004 AC-2）。
- `ui.path` は探したパス、`ui.found` は起動時の存在。`GET /` は従来どおりリクエストごとに存在を見る（REQ-0006 の書きかけ HTML は防がない）。
- `tool`、`ui` が無い `daemon.json`（本変更前のデーモン）は読めるが `status` に `tool: unknown` と出る。段階 1 では不一致として扱わない（REQ-0004 AC-4 は C、D のみ）。
- `DaemonInfo` 型は現在 `packages/mcp/src/client.ts` と `packages/runtime/src/server.ts` に同じ定義が二つある。`packages/core/src/schemas.ts` に `DaemonInfo` を一つ置き、両方がそれを使う。

`GET /api/status` は `StatusView` に `daemon: {pid, url, started_at, tool, ui}` を足す。`ui.found` は呼ばれた時点で `fs.existsSync` を評価し直す（ビルドし直した直後に正しい値が出る）。CLI の `status` の文字出力に三行を足す: `daemon: <url> (pid <pid>)`、`tool: <root> [<mode>] entry <entry>`、`ui: <path> (found|missing)`。

### 5.3 入口の対象判定と非対象時の振る舞い（REQ-0003）

`rootOf()` の既定順（`--root` → `PREPARE_DEV_ROOT` → cwd）は変えない。`--root` を明示しない呼び出しでは、求めた root について `isTarget(root)` を見る。

| 呼び出し | 非対象のとき |
| - | - |
| `mcp`（`--root` なし） | `McpServer` をツール登録なしで stdio に接続し、ホストが stdio を閉じるまで待つ（Q-0003 s-wait）。stderr に `prepare-dev: <root> is not a prepare-dev target (no .prepare-dev/config.json); no tools published. run: prepare-dev init --root <root>` を一行出す。`ensureDaemon` を呼ばないので `.prepare-dev/` も `prepare/` もできない。セッション中に `init` されても気付かない（次のセッションから有効）。MCP の `instructions` は空にする（全セッションの会話に載るため） |
| `status`、`q`、`record`、`verify`、`trace`、`bundle`、`ui`、`pending`、`stop`（`--root` なし） | `error: <root> is not a prepare-dev target (run: prepare-dev init --root <root>)` を stderr に出し終了コード 2。何も作らない |
| `init` | 対象外ではない。`.prepare-dev/config.json` と `prepare/` を作るのが仕事 |
| `serve`、または `--root` を明示したコマンド | 対象判定をしない（現状どおり）。`mcp.test.ts` と `scripts/e2e-crash.sh` はこの経路 |

`PREPARE_DEV_ROOT` だけが設定されている場合も「`--root` なし」として扱い、その root を判定する（REQ-0003 は「cwd」と書くが、既定順で求めた root に読み替える。§10）。

### 5.4 デーモンの起動と排他（REQ-0003 AC-3、AC-6）

`ensureDaemon(root)` を次の手順にする。

1. `readDaemonInfo(root)` が生きているデーモンを返せばそれを返す（現状どおり）。
2. `.prepare-dev/daemon.lock` を `fs.openSync(lock, "wx")` で作る（内容 `{pid: 入口の pid, at: ISO 時刻}`）。失敗（`EEXIST`）なら lock を読み、`pid` が死んでいるか `at` が 30 秒より古ければ lock を消して 1 からやり直す。生きていれば 150 ms 待って 1 からやり直す（他の入口が起動中）。
3. lock を取れた入口だけが `selfCommand()` で `serve --root <root>` を detached 起動する（cwd は現状どおり `toolRepoRoot()`、stdout/stderr は `.prepare-dev/daemon.log` に追記、`PREPARE_DEV_DETACHED=1`）。
4. 最大 15 秒（現状値）`daemon.json` を待つ。現れたら lock を消して返す。現れなければ lock を消し、`daemon.log` のパスを含むエラーを投げる。

`serve` 側の既存の二重起動チェック（`readDaemonInfo` が生きていれば終了）はそのまま残す。lock と `daemon.json` の二段で、同時起動でも `Runtime.open`（回復処理を含む）を実行するプロセスは一つになる。起動に失敗したデーモンは `daemon.json` を書かずに終わるので、再試行では lock が無く（手順 4 で消している）、やはり一つしか起動しない。`.gitignore` に `.prepare-dev/daemon.lock` を足す。

### 5.5 `init`（REQ-0002）

`init --root <root>` のフラグを二つ足す。既存の「あるものは書かない」規則は保つ。

| フラグ | 値 | 意味 |
| - | - | - |
| `--register` | `none`（既定）、`project` | `none`: 対象リポジトリに登録を書かず、案内を出す（案 G）。`project`: `.mcp.json` と `.codex/config.toml` にプロジェクト単位の登録を書く。既定は `root` が `toolRepoRoot()` と同じなら `project`、それ以外は `none` |
| `--migrate` | なし | 旧 `init` が書いた機械固有の項目を消してから、上の処理をする |

`--register none` の処理: `.prepare-dev/config.json`（無ければ作る）、`Runtime.open(root)`（`prepare/` を作る）。出力の `guidance` に次を含める。絶対パスは利用者のホームの設定（`~/.claude.json`、`~/.codex/config.toml`）に入り、機械で一箇所になる。

```text
claude mcp add -s user prepare-dev -- <tool>/node_modules/.bin/tsx <tool>/packages/cli/src/index.ts mcp --host claude-code
codex mcp add prepare-dev -- <tool>/node_modules/.bin/tsx <tool>/packages/cli/src/index.ts mcp --host codex
pnpm --dir <tool> cli skills --user
```

`--register project` の処理（`root === toolRepoRoot()` のときだけ。それ以外はエラー）: `.mcp.json` に `{"type":"stdio","command":"pnpm","args":["cli","mcp","--host","claude-code"]}`、`.codex/config.toml` に `command = "pnpm"`、`args = ["cli", "mcp", "--host", "codex"]`、`startup_timeout_sec = 30`、`tool_timeout_sec = 3600` のブロック。`--root` は書かない（cwd＝プロジェクト。H1）。skills は `.agents/skills/<name> -> ../../skills/<name>` の相対 symlink と `.claude/skills -> ../.agents/skills`（§5.6 の共通関数）。案 B に切り替えるときは、この値を `command: "prepare-dev"`、`args: ["mcp", "--host", ...]` にする一箇所の変更で済む。

`--migrate` の処理（m-option。`init` が書いたものだけを消す）:

- `.mcp.json`: `mcpServers["prepare-dev"]` を消す。`mcpServers` が空になり他のキーも無ければファイルを消す。
- `.codex/config.toml`: `[mcp_servers.prepare-dev]` の行から、次の `[` で始まる行の直前（または EOF）までを消す。直前の空行も一つ消す。他の行は byte 単位で変えない。
- `.agents/skills/<name>`（`name` は道具リポジトリの `skills/` にある skill 名）が絶対パスへの symlink なら消す。実体のディレクトリと相対 symlink は消さない。（消すかどうかは質問にする。§6 決定点 7）
- 消したものを出力の `removed` に列挙する。無ければ何もしない。

移行は `--register` の処理より先に行うので、`--migrate --register project` は旧ブロックを消してから新しいブロックを書く。中断して再実行しても、残っているものだけが処理される（REQ-0002 AC-4）。

### 5.6 skills（REQ-0005、b-link）

共通関数 `placeSkillLinks(destDir, linkTargetOf, {check})`: 道具リポジトリの `skills/*/SKILL.md` を持つ各 `name` について `destDir/<name>` を次のように扱い、結果を `{name, state}` の一覧で返す。

| `destDir/<name>` の状態 | `check` なし | `--check` |
| - | - | - |
| 無い | symlink を作る → `linked` | `missing` |
| symlink、先が期待どおりで解決できる | 何もしない → `ok` | `ok` |
| symlink、先が解決できない（切れたリンク） | 張り直す → `relinked` | `broken` |
| symlink、先が期待と違う（移動した道具リポジトリなど） | 張り直す → `relinked` | `moved` |
| 実体のディレクトリかファイル | 触らない → `kept`（利用者のもの） | `kept` |

- `prepare-dev skills --user [--check]`（新設の明示の操作。REQ-0005）: `destDir` は `~/.agents/skills` と `~/.claude/skills`（`os.homedir()`。テストは `HOME` を差し替える）、リンク先は `<toolRepoRoot>/skills/<name>` の絶対パス。ディレクトリ自体は共有なので、ディレクトリごとの symlink は作らない。`--check` は書き込まず、`broken` か `moved` があれば終了コード 1。
- `init --register project`（dogfooding）: `destDir` は `<root>/.agents/skills`、リンク先は `../../skills/<name>` の相対パス。`.claude/skills -> ../.agents/skills` は無ければ作る。
- `init --register none`: 対象リポジトリに skills を置かない（G。REQ-0002 §シナリオ G）。
- 出力はどちらも `state` が `ok` 以外のものを skill 名つきで列挙する（黙って飛ばさない）。コピー方式と印ファイル（REQ-0005 AC-4、AC-5）は b-link では使わないので作らない。

## 6. 検討した代替案

決定点ごとに最大三案。「機械的な選択」（フラグ名、出力の文言、関数の置き場所）は本文で決めた。

### 決定点 1: デーモンの起動経路（REQ-0003「同じ経路」）

| 案 | 仕組み | 利点 | 欠点 | 破綻する条件 | 判断 |
| - | - | - | - | - | - |
| 1a 自分と同じ実行形で再実行（採用） | `process.execPath` + `process.execArgv` + `process.argv[1]` で `serve` を起動 | 道具リポジトリの構造（`node_modules/.bin/tsx`、`packages/cli/src/index.ts`）を知る必要が無い。段階 2（単一ファイル）でも同じコードが動く。`ensureDaemon`、`init`、`mcp.test.ts` に三回書かれていた同じパス組み立てが一つ減る | `execArgv` が環境依存（tsx の loader の絶対パス）。手元で確認済みだが、`node --import tsx`（相対指定子）で起動されると cwd 依存になる | 入口を `--import tsx` のような相対指定子で起動したとき。利用者単位の登録には `node_modules/.bin/tsx` の絶対パスを案内するので避けられる | 採用。質問にする（アーキテクチャの新しい決定） |
| 1b 現状（道具リポジトリの tsx とソースの絶対パス） | `toolRepoRoot()` から `node_modules/.bin/tsx` と `packages/cli/src/index.ts` を組み立てる | 変更なし | 段階 2 では checkout が無いので別の起動方法が要る（行き止まり）。パスの組み立てが三箇所に重複 | 段階 2、または `node_modules/.bin/tsx` の置き場が変わったとき | 棄却: 1a と行数が変わらず、段階 2 で捨てる |
| 1c PATH の `prepare-dev serve` | `spawn("prepare-dev", ["serve", ...])` | 配布形態に依存しない | 案 B、C、D の PATH 配置が前提。G には無い。ホストの PATH はシェルと違いうる（DIS-0001 §制約） | PATH に無いとき | 棄却: G では成り立たない |

### 決定点 5: UI HTML の解決（REQ-0006）

## 7. 非機能要求

- 安全性: デーモンの HTTP（無認証、`access-control-allow-origin: *`）は変えない（DIS-0001 非目標、別件）。利用者単位の登録により入口が全セッションで起動するが、非対象ではツールを公開せず、ネットワークも開かない。`daemon.lock` に秘密は無い。`--migrate` は `init` が書いた項目だけを消し、他の行は変えない（REQ-0002 AC-3）。
- 性能: 入口の起動は現状 0.25 秒（H2）で、目標 1 秒（q-1s）を満たす。非対象で待機する入口はセッション数ぶん常駐する。RSS は未計測なので検証計画で一度測り、DIS-0001 に書く。lock の待ち時間は最大 15 秒（デーモンの起動待ちと同じ）。
- 互換性と移行: `daemon.json` の追加項目は任意で、旧デーモンの `daemon.json` も読める。旧 `init` の登録は `--migrate` で消す。本変更の前に立てたデーモンは `pnpm cli stop` で止めるまで残る（REQ-0007 の現状どおり）。`mcp.test.ts` と `scripts/e2e-crash.sh` は `--root` 明示の経路なので挙動は変わらない。
- 切り戻し: コードは git revert。利用者単位の登録は `claude mcp remove -s user prepare-dev`、`codex mcp remove prepare-dev`、skills リンクは `~/.agents/skills/<name>` と `~/.claude/skills/<name>` を消す。対象リポジトリ側には `init --register none` は何も書いていないので戻すものが無い。

## 問題

prepare-dev を使う人が、どの機械・どの対象リポジトリでも、同じ書き方の設定で prepare-dev を起動して使えるようにしたい。

根の問題は、「`init` が機械固有の情報を対象リポジトリの設定に書き出し、ホストと入口がその情報に頼って起動する」こと。入口が自分の checkout の位置を求める仕組み（`toolRepoRoot()`、`import.meta.url` から逆算）自体は checkout がどこにあっても動き、可搬性を壊してはいない。壊しているのは `init` が書く次の四つ。

| 機械固有の情報 | どこに現れるか | 由来 |
| - | - | - |
| 道具リポジトリの `node_modules/.bin/tsx` の絶対パス | `.mcp.json` と `.codex/config.toml` の `command` | 道具リポジトリの位置 |
| 道具リポジトリの `packages/cli/src/index.ts` の絶対パス | 同 `args` | 道具リポジトリの位置 |
| 対象リポジトリ自身の絶対パス（`--root`） | 同 `args` | ホストが入口をどの cwd で起動するか分からないため、明示している |
| 道具リポジトリの `skills/*` への絶対 symlink | 対象リポジトリの `.agents/skills/*` | 道具リポジトリの位置 |

加えて、デーモンは配信する UI を道具リポジトリ内の `packages/ui/dist/index.html` で探す（checkout がある限りは動く）。

### 問題の範囲（段階）

「同じ書き方の設定で起動できる」には二つの段階があり、どこまでを今回の問題にするかは人の判断（質問 1 の判断 a）。

| 段階 | 内容 | 満たす案 |
| - | - | - |
| 段階 0: 作らない | 現状維持。機械ごとに `init` を実行する | A |
| 段階 1: 登録の可搬化 | 対象リポジトリに機械固有の絶対パスを書かない（git で共有できる登録にするか、対象リポジトリには何も書かない）。道具リポジトリの checkout と `node_modules` は利用者の機械にあってよい | G、B、C、D |
| 段階 2: 道具リポジトリに依存しない配布 | 道具リポジトリの checkout も `node_modules` もなしに、配布物だけで入口・デーモン・UI が動く | D（と、その先の F） |

段階 1 だけなら、ビルドは必須ではなく、コードをほとんど変えない案（G）もある。段階 2 まで含めるなら、成果物を一つに束ねる案 D が最短。所有者の当初の発想（`tsc -b` でビルドして `bin` を置く、案 C）は段階 1 を満たすが、段階 2 には届かず、段階 1 だけなら G や B より手間が多い。

### 質問 1

この工程（Discover）の終わりに作る人への質問（`Q-*`。作成後に本記録の `links.questions` に id を書く）。runtime の質問は `kind` 一つと平坦な `options` 一つしか持たず、選択肢を群に分ける仕組みはない。そこで `multi_choice` にし、選択肢の `key` に `a-`、`b-`、`c-` の接頭辞を付けて「各接頭辞から一つずつ選ぶ」と質問文に書く。回答は一件の判断（`DEC-*`）になるので、後から個別に覆すときは再質問する。

- 判断 a: 問題の範囲と案（段階 0＝A、段階 1 を G で、段階 1 を B で、段階 1 を C で、段階 2 を D で）
- 判断 b: skills の置き方（常に最新を取るか、移動で壊れないことを取るか）
- 判断 c: PATH 依存への備えを今から作るか（`init` に絶対パスの逃げ道を最初から持たせるか、先行作業 H1 の結果を見てから決めるか）

## 価値

- 段階 1: 対象リポジトリに機械固有の情報が残らず、clone 直後に（道具リポジトリがあれば）起動だけで使える。道具リポジトリの場所変更が対象リポジトリ側の設定に波及しない。
- 段階 2: 道具リポジトリと `node_modules` が要らなくなり、他者が試せる状態への最短経路になる。
- 起動時間の短縮は副次的で、価値の中心ではない（束ねた成果物の起動時間と大きさは未計測。H6 の試行で測る）。

## 代替案

案は「機械固有の情報をどこに置くか（間接化の場所）」と「何を実行するか」の二軸で分かれる。

| - | - | - | - | - |

| G 利用者単位の登録 | ホームディレクトリのホスト設定（`~/.codex/config.toml` の `mcp_servers`、Claude Code の利用者スコープの MCP 登録）と利用者単位の skills 置き場（Claude Code は `~/.claude/skills`、Codex は `~/.agents/skills`） | tsx＋ソース | 対象リポジトリには何も書かない。絶対パスは機械ごとに一箇所だけ。root は cwd から取る。`init` は対象リポジトリの `prepare/` と `.prepare-dev/` だけを作る | 登録の変更はコードなしで試せる。ただし入口が機械上の全セッションで起動されるので、対象リポジトリでないときの振る舞い（終了するか、ツールを公開せず待つか）を決め、`prepare/` と `.prepare-dev/` を作らない抑止（H7。`ensureDaemon` が接続前に作るので、抑止はそれより前）が要る。15 個のツール説明（約 1.2 KB、スキーマ込みで千トークン規模）が無関係なプロジェクトの会話にも載り、セッション数ぶん Node プロセスが常駐する。利用者単位の登録も「機械で一つの指し先」なので、checkout が複数あるときの食い違いは B と同じ。「git で共有」ではなく「共有すべきものが無い」形で段階 1 を満たす。段階 2 には届かない。既存の `.gitignore` の方針（登録は機械固有）と整合する |

推奨: 段階 1 なら G（コードをほぼ変えずに試せる。H7 の抑止と非対象時の振る舞いだけ足す）。G がホストの制約で使えない、または登録を git で共有したいなら B。段階 2 なら D。

対象リポジトリが道具リポジトリ自身（dogfooding）のときは、どの案でも、プロジェクト単位の登録を `command: "pnpm"`、`args: ["cli", "mcp", ...]` にすれば絶対パスなしで「その checkout のソース」が動き、worktree ごとの食い違いが消える（前提: ホストの cwd がプロジェクト＝H1、プロジェクト単位の登録が利用者単位より優先される＝H8）。

PATH 以外の間接化として、Claude Code の `.mcp.json` は `${VAR}` 形式の環境変数展開を持つ（Codex 側は未確認）。絶対パスを環境変数に逃がす手もあるが、環境変数の設定が機械ごとに要る点は G と同じなので、独立の案にはしない。

skills の置き方は案と独立に決められる（質問 1 の判断 b）。候補は、(i) 道具リポジトリへの相対 symlink（対象＝道具リポジトリのときだけ可）、(ii) 道具リポジトリまたは配布物への絶対 symlink（常に最新だが、移動で壊れる）、(iii) 対象リポジトリへのコピー（git で共有でき移動で壊れないが、更新の仕組みが要る。現在の `init` は既にあるものを飛ばすので、上書きか版の印の比較を新設する）、(iv) 利用者単位の置き場（案 G。対象リポジトリに何も書かない）。段階 1 では (ii) か (iv)、段階 2 では (iii) が自然。

## 制約

- Node >= 26、pnpm workspace、`workspace:*` 依存、各 package は `private`。`tsc -b` の project references は設定済み。
- 入口は stdio で起動される独立プロセス。ホストは `command` と `args` の形式で登録し、cwd と PATH はホストが決める。ホストが対象リポジトリを cwd にするか、環境変数を渡せるかは未検証（H1）。H1 が片方のホストで偽なら、そのホストだけ `init` が `--root` の絶対パスか `env` を書く逃げ道が要る。
- デーモンは対象リポジトリごとに一つで、`.prepare-dev/daemon.json` で発見する。入口が detached で起動するため、入口は自分がどの実行ファイル・どの checkout から動いているかを知る必要がある。
- 入口にもデーモンにも版・経路・checkout を報告する仕組みはない。二系統（ソース／ビルド）を持つ案（C、D）では、`daemon.json` に版・実行ファイル・checkout を記録し、入口が接続時に自分の値と照合して不一致なら失敗するか再起動する規則が設計の必須項目になる（`status` に出すだけでは、エージェントが `status` を呼ばない限り古いデーモンが黙ってツールを提供し続ける）。G と B では、`daemon.json` に道具リポジトリの位置を一項目足す最小形に留める。
- デーモンは対象リポジトリの数だけ常駐し、一つ約 100 MB（実測）。終了条件は無い。
- PATH 上の `prepare-dev`（B、C、D）も利用者単位の登録（G）も機械で一つの指し先なので、道具リポジトリの checkout が複数あるとき（worktree、別ブランチ、対象＝道具リポジトリ）に、編集中の checkout と実行される checkout が黙って食い違いうる。対象が道具リポジトリ自身のときはプロジェクト単位の登録（`pnpm cli mcp`）で自分のソースを優先する（H8）。
- `exports` の解決先を変える案（C）では、開発時（tsx、vitest）とビルド時で解決先を分ける仕組みが要る（手段は設計）。
- 検証プラグインが使う `vitest`（対象の `node_modules/.bin`）と `lake`（PATH）は対象リポジトリ側の道具で、配布の対象外。
- `command: "prepare-dev"` 形式の登録は、ホストのプロセス環境の PATH にその command があることに依存する。GUI から起動されたホストの PATH はシェルと違いうる。`pnpm link --global` は Node の版ごとの領域に置かれる（`~/.local/bin` 等への symlink なら生じない）。依存を受け入れるか、`init` が解決済みの絶対パスを書く逃げ道（可搬性を失う）を残すかは、先行作業 H1 の結果を見てから決めるのが自然（質問 1 の判断 c）。
- 既存の対象リポジトリに残る絶対パスの登録は、`init` が上書きしないため、移行には削除か上書きの手段が要る（設計で扱う）。登録を git で共有する案（B、C、D）では `.gitignore` の方針転換も要る。
- デーモンの HTTP は無認証で `access-control-allow-origin: *`。段階 2（他者の機械で動かす）を選ぶなら、origin の制限を前提条件として別件で先に扱う。

| H7 | 利用者単位の MCP 登録（G）でも、対象リポジトリでないプロジェクトで入口が起動されたときに `prepare/` や `.prepare-dev/` を作らず、ツールも公開せずに済む | 現在は `ensureDaemon` が `.prepare-dev/` を作り、`Runtime.open` が `prepare/` を作る。`.prepare-dev/config.json` の有無で接続前に抑止する変更は小さいが未試行 | 未検証 |
| H8 | 対象＝道具リポジトリのとき、プロジェクト単位の登録（`pnpm cli mcp`）が利用者単位の登録より優先され、その checkout のソースが動く | 両ホストの登録の優先順位は未確認 | 未検証 |

## 非目標

- npm レジストリへの公開と版管理（具体化案 §1.7 で後回し。ただし妨げない）。
- Windows 対応（`ui` の `open` と e2e が darwin／bash 前提。配布形態と独立に扱う）。
- デーモンの複数版共存と自動更新（入口が不一致を検出して失敗・再起動する規則は本件の範囲）。
- 検証ツール（`lake`、`vitest`）の配布。
- UI の見た目と開発サーバの変更。
- skills の内容の変更。置き方は本件の範囲に含める（非目標ではない）。
- デーモンの HTTP の認証と origin 制限（本件以前からある弱点で、配布形態と独立に直せる。別件で扱い、段階 2 を選ぶ場合はその前提条件にする）。

## リスク

- やらない場合: 道具リポジトリの移動や `node_modules` の削除で全対象が黙って壊れる。登録を共有できない。他者が試せない。
- H1 が偽の場合: 段階 1 の価値（絶対パスなしの登録）がそのホストでは成り立たず、逃げ道（ホストごとの `--root` か `env`）で部分的に保つことになる。どの案を選んでも同じなので、先行作業で確かめる。
- G の場合: 入口が全セッションで起動され、抑止（H7）が無いと無関係のプロジェクトに `prepare/` ができる。ツール説明が全セッションの会話に載り（千トークン規模）、セッション数ぶんプロセスが常駐する。利用者単位の設定は機械ごとに一度の手作業になる。
- B の場合: 道具リポジトリの checkout に依存し続ける。
- C と D の場合: ソースとビルドの二系統が乖離する。ビルド忘れで古い成果物や古いデーモンが動く。入口が接続時に照合しなければ、古いデーモンが黙ってツールを提供し続ける。C では vitest も `dist/` を見る経路が生まれる。
- G、B、C、D 共通: 機械で一つの指し先なので、checkout が複数あるときに編集中と実行中が食い違う（H8 で緩和）。ホストの PATH に `prepare-dev` が無いときの起動失敗がホストのログにしか出ず、既存の単一障害点（道具リポジトリの位置）を別の単一点（PATH）に移すだけになりうる。緩和（絶対パスの逃げ道、対象側への起動ログ）は H1 の結果を見て設計で決める。
- 段階 2 の場合: 無認証・origin 無制限のデーモンが他者の機械でも動く。前提条件として origin 制限を先に入れる。
- 見返り: 対象リポジトリに機械固有の情報が残らない再現性、第三者への配布の土台。

## 成功

- 先行作業: H1 の検証結果（三通りの起動形態ごとに接続可否と、入口が見た cwd と環境変数）が本記録の H1 の証拠欄に残り、状態が「決定」になる。
- 中間: `init` の出力に絶対パスが一切含まれない（道具リポジトリ、対象リポジトリとも。G では対象リポジトリに登録ファイル自体が無い）。PATH 上の `prepare-dev`（G では利用者単位の登録）だけで `status` が返る。UI が簡易フォームではなく本来の UI で表示される。G では、対象でないプロジェクトで入口が起動されても `prepare/` も `.prepare-dev/` もできず、ツールも公開されない。
- 最終: 別の対象リポジトリで `init` し、Codex と、シェルからと GUI から起動した Claude Code の両方が接続し、質問の作成から UI での回答、`question_apply` までが通る。道具リポジトリを別の場所に移しても（B と C では再 link 後、D では無条件に、G では利用者設定の更新後に）対象リポジトリ側を変えずに動き、skills も解決される。対象＝道具リポジトリの worktree で作業したとき、その checkout のソースが動く（H8）。C と D では、入口とデーモンが版・経路を報告し、ソースだけ直してビルドしていない状態と、再ビルド後に古いデーモンが残る状態の両方で、入口が接続時に不一致を検出して失敗または再起動する。Node の版を切り替えた後も `prepare-dev` が解決される（`pnpm link --global` を使うなら、解決されなくなることを確認した上で `~/.local/bin` 等に切り替える）。`pnpm test` と `scripts/e2e-crash.sh`（実デーモンを強制終了して回答の適用が回復することを確かめる既存の e2e）が通る。

## レビューの経緯

BRAINSTORM の shootdown を三回行った（zoom_out、comprehension、design_critic の三 persona、会話履歴なし）。round 1 は REV-0001〜0003（rev 1 → rev 2）、round 2 は REV-0004〜0006（rev 2 → rev 3）、round 3 は REV-0007〜0009（rev 3 → 本版）。各 round で各 persona が新しい Major を三〜四件出し、再開（同じ箇所への再指摘）は無かった。費用の都合で round 3 で止め、未対処の Major は残していない。design_critic-1-3（PATH 依存の受容）は質問 1 の判断 c に送った。

| - | - |

| runtime | `packages/runtime`。記録の保存、質問と回答、検証ジョブ、HTTP＋SSE を実装するライブラリ。デーモンはこれを一つのプロセスとして動かしたもの |

| MCP 登録 | `.mcp.json`（Claude Code）と `.codex/config.toml`（Codex）に書く `command` と `args`。ホームディレクトリ側の利用者単位の登録もある |
| skills | エージェント向けの手順書（`skills/prepare-*/SKILL.md`）。対象リポジトリの `.agents/skills/`（Codex）と `.claude/skills`（Claude Code。`../.agents/skills` への相対 symlink）、または利用者単位の `~/.agents/skills`（Codex）と `~/.claude/skills`（Claude Code）からホストが読む |
| 可搬な登録 | 機械固有の絶対パス（道具リポジトリ、対象リポジトリとも）を含まず、そのまま git で共有できる MCP 登録 |
| 起動シム | PATH に置く小さなスクリプトで、自分の位置から道具リポジトリを求めてソースを実行するもの（案 B） |
| 束ねる | esbuild 等で複数のソースと依存を一つの JS ファイルにまとめること（案 D）。runtime のレビュー資料を作る `bundle` 操作とは別物で、実装時の名前は衝突しないものにする |
| 版の印 | コピーした skills が元と同じ版かを判定するための値（ハッシュや版番号）。skills の置き方 (iii) で要る |
| ビルド成果物 | `tsc -b` が作る `dist/`、`vite build` が作る `packages/ui/dist/index.html`、esbuild が作る単一ファイル |
| 配布形態 | 利用者の機械に prepare-dev の実行できる形を置く方法（ソース直実行、利用者単位の登録、起動シム、ビルド、束ねた単一ファイル、npm 公開） |
| 検証プラグイン | runtime が検証ジョブを委ねる workspace package。現在は `plugin-lean4`（Lean 4 のビルドツール `lake` を使う）と `plugin-vitest` |
