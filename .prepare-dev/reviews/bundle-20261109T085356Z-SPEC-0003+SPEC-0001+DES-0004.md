## 用語

- 検証の実行（RUN）: `prepare-dev verify run` 一回。結果を `prepare/runs/RUN-NNNN.json` に、検証器の出力（レポートやログ）を同じ名前のディレクトリ `prepare/runs/RUN-NNNN/` に置く。
- targets: `verify run --target` で渡す対象のファイル（テストファイル、証明のファイル）。
- project_dir: 検証器を動かすディレクトリ。ルートからの相対パスで、プラグインの設定（`.prepare-dev/config.json` の `plugins.<名前>`、または `--config-json`）に書く。
- impl_files: import やパッケージの関係からは見つからない入力を、利用者がルートからのパスかパターンで列挙する設定。パターンは `*`・`?`・`[...]` をパスの一段の中で、`**` を任意の段数のディレクトリに使える。`**` は node_modules と `.` で始まるディレクトリに入らず、`.` で始まるファイルはパターンに一致しない。一致するファイルがない書き方は誤り。Vitest ではここからも import をたどる。
- input_packages: Go のテストが実行中にビルドするパッケージ（`go build`、`go run` で作るもの）の一覧。
- ディレクトリの一覧: ディレクトリの下の名前を並べたものの sha256。一覧ごとに、下の段まで含めるかと、どの名前を数えるか（数え方）を決める。数え方は三つある。既定は、通常のファイルの名前で、`.` で始まる名前を除き、下の段では node_modules と `.` で始まるディレクトリに入らない。すべての名前は、`.` で始まるもの、ディレクトリ（`名前/`）、ほかの種類の名前も数え、どのディレクトリにも入る。go:embed の規則は、通常のファイルの名前で、`.` と `_` で始まる名前（ディレクトリならその下も）を除き、ほかのディレクトリには node_modules も含めて入る。数え方とは別に、その段だけの一覧にはパターン（`*`・`?`・`[...]`）を付けて、それに一致する名前だけを数えさせることができる。
- native 参照: 主張と、検証器のテストや定理とを結ぶ参照（主張の `native` の `ref`）。gotest と vitest の形と一致の規則は §結果と主張の対応（V4）に書く。
- 現在の版に当てはまる: RUN が記録した入力・対象・主張の版（内容の sha256）と、記録したディレクトリの一覧が、今のファイルとすべて一致し、RUN を記録したプラグインの版が今の版と同じこと。プラグインの版は、記録するファイルや検証器の出力の読み方を変えたときに上げる。前の版の RUN は今の規則を経ていない。今の runtime に無いプラグインの RUN は、そのプラグインの規則が分からないので版を比べず、入力と一覧だけで決める（デーモンは gotest・vitest・lean4 を持つ）。

## 契約

検証の結果は、記録した入力が今も同じである限りにおいて現在の版の証拠になる。プラグインは結果を左右するファイルを入力として記録し、ファイルが増えると結果が変わりうるディレクトリの一覧も記録する。runtime は、入力のどれかが変わるか消えたとき、一覧が変わったとき（ファイルの追加・削除）、または RUN を記録したプラグインの版が今の版と違うときに、その RUN を現在の版に当てはまらないものとして扱う。

Vitest（V1）は、テスト、impl_files、Vitest の設定ファイルを起点に、esbuild でバンドルするのと同じ規則（相対パス、package.json の main・exports、tsconfig.json の paths、node_modules にリンクしたワークスペースのパッケージ。拡張子の無い import は Vite の既定の順 .mjs・.js・.mts・.ts・.jsx・.tsx・.json で探す）で import をたどり、esbuild が読み込むファイルを記録する。JavaScript・TypeScript・JSON・CSS 以外の import されたファイルは、記録するが中はたどらない。型だけの import は実行時に読み込まれないので記録しない。node_modules の中に解決されたパッケージは記録せず、入力の上位ディレクトリ（ルートまで）の package.json、pnpm-lock.yaml、package-lock.json、npm-shrinkwrap.json、yarn.lock、bun.lock、bun.lockb、pnpm-workspace.yaml、.npmrc、tsconfig.json で代表する。import が読むファイルのディレクトリ（その段だけ。隣にファイルが増えると解決先が変わりうる）と、impl_files のパターンが探すディレクトリの一覧を記録する。

Go（V3）は次を記録する。集めるファイルの種類はここだけに書き、ほかの記録はここを参照する。

- `go list -deps -test -json` が報告する、テストがビルドするパッケージのソースと埋め込みのファイルすべて（Go のほか cgo・C・C++・Objective-C・Fortran・アセンブリ・ヘッダー・SWIG・syso）。対象はメインモジュール、ローカルのディレクトリへ replace したモジュール、vendor のパッケージ。テストファイルは実行するパッケージのものだけ（依存先のテストはビルドされない）。
- 実行するパッケージの `testdata/` の下のすべてのファイル。
- input_packages のパッケージとその依存先のファイル（上と同じ規則）。
- impl_files のファイル。
- モジュールの定義とロックのファイル（go.mod、go.sum、go.work、go.work.sum、vendor/modules.txt）。
- 一覧: ファイルを記録したパッケージのディレクトリ（その段だけ。既定）、`testdata/`（下の段まで。すべての名前。下のファイルはすべて入力なので）、impl_files のパターンが探すディレクトリ（既定）、go:embed のパターンが探すディレクトリと一致したディレクトリ。go:embed のパターンは、パッケージのものと、実行するパッケージのテストファイル（外部テストパッケージを含む）のもの。

go:embed は、パターンを一段ずつ、ディレクトリの中の名前に `filepath.Match` の規則で当て（`*` は `.` で始まる名前にも一致する）、一致したディレクトリからは、その下のファイルを（`all:` が無ければ `.` と `_` で始まる名前を除いて）すべて取り込む。そこで、ワイルドカードのある段から先は、探す各ディレクトリについて、その段のパターンに一致する名前の一覧（その段だけ。すべての名前。ファイルとディレクトリの両方）を記録し、最後の段で一致したディレクトリ（ワイルドカードの無いディレクトリのパターンを含む）について、その下の一覧（下の段まで。go:embed の規則。`all:` ではすべての名前）を記録する。この一覧は、go:embed が取り込むものの上位集合を数える。取り込むものが変わらない追加のうち、一覧も変わらないのは、`all:` でないディレクトリのパターンの下に `.` や `_` で始まる名前か空のディレクトリを足したときと、ワイルドカードに一致しない名前を足したとき。次の追加では、取り込むものが変わらなくても一覧が変わり、証拠は当てはまらなくなる（安全な側に倒れる）: `all:` の下のディレクトリの名前と、go:embed が `all:` でも取り込まない名前（`.git` など）、go.mod のある下のディレクトリの中。ワイルドカードの段に空のディレクトリを足したときも一覧が変わるが、このとき go:embed はビルドを失敗させる（取り込むファイルの無いディレクトリは誤り）ので、当てはまらなくするのが正しい。`testdata/` もすべての名前を数えるので、`.DS_Store` やエディタの一時ファイルでも当てはまらなくなる（`testdata/` の下のファイルはすべて入力に入るので、これらも次の実行の入力になる）。

`go test -json -count=1` で、キャッシュした結果を使わずに実行する。デーモン自身の環境の `PREPARE_DEV_` で始まる変数（`PREPARE_DEV_E2E_BINARY` など、prepare-dev のテストが何を検査するかを変えるもの）はテストに渡さない。ほかの環境変数（`GOFLAGS`、`CGO_ENABLED` など）はデーモンのものが渡り、RUN には残らない。テストは、RUN ごとのディレクトリ（環境変数 `PREPARE_DEV_BOUNDS_DIR`）に書いた JSON の数値と文字列を RUN の `scope.bounds` に残せる。

Lean（lean4）はモジュールの名前で import を読むので、ファイルが増えても結果は変わらず、ディレクトリの一覧は記録しない。どのプラグインも、検証器の有無を project_dir で調べ、使った検証器の場所を RUN の `tool.extra` に残す。

## 結果と主張の対応（V4）

主張は native 参照（`ref`）でテストに対応する。`ref` は `<前半>::<後半>` の形で、前半は、Go ではパッケージのインポートパスの末尾に、Vitest ではテストファイルのパスの末尾に、文字列として一致し（空ならどれにも一致する。パスの区切りでは分けないので、`app` は `example.com/webapp` にも一致する。分けたいときは `/app` と書く）、後半は、テストの名前（Go は `go test -json` の名前で、サブテストは `TestX/名前`。Vitest は describe を含めた名前）に含まれる文字列。前半と後半の両方に一致するテストを、その主張のテストと呼ぶ。

主張の結果は、その主張のテストの結果から決める。すべて成功なら verified、一つでも失敗（終わらなかったものを含む）なら failed、一つも無いか、失敗は無いがスキップが混ざるなら unknown。RUN の結果は、主張の結果のうち最も悪いもの（verified、unknown、failed、timeout、tool_error の順に悪い）。

テストが成功しても、検証器がテストの外での失敗を示したときは verified にしない。テストの外の失敗は、それが起きたパッケージ（Go）かファイル（Vitest）ごとに見分ける。

- Go: パッケージの失敗（`go test -json` のテスト名の無い `fail`）で、次のどれかに当たるもの。そのパッケージに失敗したテストが無い（TestMain が 0 以外で終わる、テストの後の終了、ビルドの失敗）。結果の出なかったテストがある（そのテストの途中でテストのバイナリが終わった。`go test` は出力をその時に動いていたテストに付けるので、ほかのテストが残した goroutine の panic は、動いていたテストの出力になり、そのテストには結果が出ない）。テストの外の panic がある（パッケージがテストの外で出力した `panic:` か `fatal error:` で始まる行。TestMain の中など）。テスト自身の goroutine の panic は、`go test` がそのテストの失敗にするので、そのテストの失敗として扱う。失敗したテストのあるパッケージで、panic でないテストの外の失敗（TestMain が自分の検査で 0 以外を返すなど）は、テストの失敗と区別できないので対象外とし、そのパッケージで成功したテストの主張は verified のまま残る（失敗したテストを直して実行し直せば、テストの外の失敗として見える）。
- Vitest: ファイル自体の失敗と、未処理の例外。JSON のレポートが示すのは、ファイル直下の hook の例外と読み込みの失敗（ファイルの `status` が `failed` で `message` があるか、失敗したテストが無いもの）だけで、describe の中の hook の例外は `message` に入らず、未処理の例外（テストの後に投げられた例外、拒否された Promise）は出ない（レポートは成功と報告し、Vitest は 1 で終わる）。そこでプラグインは実行のたびに小さな reporter を加え、Vitest から、ファイルとその中の suite（describe）のエラー、未処理の例外と、それが起きたテストファイルとテスト、それぞれの project がテストファイルを分けて動かすか（isolate）を受け取って `vitest-unhandled.json` に書かせる。ファイルや suite のエラーは、ファイルの中のテストが失敗していても、そのファイル自体の失敗とする。未処理の例外は、起きたファイルが分かればそのファイルの失敗とし、isolate が無効の project があるときは、ほかのファイルのテストが残したものでありうるので、起きた場所の分からない失敗とする。globalSetup の後始末の例外は reporter に届かない。0 以外の終了コードとしてだけ見え、同じ実行にほかの失敗があると区別できないので対象外とする。

テストの外の失敗は、次の主張を failed にする。

- テストの結果があるパッケージやファイルでの失敗: そこにその主張のテストがある主張。
- テストの結果が一つも無いパッケージやファイルでの失敗（ビルドや読み込みの失敗、テストを走らせる前の終了）: どのテストがあったかが分からないので、`ref` の前半が一致する主張（前半が空ならすべての主張）。
- 起きた場所が分からない失敗（ファイルの分からない未処理の例外と、検証器が 0 以外で終わったのに、失敗したテスト・パッケージ・ファイルと未処理の例外のどれも無いとき）: verified になるはずのすべての主張。このときは主張が無くても RUN の結果を failed にする。

テストの外の失敗は、それに対応しない主張の結果を変えない。RUN の要約には、主張に及んだテストの外の失敗ごとに、パッケージかファイルと理由の一行を残す。理由は、Go のビルドの失敗ではコンパイラの最初のエラー、ほかの Go の失敗では、テストの外の panic の行か、無ければパッケージがテストの外で最後に出力した行（`go test` 自身の `PASS`・`FAIL`・`ok`・`exit status` の行を除く）。Vitest ではファイルの `message` かファイルと suite のエラーの一行目、未処理の例外の message。どの主張にも及ばない失敗は要約に出ず、検証器の出力（RUN の成果物）に残る。検証器の終了コードは RUN の `tool.extra.exit_code` に残す。Vitest の reporter が何も書かなかった（reporter のフックを持たない版など）ときは、未処理の例外を読めないので 0 以外の終了コードの規則だけで扱い、終了コードが 0 以外ならそのことを要約に書く（Vitest は未処理の例外があれば 1 で終わるので、0 なら読めなくても見逃しは無い）。

## 検証

internal/plugin/vitest の [V1] で、推移的な依存と metadata の収集、変更の反映、解決の規則（tsconfig の paths、ワークスペースのリンク、import した素材、型だけの import と node_modules を含めないこと、Vite の順で拡張子を探すこと、import のディレクトリの一覧）を検査する。internal/runtime の [V1] で、記録済みの入力の変更・削除と、記録したディレクトリへのファイルの追加と、プラグインの版の違いによる適用の無効化を検査する。二つのテストファイルを同じ `verify run` の targets に含める。internal/plugin/gotest の [V3] で、入力の収集（実行中にビルドするパッケージ、testdata、impl_files のパターン、Go 以外のソース、ローカルの replace 先、依存先のテストファイルを含めないこと）、ディレクトリの一覧がファイルの追加で変わること、変更の反映、テスト名から主張への対応を検査する。go:embed については、パターンごとにファイルを一つ足し、go list が取り込むファイルが変わる追加では一覧が変わり、変わらない追加では一覧も変わらないことを、go list の結果と比べて確かめる（挙げた追加の範囲の確認）。取り込むものが変わる追加は、ワイルドカードに一致したディレクトリの下の段、新たに一致するディレクトリ、ワイルドカードに一致する `.` で始まる名前、ディレクトリのパターンの下の段と node_modules、`all:` の下の `.` で始まる名前、二段のワイルドカード、テストファイルと外部テストファイルのパターン。変わらない追加は、`all:` でないディレクトリのパターンの下の `.` と `_` で始まる名前と空のディレクトリ、一致しない名前、依存先のテストファイルのパターン。`go:embed assets/*` の下の段にファイルを足すと実際のテストが失敗し、それより前の RUN が当てはまらなくなることも確かめる。internal/plugin/gotest と internal/plugin/vitest の [V4] で、テストの外の失敗の扱いを検査する（V4 の native 参照は二つのパッケージにまたがるので、二つのテストファイルを同じ `verify run` の targets に含める）。Go は実際に `go test` を動かし、TestMain が 1 で終わるパッケージ（テストは成功）、テストを走らせる前に終わる TestMain（最後の行が理由に残る）、失敗したテストのあるパッケージでのテストの外の panic、テストの中の panic（そのテストだけが失敗する）、ほかのテストが残した goroutine の panic（パッケージのすべての主張が failed）、ビルドの失敗（コンパイラのエラーが要約に残り、参照の前半が空の主張にも及ぶ）を確かめる。説明できない 0 以外の終了コードは、作った `go test` の出力を与えて確かめる。Vitest は、実際の Vitest 5.1.0 で確かめたレポートと reporter の出力の形（docs/2026-11-09-go-verification.md に記録）を与え、ファイル直下の afterAll の例外（ファイルの中のテストが失敗していても）、describe の中の afterAll の例外、読み込みの失敗、ほかのファイルが失敗した実行での未処理の例外、ファイルの分からない未処理の例外、isolate が無効のときの未処理の例外、説明できない 0 以外の終了コードを確かめる。reporter がこれらを書き出すことも、実際の Vitest 5.1.0 で確かめた（同じ記録）。これらは実行したケースの範囲のテストであり、任意の動的な依存を自動で見つける証明ではない。

## V2: 実行中ジョブの識別

単一 runtime で検証を開始するとき、結果 JSON の完成前に作る RUN のディレクトリを ID の予約として扱う。次の実行と再起動後の採番はその予約を使用済みとして数える。異なるジョブが結果・ログを共有してはならない。結果を書く前にデーモンが止まった RUN は、status の `runs_incomplete` に示す。internal/runtime の [V2] で、非同期の完了を止めたまま二つのジョブを起動し、ID と保存先の分離、および再起動後の非再利用を確かめる。RUN-0006 は二つのジョブが同じ ID を使った実行で、証拠に使わない。

# 回答の適用

本仕様は、人間の回答を判断（decision）として確定する手順と、中断からの回復を定める。対象は runtime の永続状態であり、プロセス内の一時状態は含めない。中断後に残るのは永続状態だけだからである。

## 1. 永続状態

| 要素 | 内容 |
| - | - |
| `records` | 記録 id → 現在の版 `{rev, sha256}`。質問の対象になる要求・仕様など |
| `questions` | 質問 id → `{subjects, answers}`。`subjects` は作成時に写した対象の版の一覧 `[{id, rev, sha256}]` |
| `answers` | 回答 id → `{question, subjects_at_answer, stale, received, closed, applied_as}`。`subjects_at_answer` は回答を保存したときの対象の現在の版の写しで、`stale` の判定の根拠として残す。`applied_as` はファイル上の適用印で、確定の写し |
| `decisions` | 存在する decision ファイルの集合。各 decision は `{id, txid}` を持つ |
| `journal` | 追記のみの列。要素は `intent {txid, answer, decision_id, subjects, decision}`、`commit {txid}`、`abort {txid}`。`decision` は書く decision の下書き（題、本文、選んだ選択肢、代替案）。実装のジャーナル（`prepare/events.jsonl`）ではそれぞれ `apply.intent`、`apply.commit`、`apply.abort` の行 |

実装では、記録は `prepare/<種類>/<id>.md`、質問と回答は `prepare/questions/<id>.json`、decision は `prepare/decisions/<id>.md` にある。ジャーナルには記録の書き込みや削除（`record.write`、`record.remove`）などの行もあるが、この仕様の状態には含めない。記録の版（`rev`）は id ごとに増えるだけで、消えたファイルを runtime が書き直すとき（§2.2 の確定済みの decision の書き直し、中断した適用のロールフォワード）も、journal にあるその記録の最後の版の次にする。したがって、この版の runtime だけが書いたジャーナルには、同じ記録の二度の作成（`rev` 1 の書き込みが二つ）は現れない。前の版（TypeScript 版と、Go 版の 85477c7 まで）は消えた decision を `rev` 1 で書き直したので、起動時の検査は、ちょうど一つの `intent` が採番した decision の `rev` 1 の重複を二度の作成に数えない。二つの作業コピーが同じ番号の decision を回答から作ったマージは、同じ decision の二つの取引として見つかる。片方が回答から、もう片方が record create で同じ番号の decision を作ったマージは、起動時に decision のファイルの `txid` を、その番号を採番した取引と照らして見つける。手で作った側のファイルを残すと、ファイルの `txid` が無いか合わないので、書き込みを止める。回答の側のファイルを残すと journal とファイルは合い、手で作った判断はそのマージで無くなる（同じパスのファイルを両方が足したので、Git の衝突として人が選んでいる）。前の版で、消した記録を同じ id のまま手で作り直した（TypeScript 版の `record_put`）ジャーナルは、decision でない記録なら二度の作成として、取引が採番した decision ならファイルの `txid` が合わないことで、書き込みを止める。このリポジトリのジャーナルには、どちらの書き直しも無い。`.prepare-dev/index.json` は起動を速くするための補助で、無くても再構成できる。

導出する状態。

- `committed(a)`: `intent(tx, a)` と `commit(tx)` が存在する。
- `inflight`: `commit` も `abort` もない `intent` が存在する。
- `recovery_pending`: `inflight`、または abort 済み取引の仮 decision・仮適用印・未更新の stale 状態が残っている。`inflight = false` だけでは回復完了を意味しない。
- `public_decisions`: `decisions` のうち `txid` が commit 済みのもの。
- `pending`: 保存済みの回答のうち、`committed` でも `closed` でもないもの。`received` や `stale` は条件に含めない。

## 2. 操作

通常の操作は `recovery_pending = false` のときだけ受け付ける。回復が必要なときは先に `recover` を完了する。API の質問取得・未処理回答・変更の通知（SSE）は journal から確定を判定し、未確定の `applied_as` を公開しない。質問全体に別の確定済み回答があっても、各回答を個別に判定する。

| 操作 | 前提 | 効果 |
| - | - | - |
| `create_question(q, subjects)` | 対象の記録が存在 | 対象の現在の版を写して質問を保存 |
| `edit(r)` | デーモン停止中、または操作と操作の間 | 記録 `r` の `rev` を 1 増やし `sha256` を変える（外部編集） |
| `save_answer(q, a)` | 質問が存在 | 回答を保存し、対象の現在の版を `subjects_at_answer` に写す。そのいずれかが `q.subjects` と異なれば `stale = true` |
| `ack(a)` | 回答が存在 | `received = true`。`pending` には影響しない |
| `close(a)` | `¬committed(a)` | `closed = true` |
| `apply(a)` | 下記 | 下記 |
| `recover()` | なし | 下記 |

### 2.1 `apply(a)`

1. `committed(a)` なら、その `decision_id` を返して終わる（再試行は同じ結果）。
2. `closed(a)` なら拒否する。
3. `a.stale` であるか、`q.subjects` のいずれかが現在の版（`rev` と `sha256` の両方）と一致しなければ、`a.stale = true` にして拒否する。
4. 段階 a: `decision_id` を採番し、`intent {txid, a, decision_id, subjects = q.subjects}` を journal に追記する。
5. 段階 b: decision ファイル `{decision_id, txid}` を書く。
6. 段階 c: 回答に `applied_as = decision_id` を書く。
7. 段階 d: `commit {txid}` を journal に追記する。

段階の名前は実装の中断点でも使う: 段階 a が `intent`、b が `decision`、c が `question`、d が `commit`。適合テストの操作列の `crash_after` と、試験用に `prepare-dev serve --crash-after <段階>`（または環境変数 `PREPARE_DEV_CRASH_AFTER`）で起動したデーモンは、その段階を書いた直後に中断する。段階 a の追記以降、どの段階の後でも中断（crash）が起こりうる。中断後は `inflight` となり、`recover` が完了するまで通常の操作は受け付けない。

### 2.2 `recover()`

`inflight` の `intent` について、

- `intent.subjects` のすべてが現在の版（`rev` と `sha256`）と一致すれば、同じ `decision_id` で段階 b、c、d のうち未完了のものを順に行う（ロールフォワード）。
- 一致しなければ (1) `abort {txid}` を追記、(2) 仮 decision ファイルを削除、(3) 回答の `applied_as` を外して `stale = true` を保存する。各書き込みの後に再中断できる。`abort` 後は `inflight = false` になるが、清掃が終わるまで `recovery_pending = true` とする。
- 起動時には abort 済み取引も走査し、残存する仮 decision と回答を再清掃する。既に済んだ書き込みは繰り返しても結果を変えない。再中断は保存状態をそのまま残し、次の起動も同じディスク状態から再開する。
- 起動時には commit 済みの取引も走査し、decision のファイルが無ければ `intent` の `decision` から書き直し（版は §1 のとおり journal の最後の版の次）、回答の適用印が無ければ付け直す。これはモデルの外の操作（停止中にファイルを消す、`git stash -u` や `git clean` で消える）への備えで、モデルの `edit` は削除を含まない。デーモンの動作中に消えたファイルは次の起動まで書き直さず、その間その decision は一覧と trace に出ない（前提のとおり、動作中には消さない）。質問のファイル（回答を持つ）は journal から戻せない。それが無い取引があると、回復はその取引のものを何も書かずに、戻すファイル（`prepare/questions/<id>.json`）を示すエラーで止まる。ロールフォワードも同じ。`git clean` や `git stash -u` は、まだコミットしていない質問と、その回答から作った decision を一緒に消すので、ファイルを戻してから起動し直す。

確定済み（commit 済み）の取引は、その後に対象の版が変わっても abort しない。

## 3. 主張

| 主張 | 内容 |
| - | - |
| C1 | 任意の到達可能な状態で、各回答について commit 済みの `intent` は高々一つ。`public_decisions` の各要素は commit 済みの `intent` と一対一に対応する |
| C2 | commit 済みの各取引について、`intent.subjects` は質問の `subjects` と一致し、その回答は `stale` ではない。commit は、現在の版が `intent.subjects` と一致する状態でのみ起こる |
| C3 | 保存済み回答はすべての遷移で保持される。`recovery_pending = false` の状態で、(i) 保存済みの回答は存在し続ける、(ii) `applied_as` が付いている ⟺ `committed`、(iii) decision ファイルが存在する ⟺ その `txid` が commit 済み、(iv) `pending` はファイルから計算しても journal から計算しても同じ集合になる |
| C4 | 第4節の形式でモデルが生成した操作列を Go 実装に流したとき、各段階の観測結果がモデルと一致する |

C1 から C3 は操作単位の Lean モデルで証明する。C3 の実装側は、`internal/runtime` のテストに加え、`internal/e2e` の `[C3]` が実プロセスで確かめる。段階 c と d の後にデーモンのプロセスを終わらせ、停止中に対象を編集してから起動し直し、取り消しと確定の維持を見る（C3 の native 参照がパッケージを限らない `::[C3]` なのはこのため）。`internal/store` の `[C3]` は、前提を崩すジャーナル（二つの作業コピーのマージ）を起動時に検出し、何も書かないことを確かめる（一人の書き手が書いたジャーナルの例として、TypeScript 版のジャーナルの写し `internal/store/testdata` を使う）。`internal/runtime` の `[C3]` の「a deleted decision file is written again」で始まるテストは、確定済みの適用と段階 b の後で中断した適用のそれぞれで decision のファイルを消して起動し直し、journal から次の版で書き直されること、続く起動がそれをマージと誤らずに書き込めることを確かめる。`internal/store` の `[C3]` は、前の版が `rev` 1 で書き直した decision を二度の作成に数えないことと、二つの取引の decision と手で作った記録の二度の作成は見つけることも確かめる。`internal/runtime` の `[C3]` の「a missing question file」で始まるテストは、質問のファイルが無いとき、回復がその取引のものを何も書かずに戻すファイルを示して止まり、戻せば起動して decision を書き直すことを確かめる。「a decision of the same number made with record create」で始まるテストは、回答から作った decision と record create で作った同じ番号の decision のマージ（手で作った側のファイルを残したもの）を起動時に見つけて、書かないことを確かめる。C2 は `committed_safety` が状態と確定時の版照合をまとめ、C3 は `quiescent_with_answers` が回答保持と整合性をまとめる。モデルは `apply` の段階 a〜d と中断を含むが、`recover` の内部は一操作に抽象化している。その内部の取り消し清掃は C5 のモデルで別に扱う。操作単位のモデルの `inflight = false` は清掃完了後の状態に対応し、実ディスク上の清掃途中を含めない。

### C5: 回復途中の再中断

`model/PrepareDev/Spec/Recovery.lean` は、対象版が変わった未確定取引一件の abort 記録、decision の有無、適用印、stale 状態、保存した回答をモデルにする。`resume` は次の一つの保存段階、`crash` は保存状態を変えない中断。任意の有限な操作列で回答を保持し、続けて三回 resume すれば清掃が完了し、完了状態は再回復で変わらないことを `PrepareDev.Recovery.recovery_safe` で証明する。中断が永久に続く場合の進行は保証しない。段階は abort ログ、仮 decision の削除、回答 JSON の更新という三つの状態変更であり、補助的な index や record.remove ログの更新回数は数えない。

`lake exe prepare-model recovery` が生成する 48 本の操作列（`model/traces/recovery.jsonl`）を `internal/runtime/recovery_test.go` で実装へ流す。48 本は、apply の三つの中断点（段階 a・b・c の後。その後に対象を編集して取り消しの回復に入る）ごとに、最初の四手を `resume`（次の保存段階を一つ行う）か `crash`（何も保存せずに中断する）にした 16 通りで、その後に `resume` を四回続ける。形式は第4節の終わりに書く。各保存段階の後に中断し、実ファイルの状態、回答保持、回復待ち中の通常操作拒否、未確定印の非公開を比較する。モデル上の証明と、実装について実行した trace の範囲の適合テストを区別する。

### C6: 公開する確定状態と回復待ち

API の質問取得・未処理回答・通知は `apply.commit` を根拠に各回答の `applied_as` を組み立てる。保存途中の仮適用印は公開しない。通常の質問操作は清掃中も拒否する。`internal/runtime` の `questions_test.go` と `recovery_test.go` の `[C6]` を同じ検証実行に含める。C6 は実装テストによる保証であり、C5 の Lean 定理が API や UI を証明するという意味ではない。

## 4. 適合テストの操作列の形式（C4 用）

モデルの実行可能定義が操作列を列挙し、各段階の後の観測を JSON Lines で出力する。Go 側は同じ操作を実装に対して行い、観測を比較する。ここでの操作列（trace）は、記録のつながりを表示する `prepare-dev trace` とは別のもの。

生成は `cd model && lake exe prepare-model gen --depth N [--max-traces M] [--seed S]`。記録 R1・R2、質問 Q1（対象 R1）・Q2（対象 R1 と R2）、回答 A1（Q1 への回答）・A2（Q2 への回答）の上で、ちょうど N 手の操作列を決定的な深さ優先で列挙し、M 本（既定 2,000）で打ち切る。`--seed` は候補の操作を試す順を回す（既定 0）。打ち切ったときにどの操作列が入るかは、この順で決まる。`model/traces/depth-4.jsonl` は depth 4 の全 165 本、`model/traces/depth-6.jsonl` は seed 0 の depth 6 の先頭 2,000 本。`model/bin/test` は両方とリカバリーの操作列をモデルから作り直し、保存しているファイルと一致することを確かめる。

`internal/runtime/conformance_test.go` は環境変数 `PREPARE_DEV_TRACES`（リポジトリのルートからのパス）のファイルを、無ければ depth-4 を流し、流したファイルと本数・手数・不一致の数を、gotest プラグインが RUN ごとに用意するディレクトリ（`PREPARE_DEV_BOUNDS_DIR`）に書いて RUN の `scope.bounds` に残す。このリポジトリの検証実行は `.prepare-dev/config.json` の `plugins.gotest` の `env` で depth-6 を指定する。

操作列がモデルの生成したものであることは、次の二つで結び付ける。`model/bin/test` は操作列を作り直して保存しているファイルと一致したときだけ、モデルのソース（Lean のファイル、lakefile.toml、lean-toolchain、lake-manifest.json）の digest を `model/traces/model.sha256` に書く。`internal/runtime` の `[C4][C5]` のテストは、今のモデルの digest をこれと照合し、違えば失敗する（モデルを変えたのに照合し直していない）。モデルのソースと操作列のファイル（`model/**`）は `impl_files` で入力に記録するので、どちらかが変われば C4・C5 の RUN は当てはまらなくなる。

一行の形式。

```json
{"trace": 12, "step": 3, "action": {"type": "apply", "answer": "A1", "crash_after": "question"}, "observe": {"inflight": true, "pending": ["A1"], "committed": {}, "closed": [], "stale": [], "public_decisions": [], "result": "crashed"}}
```

`action.type` と引数。

| type | 引数 | 意味 |
| - | - | - |
| `create_question` | `question`, `subjects: [record]` | 2章の `create_question` |
| `edit` | `record` | 外部編集 |
| `save_answer` | `question`, `answer` | 回答の保存 |
| `ack` | `answer` | 受領 |
| `close` | `answer` | 終了 |
| `apply` | `answer`, `crash_after: null \| "intent" \| "decision" \| "question"` | 適用。`crash_after` があれば、その段階まで行って中断する |
| `recover` | なし | 回復 |

記録 id は `R1`、質問は `Q1`、回答は `A1`、decision は採番順に `D1`、`D2` … とする。実装側は自分の id 体系へ対応づける。

`observe` の項目。

| 項目 | 内容 |
| - | - |
| `inflight` | 進行中の取引があるか |
| `pending` | `pending` に含まれる回答 id の昇順一覧 |
| `committed` | 回答 id → decision id |
| `closed` | `closed` の回答 id の一覧 |
| `stale` | `stale` の回答 id の一覧 |
| `public_decisions` | 公開される decision id の一覧 |
| `result` | 直前の操作の結果。`ok`、`applied`、`already_applied`、`rejected_stale`、`rejected_closed`、`rejected_inflight`、`crashed`、`recovered_forward`、`recovered_abort`、`noop` |

操作列の生成は決定的で、同じ入力から同じ出力を得る。中断後は `edit` と `recover` だけを生成し、`recover` の後に通常の操作へ戻る。

### 回復の操作列（C5 用）

一行が一本の操作列で、`{"stage": "intent"|"decision"|"question", "initial": 観測, "steps": [{"action": "resume"|"crash", "observe": 観測}]}` の形。`stage` はどの段階の後に中断したか。観測は `answer`（保存されている回答の数）、`aborted`（abort が記録済み）、`decision`（仮 decision のファイルがある）、`applied`（回答に適用印がある）、`stale`、`ready`（清掃が完了し `recovery_pending = false`）。

## 実行時の流れ

CLI は root の `.prepare-dev/daemon.json` を読み、書かれた URL の `/api/identity` に問い合わせて、動いているデーモンの version と build を自分のものと比べる。デーモンは HTTP を始めてから daemon.json を書くので、lease が取られていて daemon.json が無い間は起動中である。

| 状況 | CLI の振る舞い |
| --- | --- |
| daemon.json がなく、lease も空いている | 同じ実行ファイルを `serve --root <root>` で起動し、端末から切り離す（新しいセッション）。起動したものが応答せずに終わったら、待たずに daemon.log の最後の行（起動できなかった理由）を示して終える。別の起動に lease を取られたときは、その相手が応答するのを待つ |
| デーモンが応答し、version と build が同じ | 接続する。置き場所が違う同じ build の写しも接続する |
| デーモンが応答し、version か build が違う | 接続しない。相手の version・build・場所・pid と、`prepare-dev stop --root <root>` で止めてから再実行することを示して終える |
| デーモンが停止を受け付けた後で、まだ終わっていない | identity にだけ答え、ほかの要求は 409 で拒む。CLI はその誤りを示して終える（止まってから再実行する） |
| daemon.json はあるが応答せず、lease が空いている | 強制終了したデーモンの残りとみなし、daemon.json を消して起動する。ただし daemon.json を TypeScript 版が書いていて、その版の lease がまだ取られているときは、引き継がずに止め方を示して終える（移行期の対策。§TypeScript 版からの移行） |
| lease が取られているが応答がない（daemon.json の有無によらない） | 起動中かもしれないので、時間（既定 15 秒）まで待つ。それでも応答しなければ、lease ファイルに書かれた pid を示して終える（そのプロセスを止めて再実行する） |

デーモンは、lease を取ってから記録を開き（走査と回復を済ませる）、127.0.0.1 の空いているポートで HTTP を始め、daemon.json（pid、ポート、URL、root、起動時刻、version と build と場所、停止用のトークン）を書く。lease はプロセスの終了とともに OS が外す。停止は `prepare-dev stop` が daemon.json のトークンで `/api/shutdown` を呼ぶ。検証ジョブの実行中は拒否する。デーモンは止めるまでプロジェクトごとに一つ残る。

デーモンを置く理由は三つある。人が回答している間も判断画面をいつでも開けること、回答や検証の完了を画面とエージェントの待機（`q wait`、`verify wait`）へ届けること、検証を非同期に走らせて結果を同じ書き手が記録すること。CLI がその都度ファイルロックを取って直接書く形では、画面と待機のために結局どこかで HTTP を出し続ける必要がある（代替案 no-daemon）。

## 書き手を一つにする

lease が守るのは、一つの root の永続状態（記録、質問、RUN、ジャーナル）を開くプロセスが一つだけであること。ID の採番と回答の適用は、メモリ上の索引とジャーナルを一つの書き手が持つ前提で作っている（SPEC-0001 の前提）。lease のファイルは root の中にあるので、root をどのパスで指してもロックは同じファイルに掛かる。lease を取れない `serve` は記録を開く前に終わる（CLI が lease を確かめるために一瞬ロックするので、取得は 1 秒だけ再試行する）。

lease のファイルを動作中に消されると（`git clean`、`git stash -u` など）、次の CLI は lease が空いていると見て二つ目のデーモンを起動できてしまう。これを防ぐため、デーモンはすべての操作の前に、lease のパスが自分のロックしているファイルと同じものかを確かめ、違えば何も書かずに 503 を返し、2 秒以内に終わる。`init` は `.prepare-dev/.gitignore` に daemon.json・daemon.log・lease などを書き、これらが消されたりコミットされたりしにくくする。

保証は作業コピーごとである。ブランチや worktree の作業コピーはそれぞれのデーモンを持ち、同じ基準から別々に ID を採番するので、記録を書く作業コピーは一つにする（配布物の README と prepare-dev skill に書く）。二つの作業コピーで書いた prepare/ をマージすると、同じ番号の記録とジャーナルが衝突する。これは普通のコンフリクトとして、マージのときに人が直す（DEC-0008）。prepare-dev は自動でまとめず、直し方の手順も持たない。代わりに、直した結果を黙って書き進めないための検査を持つ。

- ジャーナルに衝突の印が残っている: デーモンは起動せず、CLI が待たずにその理由（daemon.log の最後の行）を示す。
- 直した結果に矛盾がある（同じ記録・質問・回答の二度の作成、同じ decision の二つの取引、一つの回答の二つの確定、別の作業コピーで判断に反映した回答や decision が残っている）: デーモンは起動するが、回復も含めて何も書かず、status の problems に示す。
- ブランチの切り替え・stash・reset・pull で Git がジャーナルを置き換えた: 動いているデーモンは、操作の前にジャーナルが開いたときと同じファイル・同じ長さかを確かめ、違えば何も書かずに止まる。次のコマンドが今のジャーナルで起動し直す。

別の名前のファイルが同じ ID を持つ場合（手で写したときなど）は、二つ目を problems に示してどちらも書き換えない。

## データの形式

記録の Markdown（YAML の frontmatter）、質問と RUN の JSON（2 文字の字下げ）、ジャーナル（JSON Lines）の形式は TypeScript 版から変えない。読むだけではファイルを書かないので、記録ファイルの sha256（版として質問・判断・レビュー・RUN が参照する）は、内容を変えない限り変わらず、版の切り替えでファイルが書き換わることもない。

書き方（YAML の引用と順序、JSON の並び）まで TypeScript 版と同じにするのは、runtime が書き直すファイル、つまり記録（`record put` と外部編集の検出）と質問（回答・受領・終了・適用）の差分を、変えた項目だけにするためである。記録は Git に入れて差分で読む。RUN は完了時に一度書くだけ、ジャーナルは追記だけで書き直さないので、書き方の一致は求めず、読んで欠ける項目がないこと（API と回復が使う）だけを求める。

基準は TypeScript 版の最後のコミット（342bc64）が書いたファイルの写し（internal/core/testdata/ts-342bc64）で、テストは写しの記録と質問を読み直して書き出してもバイト列が変わらないこと（`cancelled` の無い古い質問に `cancelled: null` が加わるのは TypeScript 版と同じ）、RUN とジャーナルの行は読んで書き出しても欠ける項目がないこと（書き方は問わない）を確かめる（SPEC-0004 D1）。YAML の書き出しは npm の yaml パッケージに合わせて自前で実装した。書く前に読み戻し、内容が一致しなければ書かない。YAML 1.1 の読み手が改行とみなす文字（U+2028、U+2029、U+0085）と制御文字は、二重引用符の中でエスケープする。

## HTTP API

経路は標準の ServeMux で振り分ける。判断画面と CLI が使う経路は次のとおり。

| 経路 | 用途 |
| --- | --- |
| `GET /api/identity` | pid、root、起動時刻、version・build・場所 |
| `POST /api/shutdown` | 停止（daemon.json のトークンが必要） |
| `GET /api/status` | 未処理の回答、回答待ちの質問、未対処の指摘、適用できない証拠、記録されなかった検証、問題 |
| `GET/POST /api/records`、`GET/PUT /api/records/:id` | 記録の一覧・作成・取得・更新（更新は読んだ版が必要） |
| `GET/POST /api/questions`、`GET /api/questions/:id`、`GET /api/pending` | 質問の一覧・作成・取得、未処理の回答 |
| `POST /api/questions/:id/answers` | 回答（判断画面からだけ） |
| `GET /api/questions/:id/wait` | 回答を待つ |
| `POST /api/questions/:id/answers/:aid/ack`、`.../apply`、`.../close`、`POST /api/questions/:id/cancel` | 受領、判断への適用、終了、取り消し |
| `GET/POST /api/runs`、`GET /api/runs/:id`、`GET /api/runs/:id/wait` | 検証の一覧・開始・取得・待機 |
| `GET /api/trace/:id`、`GET /api/bundle`、`GET /api/plugins` | trace、レビュー資料、プラグイン一覧 |
| `GET /events` | 変更の通知（SSE） |
| `GET /`、`GET /q/:id` | 判断画面 |

Host が `127.0.0.1:<port>` か `localhost:<port>` でない要求と、Origin が自分以外の要求は 403 で拒否する。回答は判断画面の人のものなので、Origin を持たない要求（ブラウザ以外）も拒否し、CLI に回答の操作を置かない。これで防ぐのは、エージェントが手順どおりに CLI で回答することと、ほかのサイトのページからの要求である。同じ利用者のプロセスが Origin を付けて送ることは防がない（受け入れた残りのリスク）。loopback の API に認証は無いので、一人の利用者のホストを前提にする。エラーは `{error, message, details}` の形で返し、500 は daemon.log にも書く。

## CLI

コマンドは `init`、`status`、`ui`、`pending`、`record create|get|put|list`、`q create|list|show|wait|pending|ack|apply|close|cancel`、`verify run|wait|get|list`、`trace`、`bundle`、`serve`、`stop`、`guidance`、`version`。`mcp` と `q answer` は無い。出力は JSON で、`status` は既定で文章（`--json` で JSON）。エージェントが読む `verify` と `trace` は、入力ファイルの一覧を件数に、不一致と実行したテストの一覧を先頭の 5 件と残りの数に縮め、`verify list` は実行ごとの要約にする。`--json` で全体を出す。

## init と skills

`init` は `.prepare-dev/config.json` と `.prepare-dev/.gitignore` がなければ作り（あれば変えない）、skills を `.agents/skills` と `.claude/skills` にコピーし（`--skills-dir` で変更、`--no-skills` で省略）、デーモンを起動する。MCP の設定は書かない。

skills のコピーは、入れた skill の digest を `.prepare-dev/skills.json` に残す。次の `init` では、無い skill を入れ、同じ内容なら何もせず、前に入れたときのまま編集されていない skill は新しい版に置き換える。それ以外の違い（利用者の編集、別の方法で置いたもの）は残して conflicts に示す。`--replace-skills` を付けると、違うものを `.prepare-dev/skills-backup/<時刻>/` に移してから置き換える。root の外、シンボリックリンク、ディレクトリでない配置先は触らずに示す。

## 判断画面のビルド

ui/ の `pnpm build` が build/index.html、画面に入れた npm パッケージのライセンス（build/THIRD_PARTY_NOTICES.txt）、build/build.json を書く。build.json には、ビルドの元にしたソースの digest と、出力の二つのファイルの sha256 が入る。ソースは ui 直下の index.html・package.json・pnpm-lock.yaml・tsconfig.json・vite.config.ts と、src/ の下のファイル（テストと、`.` で始まる名前を除く）である。Go のテスト（SPEC-0004 B1）とリリースのスクリプトは、今のソースの digest と出力の sha256 を build.json と照合し、ソースを変えてビルドし直していないときも、出力を手で書き換えたときも失敗する。この範囲は、ビルド（ui/vite.config.ts）と Go（internal/uibuild）の二か所に同じ一覧として書き、src/ の外にビルドの入力を足すときは両方を直す。二つの計算が食い違えば B1 が失敗して分かる。Node.js（pnpm・Vite）は画面を直す人だけが使い、prepare-dev のビルドと利用には要らない。

## 検証プラグイン

- lean4: `lake env lean --src-deps` を再帰的に使って入力を集め、`lake build` と `#check`・`#print axioms` で確かめる。Lean はモジュールの名前で import を読むので、ファイルが増えても結果は変わらず、ディレクトリの一覧は記録しない。
- vitest: テスト・追加実装・Vitest の設定から、esbuild のバンドルと同じ規則で import をたどり、esbuild が読み込むファイルを入力にする。拡張子の無い import は Vite の既定の順で探す。node_modules の中のパッケージは manifest と lockfile で代表し、型だけの import は実行時に読まれないので入力にしない。import が読むファイルのディレクトリ（その段だけ）と、impl_files のパターンが探すディレクトリの一覧を記録する（SPEC-0003 V1）。
- gotest: go list が報告するテストのビルドに使うファイル、実行するパッケージの testdata、テストが実行中にビルドするパッケージ（`input_packages`）、そのほかに読むファイル（`impl_files`、`**` を使えるパターン）を入力にし、パッケージ・埋め込み・testdata・パターンのディレクトリの一覧を記録して、`go test -json -count=1` で、テストのキャッシュを使わずに実行する（SPEC-0003 V3。集めるファイルの種類は SPEC-0003 だけに書く）。デーモン自身の環境の `PREPARE_DEV_` で始まる変数はテストに渡さない（ほかの環境変数はデーモンのものが渡る）。テストは RUN ごとのディレクトリ（`PREPARE_DEV_BOUNDS_DIR`）に、流した件数や検査した実行ファイルを書いて scope.bounds に残せる。

runtime は、入力の内容の変更・削除と同じく、記録したディレクトリの一覧が変われば証拠を当てはまらないものにする。どのプラグインも、検証器の有無を project_dir で調べ（elan が project_dir の lean-toolchain の版を選ぶ）、使った道具の場所を RUN の `tool.extra` に残す。検証はデーモンが動かすので、道具の探し方（PATH に `~/.elan/bin`・`~/.cargo/bin`・`~/.local/bin` を足す）と環境変数は、デーモンを起動した CLI のものが使われ続ける。

## 配布と開発

`go run ./scripts/release -version <v>` で macOS と Linux（arm64・amd64）向けの実行ファイルを作り、README と第三者ライセンスとともに tar.gz にまとめ、sha256 を `dist/artifact.json` に残す。画面のビルドが build.json と合わなければ作らない。パッケージ管理サービスへの公開はしない。配布物そのものは、展開した実行ファイルを `PREPARE_DEV_E2E_BINARY` に渡して e2e テストで確かめる。

開発中は checkout で `go run ./cmd/prepare-dev` を使う。ソースを変えると build が変わるので、前のデーモンを `prepare-dev stop` で止めてから使う。

## TypeScript 版からの移行

TypeScript の本体（packages/ の core・runtime・mcp・cli、plugins/、scripts の build.mjs・pack.mjs、ルートの package.json・pnpm・tsconfig・vitest の設定）を消し、画面を packages/ui から ui/ に移す。実プロセスの強制終了からの回復を確かめていた scripts/e2e-crash.sh は Go の e2e テストに移す。このリポジトリの `.mcp.json` と `.codex/config.toml` の登録を消す（DEC-0007）。

切り替えるときは、TypeScript 版のデーモンを `prepare-dev stop` で止め（停止の API は同じ）、エージェントの MCP 設定から `prepare-dev mcp` を消し、`prepare-dev init --replace-skills` で skills を置き換える。戻すときは Go 版のデーモンを止め、commit 342bc64 の checkout で `pnpm install` と `pnpm ui:build` を実行して TypeScript 版を使う。TypeScript 版は Go 版の書いた記録をそのまま読み、Go 版で増えたもの（gotest の RUN、RUN の listings、skills.json）は使わない。

移行期の対策として、止め忘れた相手のデーモンを検出する。TypeScript 版の lease は root から決めた TCP のポートで、Go 版の flock とは互いを排除しない。そこで Go 版は daemon.json と `/api/identity` の識別に TypeScript 版が必須とする root（実行ファイルのディレクトリ）と mode（`package`）も書き、TypeScript 版の CLI が Go 版のデーモンを別の build として拒むようにする。逆向きは、Go 版の CLI と `serve` が TypeScript 版の書いた daemon.json を見つけ、その版の lease のポートが取られていれば、引き継がずに止め方を示す。この検出は相手の daemon.json があるときしか働かない（相手が lease を取ってから daemon.json を書くまでの間、daemon.json が消された後、手で起動した TypeScript 版の `serve`）。そのため、移行中は二つの版を同じ root で同時に使わないことを手順とする。これらは TypeScript 版を使うプロジェクトを切り替え終えるまでの対策で、0.3.0 で外し、そのとき SPEC-0004 の P3 と assumptions の該当部分も外す。

移行は、TypeScript の本体が残っていないこと、SPEC-0001・SPEC-0003・SPEC-0004 の主張の RUN が今の版に当てはまること、配布物を別の場所と Linux で動かした確認と版の共存の確認が確認記録に残っていることで完了とする。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 自前の YAML 書き出しが npm の yaml と違う書き方をする | TypeScript 版の写しで往復のバイト一致を確かめ、書く前に読み戻して違えば書かない |
| 埋め込む画面のビルドがソースとずれる、または手で書き換えられる | build.json のソースの digest と出力の sha256 を、テストとリリースで照合する |
| 強制終了したデーモンの daemon.json が残る | lease が空いていれば古いものとして消す。pid は使わない |
| 動作中に lease のファイルが消される | 操作の前に lease のファイルを確かめ、違えば書かずに終わる。init が .gitignore を置く |
| TypeScript 版のデーモンと同じ root で並ぶ | 移行期の対策として、両方の CLI が相手の daemon.json からデーモンを検出して拒む。検出できない場合（daemon.json が無いとき、手で起動した TypeScript 版の serve）は、二つの版を同時に使わない手順で防ぐ。0.3.0 で外す |
| 二つの作業コピーの prepare/ をマージする | 記録を書く作業コピーは一つと README と skill に書く。衝突はマージのときに人が直す（DEC-0008）。衝突の印があれば起動せずに理由を示し、直した結果に矛盾があれば何も書かずに problems に示す |
| ブランチの切り替えなどで Git がジャーナルを置き換える | 動いているデーモンは操作の前に気付き、何も書かずに止まる |
| デーモンが起動時の PATH と環境変数を使い続ける | 道具の場所を RUN に残す。道具や環境を変えたら止めて起動し直すと案内する |
| エージェントが人の代わりに回答する | CLI に回答の操作を置かず、API はブラウザの同じ origin の要求だけを受け付ける。同じ利用者のプロセスが Origin を偽ることは受け入れた残りのリスク |
| 出力がプロジェクトの大きさに比例して長くなる | verify と trace の既定の出力を要約にする |
| Linux の実機で動かしていない | Linux のコンテナ（arm64、amd64 はエミュレーション）で配布物を動かし、確認記録に残す |

## 前段との照合

- DEC-0004（CLI として配布し、skill から CLI を実行する）: 維持する。配布物の形を npm の tarball から実行ファイルに変える。
- DEC-0005（判断画面を React で作り、json-render を採用しない）: 維持する。
- DEC-0006（Go で作り直す）: この設計で具体化する。
- DEC-0007（MCP の入口をなくす）: `mcp` サブコマンドと MCP 用のパッケージを移さず、このリポジトリの登録を消す。
- REQ-0009: 画面の振る舞いは変えない。
- REQ-0010: Node.js の前提を外し、実行ファイル一つで使える要求に改めた。回答を判断画面からだけ受け付けることと MCP の入口が無いことは P5 で、SPEC-0004 A1 が確かめる。
- DES-0002: 画面の契約と API の形は変えない。

- 配布物の README と prepare-dev skill には、記録は一つの作業コピーで書くこと、マージで衝突したら直すこと、直した結果がおかしければ status に出ることだけを書く。
- レビュー（REV-0060・REV-0061）の残りの指摘は、記録が実装と食い違う箇所と危険な箇所だけを直し、ほかはこの判断で閉じる。

## 棄却した案

- 直し方の手順（片方の prepare/ を丸ごと採る git のコマンド、相手側で作ったものの一覧の出し方）を書き、e2e で実際のマージを確かめる: 普通のコンフリクトとして直せば済み、手順を書き込むほどの必要がない。
- 検査も外す: 両方の行を残して解いたジャーナルで、一つの回答から判断が二つできるような状態を黙って書き進めないため、検査は残す。

## 影響

## DEC-0001 — 対象版が変わった回答は保存して再確認対象に残し、自動では反映しない

kind: decision · rev 1 · status accepted · sha256 5f9580c6c28c0c2f5ef3775eafa86ccb7cfe6f5f084e2672c8f728fb80f2184d

```yaml
links:
  rationale_for:
    - REQ-0001
    - SPEC-0001
question: Q-0001
answer: ANS-0001-1
txid: bed7445173ac2c28
chosen: hold
alternatives:
  - apply
  - discard
reviewed:
  - id: REQ-0001
    rev: 1
    sha256: 2bc07c3da72d314e5124b88c47776d1fed049c55b7ff90e241fd105f2c67facc
  - id: SPEC-0001
    rev: 2
    sha256: 6b28b2592848c70099d0799e34ae21fd32d0df614f82dd025d0da94f2583a391
```

## 採用

`hold`: 回答は保存するが、対象の `rev` か `sha256` が質問作成時と異なる場合は `stale` として未処理一覧に残し、`question_apply` は拒否する。

## 理由

- 回答はその時点の文書を読んで下した判断であり、文書が変われば別の対象に対する判断になる（REQ-0001 の根拠）。
- 回答そのものは人の作業の成果であり、失わない。再確認で現在版を読み直せば再利用できる。

## 棄却した代替案

- `apply`（そのまま反映）: 古い版への判断を新しい版の判断として扱うことになり、理由と結論の対応が壊れる。
- `discard`（破棄）: 人の回答を黙って捨てることになり、何を聞いて何が答えられたかの記録が残らない。
