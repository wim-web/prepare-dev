### 実行時の流れ

CLI は `.prepare-dev/daemon.json` を読み、識別できるデーモンがなければ同じ実行ファイルを `serve --root <root>` で起動する。デーモンは root から決めた loopback のポートで lease を取り、記録を走査して回復を済ませてから、空いているポートで HTTP を始め、daemon.json を書く。判断画面は埋め込んだ HTML を返す。停止は daemon.json のトークンで受け付け、受け付けた後の新しい操作は拒否する。

### データの互換性

記録の Markdown（YAML の frontmatter）、質問と RUN の JSON、ジャーナルの形式は変えない。TypeScript 版が書いたファイルをそのまま読み、読み書きしてもバイト列が変わらないことをテストで確かめた（記録 71 件、質問 28 件、RUN 9 件、ジャーナル 224 行）。TypeScript 版のデーモンと同じ root で同時に動かないよう、lease のポートの決め方を揃える。

### HTTP API と CLI

経路、要求と応答の形、エラーの形は TypeScript 版と同じにし、判断画面をそのまま使えるようにする。旧 `/api/questions/:id/ui` は無い。壊れた `%` を含む URL は 400 を返し、デーモンは動き続ける。質問 ID は `Q-NNNN` の形だけを受け付け、質問フォルダの外のファイルを読まない。停止用のトークンはログに出さない。

CLI のコマンド、フラグ、出力は TypeScript 版と同じにする。`mcp` サブコマンドは無い。真偽値のフラグ（`--stdout`、`--wait` など）は次の語を値として取らない。

### 検証プラグイン

- lean4: そのまま移す。`lake env lean --src-deps` を再帰的に使って入力を集め、`lake build` と `#check`・`#print axioms` で確かめる。
- vitest: 入力の規則は SPEC-0003 V1 のまま。文字列で書かれた import・export・require・動的 import の指定子の構文解析を、TypeScript コンパイラから esbuild に置き換える。

### 配布と開発

`go run ./scripts/release -version <v>` で macOS と Linux（arm64・amd64）向けの実行ファイルを作り、README と第三者ライセンスとともに tar.gz にまとめ、sha256 を `dist/artifact.json` に残す。パッケージ管理サービスへの公開はしない。

開発中は `go run ./cmd/prepare-dev` で動く。判断画面を直すときは `ui/` で `pnpm build` を実行し、ビルド結果と画面の第三者ライセンスをコミットする。

## 要求
prepare-devをOSとアーキテクチャごとの実行ファイル一つで配り、使う人の環境にNode.jsなどの言語処理系を求めない。検証器（Lean・Vitest・Goなど）は対象プロジェクト側で用意する。CLIは必要時にローカルruntimeを起動し、埋め込んだ判断画面を配信する。skillsは通常の配置先にコピーし、MCPの入口は提供しない（DEC-0007）。

## 受入条件
- P1: 別の場所に置いた実行ファイルだけから help/version、init、status、ui、record、q、trace、verify が動く。元のcheckoutを参照せず、Node.jsとGoが無くても動く。
- P2: initはMCP設定を書かず、既存設定・利用者のskill編集を上書きしない。skillsのコピーは同内容なら変更せず、差異は報告する。
- P3: 自動起動・停止・再起動が動き、異なる版や別の配置のruntimeへ黙って接続しない。同じrootに複数の書き手を起動しない。
- P4: 独立したプロジェクトで要求作成→質問→UI回答→DEC→SPEC→実装→実ツールのRUN→traceを確認する。パッケージ管理サービスへの公開は対象外。

旧REQ-0002〜0008の可搬性・UI同梱・source開発維持の意図を引き継ぐ。開発中はcheckoutから `go run ./cmd/prepare-dev` で動かせる。旧案GのMCP登録を軸にした段階分けは採用しない。

## 観点の対応
- users・rationale: 別プロジェクトでprepare-devを使う利用者と、CLIを呼ぶエージェントのための要求。DEC-0004・DEC-0006・DEC-0007に基づく。
- scenarios_normal: 実行ファイルを置いてinitするとskillsとruntimeを使える。質問・回答・判断・検証を同じrootに記録し、traceで追う。
- scenarios_exception: 同時起動は一つのruntimeを共有する。別build・別配置のruntimeへの接続は拒否する。既存skillが異なる場合は上書きせず報告する。検証実行中の停止は拒否する。
- terms・data: root、配布物、source、build、daemon、skillsの意味はDES-0004と既存runtime契約に従う。配布方式の変更で過去の質問・判断・RUNを改変しない。
- states・rules: 未起動、起動中、停止、再起動、異なる配布物を区別する。同じrootの書き手を一つにし、利用者の設定とskill編集を保護する。
- quality・constraints: checkout・Node.js・Goへの依存を除き、配置先を変えて動作を確認する。macOSとLinux、loopback接続が前提で、Windowsは対象外。判断画面を直す開発者だけがNode.jsを使う。検証器は利用先が導入する。
- priority・acceptance: must。SPEC-0004のP1〜P3と、配布物による一連の利用の記録で確認する。

coverageのdecidedは観点の扱いが決まっている意味であり、全ホスト・全OSでの確認済みの意味ではない。実行環境と未確認の範囲はdocs/2026-11-09-go-verification.mdに記録する。

# 回答の適用

本仕様は、人間の回答を判断（decision）として確定する手順と、中断からの回復を定める。対象は runtime の永続状態であり、プロセス内の一時状態は含めない。中断後に残るのは永続状態だけだからである。

## 1. 永続状態

| 要素 | 内容 |
| - | - |
| `records` | 記録 id → 現在の版 `{rev, sha256}`。質問の対象になる要求・仕様など |
| `questions` | 質問 id → `{subjects, answers}`。`subjects` は作成時に写した対象の版の一覧 `[{id, rev, sha256}]` |
| `answers` | 回答 id → `{question, subjects_at_answer, stale, received, closed, applied_as}`。`applied_as` はファイル上の適用印で、確定の写し |
| `decisions` | 存在する decision ファイルの集合。各 decision は `{id, txid}` を持つ |
| `journal` | 追記のみの列。要素は `intent {txid, answer, decision_id, subjects}`、`commit {txid}`、`abort {txid}` |

導出する状態。

- `committed(a)`: `intent(tx, a)` と `commit(tx)` が存在する。
- `inflight`: `commit` も `abort` もない `intent` が存在する。
- `recovery_pending`: `inflight`、または abort 済み取引の仮 decision・仮適用印・未更新の stale 状態が残っている。`inflight = false` だけでは回復完了を意味しない。
- `public_decisions`: `decisions` のうち `txid` が commit 済みのもの。
- `pending`: 保存済みの回答のうち、`committed` でも `closed` でもないもの。`received` や `stale` は条件に含めない。

## 2. 操作

通常の操作は `recovery_pending = false` のときだけ受け付ける。回復が必要なときは先に `recover` を完了する。API の質問取得・未処理回答・SSE は journal から確定を判定し、未確定の `applied_as` を公開しない。質問全体に別の確定済み回答があっても、各回答を個別に判定する。

| 操作 | 前提 | 効果 |
| - | - | - |
| `create_question(q, subjects)` | 対象の記録が存在 | 対象の現在の版を写して質問を保存 |
| `edit(r)` | デーモン停止中、または操作と操作の間 | 記録 `r` の `rev` を 1 増やし `sha256` を変える（外部編集） |
| `save_answer(q, a)` | 質問が存在 | 回答を保存。対象のいずれかの現在の版が `q.subjects` と異なれば `stale = true` |
| `ack(a)` | 回答が存在 | `received = true`。`pending` には影響しない |
| `close(a)` | `¬committed(a)` | `closed = true` |
| `apply(a)` | 下記 | 下記 |
| `recover()` | なし | 下記 |

### 2.1 `apply(a)`

1. `committed(a)` なら、その `decision_id` を返して終わる（再試行は同じ結果）。
2. `closed(a)` なら拒否する。
3. `a.stale` であるか、`q.subjects` のいずれかが現在の版（`rev` と `sha256` の両方）と一致しなければ、`a.stale = true` にして拒否する。
4. 段階 a: `decision_id` を採番し、`intent {txid, a, decision_id, subjects = q.subjects}` を journal に追記する。
5. 段階 b: decision ファイル `{decision_id, txid}` を書く。
6. 段階 c: 回答に `applied_as = decision_id` を書く。
7. 段階 d: `commit {txid}` を journal に追記する。

段階 a の追記以降、どの段階の後でも中断（crash）が起こりうる。中断後は `inflight` となり、`recover` が完了するまで通常の操作は受け付けない。

### 2.2 `recover()`

`inflight` の `intent` について、

- `intent.subjects` のすべてが現在の版（`rev` と `sha256`）と一致すれば、同じ `decision_id` で段階 b、c、d のうち未完了のものを順に行う（ロールフォワード）。
- 一致しなければ (1) `abort {txid}` を追記、(2) 仮 decision ファイルを削除、(3) 回答の `applied_as` を外して `stale = true` を保存する。各書き込みの後に再中断できる。`abort` 後は `inflight = false` になるが、清掃が終わるまで `recovery_pending = true` とする。
- 起動時には abort 済み取引も走査し、残存する仮 decision と回答を再清掃する。既に済んだ書き込みは繰り返しても結果を変えない。再中断は保存状態をそのまま残し、次の起動も同じディスク状態から再開する。

確定済み（commit 済み）の取引は、その後に対象の版が変わっても abort しない。

## 3. 主張

| 主張 | 内容 |
| - | - |
| C1 | 任意の到達可能な状態で、各回答について commit 済みの `intent` は高々一つ。`public_decisions` の各要素は commit 済みの `intent` と一対一に対応する |
| C2 | commit 済みの各取引について、`intent.subjects` は質問の `subjects` と一致し、その回答は `stale` ではない。commit は、現在の版が `intent.subjects` と一致する状態でのみ起こる |
| C3 | 保存済み回答はすべての遷移で保持される。`recovery_pending = false` の状態で、(i) 保存済みの回答は存在し続ける、(ii) `applied_as` が付いている ⟺ `committed`、(iii) decision ファイルが存在する ⟺ その `txid` が commit 済み、(iv) `pending` はファイルから計算しても journal から計算しても同じ集合になる |
| C4 | 第4節の trace 形式で生成した操作列を Go 実装に流したとき、各段階の観測結果がモデルと一致する |

C1 から C3 は操作単位の Lean モデルで証明する。C2 は `committed_safety` が状態と確定時の版照合をまとめ、C3 は `quiescent_with_answers` が回答保持と整合性をまとめる。モデルは `apply` の段階 a〜d と中断を含むが、`recover` の内部は一操作に抽象化している。その内部の取り消し清掃は C5 のモデルで別に扱う。操作単位のモデルの `inflight = false` は清掃完了後の状態に対応し、実ディスク上の清掃途中を含めない。

### C5: 回復途中の再中断

`model/PrepareDev/Spec/Recovery.lean` は、対象版が変わった未確定取引一件の abort 記録、decision の有無、適用印、stale 状態、保存した回答をモデルにする。`resume` は次の一つの保存段階、`crash` は保存状態を変えない中断。任意の有限な操作列で回答を保持し、続けて三回 resume すれば清掃が完了し、完了状態は再回復で変わらないことを `PrepareDev.Recovery.recovery_safe` で証明する。中断が永久に続く場合の進行は保証しない。段階は abort ログ、仮 decision の削除、回答 JSON の更新という三つの状態変更であり、補助的な index や record.remove ログの更新回数は数えない。

`lake exe prepare-model recovery` が生成する48本の trace（apply の三つの中断点 × 四操作の中断・再開の全組合せ）を `internal/runtime/recovery_test.go` で実装へ流す。各保存段階の後に中断し、実ファイルの状態、回答保持、回復待ち中の通常操作拒否、未確定印の非公開を比較する。モデル上の証明と、実装について実行した trace の範囲の適合テストを区別する。

### C6: 公開する確定状態と回復待ち

API の質問取得・未処理回答・通知は `apply.commit` を根拠に各回答の `applied_as` を組み立てる。保存途中の仮適用印は公開しない。通常の質問操作は清掃中も拒否する。`internal/runtime` の `questions_test.go` と `recovery_test.go` の `[C6]` を同じ検証実行に含める。C6 は実装テストによる保証であり、C5 の Lean 定理が API や UI を証明するという意味ではない。

## 4. trace 形式（C4 用）

モデルの実行可能定義が操作列を列挙し、各段階の後の観測を JSON Lines で出力する。Go 側は同じ操作を実装に対して行い、観測を比較する。

一行の形式。

```json
{"trace": 12, "step": 3, "action": {"type": "apply", "answer": "A1", "crash_after": "question"}, "observe": {"inflight": true, "pending": ["A1"], "committed": {}, "closed": [], "stale": [], "public_decisions": [], "result": "crashed"}}
```

`action.type` と引数。

| type | 引数 | 意味 |
| - | - | - |
| `create_question` | `question`, `subjects: [record]` | 2章の `create_question` |
| `edit` | `record` | 外部編集 |
| `save_answer` | `question`, `answer` | 回答の保存 |
| `ack` | `answer` | 受領 |
| `close` | `answer` | 終了 |
| `apply` | `answer`, `crash_after: null \| "intent" \| "decision" \| "question"` | 適用。`crash_after` があれば、その段階まで行って中断する |
| `recover` | なし | 回復 |

記録 id は `R1`、質問は `Q1`、回答は `A1`、decision は採番順に `D1`、`D2` … とする。実装側は自分の id 体系へ対応づける。

`observe` の項目。

| 項目 | 内容 |
| - | - |
| `inflight` | 進行中の取引があるか |
| `pending` | `pending` に含まれる回答 id の昇順一覧 |
| `committed` | 回答 id → decision id |
| `closed` | `closed` の回答 id の一覧 |
| `stale` | `stale` の回答 id の一覧 |
| `public_decisions` | 公開される decision id の一覧 |
| `result` | 直前の操作の結果。`ok`、`applied`、`already_applied`、`rejected_stale`、`rejected_closed`、`rejected_inflight`、`crashed`、`recovered_forward`、`recovered_abort`、`noop` |

操作列の生成は決定的で、同じ入力から同じ出力を得る。中断後は `edit` と `recover` だけを生成し、`recover` の後に通常の操作へ戻る。

## REQ-0001 — 回答は依頼した版にのみ一度だけ反映する

kind: requirement · rev 1 · status proposed · sha256 2bc07c3da72d314e5124b88c47776d1fed049c55b7ff90e241fd105f2c67facc

```yaml

priority: must

  - AC-1
  - AC-2
  - AC-3
  - AC-4
```

## 要求

人間の回答は、質問が対象にした記録の版（`rev` と `sha256`）に対してのみ、一度だけ判断として確定される。対象の版が質問作成時から変わっていた場合、回答は保存されるが自動では確定されず、再確認の対象として残る。

## 根拠

- 回答は「その時点の文書」を読んで下した判断であり、文書が変わればその判断は別の対象に対するものになる。古い版への回答を新しい版の判断として扱うと、理由と結論の対応が壊れる。
- エージェントの接続は切れることがある。回答を失わないために、保存を通知より先に行い、受領と確定を分けて記録する。
- 同じ回答が再送や再試行で二度届いても、判断は一つでなければならない。

## 受入条件

- AC-1: 回答の保存後に対象を編集すると、その回答の確定は拒否され、回答は未処理のまま再確認対象として残る。
- AC-2: 同じ回答に対する確定の再試行は、最初の確定結果を返す。二つ目の判断は作られない。
- AC-3: 確定の保存途中で runtime が停止しても、再起動後に判断は高々一つで、未処理の回答は失われない。
- AC-4: 受領の記録は未処理の一覧から回答を外さない。確定または明示的な終了だけが外す。

## 対象外

- 回答が必ず処理されること（エージェントの再開は保証しない）。
- 判断の内容そのものの正しさ。

- U2: 単一選択・複数選択・自由記述に対応し、送信中の重複操作を抑止。成功・失敗・古い対象版への回答を区別して表示する。確定表示と再接続の契約C6を維持。
- U3: json-render依存、catalog、UI spec APIを除去。古い質問に残るuiデータは表示に使わず、質問・回答・判断の履歴を保持する。

今回の「残ってるUIとCLIの梱包まで進めて、一通り使えるところまで検証して」という指示に基づく実装対象。

## 観点の対応
- users・rationale: 判断する利用者が背景と帰結を読んで回答するための要求。DEC-0005とDES-0002に基づく。
- scenarios_normal: 質問があるとき、説明と候補を読み、単一選択・複数選択・自由記述で送信すると、保存した回答を確認できる。
- scenarios_exception: 初回接続が失敗したときは接続復帰後に再取得する。送信が失敗したときは入力を保持する。対象版が変わったときは回答を再確認対象として表示する。
- terms・data: prompt、options、subjects、answerは既存の質問・回答契約を使う。表示用の内部ID・版・ハッシュは補足で扱う。履歴は既存の保存契約を維持する。
- states・rules: 未回答、送信中、保存済み、反映済み、closed、stale、取消を区別する。保存と判断への反映を混同しない。
- quality・constraints: 空回答・送信中の重複操作を抑止し、HTMLを実行しないMarkdown表示とする。Reactを使い、画面JSONは使わない。表示性能の数値目標を追加する要求ではない。

- 判断画面は React のまま作る。Vite で HTML ファイル 1 枚にビルドし、Go の実行ファイルに埋め込む。Node.js は画面のビルドとテストにだけ使う。
- 既存の記録・質問・検証結果（RUN）・ジャーナルの形式は変えない。

## 棄却した案

- Node.js のまま一つの実行ファイルにする: 書き直しは要らないが、本体を TypeScript にしておく理由がないまま残り、ファイルが 140MB を超える。
- 今のまま npm の tarball で配る: Node.js を使わないプロジェクトでも Node.js 26 以上が必要になる。

## 影響

- REQ-0010（Node.js 26 以上が前提）を改訂する。
- DES-0003（npm tarball の設計）は置き換え、Go 版の設計を新しく書く。
- SPEC-0001・SPEC-0003・SPEC-0004 の確認手段を Go のテストに付け替え、配布の条件を書き換える。
- DEC-0005（判断画面を React で作る）は引き続き有効。
