## 問題

prepare-dev を使う人が、prepare-dev のソース一式を決まった場所に置いて開発用の道具を揃えなくても、どの機械・どの対象リポジトリでも同じ書き方の設定で起動して使えるようにしたい。

見えている症状は三つだが、根は一つで、「入口（CLI と MCP）が、自分がどこに置かれ、どう起動されるかを、ソースの置き場所に頼って決めている」こと。

- `init` が書く `.mcp.json` と `.codex/config.toml` に tsx とソースの絶対パスが入り、機械ごとに内容が違う（そのため git 管理から外した）。
- 入口とデーモンの起動に、道具リポジトリの `node_modules/.bin/tsx` が要る。
- デーモンが配信する UI を、道具リポジトリ内の `packages/ui/dist/index.html` という場所で探す。

## 現状

| 項目 | いま | 限界 |
| - | - | - |
| 実行 | `pnpm cli`（`tsx packages/cli/src/index.ts`）。各 package の `exports` は `./src/index.ts` を指す | `tsc -b` の設定（composite、`dist/`）はあるが、出力を `node` で起動すると `@prepare-dev/runtime` が `src/index.ts` に解決され `./errors.js` が見つからず失敗する（確認済み）。Node 26 の型除去でも同じ理由で失敗する。今日「ビルド」しても動く成果物にならない |
| 登録 | `init` が `toolRepoRoot()`（`packages/mcp/src/client.ts` の位置から逆算）と `node_modules/.bin/tsx` の絶対パスを書く。`.gitignore` で `.mcp.json` と `.codex/` を除外 | 機械ごとに `init` を実行し直す。登録を共有・コミットできない。道具リポジトリを移動・削除、または `node_modules` を消すと、全対象リポジトリの登録が黙って壊れ、ホスト側のエラーにしか出ない |
| デーモン起動 | 入口（`ensureDaemon`）が同じ絶対パスで `serve` を detached 起動。`mcp.test.ts` も同じ経路を前提 | 入口は自分自身ではなくソースの位置を知っている必要がある |

## 価値

- 登録が可搬になれば `.mcp.json` と `.codex/config.toml` を git に戻せ、clone 直後に install と起動だけで使える。
- 道具リポジトリの場所変更や再インストールが、対象リポジトリ側に波及しない。
- 「この機械でしか動かない」種類の不具合を減らし、他者が試せる状態への最短経路になる。
- 起動時間の短縮は副次的（0.25 秒 → 推定 0.05 秒程度）で、価値の中心ではない。

## 代替案

| 案 | 内容 | 評価 |
| - | - | - |
| A 作らない | 現状維持。機械ごとに `init` を実行する運用 | 工数ゼロ。限界はそのまま。所有者一人・一機械なら足りる |
| B 登録だけ可搬にする | tsx 直実行のまま、`init` が `pnpm --dir <道具リポジトリ> cli mcp` 相当を書く | 道具リポジトリの絶対パスは残り、`.mcp.json` は依然機械固有。得るものが少ない |
| C ビルド＋グローバルリンク | `tsc -b` で `dist/` を作り、`exports` と `bin`（`prepare-dev`）を `dist/` に向け、`pnpm link --global` で PATH に置く。`init` は `command: "prepare-dev"` を書く。UI の HTML はパッケージ内の相対位置で解決 | 登録は可搬。道具リポジトリの checkout と `node_modules` は必要（link は symlink）。既存の tsconfig と workspace をそのまま使える。**推奨** |
| D 単一ファイルに束ねる | esbuild 等で入口＋runtime＋プラグイン＋UI HTML を一つの JS に束ね、tarball やコピーで配る | 道具リポジトリが不要。ビルド設定が増え、sourcemap とデバッグが遠くなる。C の次の段階として自然 |
| E Node の型除去で直実行 | import 指定子を `.ts` にし `node` で直接動かす | tsx は消えるが checkout と絶対パスは残る。問題を解かない |
| F npm 公開 | レジストリに公開し `npm i -g` | 1.7 で後回しと決めた。C と D を、F を妨げない形にしておく |

## 制約

- Node >= 26、pnpm workspace、`workspace:*` 依存、各 package は `private`。`tsc -b` の project references は設定済み。
- 各 package の `exports` は一つの解決先しか持てない。ビルド後の解決先を `dist/` にすると、開発中の tsx 実行もビルドを要求する（条件付き exports や watch で回避できるが、設計で決める）。
- 入口は stdio で起動される独立プロセス。ホストは `command` と `args` の形式で登録する。
- デーモンは対象リポジトリごとに一つで、`.prepare-dev/daemon.json` で発見する。入口が detached で起動するため、入口は自分自身の実行ファイルの場所を知る必要がある。
- デーモン稼働中にビルドし直しても、稼働中のデーモンは古いコードのまま動く。`daemon.json` に版の情報はない。
- 検証プラグインが使う `vitest`（対象の `node_modules/.bin`）と `lake`（PATH）は対象リポジトリ側の道具で、配布の対象外。
- ホスト（特に GUI から起動されたもの）の PATH にグローバルの bin があるとは限らない。
- 費用: 所有者一人で、C は半日程度、D はその先に同程度（仮説）。

## 非目標

- npm レジストリへの公開と版管理（1.7 で後回し。ただし妨げない）。
- Windows 対応（`ui` の `open` と e2e が darwin／bash 前提。配布形態と独立に扱う）。
- デーモンの複数版共存と自動更新。
- 検証ツール（`lake`、`vitest`）の配布。
- UI の見た目と開発サーバの変更。
- skills の内容の変更（置き方は扱う）。

## リスク

- やらない場合: 道具リポジトリの移動や `node_modules` の削除で全対象が黙って壊れる。登録を共有できない。他者が試せない。
- やる場合: ソースとビルドの二系統が乖離する。ビルド忘れで古い `dist/` や古いデーモンが動く。`pnpm link --global` は Node の版ごとのグローバル領域に結び付き、Node を切り替えると消える。ホストの PATH に無いときの起動失敗がホストのログにしか出ない。
- 見返り: 登録の git 管理、再現性、第三者への配布の土台。

## 成功

- 中間: ビルドした入口を `node` だけで起動して `status` が返る。`init` の出力に道具リポジトリの絶対パスが含まれない。UI が簡易フォームではなく本来の UI で表示される。
- 最終: 別の対象リポジトリで `init` し、Codex と Claude Code の両方が接続し、質問の作成から UI での回答、`question_apply` までが通る。道具リポジトリを別の場所に移しても（C では再 link 後、D では無条件に）同じ登録で動く。`pnpm test` と `scripts/e2e-crash.sh` が通る。

## 用語

| 用語 | 定義 |
| - | - |
| 道具リポジトリ | prepare-dev のソースがあるリポジトリ。`toolRepoRoot()` が返す場所 |
| 対象リポジトリ | `--root` で指す、`prepare/` と `.prepare-dev/` を持つリポジトリ。道具リポジトリと同じこともある |

| ビルド成果物 | `tsc -b` が作る `dist/` と、`vite build` が作る `packages/ui/dist/index.html` |
| 配布形態 | 利用者の機械に prepare-dev の実行できる形を置く方法（ソース直実行、グローバルリンク、単一ファイル、npm 公開） |
