## 計画

本体（記録を管理するデーモン、CLI、検証プラグイン）を Go で実装し、判断画面・skills・guidance を埋め込んだ実行ファイル一つで配る。判断画面は React で作り、Vite で HTML ファイル 1 枚にビルドしたものを埋め込む。MCP の入口は作らない。

## 実行時の流れ

CLI は root の `.prepare-dev/daemon.json` を読み、書かれた URL の `/api/identity` に問い合わせて、動いているデーモンの version と build を自分のものと比べる。

| 状況 | CLI の振る舞い |
| --- | --- |
| daemon.json がなく、lease も空いている | 同じ実行ファイルを `serve --root <root>` で起動し、端末から切り離す（新しいセッション）。起動を待って接続する |
| デーモンが応答し、version と build が同じ | 接続する。置き場所が違う同じ build の写しも接続する |
| デーモンが応答し、version か build が違う | 接続しない。相手の version・build・場所・pid と、`prepare-dev stop --root <root>` で止めてから再実行することを示して終える |
| daemon.json はあるが応答せず、lease が空いている | 強制終了したデーモンの残りとみなし、daemon.json を消して起動する |
| 応答せず、lease が取られている | 起動中か、応答しないデーモンがいる。起動中なら待ち、時間内に応答しなければ pid を示して終える |

デーモンは、lease を取ってから記録を開き（走査と回復を済ませる）、127.0.0.1 の空いているポートで HTTP を始め、daemon.json（pid、ポート、URL、root、起動時刻、version と build と場所、停止用のトークン）を書く。lease はプロセスの終了とともに OS が外す。停止は `prepare-dev stop` が daemon.json のトークンで `/api/shutdown` を呼ぶ。検証ジョブの実行中は拒否し、受け付けた後の新しい操作は 409 で拒否する。デーモンは止めるまでプロジェクトごとに一つ残る。

デーモンを置く理由は三つある。人が回答している間も判断画面をいつでも開けること、回答や検証の完了を画面とエージェントの待機（`q wait`、`verify wait`）へ届けること、検証を非同期に走らせて結果を同じ書き手が記録すること。CLI がその都度ファイルロックを取って直接書く形では、画面と待機のために結局どこかで HTTP を出し続ける必要がある（代替案 no-daemon）。

## 書き手を一つにする

lease が守るのは、一つの root の永続状態（記録、質問、RUN、ジャーナル）を開くプロセスが一つだけであること。ID の採番と回答の適用は、メモリ上の索引とジャーナルを一つの書き手が持つ前提で作っている（SPEC-0001 の前提）。lease のファイルは root の中にあるので、root をどのパスで指してもロックは同じファイルに掛かる。lease を取れない `serve` は記録を開く前に終わる。

保証は作業コピーごとである。ブランチや worktree ごとの作業コピーはそれぞれのデーモンを持ち、別々に ID を採番する。マージで同じ ID の記録が二つになったら、デーモンは二つ目を問題（status の problems）として示し、どちらも書き換えない。番号の付け直しは人が行う。

## データの形式

記録の Markdown（YAML の frontmatter）、質問と RUN の JSON（2 文字の字下げ）、ジャーナル（JSON Lines）の形式は TypeScript 版から変えない。読み書きしてもバイト列が変わらないことを求める理由は三つある。記録は Git に入れて差分で読むので、書き直しで変わるのは変えた項目だけでなければならない。記録ファイルの sha256 はその版で、質問・判断・レビュー・RUN が参照している。TypeScript 版との切り替えでファイルを書き換えない。

基準は TypeScript 版の最後のコミット（342bc64）が書いたファイルの写し（internal/core/testdata/ts-342bc64）で、テストはこの写しと現在の prepare/ の両方を読み直して書き出す（SPEC-0004 D1）。YAML の書き出しは npm の yaml パッケージに合わせて自前で実装した。書く前に読み戻し、内容が一致しなければ書かない。YAML 1.1 の読み手が改行とみなす文字（U+2028、U+2029、U+0085）と制御文字は、二重引用符の中でエスケープする。

## HTTP API

経路は標準の ServeMux で振り分ける。判断画面と CLI が使う経路は次のとおり。

| 経路 | 用途 |
| --- | --- |
| `GET /api/identity` | pid、root、起動時刻、version・build・場所 |
| `POST /api/shutdown` | 停止（daemon.json のトークンが必要） |
| `GET /api/status` | 未処理の回答、回答待ちの質問、未対処の指摘、適用できない証拠、記録されなかった検証、問題 |
| `GET/POST /api/records`、`GET/PUT /api/records/:id` | 記録の一覧・作成・取得・更新（更新は読んだ版が必要） |
| `GET/POST /api/questions`、`GET /api/questions/:id`、`GET /api/pending` | 質問の一覧・作成・取得、未処理の回答 |
| `POST /api/questions/:id/answers` | 回答（判断画面からだけ） |
| `GET /api/questions/:id/wait` | 回答を待つ |
| `POST /api/questions/:id/answers/:aid/ack`、`.../apply`、`.../close`、`POST /api/questions/:id/cancel` | 受領、判断への適用、終了、取り消し |
| `GET/POST /api/runs`、`GET /api/runs/:id`、`GET /api/runs/:id/wait` | 検証の一覧・開始・取得・待機 |
| `GET /api/trace/:id`、`GET /api/bundle`、`GET /api/plugins` | trace、レビュー資料、プラグイン一覧 |
| `GET /events` | 変更の通知（SSE） |
| `GET /`、`GET /q/:id` | 判断画面 |

Host が `127.0.0.1:<port>` か `localhost:<port>` でない要求と、Origin が自分以外の要求は 403 で拒否する。回答は判断画面の人のものなので、Origin を持たない要求（ブラウザ以外）も拒否し、CLI に回答の操作を置かない。エラーは `{error, message, details}` の形で返し、500 は daemon.log にも書く。同じ利用者の別のプロセスが Origin を偽って送ることは防がない（範囲外）。

## CLI

コマンドは `init`、`status`、`ui`、`pending`、`record create|get|put|list`、`q create|list|show|wait|pending|ack|apply|close|cancel`、`verify run|wait|get|list`、`trace`、`bundle`、`serve`、`stop`、`guidance`、`version`。`mcp` と `q answer` は無い。出力は JSON で、`status` は既定で文章（`--json` で JSON）。エージェントが読む `verify` と `trace` は、入力ファイルの一覧を件数に、不一致と実行したテストの一覧を先頭の 5 件と残りの数に縮め、`verify list` は実行ごとの要約にする。`--json` で全体を出す。

## init と skills

`init` は `.prepare-dev/config.json` がなければ作り（あれば変えない）、skills を `.agents/skills` と `.claude/skills` にコピーし（`--skills-dir` で変更、`--no-skills` で省略）、デーモンを起動する。MCP の設定は書かない。

skills のコピーは、入れた skill の digest を `.prepare-dev/skills.json` に残す。次の `init` では、無い skill を入れ、同じ内容なら何もせず、前に入れたときのまま編集されていない skill は新しい版に置き換える。それ以外の違い（利用者の編集、別の方法で置いたもの）は残して conflicts に示す。`--replace-skills` を付けると、違うものを `.prepare-dev/skills-backup/<時刻>/` に移してから置き換える。root の外、シンボリックリンク、ディレクトリでない配置先は触らずに示す。

## 判断画面のビルド

ui/ の `pnpm build` が build/index.html、画面に入れた npm パッケージのライセンス（build/THIRD_PARTY_NOTICES.txt）、ビルドの元にしたソースの digest（build/source.sha256）を書く。Go のテスト（SPEC-0004 B1）とリリースのスクリプトは、今のソースの digest と照合し、違えば失敗する。Node.js（pnpm・Vite）は画面を直す人だけが使い、prepare-dev のビルドと利用には要らない。

## 検証プラグイン

- lean4: `lake env lean --src-deps` を再帰的に使って入力を集め、`lake build` と `#check`・`#print axioms` で確かめる。
- vitest: テスト・追加実装・Vitest の設定から、esbuild のバンドルと同じ規則（相対パス、package.json の main・exports、tsconfig の paths、node_modules にリンクしたワークスペース）で import をたどり、esbuild が読み込むファイルを入力にする。node_modules の中のパッケージは manifest と lockfile で代表する。型だけの import は実行時に読まれないので入力にしない。Vite の設定で決まる解決は評価しない（SPEC-0003 V1）。
- gotest: `go list -deps -test -json` で、テストがビルドするパッケージのファイル（Go・cgo・C・アセンブリ・ヘッダー・syso・埋め込み）を、メインモジュール・ローカルの replace 先・vendor について集める。テストが実行中にビルドするパッケージ（`input_packages`）と読むファイル（`data_files`）も設定で加える。`go test -json -count=1` で、テストのキャッシュを使わずに実行する（SPEC-0003 V3）。

どのプラグインも、使った道具の場所を RUN の `tool.extra` に残す。デーモンは起動した CLI の PATH に `~/.elan/bin`・`~/.cargo/bin`・`~/.local/bin` を足して道具を探す。

## 配布と開発

`go run ./scripts/release -version <v>` で macOS と Linux（arm64・amd64）向けの実行ファイルを作り、README と第三者ライセンスとともに tar.gz にまとめ、sha256 を `dist/artifact.json` に残す。画面のビルドがソースと合わなければ作らない。パッケージ管理サービスへの公開はしない。配布物そのものは、展開した実行ファイルを `PREPARE_DEV_E2E_BINARY` に渡して e2e テストで確かめる。

開発中は checkout で `go run ./cmd/prepare-dev` を使う。ソースを変えると build が変わるので、前のデーモンを `prepare-dev stop` で止めてから使う。

## TypeScript 版からの移行

TypeScript の本体（packages/ の core・runtime・mcp・cli、plugins/、scripts の build.mjs・pack.mjs、ルートの package.json・pnpm・tsconfig・vitest の設定）を消し、画面を packages/ui から ui/ に移す。実プロセスの強制終了からの回復を確かめていた scripts/e2e-crash.sh は Go の e2e テストに移す。このリポジトリの `.mcp.json` と `.codex/config.toml` の登録を消す（DEC-0007）。

切り替えるときは、TypeScript 版のデーモンを `prepare-dev stop` で止め（停止の API は同じ）、エージェントの MCP 設定から `prepare-dev mcp` を消し、`prepare-dev init --replace-skills` で skills を置き換える。TypeScript 版と Go 版の lease は仕組みが違うので、同じ root で両方のデーモンを動かさない。片方が動いていて応答する間は、もう片方の CLI は build の違いで接続を拒み、デーモンを起動しない。戻すときは Go 版のデーモンを止め、commit 342bc64 の TypeScript 版を使う。記録の形式は同じで、Go 版で増えたもの（gotest の RUN、skills.json）は TypeScript 版では使われない。

移行は、TypeScript の本体が残っていないこと、SPEC-0001・SPEC-0003・SPEC-0004 の主張の RUN が今の版に当てはまること、配布物を別の場所で動かした確認が記録されたことで完了とする。確認の結果は docs/2026-11-09-go-verification.md に記録する。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 自前の YAML 書き出しが npm の yaml と違う書き方をする | TypeScript 版の写しで往復のバイト一致を確かめ、書く前に読み戻して違えば書かない |
| 埋め込む画面のビルドがソースとずれる | ビルドにソースの digest を記録し、テストとリリースで照合する |
| 強制終了したデーモンの daemon.json が残る | lease が空いていれば古いものとして消す。pid は使わない |
| デーモンが起動時の PATH を使い続ける | 道具の場所を RUN に残す。道具を入れ替えたら止めて起動し直すと案内する |

## 要求
prepare-dev を OS とアーキテクチャごとの実行ファイル一つで配り、使う人の環境に Node.js などの言語処理系を求めない。検証器（Lean・Vitest・Go など）は、検証する環境に利用者が用意する。エージェントは skills の手順に従って CLI を使い、人は判断画面で回答する。MCP の入口は提供しない（DEC-0007）。prepare-dev 自体の開発者は、配布物を作らずにソースの checkout から動かせる。

## 用語
- 対象プロジェクト（root）: prepare-dev が記録を置くディレクトリ。パスの書き方が違っても、同じディレクトリなら同じ対象プロジェクト。
- 実行ファイル: OS とアーキテクチャごとの `prepare-dev`。配布物は、それを含む tar.gz。
- build: 実行ファイルの内容。内容が同じなら、置き場所が違っても同じ build。
- 書き手: 対象プロジェクトの記録・質問・検証記録を書き換えるプロセス。CLI はこれを通して記録を扱う。
- skills の配置先: 対象プロジェクトの `.agents/skills` と `.claude/skills`。利用者は別の場所を指定するか、コピーしないことを選べる。
- 利用者の設定: 対象プロジェクトに既にある prepare-dev の設定（`.prepare-dev/config.json`）と、エージェントの設定ファイル（MCP の設定など）。

## 受入条件
- P1: 別の場所に置いた実行ファイルだけで help・version、init、status、ui、record、q、trace、verify が動く。元の checkout を参照せず、Node.js と Go が PATH に無くても動く。verify は、検証器が環境にあるプラグイン（受入では Lean）で確かめる。
- P2: init は skills を配置先にコピーし、MCP の設定を書かず、利用者の設定を変えない。同じ内容なら何も変えない。利用者が編集した skill は上書きせずに差異を報告し、利用者が求めたときだけ退避してから置き換える。prepare-dev が入れて編集されていない skill は、新しい版で更新できる。
- P3: 一つの対象プロジェクトの書き手は同時に一つだけ。CLI は必要なときに書き手を起動し、止めて起動し直せる。異なる build の書き手には黙って接続せず、動いている build と止め方を示す。書き手が異常終了しても、利用者が手で後片付けをせずに次の操作を続けられる。
- P4: 独立したプロジェクトで、要求作成→質問→判断画面で回答→DEC→SPEC→実装→実際の検証器での RUN→trace を通す。パッケージ管理サービスへの公開は対象外。

旧 REQ-0002〜0008（配布と起動の要求。いずれも superseded）の、機械固有のパスを書かない、配布物だけで動く、UI を同梱する、ソースから開発できる、という意図を引き継ぐ。DIS-0001 の案 G（skills を利用者単位の置き場に置き、MCP の登録を軸に段階を分ける案）は採用しない。

## 観点の対応
- users・rationale: 別プロジェクトで prepare-dev を使う利用者と、CLI を呼ぶエージェントのための要求。DEC-0004・DEC-0006・DEC-0007 に基づく。
- scenarios_normal: 実行ファイルを置いて init すると、skills と記録の操作を使える。質問・回答・判断・検証を同じ対象プロジェクトに記録し、trace で追う。
- scenarios_exception: 同時に起動しても書き手は一つになる。異なる build の書き手が動いていれば接続せず、止め方を示す。書き手が異常終了した後も次の操作で続けられる。利用者が編集した skill は上書きせずに報告する。検証の実行中は停止を拒否する。
- terms・data: 上の用語のとおり。配布方式を変えても、過去の質問・判断・RUN のファイルを書き換えない（読み直して書き出しても内容が変わらない）。
- states・rules: 書き手が無い、起動中、動いている、停止中、異なる build が動いている、異常終了の残りがある、を区別する。書き手を一つにし、利用者の設定と skill の編集を守る。
- quality・constraints: checkout・Node.js・Go に依存しない。macOS と Linux（arm64・amd64）、loopback 接続が前提で、Windows は対象外。判断画面を直す開発者だけが Node.js を使う。検証器は利用者が用意する。
- priority・acceptance: must。SPEC-0004 の P1〜P3・B1・D1 と、配布物による一連の利用の記録（P4）で確認する。

coverage の decided は観点の扱いが決まっている意味であり、全ホスト・全 OS での確認済みの意味ではない。実行環境と確認した範囲は docs/2026-11-09-go-verification.md に記録する。

# 回答の適用

本仕様は、人間の回答を判断（decision）として確定する手順と、中断からの回復を定める。対象は runtime の永続状態であり、プロセス内の一時状態は含めない。中断後に残るのは永続状態だけだからである。

## 1. 永続状態

| 要素 | 内容 |
| - | - |
| `records` | 記録 id → 現在の版 `{rev, sha256}`。質問の対象になる要求・仕様など |
| `questions` | 質問 id → `{subjects, answers}`。`subjects` は作成時に写した対象の版の一覧 `[{id, rev, sha256}]` |
| `answers` | 回答 id → `{question, subjects_at_answer, stale, received, closed, applied_as}`。`subjects_at_answer` は回答を保存したときの対象の現在の版の写しで、`stale` の判定の根拠として残す。`applied_as` はファイル上の適用印で、確定の写し |
| `decisions` | 存在する decision ファイルの集合。各 decision は `{id, txid}` を持つ |
| `journal` | 追記のみの列。要素は `intent {txid, answer, decision_id, subjects}`、`commit {txid}`、`abort {txid}`。実装のジャーナル（`prepare/events.jsonl`）ではそれぞれ `apply.intent`、`apply.commit`、`apply.abort` の行 |

実装では、記録は `prepare/<種類>/<id>.md`、質問と回答は `prepare/questions/<id>.json`、decision は `prepare/decisions/<id>.md` にある。ジャーナルには記録の書き込みや削除（`record.write`、`record.remove`）などの行もあるが、この仕様の状態には含めない。`.prepare-dev/index.json` は起動を速くするための補助で、無くても再構成できる。

導出する状態。

- `committed(a)`: `intent(tx, a)` と `commit(tx)` が存在する。
- `inflight`: `commit` も `abort` もない `intent` が存在する。
- `recovery_pending`: `inflight`、または abort 済み取引の仮 decision・仮適用印・未更新の stale 状態が残っている。`inflight = false` だけでは回復完了を意味しない。
- `public_decisions`: `decisions` のうち `txid` が commit 済みのもの。
- `pending`: 保存済みの回答のうち、`committed` でも `closed` でもないもの。`received` や `stale` は条件に含めない。

## 2. 操作

通常の操作は `recovery_pending = false` のときだけ受け付ける。回復が必要なときは先に `recover` を完了する。API の質問取得・未処理回答・変更の通知（SSE）は journal から確定を判定し、未確定の `applied_as` を公開しない。質問全体に別の確定済み回答があっても、各回答を個別に判定する。

| 操作 | 前提 | 効果 |
| - | - | - |
| `create_question(q, subjects)` | 対象の記録が存在 | 対象の現在の版を写して質問を保存 |
| `edit(r)` | デーモン停止中、または操作と操作の間 | 記録 `r` の `rev` を 1 増やし `sha256` を変える（外部編集） |
| `save_answer(q, a)` | 質問が存在 | 回答を保存し、対象の現在の版を `subjects_at_answer` に写す。そのいずれかが `q.subjects` と異なれば `stale = true` |
| `ack(a)` | 回答が存在 | `received = true`。`pending` には影響しない |
| `close(a)` | `¬committed(a)` | `closed = true` |
| `apply(a)` | 下記 | 下記 |
| `recover()` | なし | 下記 |

### 2.1 `apply(a)`

1. `committed(a)` なら、その `decision_id` を返して終わる（再試行は同じ結果）。
2. `closed(a)` なら拒否する。
3. `a.stale` であるか、`q.subjects` のいずれかが現在の版（`rev` と `sha256` の両方）と一致しなければ、`a.stale = true` にして拒否する。
4. 段階 a: `decision_id` を採番し、`intent {txid, a, decision_id, subjects = q.subjects}` を journal に追記する。
5. 段階 b: decision ファイル `{decision_id, txid}` を書く。
6. 段階 c: 回答に `applied_as = decision_id` を書く。
7. 段階 d: `commit {txid}` を journal に追記する。

段階の名前は実装の中断点（`--crash-after`、適合テストの操作列の `crash_after`）でも使う: 段階 a が `intent`、b が `decision`、c が `question`、d が `commit`。段階 a の追記以降、どの段階の後でも中断（crash）が起こりうる。中断後は `inflight` となり、`recover` が完了するまで通常の操作は受け付けない。

### 2.2 `recover()`

`inflight` の `intent` について、

- `intent.subjects` のすべてが現在の版（`rev` と `sha256`）と一致すれば、同じ `decision_id` で段階 b、c、d のうち未完了のものを順に行う（ロールフォワード）。
- 一致しなければ (1) `abort {txid}` を追記、(2) 仮 decision ファイルを削除、(3) 回答の `applied_as` を外して `stale = true` を保存する。各書き込みの後に再中断できる。`abort` 後は `inflight = false` になるが、清掃が終わるまで `recovery_pending = true` とする。
- 起動時には abort 済み取引も走査し、残存する仮 decision と回答を再清掃する。既に済んだ書き込みは繰り返しても結果を変えない。再中断は保存状態をそのまま残し、次の起動も同じディスク状態から再開する。

確定済み（commit 済み）の取引は、その後に対象の版が変わっても abort しない。

## 3. 主張

| 主張 | 内容 |
| - | - |
| C1 | 任意の到達可能な状態で、各回答について commit 済みの `intent` は高々一つ。`public_decisions` の各要素は commit 済みの `intent` と一対一に対応する |
| C2 | commit 済みの各取引について、`intent.subjects` は質問の `subjects` と一致し、その回答は `stale` ではない。commit は、現在の版が `intent.subjects` と一致する状態でのみ起こる |
| C3 | 保存済み回答はすべての遷移で保持される。`recovery_pending = false` の状態で、(i) 保存済みの回答は存在し続ける、(ii) `applied_as` が付いている ⟺ `committed`、(iii) decision ファイルが存在する ⟺ その `txid` が commit 済み、(iv) `pending` はファイルから計算しても journal から計算しても同じ集合になる |
| C4 | 第4節の形式でモデルが生成した操作列を Go 実装に流したとき、各段階の観測結果がモデルと一致する |

C1 から C3 は操作単位の Lean モデルで証明する。C2 は `committed_safety` が状態と確定時の版照合をまとめ、C3 は `quiescent_with_answers` が回答保持と整合性をまとめる。モデルは `apply` の段階 a〜d と中断を含むが、`recover` の内部は一操作に抽象化している。その内部の取り消し清掃は C5 のモデルで別に扱う。操作単位のモデルの `inflight = false` は清掃完了後の状態に対応し、実ディスク上の清掃途中を含めない。

### C5: 回復途中の再中断

`model/PrepareDev/Spec/Recovery.lean` は、対象版が変わった未確定取引一件の abort 記録、decision の有無、適用印、stale 状態、保存した回答をモデルにする。`resume` は次の一つの保存段階、`crash` は保存状態を変えない中断。任意の有限な操作列で回答を保持し、続けて三回 resume すれば清掃が完了し、完了状態は再回復で変わらないことを `PrepareDev.Recovery.recovery_safe` で証明する。中断が永久に続く場合の進行は保証しない。段階は abort ログ、仮 decision の削除、回答 JSON の更新という三つの状態変更であり、補助的な index や record.remove ログの更新回数は数えない。

`lake exe prepare-model recovery` が生成する 48 本の操作列（`model/traces/recovery.jsonl`）を `internal/runtime/recovery_test.go` で実装へ流す。48 本は、apply の三つの中断点（段階 a・b・c の後。その後に対象を編集して取り消しの回復に入る）ごとに、最初の四手を `resume`（次の保存段階を一つ行う）か `crash`（何も保存せずに中断する）にした 16 通りで、その後に `resume` を四回続ける。形式は第4節の終わりに書く。各保存段階の後に中断し、実ファイルの状態、回答保持、回復待ち中の通常操作拒否、未確定印の非公開を比較する。モデル上の証明と、実装について実行した trace の範囲の適合テストを区別する。

### C6: 公開する確定状態と回復待ち

API の質問取得・未処理回答・通知は `apply.commit` を根拠に各回答の `applied_as` を組み立てる。保存途中の仮適用印は公開しない。通常の質問操作は清掃中も拒否する。`internal/runtime` の `questions_test.go` と `recovery_test.go` の `[C6]` を同じ検証実行に含める。C6 は実装テストによる保証であり、C5 の Lean 定理が API や UI を証明するという意味ではない。実プロセスでの確認として、`internal/e2e` の `[C3]` は段階 c と d の後にデーモンのプロセスを終わらせ、停止中に対象を編集してから起動し直し、取り消しと確定の維持を確かめる。

## 4. 適合テストの操作列の形式（C4 用）

モデルの実行可能定義が操作列を列挙し、各段階の後の観測を JSON Lines で出力する。Go 側は同じ操作を実装に対して行い、観測を比較する。ここでの操作列（trace）は、記録のつながりを表示する `prepare-dev trace` とは別のもの。

生成は `cd model && lake exe prepare-model gen --depth N [--max-traces M] [--seed S]`。記録 R1・R2、質問 Q1（対象 R1）・Q2（対象 R1 と R2）、回答 A1・A2 の上で、長さ N までの操作列を決定的な深さ優先で列挙し、M 本（既定 2,000）で打ち切る。`model/traces/depth-4.jsonl` は depth 4 の全 165 本、`model/traces/depth-6.jsonl` は depth 6 の先頭 2,000 本。`model/bin/test` は両方とリカバリーの操作列をモデルから作り直し、保存しているファイルと一致することを確かめる。

`internal/runtime/conformance_test.go` は環境変数 `PREPARE_DEV_TRACES`（リポジトリのルートからのパス）のファイルを、無ければ depth-4 を流す。このリポジトリの検証実行は `.prepare-dev/config.json` の gotest の設定で depth-6 を流し、操作列のファイルを入力（`data_files`）として記録する。

一行の形式。

```json
{"trace": 12, "step": 3, "action": {"type": "apply", "answer": "A1", "crash_after": "question"}, "observe": {"inflight": true, "pending": ["A1"], "committed": {}, "closed": [], "stale": [], "public_decisions": [], "result": "crashed"}}
```

`action.type` と引数。

| type | 引数 | 意味 |
| - | - | - |
| `create_question` | `question`, `subjects: [record]` | 2章の `create_question` |
| `edit` | `record` | 外部編集 |
| `save_answer` | `question`, `answer` | 回答の保存 |
| `ack` | `answer` | 受領 |
| `close` | `answer` | 終了 |
| `apply` | `answer`, `crash_after: null \| "intent" \| "decision" \| "question"` | 適用。`crash_after` があれば、その段階まで行って中断する |
| `recover` | なし | 回復 |

記録 id は `R1`、質問は `Q1`、回答は `A1`、decision は採番順に `D1`、`D2` … とする。実装側は自分の id 体系へ対応づける。

`observe` の項目。

| 項目 | 内容 |
| - | - |
| `inflight` | 進行中の取引があるか |
| `pending` | `pending` に含まれる回答 id の昇順一覧 |
| `committed` | 回答 id → decision id |
| `closed` | `closed` の回答 id の一覧 |
| `stale` | `stale` の回答 id の一覧 |
| `public_decisions` | 公開される decision id の一覧 |
| `result` | 直前の操作の結果。`ok`、`applied`、`already_applied`、`rejected_stale`、`rejected_closed`、`rejected_inflight`、`crashed`、`recovered_forward`、`recovered_abort`、`noop` |

操作列の生成は決定的で、同じ入力から同じ出力を得る。中断後は `edit` と `recover` だけを生成し、`recover` の後に通常の操作へ戻る。

### 回復の操作列（C5 用）

一行が一本の操作列で、`{"stage": "intent"|"decision"|"question", "initial": 観測, "steps": [{"action": "resume"|"crash", "observe": 観測}]}` の形。`stage` はどの段階の後に中断したか。観測は `answer`（保存されている回答の数）、`aborted`（abort が記録済み）、`decision`（仮 decision のファイルがある）、`applied`（回答に適用印がある）、`stale`、`ready`（清掃が完了し `recovery_pending = false`）。

## 用語

- 検証の実行（RUN）: `verify run` 一回。結果を `prepare/runs/RUN-NNNN.json` に、検証器の出力（レポートやログ）を同じ名前のディレクトリ `prepare/runs/RUN-NNNN/` に置く。
- targets: `verify run --target` で渡す対象のファイル（テストファイル、証明のファイル）。
- project_dir: 検証器を動かすディレクトリ。ルートからの相対パスで、プラグインの設定（`.prepare-dev/config.json` の `plugins.<名前>`、または `--config-json`）に書く。
- impl_files: import をたどっても見つからない入力を、利用者がルートからの相対パスで列挙する設定。Vitest ではここからも import をたどる。
- input_packages・data_files: Go のテストが実行中にビルドするパッケージと、実行中に読むファイル（ルートからの glob）を列挙する設定。
- 現在の版に当てはまる: RUN が記録した入力・対象・主張の版（内容の sha256）が、今のファイルとすべて一致すること。

## 契約

検証の結果は、記録した入力の内容が今も同じである限りにおいて現在の版の証拠になる。プラグインは結果を左右するファイルを入力として記録し、runtime は入力のどれかが変わるか消えたら、その RUN を現在の版に当てはまらないものとして扱う。

Vitest（V1）は、テスト、impl_files、Vitest の設定ファイルを起点に、esbuild でバンドルするのと同じ規則（相対パス、package.json の main・exports、tsconfig.json の paths、node_modules にリンクしたワークスペースのパッケージ）で import をたどり、esbuild が読み込むファイルを記録する。JavaScript・TypeScript・JSON・CSS 以外の import されたファイルは、記録するが中はたどらない。型だけの import は実行時に読み込まれないので記録しない。node_modules の中に解決されたパッケージは記録せず、入力の上位ディレクトリ（ルートまで）の package.json、pnpm-lock.yaml、package-lock.json、npm-shrinkwrap.json、yarn.lock、bun.lock、bun.lockb、pnpm-workspace.yaml、.npmrc、tsconfig.json で代表する。

Go（V3）は、テストがビルドするパッケージのうち、メインモジュール、ローカルのディレクトリへ replace したモジュール、vendor のものについて、Go・cgo・C・C++・アセンブリ・ヘッダー・syso と埋め込みのファイルを記録する。テストファイルは実行するパッケージのものだけを含める。input_packages のパッケージも同じ規則で含め、data_files と impl_files のファイル、go.mod・go.sum・go.work・go.work.sum・vendor/modules.txt を加える。`go test -json -count=1` で、キャッシュした結果を使わずに実行する。

どのプラグインも、使った検証器の場所を RUN の `tool.extra` に残す。

## 検証

internal/plugin/vitest の [V1] で、推移的な依存と metadata の収集、変更の反映、解決の規則（tsconfig の paths、ワークスペースのリンク、import した素材、型だけの import と node_modules を含めないこと）を検査する。internal/runtime の [V1] で、記録済みの入力の変更・削除による適用の無効化を検査する。二つのテストファイルを同じ verify_run の targets に含める。internal/plugin/gotest の [V3] で、入力の収集（実行中にビルドするパッケージ、data_files、Go 以外のソース、ローカルの replace 先、依存先のテストファイルを含めないこと）、変更の反映、テスト名から主張への対応を検査する。これらは実行したケースの範囲のテストであり、任意の動的な依存を自動で見つける証明ではない。

## V2: 実行中ジョブの識別

単一 runtime で検証を開始するとき、結果 JSON の完成前に作る RUN のディレクトリを ID の予約として扱う。次の実行と再起動後の採番はその予約を使用済みとして数える。異なるジョブが結果・ログを共有してはならない。結果を書く前にデーモンが止まった RUN は、status の `runs_incomplete` に示す。internal/runtime の [V2] で、非同期の完了を止めたまま二つのジョブを起動し、ID と保存先の分離、および再起動後の非再利用を確かめる。RUN-0006 は二つのジョブが同じ ID を使った実行で、証拠に使わない。

## 根拠

検証の結果が「今の」実装と仕様の証拠であることを、記録した入力の内容で判断するための契約。DEC-0006 で prepare-dev 本体を Go へ移したため、本体の証拠は gotest で記録する。Vitest の規則（V1）は、判断画面（ui/）と、TypeScript のプロジェクトを検証するときの契約として残す。

## 採用

`hold`: 回答は保存するが、対象の `rev` か `sha256` が質問作成時と異なる場合は `stale` として未処理一覧に残し、`question_apply` は拒否する。

## 理由

- 回答はその時点の文書を読んで下した判断であり、文書が変われば別の対象に対する判断になる（REQ-0001 の根拠）。
- 回答そのものは人の作業の成果であり、失わない。再確認で現在版を読み直せば再利用できる。

## 棄却した代替案

- `apply`（そのまま反映）: 古い版への判断を新しい版の判断として扱うことになり、理由と結論の対応が壊れる。
- `discard`（破棄）: 人の回答を黙って捨てることになり、何を聞いて何が答えられたかの記録が残らない。
