## 要求

人が、判断画面のアプリで、仕様の一つについて次の四つを見られる。

1. 何の話かが分かる例。仕様が扱う場面を、具体的な一件で順に見せる。
2. 仕様が約束していること。その約束が無いと何が困るかと並べて見せる。約束ごとに、元になった仕様の主張を示す。
3. 試せる画面。人が「途中で起きること」を選ぶと、仕様がどう答えるか（何を確かめ、どう終わり、後に何が残るか）が、流れの図と並んで出る。「途中で起きること」は、仕様が備えている出来事である。SPEC-0001 では、「人が答えた後に、質問の対象の文書が書き直された」「書き込みの途中で prepare-dev が落ちた」などがある。
4. 理解の確認。人が問いに答えると、正しいかどうかと理由が出る。

説明の文は、仕様の本文にある内部の言葉や記録の番号を知らなくても読めるものにする。

最初に対象にする仕様は、SPEC-0001（回答の適用）の一つである（DEC-0018）。

## 根拠

人が 2026-11-10 のチャットで指摘した。「全然pdd-kitのスピリットを感じないんだよね」「ずとかもないし、ダイアグラムもない」「Run a login against the spec　みたいなのもない」。PDD Kit は、prepare-dev が参考にした既存の仕組みである（REC-0001）。人の言葉は、PDD Kit の紹介にある、仕様の図と、仕様に当てて試せる画面を指している。

今の判断画面のアプリで人が見られるのは、質問の文章と表と、対象の記録の本文だけである。画面は質問の画面一つで、図を描く部品も、仕様を試す画面も無い（ui/src）。

SPEC-0001 を題材に、上の四つを一枚にした試作を作った。版は三つで、直したのは二回である。画面の形は一版目から方向が合っていた。直したのは例と文言で、仕様の中の言葉と記録の番号をそのまま使い、誰が何をするのかを書いていなかった。三版目に、人は「いいんじゃない大枠は」と言った。試作は本体の外にあり、リポジトリには入れていない。経緯は DEC-0018 にある。

理解の確認は、人が指摘で挙げたものではない。試作に入れてあり、三版目の感想の対象に含まれていた。答えは保存しないので、人が自分で分かったかを確かめるためのもので、分かったことの記録にはならない。

問題の整理（DIS）は書いていない。この人とこの仕様については、問題が、人の指摘と試作への感想で具体的に分かっているためである。prepare-dev を使うほかの人に同じ問題があるかは、確かめていない。

## シナリオ

通常の場合。

- S1: 説明が用意されている仕様がある。人がその仕様のページを開く。例、約束、試せる画面、理解の確認が出る。人がどこから仕様のページを開くかは、設計で決める。
- S2: S1 のページで、人が「途中で起きること」を一つ選ぶ。その場面で仕様がどう答えるかと、図の上で通った道が出る。
- S3: S1 のページで、人が理解の確認の問いに答える。正しいかどうかと理由が出る。その問いが扱っている場面を、試せる画面で開ける。

例外の場合。

- X1: 説明がまだ無い仕様のページを、人が開く。説明が無いことが分かり、仕様の本文は読める。
- X2: 説明を用意した後で、仕様が変わった。人がそのページを開く。説明が前の版の仕様に基づいていることが分かる。
- X3: 説明のデータが読めない（壊れている、形が違う）。人がそのページを開く。画面は止まらず、読めないことと、どの仕様の説明かが分かる。
- X4（中断と再試行）: ページを開いている間に、prepare-dev との接続が切れた。接続が戻ると、人が操作し直さなくても、ページは今の内容を取り直す。

## 受入条件

- AC-1: 説明が用意されている仕様のページを開くと、例、約束、試せる画面、理解の確認が出る（S1）。約束には、元になった仕様の主張が付く。説明は SPEC-0001 について用意する。
- AC-2: 試せる画面に出る終わり方と、後に残るものは、人が選べるすべての場面について、その仕様のモデルが出す結果と同じである。同じであることを、検証の実行（RUN）で確かめられる（S2）。何を確かめたかと、図の上で通った道を、モデルの結果とどう結び付けるかは、設計で決める。
- AC-3: 理解の確認は、答えると正誤と理由が出る。その問いが扱っている場面を、試せる画面で開ける（S3）。
- AC-4: 説明が無い場合、古い場合、読めない場合に、それぞれそうと分かり、画面が止まらない（X1〜X3）。接続が戻ると取り直す（X4）。
- AC-5: 説明の文は、仕様の内部の言葉と記録の番号を、説明なしに使わない。会話の経緯を知らない読み手に説明の文だけを読ませ、「何の話か」と「約束が無いと何が困るか」を言い直せることを、確認記録に残す。読み手を人にするか AI にするかと、確かめ方の手順は、設計で決める（DEC-0018）。約束に付ける元の主張は、仕様の文そのままなので、ここで言う説明の文には入らない。

## 制約

- 配るのは実行ファイル一つのままにする（REQ-0010）。
- 説明の中に書かれたプログラムや HTML を、画面で実行しない。説明を記録にしても、しなくても同じである（REQ-0009 の「HTMLを実行しないMarkdown表示」と同じ考え）。説明は AI が書くもので、判断画面のアプリと同じ画面に出る。そこでプログラムが動くと、AI の書いたものが、人の代わりに質問に答えられてしまう。
- 画面から、仕様や説明を書き換えない。

## 対象外

- SPEC-0001 以外の仕様の説明を書くこと。モデルが無い仕様で試せる画面をどうするかも、その仕様の説明を書く時に決める。
- 取り消しの途中でまた落ちる場面（SPEC-0001 の主張 C5）を、試せる画面で扱うこと。
- 理解の確認の答えを保存すること。
- 表示の速さの数値目標。

一つ目は、この見せ方を、どの仕様まで使えるようにするかである。どちらを選んでも、最初に説明を用意するのは SPEC-0001 だけである。どちらを選ぶかで、作るものの大きさと、足す必要がある要求が変わる。

| 案 | 足す必要がある要求、困ること |
| - | - |
| prepare-dev を使うどのプロジェクトの仕様でも、説明を用意すれば出せる仕組みにする | モデルが無い仕様で何を出すか。説明を書く側（AI）の手順と、書いた時の検査。説明のデータの形を、prepare-dev の版が変わっても読めるようにすること。上の S1・AC-1・AC-2 は、モデルがある仕様についてしか決めていない。DEC-0018 は、ほかの仕様が同じ形に乗るかを設計で確かめるとした。この案は、それを確かめる前に、広げると決めることになる。ほかの人に同じ問題があるかも、確かめていない |

二つ目は、次の機能を要求に入れるかである。prepare-dev の作りにわざと間違いを一つ入れた場合を人が選ぶと、どの約束が破れるかが出る。試作にはある。入れるなら、間違いを入れた場合の結果を何が出すかを、設計で決める必要がある（今のモデルには、間違いを入れた版が無い）。

### レビューで足りないと指摘され、足すかどうかを人に聞くこと

次の四つは、レビューで足りないと指摘された。どれも、決めるには要求に新しい決まりを足す必要がある。足すかどうかを、一つずつ人に聞く（今足す、設計で案を作ってから決める、足さない）。

- 説明の中身のうち、モデルと照らせないものが、仕様と食い違わないことを、確かめるようにするか。照らせないものは、例、約束の言い直し、場面の言葉とモデルに与える操作の並びの対応、理解の確認の正解と理由である。説明が間違っていると、人は間違ったものを確かめることになり、説明が無いより悪い。
- 仕様が変わった時に、説明をいつ、誰が直すかを決めるか。
- 試せる画面の結果をモデルと照らした後で、説明かモデルが変わった時に、照らし直されていないことを、人が分かるようにするか。説明は仕様とは別に何度も直すので、モデルだけが変わる場合より多く起きる。今の四つの状態（無い・ある・古い・読めない）は、仕様の版しか見ない。
- 説明が扱っていないものを、ページで示すか。書き手が約束に選ばなかった主張、仕様の前提、仕様が約束していないことがある。示さないと、人は一部を見て、仕様の全部を見たと受け取る。試作には、仕様が約束していないこと、仕様の前提、テストで確かめる主張を出す節がある。上の要求の四つに入れていなかったのは、書き漏らしである。

### 設計で決めること

- AC-5 の読み手と手順。言い直しを何と照らして合否にするか。
- 人が質問に答えた時に見ていた説明の版を、回答や決定に残すか。説明を仕様とは別にすると、回答と決定に残るのは仕様の版だけで、間違った説明を見て確定した決定が、説明を直した後も今のものとして残る。
- 接続が戻って取り直した後に、選んでいた場面と、答えかけの問いを残すか。
- 図の部品などで、埋め込む画面と配布物がどれだけ大きくなるか。

### 優先度

優先度は should と置いた。設計を始めることは人が決めた（DEC-0018）が、作るかどうかは、設計を人が確認した後に決まる。

## 観点の対応

- users・rationale: 仕様を確かめて確定する人のための要求。人の指摘と試作への感想に基づく（DEC-0018）。この人以外の利用者に必要かは、確かめていない。誰の要求かは、どの仕様まで使えるようにするかの答えで変わるので、users は hypothesis とする。
- scenarios_normal・scenarios_exception: S1〜S3 と X1〜X4。
- terms・data: 上の用語。説明は、どの版の仕様に基づくかを持つ（X2 のため）。データの形は設計で決める。
- states・rules: 説明の状態は、無い・ある・古い・読めないの四つ。試せる画面の終わり方と後に残るものは、モデルの結果と同じにする。人に聞く四つの答えで、状態と決まりが増えうるので、states と rules は hypothesis とする。
- quality・constraints: 読みやすさは AC-5 で確かめる。制約は上の三つ。
- priority: should（仮）。作るかどうかは設計の確認の後に人が決めるので、hypothesis とする。
- acceptance: AC-1〜AC-5。

coverage の decided は、観点の扱いが決まっているという意味で、検証済みという意味ではない。

## 決定

仕様を、例・図・試せる画面で見せる形を、prepare-dev の本体（判断画面のアプリ）に入れる方向で、設計を始める。

- AI が、判断画面のアプリに「仕様を見るページ」を足す設計の文書を書く。
- 最初は、試作で扱った仕様一つ（SPEC-0001、回答の適用）を見るページだけにする。
- 設計には、図をどう描くか、試せる部分をどう用意するか、例と文言を誰がどう確かめるかを書く。ほかの仕様に当てはめるとどうなるかも書いて確かめる。
- 設計が書けたら、作る前にもう一度人に確認する。それまで本体（ui/、internal/）は変えない。

## 代替案

- 別の仕様でもう一つ試してから決める（ほかの仕様で同じ形の試しの画面を作り、この形が通じるかを見る）: 採らない。

## 理由

人が判断画面（Q-0041）で「本体に入れる設計を始める」を選んだ。記述欄には何も書かれていない。

始まりは、2026-11-10 のチャットでの指摘である。「全然pdd-kitのスピリットを感じないんだよね」「ずとかもないし、ダイアグラムもない」「Run a login against the spec　みたいなのもない」。引き継ぎ記録（REC-0001）が PDD Kit から取り入れると書いたのは工程の流れだけで、人への見せ方は、取り入れるものとして書かれていなかった。

「試作を作る」と言われて、SPEC-0001 を題材に、例、流れの図、起きることを選んで試す画面、理解の確認を一枚にした試作を作った。試作は本体の外にあり、リポジトリには入れていない。三回作り直し、そのたびに次の感想があった。

- 一版目: 「UI的にはそういう方向だけど、回答の適用を試すがよくわからんでなにをしてるのかがわからんかった」
- 二版目: 「UIは別にいいんだけど説明とかいいまわしとか文言がわかりづらすぎる」
- 三版目: 「いいんじゃない大枠は」

試作で分かったことは、次の四つである。

- 画面の形（例の四コマ、起きることを選ぶカード、流れの図、結果、理解の確認）は、一版目から方向が合っていた。
- 難しかったのは、例と文言である。仕様の中の言葉と記録の番号をそのまま使い、誰が何をするのかを書いていなかった。仕様ごとに毎回要る作業で、画面の部品を本体に入れても自動にはならない。
- 試せる部分は、Lean のモデル（model/PrepareDev/Spec/Step.lean）を AI が JavaScript に手で写したものである。写しは、Lean が出した操作列 2,000 本（model/traces/depth-6.jsonl）と照合した。本体に入れるなら、これをどう用意するかを決める必要がある。
- 試したのは仕様一つだけで、ほかの仕様が同じ形に乗るかは確かめていない。

受け入れた欠点は、仕様一つでしか確かめていないので、その仕様に寄った作りになるおそれがあることである。設計の中で、ほかの仕様に当てはめるとどうなるかを書いて確かめる。
