## 問題

prepare-dev を使う人が、どの機械・どの対象リポジトリでも、同じ書き方の設定で prepare-dev を起動して使えるようにしたい。

根の問題は一つで、「入口（CLI と MCP）が、自分がどこに置かれ、どう起動されるかを、ソースの置き場所に頼って決めている」こと。その結果、対象リポジトリに書かれる設定が四つの機械固有の情報を含む。

| 機械固有の情報 | どこに現れるか |
| - | - |
| 道具リポジトリの `node_modules/.bin/tsx` の絶対パス | `.mcp.json` と `.codex/config.toml` の `command` |
| 道具リポジトリの `packages/cli/src/index.ts` の絶対パス | 同 `args` |
| 対象リポジトリ自身の絶対パス（`--root`） | 同 `args` |
| 道具リポジトリの `skills/*` への絶対 symlink | 対象リポジトリの `.agents/skills/*`（`init` が書く） |

加えて、デーモンは配信する UI を道具リポジトリ内の `packages/ui/dist/index.html` で探す。

### 問題の範囲（段階）

「同じ書き方の設定で起動できる」には二つの段階があり、どこまでを今回の問題にするかは人の判断（質問 1）。

| 段階 | 内容 | 満たす案 |
| - | - | - |
| 段階 1: 登録の可搬化 | 対象リポジトリに書かれる登録と skills 参照が機械固有の絶対パスを含まず、git で共有できる。道具リポジトリの checkout と `node_modules` は利用者の機械にあってよい | B、C、D |
| 段階 2: 道具リポジトリに依存しない配布 | 道具リポジトリの checkout も `node_modules` もなしに、配布物だけで入口・デーモン・UI が動く | D（と、その先の F） |

段階 1 だけなら、ビルドは必須ではない（案 B）。段階 2 まで含めるなら、成果物を一つに束ねる案 D が最短。所有者の当初の発想（`tsc -b` でビルドして `bin` を置く、案 C）は段階 1 を満たすが、段階 2 には届かず、段階 1 だけなら案 B より手間が多い。

## 価値

- 段階 1: `.mcp.json`、`.codex/config.toml`、`.agents/skills/*` を git に戻せ、clone 直後に（道具リポジトリがあれば）起動だけで使える。道具リポジトリの場所変更が対象リポジトリ側の設定に波及しない。
- 段階 2: 道具リポジトリと `node_modules` が要らなくなり、他者が試せる状態への最短経路になる。
- 起動時間の短縮は副次的（0.25 秒 → 推定 0.05 秒程度）で、価値の中心ではない。

## 代替案

案は「登録の間接化をどこで行うか」と「何を実行するか」の二軸で分かれる。

| 案 | 間接化 | 実行形 | 内容 | 評価 |
| - | - | - | - | - |
| A 作らない | 登録ファイル内の絶対パス | tsx＋ソース | 現状維持。機械ごとに `init` を実行する運用 | 工数ゼロ。限界はそのまま。所有者一人・一機械なら足りる（H5 の確認が先） |
| B 起動シム | PATH 上の `prepare-dev` | tsx＋ソース | CLI package に小さな `bin` スクリプトを置き、自分の位置から道具リポジトリを求めて tsx でソースを読む。`pnpm link --global` か `~/.local/bin` への symlink で PATH に置く。`init` は `command: "prepare-dev"`、`args` に絶対パスなし（root は cwd か環境変数）。UI も skills も checkout 内の相対位置で解決 | 段階 1 を最小の変更で満たす。実行経路は一つのまま（二系統の乖離なし）。H2 より tsx の起動コストは問題でない。checkout と `node_modules` は必要。**段階 1 ならこれを推奨** |
| C ビルド（`tsc -b`） | PATH 上の `prepare-dev` | node＋`dist/` | `exports` と `bin` を `dist/` に向け、`pnpm link --global` で PATH に置く。UI はパッケージ相対で解決 | 段階 1 を満たすが、6 package の `exports` 変更、開発時（tsx、vitest）とビルド時の解決先の衝突処理、版の報告の新設が要る。段階 2 には届かない（workspace 依存が `node_modules` に残る）。B より手間が多く、得るものは「tsx を外す」ことだけ。推奨しない |
| D 束ねる（esbuild） | PATH 上の `prepare-dev` | node＋単一ファイル | esbuild（tsx と vite の依存として既に導入済み、`pnpm-workspace.yaml` の `allowBuilds` にも記載）で入口＋runtime＋プラグインを一つの JS に束ね、UI HTML を同梱する。`exports` は触らない。tarball やコピーで配る | 段階 1 と 2 を満たし、F への土台になる。MCP SDK の ESM 束ね、プラグインが参照する同梱ファイル（guidance 文書）の扱いは要試行（H6）。ソースと束ねた物の二系統になるが、「インストール＝ビルド」として扱える。**段階 2 ならこれを推奨** |
| E Node の型除去で直実行 | — | node＋ソース | import 指定子を `.ts` にし `node` で直接動かす | tsx は消えるが、登録の問題を解かない。棄却 |
| F npm 公開 | PATH 上の `prepare-dev` | node＋公開物 | レジストリに公開し `npm i -g` | 具体化案 §1.7 で後回し。D の成果物をそのまま公開できる形にしておく |

skills の置き方は案と独立に決められる。候補は、(i) 道具リポジトリへの相対 symlink（対象＝道具リポジトリのときだけ可）、(ii) 道具リポジトリまたは配布物への絶対 symlink（常に最新だが、移動で壊れる）、(iii) 対象リポジトリへのコピー（git で共有でき移動で壊れないが、更新には `init` の再実行が要る）。段階 1 では (ii)、段階 2 では (iii) が自然だが、「常に最新」と「壊れない」のどちらを取るかは価値判断（質問 1）。

## 制約

- Node >= 26、pnpm workspace、`workspace:*` 依存、各 package は `private`。`tsc -b` の project references は設定済み。
- 入口は stdio で起動される独立プロセス。ホストは `command` と `args` の形式で登録し、cwd と PATH はホストが決める。ホストが対象リポジトリを cwd にするかは未検証（H1）。
- デーモンは対象リポジトリごとに一つで、`.prepare-dev/daemon.json` で発見する。入口が detached で起動するため、入口は自分自身の実行ファイルの場所を知る必要がある（`process.argv[1]` で足りる見込み）。
- 入口にもデーモンにも版・経路を報告する仕組みはない。二系統（ソース／ビルド）を持つ案（C、D）ではこれを新設しないと、ビルド忘れや古いデーモンを検出できない。
- `exports` の解決先を変える案（C）では、開発時（tsx、vitest）が `src` を見続けるように条件付き exports か vitest の alias を設計で決める必要がある。
- 検証プラグインが使う `vitest`（対象の `node_modules/.bin`）と `lake`（PATH）は対象リポジトリ側の道具で、配布の対象外。
- `command: "prepare-dev"` 形式の登録は、ホストのプロセス環境の PATH にその command があることに依存する。GUI から起動されたホストの PATH はシェルと違いうる。`pnpm link --global` は Node の版ごとのグローバル領域に結び付く（`~/.local/bin` 等への symlink なら生じない）。この依存を受け入れるか、`init` が解決済みの絶対パスを書く逃げ道（可搬性を失う）を残すかは価値判断（質問 1）。

## 非目標

- npm レジストリへの公開と版管理（具体化案 §1.7 で後回し。ただし妨げない）。
- Windows 対応（`ui` の `open` と e2e が darwin／bash 前提。配布形態と独立に扱う）。
- デーモンの複数版共存と自動更新。
- 検証ツール（`lake`、`vitest`）の配布。
- UI の見た目と開発サーバの変更。
- skills の内容の変更。置き方は本件の範囲に含める（非目標ではない）。

## リスク

- やらない場合: 道具リポジトリの移動や `node_modules` の削除で全対象が黙って壊れる。登録を共有できない。他者が試せない。
- B の場合: 道具リポジトリの checkout に依存し続ける。段階 2 が後から必要になれば D の費用が追加される。
- C と D の場合: ソースとビルドの二系統が乖離する。ビルド忘れで古い成果物や古いデーモンが動く。C では vitest も `dist/` を見る経路が生まれる。
- B、C、D 共通: ホストの PATH に `prepare-dev` が無いときの起動失敗がホストのログにしか出ず、既存の単一障害点（道具リポジトリの位置）を別の単一点（PATH）に移すだけになりうる。緩和（絶対パスの逃げ道、対象側への起動ログ）は設計で決める。
- 見返り: 登録と skills 参照の git 管理、再現性、第三者への配布の土台。

## 成功

- 中間: `init` の出力に絶対パスが一切含まれない（道具リポジトリ、対象リポジトリとも）。PATH 上の `prepare-dev` だけで `status` が返る。UI が簡易フォームではなく本来の UI で表示される。
- 最終: 別の対象リポジトリで `init` し、Codex と、シェルからと GUI から起動した Claude Code の両方が接続し、質問の作成から UI での回答、`question_apply` までが通る。道具リポジトリを別の場所に移しても（B と C では再 link 後、D では無条件に）登録を変えずに動き、skills も解決される。Node の版を切り替えた後の挙動を確認する。`pnpm test` と `scripts/e2e-crash.sh` が通る。

| 用語 | 定義 |
| - | - |
| 道具リポジトリ | prepare-dev のソースがあるリポジトリ。`toolRepoRoot()` が返す場所 |
| 対象リポジトリ | `--root` で指す、`prepare/` と `.prepare-dev/` を持つリポジトリ。道具リポジトリと同じこともある |
| 入口 | CLI と MCP（stdio）のプロセス。デーモンの HTTP クライアントで、デーモンがなければ起動する |
| デーモン | `prepare-dev serve` のプロセス。対象リポジトリごとに一つ。記録の書き込みと UI の配信を行う |
| MCP 登録 | `.mcp.json`（Claude Code）と `.codex/config.toml`（Codex）に書く `command` と `args` |
| 可搬な登録 | 機械固有の絶対パス（道具リポジトリ、対象リポジトリとも）を含まず、そのまま git で共有できる MCP 登録 |
| 起動シム | PATH に置く小さなスクリプトで、自分の位置から道具リポジトリを求めてソースを実行するもの（案 B） |
| 束ねる | esbuild 等で複数のソースと依存を一つの JS ファイルにまとめること（案 D） |
| ビルド成果物 | `tsc -b` が作る `dist/`、`vite build` が作る `packages/ui/dist/index.html`、esbuild が作る単一ファイル |
| 配布形態 | 利用者の機械に prepare-dev の実行できる形を置く方法（ソース直実行、起動シム、ビルド、束ねた単一ファイル、npm 公開） |
| 検証プラグイン | runtime が検証ジョブを委ねるプラグイン。現在は `lean4`（Lean 4 のビルドツール `lake` を使う）と `vitest` |
| `status`、`question_apply` | runtime の操作名。`status` は未処理の回答や未対処の指摘の一覧、`question_apply` は人の回答を判断（`DEC-*`）として確定する操作。CLI と MCP の両方にある |
| 具体化案 | `docs/2026-11-08-concretization-proposal.md`。§1.7 が配布と起動の当初方針 |
| 状態（決定／仮説／未検証／対象外） | 記録の `coverage` と仮説の状態。**決定**: 証拠または人の判断で確定した。**未検証**: 試せば分かるが未試行。**仮説**: 人の判断や利用の反応がないと確かめられない。**対象外**: 今回扱わない（理由を書く）。`coverage` の値が「仮説」なら、その観点の内容が人の判断待ちであることを示す |
