## 問題

prepare-dev を使う人が、どの機械・どの対象リポジトリでも、同じ書き方の設定で prepare-dev を起動して使えるようにしたい。

根の問題は、「`init` が機械固有の情報を対象リポジトリの設定に書き出し、ホストと入口がその情報に頼って起動する」こと。入口が自分の checkout の位置を求める仕組み（`toolRepoRoot()`、`import.meta.url` から逆算）自体は checkout がどこにあっても動き、可搬性を壊してはいない。壊しているのは `init` が書く次の四つ。

| 機械固有の情報 | どこに現れるか | 由来 |
| - | - | - |
| 道具リポジトリの `node_modules/.bin/tsx` の絶対パス | `.mcp.json` と `.codex/config.toml` の `command` | 道具リポジトリの位置 |
| 道具リポジトリの `packages/cli/src/index.ts` の絶対パス | 同 `args` | 道具リポジトリの位置 |
| 対象リポジトリ自身の絶対パス（`--root`） | 同 `args` | ホストが入口をどの cwd で起動するか分からないため、明示している |
| 道具リポジトリの `skills/*` への絶対 symlink | 対象リポジトリの `.agents/skills/*` | 道具リポジトリの位置 |

加えて、デーモンは配信する UI を道具リポジトリ内の `packages/ui/dist/index.html` で探す（checkout がある限りは動く）。

### 問題の範囲（段階）

「同じ書き方の設定で起動できる」には二つの段階があり、どこまでを今回の問題にするかは人の判断（質問 1 の判断 a）。

| 段階 | 内容 | 満たす案 |
| - | - | - |
| 段階 1: 登録の可搬化 | 対象リポジトリに機械固有の絶対パスを書かない（git で共有できる登録にするか、対象リポジトリには何も書かない）。道具リポジトリの checkout と `node_modules` は利用者の機械にあってよい | G、B、C、D |
| 段階 2: 道具リポジトリに依存しない配布 | 道具リポジトリの checkout も `node_modules` もなしに、配布物だけで入口・デーモン・UI が動く | D（と、その先の F） |

段階 1 だけなら、ビルドは必須ではなく、コードをほとんど変えない案（G）もある。段階 2 まで含めるなら、成果物を一つに束ねる案 D が最短。所有者の当初の発想（`tsc -b` でビルドして `bin` を置く、案 C）は段階 1 を満たすが、段階 2 には届かず、段階 1 だけなら G や B より手間が多い。

## 価値

- 段階 1: 対象リポジトリに機械固有の情報が残らず、clone 直後に（道具リポジトリがあれば）起動だけで使える。道具リポジトリの場所変更が対象リポジトリ側の設定に波及しない。

- 起動時間の短縮は副次的で、価値の中心ではない（束ねた成果物の起動時間と大きさは未計測。H6 の試行で測る）。

| - | - | - | - | - |
| A 作らない | 対象リポジトリの登録ファイル内の絶対パス | tsx＋ソース | 現状維持。機械ごとに `init` を実行する運用 | 工数ゼロ。限界はそのまま。所有者一人・一機械なら足りる（H5 の確認が先） |
| G 利用者単位の登録 | ホームディレクトリのホスト設定（`~/.codex/config.toml` の `mcp_servers`、Claude Code の利用者スコープの MCP 登録）と利用者単位の skills 置き場（Claude Code は `~/.claude/skills`。Codex の利用者単位の skills 置き場は要確認） | tsx＋ソース | 対象リポジトリには何も書かない。絶対パスは機械ごとに一箇所だけ。root は cwd から取る。`init` は対象リポジトリの `prepare/` と `.prepare-dev/` だけを作る | 登録の変更はコードなしで試せる。ただし入口が全プロジェクトで起動されうるので、対象リポジトリでないときに `prepare/` を作らない抑止が要る（H7）。「git で共有」ではなく「共有すべきものが無い」形で段階 1 を満たす。段階 2 には届かない。既存の `.gitignore` の方針（登録は機械固有）と整合する |

## 制約

- Node >= 26、pnpm workspace、`workspace:*` 依存、各 package は `private`。`tsc -b` の project references は設定済み。
- 入口は stdio で起動される独立プロセス。ホストは `command` と `args` の形式で登録し、cwd と PATH はホストが決める。ホストが対象リポジトリを cwd にするか、環境変数を渡せるかは未検証（H1）。H1 が片方のホストで偽なら、そのホストだけ `init` が `--root` の絶対パスか `env` を書く逃げ道が要る。
- デーモンは対象リポジトリごとに一つで、`.prepare-dev/daemon.json` で発見する。入口が detached で起動するため、入口は自分がどの実行ファイル・どの checkout から動いているかを知る必要がある。
- 入口にもデーモンにも版・経路・checkout を報告する仕組みはない。二系統（ソース／ビルド）を持つ案（C、D）ではこれを新設しないと、ビルド忘れや古いデーモンを検出できない。
- PATH 上の `prepare-dev`（B、C、D）は機械で一つの状態なので、道具リポジトリの checkout が複数あるとき（worktree、別ブランチ、対象＝道具リポジトリ）に、編集中の checkout と実行される checkout が黙って食い違いうる。対象が道具リポジトリ自身のときは自分のソースを優先する規則か、明示の上書き（環境変数か `init` のオプション）が要る。
- `exports` の解決先を変える案（C）では、開発時（tsx、vitest）とビルド時で解決先を分ける仕組みが要る（手段は設計）。
- 検証プラグインが使う `vitest`（対象の `node_modules/.bin`）と `lake`（PATH）は対象リポジトリ側の道具で、配布の対象外。
- `command: "prepare-dev"` 形式の登録は、ホストのプロセス環境の PATH にその command があることに依存する。GUI から起動されたホストの PATH はシェルと違いうる。`pnpm link --global` は Node の版ごとの領域に置かれる（`~/.local/bin` 等への symlink なら生じない）。この依存を受け入れるか、`init` が解決済みの絶対パスを書く逃げ道（可搬性を失う）を残すかは価値判断（質問 1 の判断 c）。
- 既存の対象リポジトリに残る絶対パスの登録は、`init` が上書きしないため、移行には削除か上書きの手段が要る（設計で扱う）。

## 非目標

- npm レジストリへの公開と版管理（具体化案 §1.7 で後回し。ただし妨げない）。
- Windows 対応（`ui` の `open` と e2e が darwin／bash 前提。配布形態と独立に扱う）。
- デーモンの複数版共存と自動更新。
- 検証ツール（`lake`、`vitest`）の配布。
- UI の見た目と開発サーバの変更。
- skills の内容の変更。置き方は本件の範囲に含める（非目標ではない）。

## リスク

- やらない場合: 道具リポジトリの移動や `node_modules` の削除で全対象が黙って壊れる。登録を共有できない。他者が試せない。
- H1 が偽の場合: 段階 1 の価値（絶対パスなしの登録）がそのホストでは成り立たず、逃げ道（ホストごとの `--root` か `env`）で部分的に保つことになる。どの案を選んでも同じなので、前工程で確かめる。
- G の場合: 入口が全プロジェクトで起動されうる。抑止（H7）が無いと無関係のプロジェクトに `prepare/` ができる。利用者単位の設定は機械ごとに一度の手作業になる。
- B の場合: 道具リポジトリの checkout に依存し続ける。
- C と D の場合: ソースとビルドの二系統が乖離する。ビルド忘れで古い成果物や古いデーモンが動く。C では vitest も `dist/` を見る経路が生まれる。
- B、C、D 共通: PATH の `prepare-dev` は機械で一つなので、checkout が複数あるときに編集中と実行中が食い違う。ホストの PATH に `prepare-dev` が無いときの起動失敗がホストのログにしか出ず、既存の単一障害点（道具リポジトリの位置）を別の単一点（PATH）に移すだけになりうる。緩和（優先規則、絶対パスの逃げ道、対象側への起動ログ）は設計で決める。
- 見返り: 対象リポジトリに機械固有の情報が残らない再現性、第三者への配布の土台。

## 成功

- 前工程: H1 の検証結果（三通りの起動形態ごとに接続可否と、入口が見た cwd と環境変数）が記録に残る。
- 中間: `init` の出力に絶対パスが一切含まれない（道具リポジトリ、対象リポジトリとも。G では対象リポジトリに登録ファイル自体が無い）。PATH 上の `prepare-dev`（G では利用者単位の登録）だけで `status` が返る。UI が簡易フォームではなく本来の UI で表示される。
- 最終: 別の対象リポジトリで `init` し、Codex と、シェルからと GUI から起動した Claude Code の両方が接続し、質問の作成から UI での回答、`question_apply` までが通る。道具リポジトリを別の場所に移しても（B と C では再 link 後、D では無条件に、G では利用者設定の更新後に）対象リポジトリ側を変えずに動き、skills も解決される。道具リポジトリの別の checkout（worktree）で作業したとき、意図した側（対象＝道具リポジトリなら自分のソース）が動くことを `status` の報告で確かめられる。C と D では、入口とデーモンが版・経路を報告し、ソースだけ直してビルドしていない状態と、再ビルド後に古いデーモンが残る状態の両方が `status` に不一致として出る。Node の版を切り替えた後も `prepare-dev` が解決される（`pnpm link --global` を使うなら、解決されなくなることを確認した上で `~/.local/bin` 等に切り替える）。`pnpm test` と `scripts/e2e-crash.sh`（実デーモンを強制終了して回答の適用が回復することを確かめる既存の e2e）が通る。

## 用語

| 用語 | 定義 |
| - | - |
| 道具リポジトリ | prepare-dev のソースがあるリポジトリ。`toolRepoRoot()` が返す場所。worktree などで複数の checkout がありうる |
| 対象リポジトリ | `--root` で指す、`prepare/` と `.prepare-dev/` を持つリポジトリ。道具リポジトリと同じこともある |
| runtime | `packages/runtime`。記録の保存、質問と回答、検証ジョブ、HTTP＋SSE を実装するライブラリ。デーモンはこれを一つのプロセスとして動かしたもの |
| 入口 | CLI と MCP（stdio）のプロセス。デーモンの HTTP クライアントで、デーモンがなければ起動する |
| デーモン | `prepare-dev serve` のプロセス。対象リポジトリごとに一つ。runtime を動かし、記録の書き込みと UI の配信を行う |
| MCP 登録 | `.mcp.json`（Claude Code）と `.codex/config.toml`（Codex）に書く `command` と `args`。ホームディレクトリ側の利用者単位の登録もある |
| skills | エージェント向けの手順書（`skills/prepare-*/SKILL.md`）。対象リポジトリの `.agents/skills/`（Codex）と `.claude/skills`（Claude Code。`../.agents/skills` への相対 symlink）からホストが読む |
| 可搬な登録 | 機械固有の絶対パス（道具リポジトリ、対象リポジトリとも）を含まず、そのまま git で共有できる MCP 登録 |
| 起動シム | PATH に置く小さなスクリプトで、自分の位置から道具リポジトリを求めてソースを実行するもの（案 B） |
| 束ねる | esbuild 等で複数のソースと依存を一つの JS ファイルにまとめること（案 D）。runtime のレビュー資料を作る `bundle` 操作とは別物で、実装時の名前は衝突しないものにする |
| ビルド成果物 | `tsc -b` が作る `dist/`、`vite build` が作る `packages/ui/dist/index.html`、esbuild が作る単一ファイル |
| 配布形態 | 利用者の機械に prepare-dev の実行できる形を置く方法（ソース直実行、利用者単位の登録、起動シム、ビルド、束ねた単一ファイル、npm 公開） |
| 検証プラグイン | runtime が検証ジョブを委ねる workspace package。現在は `plugin-lean4`（Lean 4 のビルドツール `lake` を使う）と `plugin-vitest` |
| guidance 文書 | 検証プラグインが `guidance()` で名前を返す相対パスの文書（`guidance/lean4.md` など）。現在はそれを読む側の実装が無い |
| `status`、`question_apply` | runtime の操作名。`status` は未処理の回答や未対処の指摘の一覧、`question_apply` は人の回答を判断（`DEC-*`）として確定する操作。CLI と MCP の両方にある |
| 具体化案 | `docs/2026-11-08-concretization-proposal.md`。§1.7 が配布と起動の当初方針 |
| 状態（決定／仮説／未検証／対象外） | 記録の `coverage` と仮説の状態。YAML の値はそれぞれ `decided`／`hypothesis`／`unverified`／`out_of_scope`。**決定**: 証拠または人の判断で確定した。**未検証**: 試せば分かるが未試行。**仮説**: 人の判断や利用の反応がないと確かめられない。**対象外**: 今回扱わない（理由を書く）。`coverage` の値が `hypothesis` なら、その観点の内容が人の判断待ちであることを示す |
