# 配布と起動（段階 1、案 G）の仕様

本仕様は、DES-0001 rev 4 の設計に従って REQ-0002〜REQ-0007 の受入条件を検査可能な主張に変える。REQ-0008（段階 2）は対象外。主張はすべて vitest プラグインによるテストで確かめる。検証記録（`RUN-*`、`packages/core/src/schemas.ts` の `RunRecord`）では、証拠の種類（`method`）が `test`、`scope.bounded` が true（実行した範囲の検査で、証明ではない）になる。証明（lean4）は使わない: 本件の性質は有限の操作列（ファイルの有無、プロセスの起動と終了、lock の取得）に対する観測で、任意長の操作列に対する不変条件や状態機械の安全性ではないため。排他（claim）だけは状態遷移を §2.2 に明示し、操作を差し替えた決定的なテスト（C10）、起動手順の操作単位の状態探索（C27）、実プロセスの同時起動テスト（C11）の三つで覆う。書き手が一つであることの残りの経路（`init`、停止）は C29、C30 で覆う。状態探索は有限の状態空間を網羅するので証明ではないが、本件の状態は `serve` の数と初期状態を決めれば有限で、競合の場合分けを人が列挙する C10 より漏れが少ない。

## 2. 状態モデルと契約

### 2.1 root の決定と対象判定（DES-0001 §5.3）

入口が `--root` を明示されずに起動されたとき、root `r` を `PREPARE_DEV_ROOT` があればその値、無ければ `findRoot(cwd)`（cwd から親へたどり、`.prepare-dev/config.json` を持つ最も近いディレクトリ。無ければ cwd）として、次の表で判定する。

| `<r>/.prepare-dev/config.json` | `r` の実パスが対象一覧にある | 判定 | `mcp` の振る舞い | CLI（`init`、`serve`、`skills` 以外）の振る舞い |
| - | - | - | - | - |
| ある | ある | 対象 | stdio を接続して `createMcpServer` が登録する全ツールを公開し、裏でデーモンの起動を始める（ツール呼び出しはその完了を待つ） | デーモンに接続して実行する |
| ある | 無い | 非対象 | `tools` capability を宣言し、ツールを一つも登録せずに待つ。stderr に `not a prepare-dev target` と理由を含む一行を出す。何も作らない | 終了コード 2。stderr に `not a prepare-dev target` と理由を含む。何も作らない |
| 無い | ある | 非対象 | 同上 | 同上 |
| 無い | 無い | 非対象 | 同上 | 同上 |

`--root` を明示した呼び出しと `init`、`serve`、`skills` は判定しない（`skills` は root を使わない。`init` が案内する `pnpm --dir <道具> cli skills --user` は道具リポジトリを cwd にして動くが、道具リポジトリは対象一覧に無いことがある）。`mcp` は CLI と同じ `targetRootOf` の結果を受け取り、`packages/mcp` の側で判定し直さない。

対象一覧は `<PREPARE_DEV_USER_DIR または ~/.prepare-dev>/targets.json` の `targets` 配列。`init` が `realpath(root)` を加え、親ディレクトリはあるが存在しなくなった項目を落とし、一時ファイルと `rename` で原子的に書く。`targets.json` が無ければ一覧は空。読めない（JSON でない、`targets` が文字列の配列でない）ときは、入口はすべての root を非対象と判定して理由に `targets.json` の絶対パスを含め、`init` は上書きせず終了コード 1 で終わる（他の対象の登録を黙って失わない）。

### 2.2 デーモン起動の排他と書き手（DES-0001 §5.4 の性質 P1〜P7 の手順）

同じ root について、journal、index、記録を書くプロセス（書き手）は同時に一つでなければならない（SPEC-0001 の前提）。書き手は、`openRuntime` を実行してから停止を終えるか強制終了されるまでの `serve` だけである。`init` は `Runtime.open` を呼ばず（`Store.initLayout` でディレクトリと空の journal を作るだけ）、書き手にならない（C29）。停止は書き込みを止めて runtime を閉じてから `daemon.json` を消す（C30）。以下は `serve` の起動手順である。

`L` は `<root>/.prepare-dev/daemon.lock`、`B` は `<root>/.prepare-dev/daemon.lock.break`（他人の古い `L` を消す権利の印）、`D` は `daemon.json`、`me` は自分の pid。`serve` は最初に `<root>/.prepare-dev/` を作る（既にあれば何もしない）。`X` は死んだ保持者と判定したときに読んだ `L` の内容、`Y` は死んだ保持者と判定したときに読んだ `B` の内容（どちらもバイト列）。内容が「読めない」とは、空、JSON でない、または `pid` が正の整数でないこと（`process.kill(0, 0)` や負の pid は成功してしまうため）。読めない回数と待った回数は、一つの `serve` の中で通算して数え、やり直しても数え直さない。

| 状態 | 遷移 | 次の状態 |
| - | - | - |
| 確認 | `D` が生きたデーモンを指す（`readLiveDaemon`） | 終了 `already-running`（コード 0） |
| 確認 | それ以外 | 取得 |
| 取得 | `L` を作れた（下の「作成」） | claim 済み |
| 取得 | `L` があり、読もうとしたら無かった | 取得 |

**作成**: `L` と `B` は次の手順で作る。内容を一時ファイル `<対象>.tmp.<me>` に上書きで書き（前の強制終了で残っていても上書きする）、`link(一時ファイル, 対象)` で置き、一時ファイルを消す。`link` は対象が既にあれば EEXIST で失敗するので、作成は排他的で、作られたファイルは最初から内容を持つ。「作れなかった」（false）は `link` の EEXIST だけで、それ以外の失敗は例外（`serve` は終了コード 1）。生きた書き手の `L` が空や書きかけに見えることは無いので、読めない `L` は人が手で編集したかディスクの故障で壊れたもので、読み直しの規則はそのための防御である。

不変条件:

- I1: 同じ root について、claim 済み（claim 済み、再確認、起動の状態）にある生きた `serve` は高々一つ。
- I2: 同じ root について、書き手は高々一つ。生きたデーモンが `D` にある間に `openRuntime` を始める `serve` は無い。
- I3: `L` を消すのは、`L` の保持者自身か、`B` を保持し、`B` の保持中に読み直した `L` が `X` と一致した `serve` だけ。`B` を消すのは、`B` の保持者自身か、`L` の保持者（保持者の死んだ `B` だけ）。

I1 が I3 から従う理由: `L` は作成（排他的）でしか作られないので、claim 済みになれるのは `L` が無い瞬間に作れた一つだけ。生きた保持者の `L` の内容はその保持者の pid を持ち、死んだ保持者の内容 `X` とは異なるので、`B` の保持者はそれを消さない。`B` も作成でしか作られず、保持者が死んだ `B` を消すのは `L` の保持者（I1 により一つ）だけなので、他人の `L` を消す操作は同時に一つしか進まず、読み直しから削除までの間に `L` が変わることはない。I2 は I1、claim 後の `D` の読み直し、停止の順序から従う: 稼働するデーモンは `D` を書いてから `L` を消し、停止では書き込みを止めてから `D` を消すので、`L` を消した後に claim した `serve` は生きた `D` を見て終わり、`D` が消えた後には古い書き手は残っていない。

すべての待ちに通算の上限があるので、どの `serve` も有限の操作で終わる（C27 (3)）。`stale-break-lock` は `B` が実際に残っていて、その保持者が死んでいるときだけ起きる（読み直しで確かめる。C10 (j)）。保持者の死んだ `B` は、`L` の保持者がいればその保持者が消すので、残るのは `L` の保持者も `B` の保持者も死んだときだけで、そのときは人が消す。

rev 3 以前の手順（DES-0001 rev 3 §5.4。`L` を `rename(L, L.<me>)` で引き取り、claim 後に `D` を見ない）では I1 も I2 も成り立たなかった。`rename` は「その時点でそのパスにあるファイル」に効くので、P1 と P2 が同じ死んだ `L` を読んだあと、P1 が引き取って `L` を作り直してから P2 が `rename` すると、P2 は P1 の生きた `L` を奪って消し、両方が claim 済みになる。また、`D` を見てから `L` を作るまでの間に先行のデーモンが `D` を書いて `L` を消すと、後の `serve` は二つ目の `Runtime.open` に進む。

**起動手順の形**（C10 と C27 が依存する）: 手順は、状態を明示した遷移関数として書く。状態は JSON で表せる値で、C27 はこの状態をそのまま重複判定の鍵に使う。

```text
type Op =
  | {op: "readDaemon"}                                    // → number | null（readLiveDaemon。生きたデーモンの pid か null）
  | {op: "isAlive", pid: number}                          // → boolean（例外は true と同じに扱う）
  | {op: "createExclusive", path: string, data: string}   // → boolean（作成。false は EEXIST だけ）
  | {op: "read", path: string}                            // → string | null（無ければ null）
  | {op: "unlink", path: string}                          // → void（無ければ何もしない）
  | {op: "sleep", ms: number}                             // → void
  | {op: "openRuntime"}                                   // → "ok" | "error"（Runtime.open と HTTP の待ち受け。D は書かない）
  | {op: "writeDaemon"}                                   // → void（D を原子的に書く）
type Outcome = "running" | "already-running" | "held" | "stale-break-lock" | "failed"
type StartState = { phase: string, x: string | null, y: string | null, unreadableL: number, unreadableB: number, waitB: number, ... }  // JSON
startInit(paths: {daemon, lock, breakLock}, me: number, now: () => string): StartState
startNext(s: StartState, response: unknown): {state: StartState, op: Op} | {state: StartState, outcome: Outcome}
runStart(s: StartState, effects): Promise<Outcome>          // 実際の操作で進める駆動部。cmdServe が使う
claimDaemonLock(lockFile, {pid, isAlive?, sleep?, now?, fs?}): Promise<"claimed" | "held">
  // 取得から claim 済み（B の片付けを含む）までを同じ startNext で進める駆動部。stale-break-lock は
  // RuntimeError("conflict", "<B の絶対パス>: stale break lock (pid N). Remove it after checking no prepare-dev serve is running.") を投げる
```

- `cmdServe` は `runStart` を使い、`Outcome` を終了コード（`running` は稼働を続ける、`already-running` と `held` は 0、`stale-break-lock` と `failed` は 1）に写す。`openRuntime` の失敗は応答 `"error"` として遷移関数に返し、遷移関数が `unlink(lock)` を要求してから `failed` で終わる。
- `claimDaemonLock` は本番の経路では使わない。C10 が、本番と同じ `startNext` の取得から claim 済みまでの部分を、差し替えた操作で確かめるための駆動部である。
- `openRuntime` と `writeDaemon` を分けるため、`Server.listen()` は `{writeDaemonFile?: boolean}`（既定 true）を受け、`cmdServe` は false で待ち受けてから `writeDaemon` で `server.writeDaemonFile()` を呼ぶ。C12、C18 は既定のまま `listen()` して `D` を観測する。
- `isAlive` の既定は `process.kill(pid, 0)` が成功か EPERM なら true、ESRCH なら false。`readLiveDaemon(root)` は `D` を読み、pid が正の整数で `isAlive` が真のときだけ返す。入口と `serve` は同じ `readLiveDaemon` を使う。
- lock と `B` の内容は `{"pid": <number>, "at": <ISO 8601 の文字列>}` の JSON。読む側は `pid` だけを使う。
- 入口（`ensureDaemon`）は `readLiveDaemon` で `D` を見て、無ければ `entryCommand()` で `serve` を起動し、最大 15 秒 `D` を待つ。子の終了を受け取ったら `D` を読み直し、無く終了コードが 0 以外なら即座に失敗する。終了コードが 0 なら待ち続けるが、`D`、`L`、`B` のどれも無い状態が 1 秒続いたら失敗する。15 秒を過ぎたら、残っている `L` か `B` の絶対パスと保持者の pid を含むエラーで失敗する。

## 1. 概要と問題

prepare-dev の入口（CLI と MCP）とデーモンを、対象リポジトリに機械固有の絶対パスを書かずに起動できるようにする。DIS-0001 の根の問題は、`init` が道具リポジトリの `tsx`、入口ソース、対象の `--root`、skills の symlink 先という四つの絶対パスを対象リポジトリに書き出し、ホストと入口がそれに頼っていることにある。本設計は Q-0002 の推奨（段階 1 を案 G＝利用者単位の MCP 登録で。skills はリンク。PATH 依存の備えは H1 の後）と Q-0003 の推奨を前提に、REQ-0002〜REQ-0007 を満たす最小の変更を定める。REQ-0008（段階 2）は扱わないが、妨げない構造にする。用語は DIS-0001 の「用語」と本記録末尾の「用語」に従う。「段階」は本記録では DIS-0001 の段階 0／1／2（問題の範囲）だけを指し、実装の作業の区切りは「フェーズ」と呼ぶ。

## 2. 目標と非目標

目標（優先度は REQ の `priority`）:

- REQ-0002（must）: 対象リポジトリの git 共有ファイルに絶対パスを書かない。既存の絶対パス入りの登録を移行できる。
- REQ-0003（must）: 入口は自分の位置と対象リポジトリを設定ファイルなしで決め、対象外の場所では副作用を出さない。同時起動でもデーモンは一つ。
- REQ-0005（must）: skills が解決でき、切れたリンクを検出して報告・張り直す。
- REQ-0006（must）: デーモンは自分の checkout 内の UI を配信し、無ければ探したパスとともにそれと分かる。
- REQ-0004（should）: `daemon.json` と `status` に道具リポジトリの位置を出す（段階 1 の最小形）。
- REQ-0007（should）: `pnpm cli` と `pnpm test` は常にソースを見る。`mcp.test.ts` と `scripts/e2e-crash.sh` が新しい起動経路で通る。

非目標:

- REQ-0008（could）: 配布物だけで動く段階 2。Q-0002 で a-2d が選ばれない限り着手しない（Q-0003 p8-could）。本設計は段階 2 を妨げないが、段階 2 のための項目や経路を先取りしない。
- DIS-0001 の非目標（npm 公開、Windows、複数版共存、検証ツールの配布、UI の見た目、skills の内容）。デーモンの HTTP の認証と origin 制限は DIS-0001 で別件とされたが、案 G で露出の条件が変わる点を §7 と決定点 6 で扱う。
- 案 B（起動シム）の実装。Q-0002 c-defer により、H1 が偽のホストが見つかるまで作らない。切り替え時の差分は §6 決定点 1 に書く。
- 再ビルド後の古いデーモンの検出（REQ-0004 AC-2〜AC-4 は案 C、D のみ）。

### 3.2 検証で決まる前提（人の判断ではないが未確認）

### 3.3 本設計から人に聞く判断

質問にする基準は二つ。(a) §6 の決定点のうち、複数の案が残り、人が受け入れるトレードオフを含むもの。(b) §10 の矛盾候補。`new_decisions` に挙げただけで、他の案が要求や前段の前提に反して一つに決まるもの（決定点 2、3、8）は、報告に留めて質問にしない（`prepare-design` 手順 1「機械的な選択は自分で決める」）。該当するのは次の五つで、レビューの修正を済ませてから登録する。質問の id は本記録の本文には書かず、質問側の `subjects`（質問が対象にした記録 id の一覧）から `trace` で引く（本文に書くと版が進み、回答が stale になる）。レビューの進め方とその経緯も本文に書かない（`REV-*` の `findings` と `status` の `open_findings` が持つ）。

1. 決定点 1: 利用者単位の登録に書く入口コマンドの形（絶対パスの `node` か、PATH の `node` か）。1b の可否はフェーズ 0 の実測で分かるので、回答はフェーズ 0 の結果を見てからでよい。
2. 決定点 5: dogfooding のプロジェクト登録を git 管理に入れるか。
3. 決定点 6: 案 G での同意の関門（利用者単位の対象一覧を置くか、`config.json` だけで起動するか、origin 制限を前提条件に前倒しするか）。
4. 決定点 7: `--migrate` が対象リポジトリ内の skills の絶対 symlink を消すか。
5. §10 矛盾候補 1: REQ-0006「固定の場所を前提にしない」の読み方。

§6 の各決定点の「判断」欄は次の語で書く。選んだ案の行は「採用（前提）」＝本設計がその案を前提に書かれており質問で確認する、「採用（機械的）」＝他の案が要求や前提に反し一つに決まるので質問にしない、のどちらか。未決の決定点（5、7）は両案とも「open」＝本設計は両案を書き分けており質問で決まる。選ばなかった案の行は「代替」＝質問で選ばれれば採る、「棄却」＝理由つきで採らない、のどちらか。frontmatter の `alternatives[].status` は、採用が `chosen`、open と代替が `open`、棄却が `rejected`。

frontmatter の `coverage` の値の根拠: `hypothesis` は人の判断待ちに対応する（architecture は決定点 1、5、6 と Q-0002 の判断 a、security は決定点 6、compatibility_migration は決定点 7 と Q-0003 m、prior_reconciliation は §10 の矛盾候補 1）。`unverified` は試せば分かるもの（integrations は §3.2 のホストの振る舞いと H1、H8）。`decided` はそれ以外。

### CUJ 1: 新しい機械で対象リポジトリを使い始める（REQ-0002 AC-1、AC-2、REQ-0003 AC-1、AC-4）

- Then: 対象リポジトリには `init` 前後で git 差分が無い（`init` が書くものは既に git にあり、一時ファイルは `.prepare-dev/.gitignore` で除外される）。利用者単位の対象一覧（§5.3）に対象が登録される。ホストは cwd から対象を決めた入口に接続し、`status` が返る。`daemon.json` に道具リポジトリの位置が出る。

### CUJ 2: 無関係なプロジェクトでホストを起動する（REQ-0003 AC-2）

- Given: 利用者単位の登録が済んでいる。cwd は `init` していないディレクトリ（`.prepare-dev/config.json` が無い、または対象一覧に無い）。
- When: ホストが入口を `mcp` で起動する。
- Then: 入口は MCP の initialize に応答し、ツールを一つも公開せず、そのまま待つ。cwd に `prepare/` も `.prepare-dev/` も作られない。ホストのログ（stderr）に「対象ではない。`init` で対象にできる」という一行が出る。

### CUJ 3: 既存の絶対パス入りの登録を移行する（REQ-0002 AC-3、AC-4）

- Given: 旧 `init` が書いた `.mcp.json`、`.codex/config.toml` の `[mcp_servers.prepare-dev]` ブロック、`.agents/skills/*` の絶対 symlink がある対象リポジトリ。`.codex/config.toml` には利用者が書いた別の設定もある。
- When: `pnpm cli init --root <対象> --migrate` を実行する。途中で止めてもう一度実行する。
- Then: `.mcp.json` の `prepare-dev` 項目と TOML のそのブロック（旧 `init` の内容を含むものだけ）が消え、TOML の他の行は byte 単位で変わらない（`.mcp.json` は JSON として読み書きするので、他の項目は意味が変わらない）。出力の `removed` に消したものが列挙される。二回目の実行は何も消さず、結果は一回で完了した場合と同じ。

### CUJ 4: 道具リポジトリ自身で作業する（dogfooding。REQ-0003 AC-5）

- Given: 道具リポジトリの worktree を二つ持つ。利用者単位の登録は片方の checkout を指す。
- When: 各 worktree で `pnpm cli init`（`--root` は worktree）を実行し、ホストをその worktree で起動する。
- Then: `.mcp.json` と `.codex/config.toml` に `pnpm cli mcp --host <host>` のプロジェクト登録があり（決定点 5a なら git から、5b なら `init` が書く）、絶対パスを含まない。プロジェクト単位の登録が優先され（H8）、その worktree のソースが動く。`.agents/skills/*` は `../../skills/*` への相対 symlink。`status` の `tool.root` がその worktree を指す。

### CUJ 5: 道具リポジトリを移動した（REQ-0005 AC-2、AC-3、REQ-0006 AC-1）

- Given: 利用者単位の skills リンクと MCP 登録が旧い場所を指している。デーモンは止まっている。
- When: 新しい場所の道具リポジトリで `pnpm cli init --root <対象>` を実行し、出力の `setup_commands` を再実行する。ホストを対象で起動する。
- Then: `skills --user` は切れたリンクを skill 名つきで報告して張り直す。新しい場所から起動した入口がデーモンを立て、`GET /` が新しい場所の UI を返す。

### CUJ 6: 二つのホストが同時に入口を起動する（REQ-0003 AC-3、AC-6）

- Given: 対象リポジトリにデーモンが無い。
- When: Claude Code と Codex（または CLI）がほぼ同時に入口を起動する。
- Then: 二つの `serve` が起動しうるが、claim（§5.4）を取れた一つだけが `Runtime.open` に進み、もう一つは何も書かずに終了する。`daemon.json` は一つの生きているデーモンを指し、孤児プロセスは残らない。`serve` が起動に失敗した場合は原因が `.prepare-dev/daemon.log` に残り、どちらの入口も 15 秒待たずに失敗し（負けた側の入口も、lock も daemon.json も無いと分かった時点で失敗する）、再試行でも二つ目は立たない。

### CUJ 7: UI がビルドされていない（REQ-0006 AC-2）

- Given: `packages/ui/dist/index.html` が無い checkout からデーモンが立った。
- When: ブラウザで `/` を開き、`pnpm cli status` を実行する。
- Then: 簡易フォームが表示され、`status` に `ui: <探したパス> (missing)` が出る。`daemon.json` の `ui.path` に同じパスがある。

### 5.2 データ: `daemon.json` と `status`

`daemon.json`（`.prepare-dev/daemon.json`、デーモンが `listen()` で原子的に書く）に二項目を足す。既存項目は変えない。

```json
{
  "pid": 12345, "port": 50837, "url": "http://127.0.0.1:50837", "root": "/abs/target", "started_at": "...",
  "tool": { "root": "/abs/tool-repo" },
  "ui": { "path": "/abs/tool-repo/packages/ui/dist/index.html", "found": true }
}
```

- `tool.root` は `toolRepoRoot()`。段階 1 ではこの一項目だけ（REQ-0004「道具リポジトリの位置を一項目足す最小形」）。案 C、D で要る識別子は、そのとき任意項目として足す（本設計は名前を予約しない）。
- `ui.path` は探したパス、`ui.found` は起動時の存在。`GET /` は従来どおりリクエストごとに存在を見る（REQ-0006 の書きかけ HTML は防がない）。
- `tool`、`ui` が無い `daemon.json`（本変更前のデーモン）は読め、`status` に `tool: unknown` と出る。段階 1 では不一致として扱わない（REQ-0004 AC-4 は C、D のみ）。
- `DaemonInfo` 型は現在 `packages/mcp/src/client.ts` と `packages/runtime/src/server.ts` に同じ定義が二つあり、`readDaemonInfo` 関数も両方にある（runtime 側は export されるが誰も使っていない）。型は `packages/core/src/schemas.ts` に一つ置き、関数は mcp 側の `readLiveDaemon`（§5.1。生存の判定を入口と `serve` で共有する）一つにする。

`GET /api/status` は `StatusView` に `daemon: {pid, url, started_at, tool, ui}` を足す。`ui.found` は呼ばれた時点で存在を評価し直す。CLI の `status` の文字出力に三行を足す: `daemon: <url> (pid <pid>)`、`tool: <root>`、`ui: <path> (found|missing)`。

### 5.3 入口の root の決定と対象判定（REQ-0003、H7、同意の関門）

`rootOf()` の既定順（`--root` → `PREPARE_DEV_ROOT` → cwd）は保ち、三つ目を `findRoot(cwd)` にする: cwd から親へたどり、`.prepare-dev/config.json` を持つ最も近いディレクトリを root にする。見つからなければ cwd を root にする（その root は非対象になる）。ホストを対象のサブディレクトリで開いてもツールが消えないようにするため（決定点 8）。`--root` を明示しない呼び出しでは、求めた root について `isTarget(root)` を見る。

`isTarget(root)` は次の両方が成り立つとき真。

1. `<root>/.prepare-dev/config.json` がある。
2. 利用者単位の対象一覧（`<利用者単位のディレクトリ>/targets.json`。内容は `{"targets": ["<realpath>", ...]}`）に `realpath(root)` がある。`init` が登録する。利用者単位のディレクトリは環境変数 `PREPARE_DEV_USER_DIR` で差し替えられ、既定は `~/.prepare-dev`。テストと `scripts/e2e-crash.sh` は一時ディレクトリに向け、利用者の実ファイルを汚さない。

対象一覧の扱い: `targets.json` が無ければ一覧は空。読めない（JSON でない、`targets` が文字列の配列でない）ときは、すべての root を非対象と判定し、理由に一覧の絶対パスを含める（全セッションの入口が読むので、例外で落とさず、誤ってツールを公開する側にも倒さない）。`init` は一覧を一時ファイルと `rename` で原子的に書き、読めない一覧は上書きせずに終了コード 1 で失敗する（他の対象の登録を黙って失わない）。存在しなくなった項目を落とすのは、親ディレクトリはあるが root が無いときだけ（外付けのボリュームが外れているだけの項目は残す）。二つの `init` が同時に書くと片方の登録が失われうるが、`init` をもう一度実行すれば直る。

2 を置く理由（決定点 6a）: 利用者単位の登録では入口が全セッションで起動するので、1 だけだと「clone した見知らぬリポジトリに `config.json` があるだけでデーモンが自動で立つ」。デーモンの HTTP は無認証で `access-control-allow-origin: *` を返し（DIS-0001 §現状）、`/api/runs` は対象の `vitest` や `lake` を実行するので、起動の同意は利用者の明示の操作（`init`）に残す。現状のプロジェクト単位の登録ではホストが承認を求めていたのと同じ関門を、`init` に移す。

| 呼び出し | 非対象のとき |
| - | - |
| `mcp`（`--root` なし） | `McpServer` を `capabilities: {tools: {}}` を宣言し、ツールを一つも登録しない状態で stdio に接続し、ホストが stdio を閉じるまで待つ（Q-0003 s-wait）。宣言が無いと MCP SDK 1.32 は `tools/list` のハンドラを置かず Method not found を返す（`server/mcp.js`）。宣言すれば空の一覧を返す。stderr に `prepare-dev: <root> is not a prepare-dev target (<理由>); no tools published. to enable: pnpm --dir <道具> cli init --root <root>` を一行出す。理由は「`config.json` が無い」「対象一覧に無い」「対象一覧が読めない: <パス>」のどれか。`ensureDaemon` を呼ばないので `.prepare-dev/` も `prepare/` もできない。セッション中に `init` されても気付かない（次のセッションから有効）。MCP の `instructions` は空にする（全セッションの会話に載るため）。診断は、ホストの MCP 一覧（`claude mcp list`、`codex mcp list`）で接続状態とこの一行を見る |
| `status`、`q`、`record`、`verify`、`trace`、`bundle`、`ui`、`pending`、`stop`（`--root` なし） | `error: <root> is not a prepare-dev target (<理由>). to enable: pnpm --dir <道具> cli init --root <root>` を stderr に出し終了コード 2。何も作らない |
| `init` | 対象外ではない。`.prepare-dev/config.json` と `prepare/` を作り、対象一覧に登録するのが仕事 |
| `skills` | root を使わないので判定しない（`init` の案内の `pnpm --dir <道具> cli skills --user` は道具リポジトリを cwd にして動き、道具リポジトリは対象一覧に無いことがある） |
| `serve`、または `--root` を明示したコマンド | 対象判定をしない（現状どおり）。`--root` の明示が同意に当たる。`mcp.test.ts` と `scripts/e2e-crash.sh` はこの経路 |

案内の `<道具>` は入口が `toolRepoRoot()` で知っている絶対パスで、そのまま実行できる形で出す（G では PATH に `prepare-dev` が無い）。`PREPARE_DEV_ROOT` だけが設定されている場合も「`--root` なし」として扱い、その root を判定する（REQ-0003 は「cwd」と書くが、既定順で求めた root に読み替える。§10）。

判定を置く場所は一箇所にする。`rootOf(args)` の直後に `targetRootOf(args)`（`--root` が無く `isTarget` が偽なら上の振る舞い）を置き、`init`、`serve`、`skills` 以外のすべてのコマンドがそれを通る。`mcp` も `targetRootOf` の結果（root と、対象か、理由）を `serveStdio` に渡すだけで、`packages/mcp` の側で判定し直さない。特に `ui` は現在 `client()` を通らず `ensureDaemon(rootOf(args))` を直接呼ぶので、個別に例外にしない。

設定の検証: `Store.loadConfig()` は `records_dir` を `path.resolve(root, records_dir)` に解決し、root の外を指す値（`../` など）を `invalid` として拒否する。現在は無検査で結合して `mkdir` と走査をしており（`store.ts`）、`config.json` の中身で root の外に書けた。自動起動の経路が増えるので塞ぐ。検査は字面だけで、git に symlink としてコミットされた `prepare` が root の外を指す場合は通る（限界。主な関門は決定点 6a の対象一覧）。

### 5.4 デーモンの起動、排他、停止（REQ-0003 AC-3、AC-6）

`Runtime.open` は `prepare/` の作成、index の再構築、外部変更の走査に加えて回復処理（中断した回答適用の取引をロールフォワードまたは撤回する処理。SPEC-0001 §2.2）を行い、journal（`prepare/events.jsonl`）に追記する。動いているデーモンも journal、index、記録を書く。SPEC-0001 は「書き込むデーモンは一つ」を前提にしているので、同じ root について書き手は同時に一つでなければならない。本設計は次の性質でそれを守る（決定点 2a）。

| 性質 | 内容 |
| - | - |
| P1 | `serve` は `Runtime.open` の前に `.prepare-dev/daemon.lock` を claim し、`daemon.json` を書いた後に解放する |
| P2 | lock の作成は内容ごと原子的（内容を書いた一時ファイルを `link` で置く）。生きた書き手の lock が空や書きかけに見えることは無い |
| P3 | 死んだ保持者の lock の引き取りは同時に一つしか進まず、判定に使った lock より新しい lock を消さない |
| P4 | claim の後に `daemon.json` を読み直し、生きたデーモンがあれば何もせずに lock を解放して終わる（先行のデーモンが `daemon.json` を書いて lock を消した直後に claim した場合） |
| P5 | 待ちはすべて回数に上限があり、`serve` は必ず終わる |
| P6 | 停止は、受付と検証ジョブを止め、runtime を閉じてから `daemon.json` を消す。`daemon.json` が無いときに書き手は残っていない |
| P7 | `init` は `Runtime.open` を呼ばない（§5.5）。journal、index、記録を書くのはデーモンだけ |

rev 3 までの手順（死んだ保持者の lock を `rename(L, L.<pid>)` で引き取り、claim の後に `daemon.json` を見ない）は P3 と P4 を満たさなかった。`rename` はその時点のパスにあるファイルに効くので、二つの `serve` が同じ死んだ lock を読んだあと、先の一方が引き取って作り直した生きた lock を、後の一方が奪える（決定点 2 が 2b を棄てた理由と同じ競合）。具体的な手順（`daemon.lock.break` で引き取りを直列化する案など）と、その検証（操作単位の状態探索）は SPEC-0002 §2.2 にあり、手順の選び方は人の判断を待っている。本設計はどの手順でも P1〜P7 を満たすことだけを求める。

`serve`（`cmdServe`）の順序:

1. `readLiveDaemon(root)` が生きているデーモンを返せば「already running」を stderr に出して終了コード 0 で終わる（現状は終了コード 1。入口が「子が 0 以外で終わった」を失敗とみなすので 0 にする）。
2. claim（SPEC-0002 §2.2）。他の生きた保持者がいれば「another daemon is starting」を stderr に出して終了コード 0 で終わる。
3. `readLiveDaemon(root)` をもう一度見て、生きていれば lock を解放して終了コード 0（P4）。
4. `Runtime.open(root)` と HTTP の待ち受け。
5. `daemon.json` を原子的に書く。
6. lock を消す。4〜5 で例外が出たら lock を消して終了コード 1 で終わる（stderr は `daemon.log`）。強制終了で lock が残っても、保持者の pid が死んでいるので次の `serve` が引き取る。

停止（`Server.close()`。`stop` の SIGTERM で呼ばれる）の順序（P6）: 新しい要求とジョブの受付を止める → 実行中の検証ジョブの子プロセスを終わらせる（その実行の `RUN-*` は記録しない）→ HTTP を閉じる → runtime を閉じる → `daemon.json` を消す → 終了する。現在は `daemon.json` を先に消してから排出を待つので、その間に起動した `serve` が二つ目の書き手になりえた。停止中は `daemon.json` が生きた pid を指したままなので、そのとき起動した `serve` は already running で終わり、入口の接続は失敗する（利用者が再実行すれば、停止の後に新しいデーモンが立つ）。

入口（`ensureDaemon(root)`）:

1. `readLiveDaemon(root)` が生きているデーモンを返せばそれを返す。
2. `entryCommand()` の `command` と `args` に `serve --root <root>` を続けて detached 起動する（cwd は現状どおり `toolRepoRoot()`、stdout/stderr は `.prepare-dev/daemon.log` に追記）。現在渡している環境変数 `PREPARE_DEV_DETACHED=1` は読む側が無いので、この変更で消す。
3. 最大 15 秒（現状値）`daemon.json` を待つ。子プロセスの終了も監視する。子の終了を受け取ったら、まず `daemon.json` を読み直し、生きたデーモンがあればそれを返す。無く、終了コードが 0 以外なら待たずに `daemon.log` のパスを含むエラーを投げる。終了コードが 0 なら（別の `serve` が claim を取っていた、または既に動いていた）待ち続けるが、`daemon.json`、`daemon.lock`、`daemon.lock.break` のどれも無い状態が 1 秒続いたら、勝った側も起動に失敗したとみなし、`daemon.log` のパスを含むエラーを投げる。15 秒を過ぎたら、残っている lock の絶対パスと保持者の pid を含むエラーを投げる（pid の再利用で lock が引き取れないときに、人が原因を辿れるようにする）。

MCP の入口（`serveStdio`）は、対象の場合も stdio を先に接続してツールを登録し、`ensureDaemon` は接続の直後に裏で始める。ツール呼び出しはその完了を待ち、失敗したらそのエラーを返す。MCP の initialize がデーモンの起動を待たないので、Q-0003 q の目標（initialize まで 1 秒）とホストの起動の時間切れ（Codex の `startup_timeout_sec`）にデーモンの冷起動が乗らない。CLI は従来どおり `ensureDaemon` を待ってから実行する。

同時に二つの入口が起動すると二つの `serve` が立ち上がるが、claim を取れなかった方は何も書かずに約 0.3 秒で終わる。その費用は、入口側で lock を取り合う案（決定点 2b）より小さい。

### 5.5 `init`（REQ-0002）

`init --root <root>` は次を行う。既存の「あるものは書かない」規則は保つ。

1. `.prepare-dev/config.json`（無ければ作る）と、`Store.initLayout(root)` で `prepare/` のディレクトリと空の journal（`prepare/events.jsonl`、無ければ作る）を作る。`Runtime.open` は呼ばない（現在は呼んでいる）。`Runtime.open` は回復処理、走査、index の書き込みを行うので、動いているデーモンと並行に呼ぶと二つ目の書き手になる（§5.4 の P7）。journal への追記と index はデーモンが起動時に行う。
2. `.prepare-dev/.gitignore`（無ければ作る）: 内容は `*`、`!.gitignore`、`!config.json`、`!reviews/`、`!reviews/**` の五行（許可リスト形式）。git 管理に入れるのは設定とレビュー資料で、`daemon.json`、`daemon.lock` とその一時名、`daemon.lock.break`、`daemon.log`、`index.json`、`tmp/`、`runs/` は除外される。レビュー資料（`reviews/` の bundle）は、レビュー役が読んだ版の唯一の写しなので残す（`buildBundle` は現在の版しか読めず、store は過去の版を持たない。`REV-*` の本文は bundle のパスを資料として引く）。許可リスト形式なら状態ファイルが増えても `init` と既存の対象を更新しなくて済む。現在は道具リポジトリ自身の root の `.gitignore` に項目が列挙されているだけで、他の対象では利用者任せだった。
3. 利用者単位の対象一覧（`PREPARE_DEV_USER_DIR`、既定 `~/.prepare-dev`、の `targets.json`）に `realpath(root)` を登録する（無ければ作る。既にあれば何もしない）。書き込みは一時ファイルと `rename` で原子的に行う。同時に、親ディレクトリはあるが root が無くなった項目を落とす。一覧が読めないときは上書きせず、一覧の絶対パスを含むエラーで終了コード 1（§5.3）。
4. 出力の `setup_commands` に、利用者が手で行う登録を、この機械で解決した絶対パスで出す。絶対パスは利用者のホームの設定（`~/.claude.json`、`~/.codex/config.toml`）に入り、機械で一箇所になる。`<node>` は `init` を実行した `process.execPath`。

```text
claude mcp add -s user prepare-dev -- <node> <tool>/node_modules/tsx/dist/cli.mjs <tool>/packages/cli/src/index.ts mcp --host claude-code
codex mcp add prepare-dev -- <node> <tool>/node_modules/tsx/dist/cli.mjs <tool>/packages/cli/src/index.ts mcp --host codex
  （続けて ~/.codex/config.toml の [mcp_servers.prepare-dev] に次の二行を足す）
  startup_timeout_sec = 30
  tool_timeout_sec = 3600
pnpm --dir <tool> cli skills --user
```

`codex mcp add` には時間切れの値を設定する項目が無い（codex-cli 0.167.0 の `--help`。レビュー役が確認）。現在の `init` は `.codex/config.toml` に `startup_timeout_sec = 30` と `tool_timeout_sec = 3600` を書いており、これが落ちると Codex の既定値（文書によれば起動 10 秒、ツール 60 秒。未確認）になって、`question_wait` の長い待ちが打ち切られる。そこで二行を足す手順を案内に含める。二行を足せば Codex がそれを読むことはフェーズ 0 で確かめる。登録をやり直すとき（Node の版や道具リポジトリの場所を変えたとき）に、同名の登録が上書きされるかは未確認（フェーズ 0）なので、出力には先に実行する `claude mcp remove -s user prepare-dev` と `codex mcp remove prepare-dev` も載せる。

5. 旧 `init` の痕跡（`.mcp.json` の `prepare-dev` 項目、`.codex/config.toml` の旧ブロック、`.agents/skills/*` の絶対 symlink）があれば、出力の `legacy` に列挙する。`--migrate` が無ければ消さない。
6. dogfooding（`root` が `toolRepoRoot()` と同じ）: 決定点 5a（推奨。登録ファイルと相対 symlink を git 管理に入れる）なら `init` は何も足さない。5b なら、`.mcp.json` に `{"type":"stdio","command":"pnpm","args":["cli","mcp","--host","claude-code"]}`、`.codex/config.toml` に `command = "pnpm"`、`args = ["cli", "mcp", "--host", "codex"]`、`startup_timeout_sec = 30`、`tool_timeout_sec = 3600` のブロック、`.agents/skills/<name> -> ../../skills/<name>`、`.claude/skills -> ../.agents/skills` を書く。どちらでも `--root` は書かない（cwd＝プロジェクト。H1）。`command: "pnpm"` は PATH に依存する（絶対パス無しの登録は PATH 依存と表裏。限界として §7 に書く）。案 B に切り替えるときは、この値を `command: "prepare-dev"`、`args: ["mcp", "--host", ...]` にする一箇所の変更で済む。

`--migrate`（m-option。`init` が書いたものだけを消し、1〜6 の前に行う）:

- `.mcp.json`: JSON として読み、`mcpServers["prepare-dev"]` を消して 2 スペース字下げで書き戻す（現在の `init` と同じ整形）。`mcpServers` が空になり他のキーも無ければファイルを消す。他の項目は意味が変わらない（byte 単位の同一は保証しない）。
- `.codex/config.toml`: `[mcp_servers.prepare-dev]` の行から、次の `[` で始まる行の直前（または EOF）までを一つのブロックとし、そのブロックに `node_modules/.bin/tsx` か `packages/cli/src/index.ts` を含む行があるとき（旧 `init` が書いた内容）だけ消す。直前の空行も一つ消す。他の行は byte 単位で変えない。利用者が自分で書いた同名ブロックは条件に合わないので残る。
- `.agents/skills/<name>`（`name` は道具リポジトリの `skills/` にある skill 名）が絶対パスへの symlink なら消す。実体のディレクトリと相対 symlink は消さない（決定点 7a。7b なら消さず `legacy` に残す）。
- 消したものを出力の `removed` に列挙する。無ければ何もしない。中断して再実行しても、残っているものだけが処理される（REQ-0002 AC-4）。

出力は `{root, written, removed, legacy, setup_commands, skills}`。`skills` は dogfooding で置いた相対 symlink の結果（§5.6 の表の `state`）で、決定点 5a では常に空。出力の詳しい形は SPEC-0002 §2.3。

### 5.6 skills（REQ-0005、b-link）

共通関数 `placeSkillLinks(destDir, linkTargetOf)`: 道具リポジトリの `skills/*/SKILL.md` を持つ各 `name` について `destDir/<name>` を次のように扱い、結果を `{name, state}` の一覧で返す。書き込まない検査モードは作らない（配置の結果を列挙すれば REQ-0005 の「検出して報告」を満たす）。

| `destDir/<name>` の状態 | 処理 | `state` |
| - | - | - |
| 無い | symlink を作る | `linked` |
| symlink、先が期待どおりで解決できる | 何もしない | `ok` |
| symlink、先が解決できない（切れたリンク） | 張り直す | `relinked` |
| symlink、先が期待と違う（移動した道具リポジトリなど） | 張り直す | `relinked` |
| 実体のディレクトリかファイル | 触らない（利用者のもの） | `kept` |

- `prepare-dev skills --user`（新設の明示の操作。REQ-0005）: `destDir` は `~/.agents/skills` と `~/.claude/skills`（`os.homedir()`。テストは `HOME` を差し替える）、リンク先は `<toolRepoRoot>/skills/<name>` の絶対パス。ディレクトリ自体は利用者の他の skills と共有なので、ディレクトリごとの symlink は作らない。`ok` 以外を skill 名つきで出力する（黙って飛ばさない）。
- dogfooding（決定点 5b のとき `init` が置く）: `destDir` は `<root>/.agents/skills`、リンク先は `../../skills/<name>` の相対パス。
- `init`（G）: 対象リポジトリに skills を置かない（REQ-0002 §シナリオ G）。
- コピー方式と印ファイル（REQ-0005 AC-4、AC-5）は b-link では使わないので作らない。

## 7. 非機能要求

- 安全性: 案 G は入口を全セッションで起動するので、デーモンの自動起動の条件を利用者の `init` を経た対象に限る（決定点 6a）。`records_dir` を root 内に制限する（字面の検査。symlink は限界、§5.3）。デーモンの HTTP（無認証、`access-control-allow-origin: *`）自体は変えず、別件のままにする（決定点 6c は質問）。非対象で待機する入口はネットワークを開かない。`--migrate` は旧 `init` が書いた項目だけを消す（REQ-0002 AC-3）。同じ root の書き手は一つ（§5.4 の P1〜P7）。
- 性能（実測、Node 26.13、tsx 4.23、macOS、2026-11-08）: 入口は tsx のラッパーと、入口ファイルを実行する子の二プロセスで動く。対象で起動した入口（デーモンを除く）は、initialize の応答まで 576〜652 ms（三回）、RSS の和は約 170 MB（ラッパー約 60 MB、子約 111 MB）。rev 3 までの「約 95 MB」は片方のプロセスだけを測った値で、一セッションの費用ではなかった。費用の大半は Node と tsx のローダ自体で、runtime やプラグインの読み込みを遅延させても大きくは変わらない。費用は「セッション数 × 約 170 MB」で、10 セッションなら約 1.7 GB。これを受け入れるかが Q-0003 s（s-wait か s-exit か）の判断材料になる。`node --import` で tsx のローダを読み込む形にすればラッパーが要らず一プロセスで済むので、決定点 1 の改善の候補になる（未試行）。待機中の入口は CPU を使わない。MCP の initialize はデーモンの起動を待たない（§5.4）ので、Q-0003 q の目標（1 秒）に冷起動は乗らない。
- 互換性と移行: `daemon.json` の追加項目は任意で、旧デーモンの `daemon.json` も読める。利用者単位のディレクトリは `PREPARE_DEV_USER_DIR` で差し替えられ、テストと `scripts/e2e-crash.sh` は一時ディレクトリを使う（`init` を呼ぶ自動化が利用者の対象一覧を汚さない）。旧 `init` の登録は `--migrate` で消す。本変更の前に立てたデーモンは `pnpm cli stop` で止めるまで残る（REQ-0007 の現状どおり）。本変更の前に `init` した対象は対象一覧に無いので、`init` をもう一度実行するまでツールが出ない。`mcp.test.ts` と `scripts/e2e-crash.sh` は `--root` 明示の経路なので挙動は変わらない。利用者単位の登録は `node` と道具リポジトリの絶対パスを含むので、Node の版や checkout の場所を変えたら `init` の案内を再実行する（決定点 1 の欠点）。Codex のタイムアウトの二行も案内に含める（§5.5）。dogfooding の `command: "pnpm"` は PATH に依存する（絶対パス無しの登録は PATH 依存と表裏）。GUI 起動のホストで PATH に `pnpm` が無ければ、利用者単位の登録（別 checkout）が動く。
- 切り戻し: コードは git revert。利用者単位の登録は `claude mcp remove -s user prepare-dev`、`codex mcp remove prepare-dev`（足した二行も同じ表にあるので一緒に消える。未確認）、skills リンクは `~/.agents/skills/<name>` と `~/.claude/skills/<name>` を消す。`~/.prepare-dev/targets.json` を消す。対象リポジトリ側には `init`（G）は `.prepare-dev/.gitignore` と空の journal 以外の新しいものを書いていない。

- 通常: Given 配布物だけの機械、When ブラウザで `/` を開く、Then 同梱の UI が表示される。
- 通常: Given 配布物だけの機械、When `verify run --plugin vitest` を実行する、Then 対象リポジトリ側の vitest で検証が動く。
- 例外: Given Node の版が要件（>= 26）を満たさない、When 入口を起動する、Then 分かるエラーで止まる。
- 例外: Given origin 制限の要求がまだ `accepted` でない、When 本要求を `accepted` にしようとする、Then 前提条件を満たしていないので `accepted` にしない。
- 例外（中断と再試行）: Given 配布物の置き換え中にデーモンが動いていた、When 新しい入口が接続する、Then REQ-0004 の照合で不一致を検出し、失敗するか再起動する。

## 受入条件

- AC-1: `node_modules` と checkout を消した環境で `prepare-dev status` が動く。
- AC-2: 同じ環境で `GET /` が本来の UI を返す。
- AC-3: 同じ環境で vitest プラグインと lean4 プラグインが対象側の道具で動く。
- AC-4: 入口の起動（MCP の initialize 応答まで）が目標値以内（目標値は Q-0003 で決める。上限は Codex の `startup_timeout_sec = 30` 秒）。配布物の大きさと起動時間を計測して DIS-0001 の H6 の証拠欄に記録する。
- AC-5: Node の版が足りないとき、分かるエラーで止まる。
- AC-6: 前提条件の要求が `accepted` になっている。

## 問題

prepare-dev を使う人が、どの機械・どの対象リポジトリでも、同じ書き方の設定で prepare-dev を起動して使えるようにしたい。

根の問題は、「`init` が機械固有の情報を対象リポジトリの設定に書き出し、ホストと入口がその情報に頼って起動する」こと。入口が自分の checkout の位置を求める仕組み（`toolRepoRoot()`、`import.meta.url` から逆算）自体は checkout がどこにあっても動き、可搬性を壊してはいない。壊しているのは `init` が書く次の四つ。

| 機械固有の情報 | どこに現れるか | 由来 |
| - | - | - |
| 道具リポジトリの `node_modules/.bin/tsx` の絶対パス | `.mcp.json` と `.codex/config.toml` の `command` | 道具リポジトリの位置 |
| 道具リポジトリの `packages/cli/src/index.ts` の絶対パス | 同 `args` | 道具リポジトリの位置 |
| 対象リポジトリ自身の絶対パス（`--root`） | 同 `args` | ホストが入口をどの cwd で起動するか分からないため、明示している |
| 道具リポジトリの `skills/*` への絶対 symlink | 対象リポジトリの `.agents/skills/*` | 道具リポジトリの位置 |

加えて、デーモンは配信する UI を道具リポジトリ内の `packages/ui/dist/index.html` で探す（checkout がある限りは動く）。

### 問題の範囲（段階）

「同じ書き方の設定で起動できる」には二つの段階があり、どこまでを今回の問題にするかは人の判断（質問 1 の判断 a）。

| 段階 | 内容 | 満たす案 |
| - | - | - |
| 段階 0: 作らない | 現状維持。機械ごとに `init` を実行する | A |
| 段階 1: 登録の可搬化 | 対象リポジトリに機械固有の絶対パスを書かない（git で共有できる登録にするか、対象リポジトリには何も書かない）。道具リポジトリの checkout と `node_modules` は利用者の機械にあってよい | G、B、C、D |
| 段階 2: 道具リポジトリに依存しない配布 | 道具リポジトリの checkout も `node_modules` もなしに、配布物だけで入口・デーモン・UI が動く | D（と、その先の F） |

段階 1 だけなら、ビルドは必須ではなく、コードをほとんど変えない案（G）もある。段階 2 まで含めるなら、成果物を一つに束ねる案 D が最短。所有者の当初の発想（`tsc -b` でビルドして `bin` を置く、案 C）は段階 1 を満たすが、段階 2 には届かず、段階 1 だけなら G や B より手間が多い。

## 代替案

案は「機械固有の情報をどこに置くか（間接化の場所）」と「何を実行するか」の二軸で分かれる。

| 案 | 間接化 | 実行形 | 内容 | 評価 |
| - | - | - | - | - |
| A 作らない | 対象リポジトリの登録ファイル内の絶対パス | tsx＋ソース | 現状維持。機械ごとに `init` を実行する運用 | 工数ゼロ。限界はそのまま。所有者一人・一機械なら足りる（H5 の確認が先） |
| G 利用者単位の登録 | ホームディレクトリのホスト設定（`~/.codex/config.toml` の `mcp_servers`、Claude Code の利用者スコープの MCP 登録）と利用者単位の skills 置き場（Claude Code は `~/.claude/skills`、Codex は `~/.agents/skills`） | tsx＋ソース | 対象リポジトリには何も書かない。絶対パスは機械ごとに一箇所だけ。root は cwd から取る。`init` は対象リポジトリの `prepare/` と `.prepare-dev/` だけを作る | 登録の変更はコードなしで試せる。ただし入口が機械上の全セッションで起動されるので、対象リポジトリでないときの振る舞い（終了するか、ツールを公開せず待つか）を決め、`prepare/` と `.prepare-dev/` を作らない抑止（H7。`ensureDaemon` が接続前に作るので、抑止はそれより前）が要る。15 個のツール説明（約 1.2 KB、スキーマ込みで千トークン規模）が無関係なプロジェクトの会話にも載り、セッション数ぶん Node プロセスが常駐する。利用者単位の登録も「機械で一つの指し先」なので、checkout が複数あるときの食い違いは B と同じ。「git で共有」ではなく「共有すべきものが無い」形で段階 1 を満たす。段階 2 には届かない。既存の `.gitignore` の方針（登録は機械固有）と整合する |
| B 起動シム | PATH 上の `prepare-dev` | tsx＋ソース | CLI package に小さな `bin` スクリプトを置き、既存の `toolRepoRoot()` で checkout を求めて tsx でソースを読む。`pnpm link --global` か `~/.local/bin` への symlink で PATH に置く。`init` は `command: "prepare-dev"`、`args` に絶対パスなし（root は cwd か環境変数）。UI も skills も checkout 内の相対位置で解決 | 段階 1 を小さな変更で満たし、登録を git で共有できる（`.gitignore` の方針転換と、追記型の `.codex/config.toml` の扱いが要る）。実行経路は一つのまま（二系統の乖離なし）。H2 より tsx の起動コストは問題でない。checkout と `node_modules` は必要。PATH の `prepare-dev` は機械で一つなので、checkout が複数あるときの優先規則が要る |
| C ビルド（`tsc -b`） | PATH 上の `prepare-dev` | node＋`dist/` | `exports` と `bin` を `dist/` に向け、`pnpm link --global` で PATH に置く。UI はパッケージ相対で解決 | 段階 1 を満たすが、6 package の `exports` 変更、開発時（tsx、vitest）とビルド時の解決先を分ける仕組み、版の報告の新設が要る。段階 2 には届かない（workspace 依存が `node_modules` に残る）。B より手間が多く、得るものは「tsx を外す」ことだけ。推奨しない |
| D 束ねる（esbuild） | PATH 上の `prepare-dev` | node＋単一ファイル | esbuild（tsx と vite の依存として既に導入済み）で入口＋runtime＋検証プラグインを一つの JS に束ね、UI HTML を同梱する。配布物はビルド済みの束を release 成果物として置く（利用者の機械でビルドしない） | 段階 1 と 2 を満たし、F への土台になる。MCP SDK の ESM 束ねと UI の同梱方法は要試行（H6）。ソースと束ねた物の二系統になるので版の報告が要る。段階 1 の作業（`init` から絶対パスを外す、root の既定、H1 の検証）は B と共通で、B から D へ進んでも捨てるのはシム一本程度。G から D へ進む場合は、G がコードをほぼ変えないため捨てるものは無く、利用者単位の登録を PATH の `prepare-dev` に書き換えるだけ。同梱と配布経路の細部は設計で決める |
| E Node の型除去で直実行 | — | node＋ソース | import 指定子を `.ts` にし `node` で直接動かす | tsx は消えるが、登録の問題を解かない。棄却 |
| F npm 公開 | PATH 上の `prepare-dev` | node＋公開物 | レジストリに公開し `npm i -g` | 具体化案 §1.7 で後回し。D の成果物をそのまま公開できる形にしておく |

推奨: 段階 1 なら G（コードをほぼ変えずに試せる。H7 の抑止と非対象時の振る舞いだけ足す）。G がホストの制約で使えない、または登録を git で共有したいなら B。段階 2 なら D。

対象リポジトリが道具リポジトリ自身（dogfooding）のときは、どの案でも、プロジェクト単位の登録を `command: "pnpm"`、`args: ["cli", "mcp", ...]` にすれば絶対パスなしで「その checkout のソース」が動き、worktree ごとの食い違いが消える（前提: ホストの cwd がプロジェクト＝H1、プロジェクト単位の登録が利用者単位より優先される＝H8）。

PATH 以外の間接化として、Claude Code の `.mcp.json` は `${VAR}` 形式の環境変数展開を持つ（Codex 側は未確認）。絶対パスを環境変数に逃がす手もあるが、環境変数の設定が機械ごとに要る点は G と同じなので、独立の案にはしない。

skills の置き方は案と独立に決められる（質問 1 の判断 b）。候補は、(i) 道具リポジトリへの相対 symlink（対象＝道具リポジトリのときだけ可）、(ii) 道具リポジトリまたは配布物への絶対 symlink（常に最新だが、移動で壊れる）、(iii) 対象リポジトリへのコピー（git で共有でき移動で壊れないが、更新の仕組みが要る。現在の `init` は既にあるものを飛ばすので、上書きか版の印の比較を新設する）、(iv) 利用者単位の置き場（案 G。対象リポジトリに何も書かない）。段階 1 では (ii) か (iv)、段階 2 では (iii) が自然。

## 制約

- Node >= 26、pnpm workspace、`workspace:*` 依存、各 package は `private`。`tsc -b` の project references は設定済み。
- 入口は stdio で起動される独立プロセス。ホストは `command` と `args` の形式で登録し、cwd と PATH はホストが決める。ホストが対象リポジトリを cwd にするか、環境変数を渡せるかは未検証（H1）。H1 が片方のホストで偽なら、そのホストだけ `init` が `--root` の絶対パスか `env` を書く逃げ道が要る。
- デーモンは対象リポジトリごとに一つで、`.prepare-dev/daemon.json` で発見する。入口が detached で起動するため、入口は自分がどの実行ファイル・どの checkout から動いているかを知る必要がある。
- 入口にもデーモンにも版・経路・checkout を報告する仕組みはない。二系統（ソース／ビルド）を持つ案（C、D）では、`daemon.json` に版・実行ファイル・checkout を記録し、入口が接続時に自分の値と照合して不一致なら失敗するか再起動する規則が設計の必須項目になる（`status` に出すだけでは、エージェントが `status` を呼ばない限り古いデーモンが黙ってツールを提供し続ける）。G と B では、`daemon.json` に道具リポジトリの位置を一項目足す最小形に留める。
- デーモンは対象リポジトリの数だけ常駐し、一つ約 100 MB（実測）。終了条件は無い。
- PATH 上の `prepare-dev`（B、C、D）も利用者単位の登録（G）も機械で一つの指し先なので、道具リポジトリの checkout が複数あるとき（worktree、別ブランチ、対象＝道具リポジトリ）に、編集中の checkout と実行される checkout が黙って食い違いうる。対象が道具リポジトリ自身のときはプロジェクト単位の登録（`pnpm cli mcp`）で自分のソースを優先する（H8）。
- `exports` の解決先を変える案（C）では、開発時（tsx、vitest）とビルド時で解決先を分ける仕組みが要る（手段は設計）。
- 検証プラグインが使う `vitest`（対象の `node_modules/.bin`）と `lake`（PATH）は対象リポジトリ側の道具で、配布の対象外。
- `command: "prepare-dev"` 形式の登録は、ホストのプロセス環境の PATH にその command があることに依存する。GUI から起動されたホストの PATH はシェルと違いうる。`pnpm link --global` は Node の版ごとの領域に置かれる（`~/.local/bin` 等への symlink なら生じない）。依存を受け入れるか、`init` が解決済みの絶対パスを書く逃げ道（可搬性を失う）を残すかは、先行作業 H1 の結果を見てから決めるのが自然（質問 1 の判断 c）。
- 既存の対象リポジトリに残る絶対パスの登録は、`init` が上書きしないため、移行には削除か上書きの手段が要る（設計で扱う）。登録を git で共有する案（B、C、D）では `.gitignore` の方針転換も要る。
- デーモンの HTTP は無認証で `access-control-allow-origin: *`。段階 2（他者の機械で動かす）を選ぶなら、origin の制限を前提条件として別件で先に扱う。

## 非目標

- npm レジストリへの公開と版管理（具体化案 §1.7 で後回し。ただし妨げない）。
- Windows 対応（`ui` の `open` と e2e が darwin／bash 前提。配布形態と独立に扱う）。
- デーモンの複数版共存と自動更新（入口が不一致を検出して失敗・再起動する規則は本件の範囲）。
- 検証ツール（`lake`、`vitest`）の配布。
- UI の見た目と開発サーバの変更。
- skills の内容の変更。置き方は本件の範囲に含める（非目標ではない）。
- デーモンの HTTP の認証と origin 制限（本件以前からある弱点で、配布形態と独立に直せる。別件で扱い、段階 2 を選ぶ場合はその前提条件にする）。

## リスク

- やらない場合: 道具リポジトリの移動や `node_modules` の削除で全対象が黙って壊れる。登録を共有できない。他者が試せない。
- H1 が偽の場合: 段階 1 の価値（絶対パスなしの登録）がそのホストでは成り立たず、逃げ道（ホストごとの `--root` か `env`）で部分的に保つことになる。どの案を選んでも同じなので、先行作業で確かめる。
- G の場合: 入口が全セッションで起動され、抑止（H7）が無いと無関係のプロジェクトに `prepare/` ができる。ツール説明が全セッションの会話に載り（千トークン規模）、セッション数ぶんプロセスが常駐する。利用者単位の設定は機械ごとに一度の手作業になる。
- B の場合: 道具リポジトリの checkout に依存し続ける。
- C と D の場合: ソースとビルドの二系統が乖離する。ビルド忘れで古い成果物や古いデーモンが動く。入口が接続時に照合しなければ、古いデーモンが黙ってツールを提供し続ける。C では vitest も `dist/` を見る経路が生まれる。
- G、B、C、D 共通: 機械で一つの指し先なので、checkout が複数あるときに編集中と実行中が食い違う（H8 で緩和）。ホストの PATH に `prepare-dev` が無いときの起動失敗がホストのログにしか出ず、既存の単一障害点（道具リポジトリの位置）を別の単一点（PATH）に移すだけになりうる。緩和（絶対パスの逃げ道、対象側への起動ログ）は H1 の結果を見て設計で決める。
- 段階 2 の場合: 無認証・origin 無制限のデーモンが他者の機械でも動く。前提条件として origin 制限を先に入れる。
- 見返り: 対象リポジトリに機械固有の情報が残らない再現性、第三者への配布の土台。

## 成功

- 先行作業: H1 の検証結果（三通りの起動形態ごとに接続可否と、入口が見た cwd と環境変数）が本記録の H1 の証拠欄に残り、状態が「決定」になる。
- 中間: `init` の出力に絶対パスが一切含まれない（道具リポジトリ、対象リポジトリとも。G では対象リポジトリに登録ファイル自体が無い）。PATH 上の `prepare-dev`（G では利用者単位の登録）だけで `status` が返る。UI が簡易フォームではなく本来の UI で表示される。G では、対象でないプロジェクトで入口が起動されても `prepare/` も `.prepare-dev/` もできず、ツールも公開されない。
- 最終: 別の対象リポジトリで `init` し、Codex と、シェルからと GUI から起動した Claude Code の両方が接続し、質問の作成から UI での回答、`question_apply` までが通る。道具リポジトリを別の場所に移しても（B と C では再 link 後、D では無条件に、G では利用者設定の更新後に）対象リポジトリ側を変えずに動き、skills も解決される。対象＝道具リポジトリの worktree で作業したとき、その checkout のソースが動く（H8）。C と D では、入口とデーモンが版・経路を報告し、ソースだけ直してビルドしていない状態と、再ビルド後に古いデーモンが残る状態の両方で、入口が接続時に不一致を検出して失敗または再起動する。Node の版を切り替えた後も `prepare-dev` が解決される（`pnpm link --global` を使うなら、解決されなくなることを確認した上で `~/.local/bin` 等に切り替える）。`pnpm test` と `scripts/e2e-crash.sh`（実デーモンを強制終了して回答の適用が回復することを確かめる既存の e2e）が通る。

## レビューの経緯

BRAINSTORM の shootdown を三回行った（zoom_out、comprehension、design_critic の三 persona、会話履歴なし）。round 1 は REV-0001〜0003（rev 1 → rev 2）、round 2 は REV-0004〜0006（rev 2 → rev 3）、round 3 は REV-0007〜0009（rev 3 → 本版）。各 round で各 persona が新しい Major を三〜四件出し、再開（同じ箇所への再指摘）は無かった。費用の都合で round 3 で止め、未対処の Major は残していない。design_critic-1-3（PATH 依存の受容）は質問 1 の判断 c に送った。

| guidance 文書 | 検証プラグインが `guidance()` で名前を返す相対パスの文書（`guidance/lean4.md` など）。現在はそれを読む側の実装が無い |
| `status`、`question_apply` | runtime の操作名。`status` は未処理の回答や未対処の指摘の一覧、`question_apply` は人の回答を判断（`DEC-*`）として確定する操作。CLI と MCP の両方にある |
| 具体化案 | `docs/2026-11-08-concretization-proposal.md`。§1.7 が配布と起動の当初方針、§0 がホストの環境調査 |
| 状態（決定／仮説／未検証／対象外） | 記録の `coverage` と仮説の状態。YAML の値はそれぞれ `decided`／`hypothesis`／`unverified`／`out_of_scope`。**決定**: 証拠または人の判断で確定した。**未検証**: 試せば分かるが未試行。**仮説**: 人の判断や利用の反応がないと確かめられない。**対象外**: 今回扱わない（理由を書く）。`coverage` の値が `hypothesis` なら、その観点の内容が人の判断待ちであることを示す |
