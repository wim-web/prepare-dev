## 問題

prepare-dev を使う人が、どの機械・どの対象リポジトリでも、同じ書き方の設定で prepare-dev を起動して使えるようにしたい。

根の問題は、「`init` が機械固有の情報を対象リポジトリの設定に書き出し、ホストと入口がその情報に頼って起動する」こと。入口が自分の checkout の位置を求める仕組み（`toolRepoRoot()`、`import.meta.url` から逆算）自体は checkout がどこにあっても動き、可搬性を壊してはいない。壊しているのは `init` が書く次の四つ。

| 機械固有の情報 | どこに現れるか | 由来 |
| - | - | - |
| 道具リポジトリの `node_modules/.bin/tsx` の絶対パス | `.mcp.json` と `.codex/config.toml` の `command` | 道具リポジトリの位置 |
| 道具リポジトリの `packages/cli/src/index.ts` の絶対パス | 同 `args` | 道具リポジトリの位置 |
| 対象リポジトリ自身の絶対パス（`--root`） | 同 `args` | ホストが入口をどの cwd で起動するか分からないため、明示している |
| 道具リポジトリの `skills/*` への絶対 symlink | 対象リポジトリの `.agents/skills/*` | 道具リポジトリの位置 |

加えて、デーモンは配信する UI を道具リポジトリ内の `packages/ui/dist/index.html` で探す（checkout がある限りは動く）。

### 問題の範囲（段階）

「同じ書き方の設定で起動できる」には二つの段階があり、どこまでを今回の問題にするかは人の判断（質問 1 の判断 a）。

| 段階 | 内容 | 満たす案 |
| - | - | - |
| 段階 0: 作らない | 現状維持。機械ごとに `init` を実行する | A |
| 段階 1: 登録の可搬化 | 対象リポジトリに機械固有の絶対パスを書かない（git で共有できる登録にするか、対象リポジトリには何も書かない）。道具リポジトリの checkout と `node_modules` は利用者の機械にあってよい | G、B、C、D |
| 段階 2: 道具リポジトリに依存しない配布 | 道具リポジトリの checkout も `node_modules` もなしに、配布物だけで入口・デーモン・UI が動く | D（と、その先の F） |

段階 1 だけなら、ビルドは必須ではなく、コードをほとんど変えない案（G）もある。段階 2 まで含めるなら、成果物を一つに束ねる案 D が最短。所有者の当初の発想（`tsc -b` でビルドして `bin` を置く、案 C）は段階 1 を満たすが、段階 2 には届かず、段階 1 だけなら G や B より手間が多い。

## 価値

- 段階 1: 対象リポジトリに機械固有の情報が残らず、clone 直後に（道具リポジトリがあれば）起動だけで使える。道具リポジトリの場所変更が対象リポジトリ側の設定に波及しない。
- 段階 2: 道具リポジトリと `node_modules` が要らなくなり、他者が試せる状態への最短経路になる。
- 起動時間の短縮は副次的で、価値の中心ではない（束ねた成果物の起動時間と大きさは未計測。H6 の試行で測る）。

対象リポジトリが道具リポジトリ自身（dogfooding）のときは、どの案でも、プロジェクト単位の登録を `command: "pnpm"`、`args: ["cli", "mcp", ...]` にすれば絶対パスなしで「その checkout のソース」が動き、worktree ごとの食い違いが消える（前提: ホストの cwd がプロジェクト＝H1、プロジェクト単位の登録が利用者単位より優先される＝H8）。

PATH 以外の間接化として、Claude Code の `.mcp.json` は `${VAR}` 形式の環境変数展開を持つ（Codex 側は未確認）。絶対パスを環境変数に逃がす手もあるが、環境変数の設定が機械ごとに要る点は G と同じなので、独立の案にはしない。

skills の置き方は案と独立に決められる（質問 1 の判断 b）。候補は、(i) 道具リポジトリへの相対 symlink（対象＝道具リポジトリのときだけ可）、(ii) 道具リポジトリまたは配布物への絶対 symlink（常に最新だが、移動で壊れる）、(iii) 対象リポジトリへのコピー（git で共有でき移動で壊れないが、更新の仕組みが要る。現在の `init` は既にあるものを飛ばすので、上書きか版の印の比較を新設する）、(iv) 利用者単位の置き場（案 G。対象リポジトリに何も書かない）。段階 1 では (ii) か (iv)、段階 2 では (iii) が自然。

## 制約

- Node >= 26、pnpm workspace、`workspace:*` 依存、各 package は `private`。`tsc -b` の project references は設定済み。
- 入口は stdio で起動される独立プロセス。ホストは `command` と `args` の形式で登録し、cwd と PATH はホストが決める。ホストが対象リポジトリを cwd にするか、環境変数を渡せるかは未検証（H1）。H1 が片方のホストで偽なら、そのホストだけ `init` が `--root` の絶対パスか `env` を書く逃げ道が要る。
- デーモンは対象リポジトリごとに一つで、`.prepare-dev/daemon.json` で発見する。入口が detached で起動するため、入口は自分がどの実行ファイル・どの checkout から動いているかを知る必要がある。
- 入口にもデーモンにも版・経路・checkout を報告する仕組みはない。二系統（ソース／ビルド）を持つ案（C、D）では、`daemon.json` に版・実行ファイル・checkout を記録し、入口が接続時に自分の値と照合して不一致なら失敗するか再起動する規則が設計の必須項目になる（`status` に出すだけでは、エージェントが `status` を呼ばない限り古いデーモンが黙ってツールを提供し続ける）。G と B では、`daemon.json` に道具リポジトリの位置を一項目足す最小形に留める。
- デーモンは対象リポジトリの数だけ常駐し、一つ約 100 MB（実測）。終了条件は無い。
- PATH 上の `prepare-dev`（B、C、D）も利用者単位の登録（G）も機械で一つの指し先なので、道具リポジトリの checkout が複数あるとき（worktree、別ブランチ、対象＝道具リポジトリ）に、編集中の checkout と実行される checkout が黙って食い違いうる。対象が道具リポジトリ自身のときはプロジェクト単位の登録（`pnpm cli mcp`）で自分のソースを優先する（H8）。
- `exports` の解決先を変える案（C）では、開発時（tsx、vitest）とビルド時で解決先を分ける仕組みが要る（手段は設計）。
- 検証プラグインが使う `vitest`（対象の `node_modules/.bin`）と `lake`（PATH）は対象リポジトリ側の道具で、配布の対象外。
- `command: "prepare-dev"` 形式の登録は、ホストのプロセス環境の PATH にその command があることに依存する。GUI から起動されたホストの PATH はシェルと違いうる。`pnpm link --global` は Node の版ごとの領域に置かれる（`~/.local/bin` 等への symlink なら生じない）。依存を受け入れるか、`init` が解決済みの絶対パスを書く逃げ道（可搬性を失う）を残すかは、先行作業 H1 の結果を見てから決めるのが自然（質問 1 の判断 c）。
- 既存の対象リポジトリに残る絶対パスの登録は、`init` が上書きしないため、移行には削除か上書きの手段が要る（設計で扱う）。登録を git で共有する案（B、C、D）では `.gitignore` の方針転換も要る。
- デーモンの HTTP は無認証で `access-control-allow-origin: *`。段階 2（他者の機械で動かす）を選ぶなら、origin の制限を前提条件として別件で先に扱う。

## 非目標

- npm レジストリへの公開と版管理（具体化案 §1.7 で後回し。ただし妨げない）。
- Windows 対応（`ui` の `open` と e2e が darwin／bash 前提。配布形態と独立に扱う）。
- デーモンの複数版共存と自動更新（入口が不一致を検出して失敗・再起動する規則は本件の範囲）。
- 検証ツール（`lake`、`vitest`）の配布。
- UI の見た目と開発サーバの変更。
- skills の内容の変更。置き方は本件の範囲に含める（非目標ではない）。
- デーモンの HTTP の認証と origin 制限（本件以前からある弱点で、配布形態と独立に直せる。別件で扱い、段階 2 を選ぶ場合はその前提条件にする）。

## リスク

- やらない場合: 道具リポジトリの移動や `node_modules` の削除で全対象が黙って壊れる。登録を共有できない。他者が試せない。
- H1 が偽の場合: 段階 1 の価値（絶対パスなしの登録）がそのホストでは成り立たず、逃げ道（ホストごとの `--root` か `env`）で部分的に保つことになる。どの案を選んでも同じなので、先行作業で確かめる。
- G の場合: 入口が全セッションで起動され、抑止（H7）が無いと無関係のプロジェクトに `prepare/` ができる。ツール説明が全セッションの会話に載り（千トークン規模）、セッション数ぶんプロセスが常駐する。利用者単位の設定は機械ごとに一度の手作業になる。
- B の場合: 道具リポジトリの checkout に依存し続ける。
- C と D の場合: ソースとビルドの二系統が乖離する。ビルド忘れで古い成果物や古いデーモンが動く。入口が接続時に照合しなければ、古いデーモンが黙ってツールを提供し続ける。C では vitest も `dist/` を見る経路が生まれる。
- G、B、C、D 共通: 機械で一つの指し先なので、checkout が複数あるときに編集中と実行中が食い違う（H8 で緩和）。ホストの PATH に `prepare-dev` が無いときの起動失敗がホストのログにしか出ず、既存の単一障害点（道具リポジトリの位置）を別の単一点（PATH）に移すだけになりうる。緩和（絶対パスの逃げ道、対象側への起動ログ）は H1 の結果を見て設計で決める。
- 段階 2 の場合: 無認証・origin 無制限のデーモンが他者の機械でも動く。前提条件として origin 制限を先に入れる。
- 見返り: 対象リポジトリに機械固有の情報が残らない再現性、第三者への配布の土台。

## 成功

- 先行作業: H1 の検証結果（三通りの起動形態ごとに接続可否と、入口が見た cwd と環境変数）が本記録の H1 の証拠欄に残り、状態が「決定」になる。
- 中間: `init` の出力に絶対パスが一切含まれない（道具リポジトリ、対象リポジトリとも。G では対象リポジトリに登録ファイル自体が無い）。PATH 上の `prepare-dev`（G では利用者単位の登録）だけで `status` が返る。UI が簡易フォームではなく本来の UI で表示される。G では、対象でないプロジェクトで入口が起動されても `prepare/` も `.prepare-dev/` もできず、ツールも公開されない。
- 最終: 別の対象リポジトリで `init` し、Codex と、シェルからと GUI から起動した Claude Code の両方が接続し、質問の作成から UI での回答、`question_apply` までが通る。道具リポジトリを別の場所に移しても（B と C では再 link 後、D では無条件に、G では利用者設定の更新後に）対象リポジトリ側を変えずに動き、skills も解決される。対象＝道具リポジトリの worktree で作業したとき、その checkout のソースが動く（H8）。C と D では、入口とデーモンが版・経路を報告し、ソースだけ直してビルドしていない状態と、再ビルド後に古いデーモンが残る状態の両方で、入口が接続時に不一致を検出して失敗または再起動する。Node の版を切り替えた後も `prepare-dev` が解決される（`pnpm link --global` を使うなら、解決されなくなることを確認した上で `~/.local/bin` 等に切り替える）。`pnpm test` と `scripts/e2e-crash.sh`（実デーモンを強制終了して回答の適用が回復することを確かめる既存の e2e）が通る。

## レビューの経緯

BRAINSTORM の shootdown を三回行った（zoom_out、comprehension、design_critic の三 persona、会話履歴なし）。round 1 は REV-0001〜0003（rev 1 → rev 2）、round 2 は REV-0004〜0006（rev 2 → rev 3）、round 3 は REV-0007〜0009（rev 3 → 本版）。各 round で各 persona が新しい Major を三〜四件出し、再開（同じ箇所への再指摘）は無かった。費用の都合で round 3 で止め、未対処の Major は残していない。design_critic-1-3（PATH 依存の受容）は質問 1 の判断 c に送った。

## 変更の範囲

## 判断画面の契約

- エージェントは質問の背景、何を決めるか、なぜ人の判断が必要か、候補とその帰結、推奨と理由を整理する。
- `prompt` の説明と、`options` の `label`、`summary`、`recommended`、`reason` を React の部品で表示する。説明は Markdown の段落・箇条書き・表を表示でき、比較が必要なときは表を使える。画面の配置は UI 側が管理する。
- 一つの質問は一つの独立した判断を扱う。複数の判断は別の質問にする。複数選択は一つの判断の中で複数候補を選ぶ場合に使う。
- 技術的な調査で決められる事項はエージェントが調べて処理する。人に尋ねるのは目的、優先順位、価値判断、許容するトレードオフ、調査では得られない事実。
- CLI から質問の内容を登録し、ブラウザ UI で回答し、その回答を runtime から取得・判断として適用できる。DEC-0004 の CLI 配布の方針と、MCP の入口を提供しない DEC-0007 に従う。
- 回答と対象の版の対応、一度だけの適用、中断後の再取得、検証プラグインの契約は変更しない。

## 廃止する契約と実装との差

新しい質問作成 API は画面レイアウト用の `ui` を受け取らず、`ui.spec` を正本に含めない。CLI に画面 JSON を渡す機能は追加しない。旧 `GET /api/questions/:id/ui` の json-render spec 生成契約も廃止し、UI は質問データから描画する。

移行時は CLI・MCP・HTTP の入力、UI の呼び出し、runtime の生成処理、依存パッケージを同じ変更で更新する。過去の質問と回答は保持し、既存質問の `ui.spec` が残っていても新しい表示には使わない。過去の回答や判断を書き換えない。

## 変更後の受入条件

4. json-render の依存・画面生成・catalog 検証を要求せずに、1〜3 を満たす。既存の版照合、二重適用防止、再取得の検証も通る。

  - デーモンはすべての操作の前に lease のファイルが自分のロックしているものかを確かめ、違えば書かずに終わる。init は .prepare-dev/.gitignore にデーモンのファイルを書く。
  - "移行期の対策（TypeScript 版を使うプロジェクトが残っていないことを確かめてから外す）: 識別に TypeScript 版が読む root と mode も書き、TypeScript 版の書いた daemon.json があってその版の lease のポートが取られていれば引き継がない。"
  - デーモンは同じ実行ファイルを serve で起動し直し、新しいセッションで端末から切り離す。起動したデーモンが応答せずに終われば、CLI は待たずに daemon.log の最後の行を示す。
  - HTTP の経路は標準の ServeMux で振り分ける。回答の API は判断画面（同じ origin のブラウザの要求）からだけ受け付け、CLI に回答の操作を置かない。
  - verify と trace の CLI の出力は既定で要約し、--json で全体を出す。
  - skills を入れたときの digest を .prepare-dev/skills.json に残し、編集されていない skill は次の init で置き換える。--replace-skills で、違うものを退避してから置き換える。
  - vitest プラグインは esbuild のバンドルの解決（拡張子は Vite の順）とメタファイルで入力を集める。型だけの import は入力にしない。
  - Go のテストを証拠にする gotest プラグインを加える。テストが読むファイルは testdata を自動で、それ以外は impl_files（** を使えるパターン）で入力にし、テストが実行中にビルドするパッケージは input_packages で加える。デーモンの PREPARE_DEV_ で始まる環境変数はテストに渡さず、テストは RUN ごとのディレクトリに書いた内容を scope.bounds に残せる。
  - 入力を集めたディレクトリのファイル名の一覧を RUN に記録し、ファイルの追加でも証拠を当てはまらないものにする。
  - 判断画面のビルドにソースの digest と出力の sha256 を記録し（build.json）、Go のテストとリリースで照合する。
  - Lean のモデルから操作列を作り直して照合できたときだけ、model/bin/test がモデルの digest を model/traces/model.sha256 に書き、Go のテストが今のモデルと照合する。
  - 記録を書く作業コピーは一つとし、二つの作業コピーで書いた prepare/ のマージの衝突は人がマージのときに直す（DEC-0008）。デーモンは、起動時にジャーナルの矛盾を、操作の前にジャーナルの置き換わりを確かめ、どちらでも何も書かない。
  - MCP の入口を作らない（DEC-0007）。
  - 工程の外で残すものには記録の種類 record（REC-*）と proposal（PRO-*）を使い、確認記録は確かめた記録を自分の links.related_to から指す（§工程の外の記録）。この規則は skills ですべての対象プロジェクトに入る。

  - status は、init が入れた skills の配置先に対して init を書き込まずに動かし、次の init がすること（入れる、置き換える、残す）を示す。

## 実行時の流れ

CLI は root の `.prepare-dev/daemon.json` を読み、書かれた URL の `/api/identity` に問い合わせて、動いているデーモンの version と build を自分のものと比べる。デーモンは HTTP を始めてから daemon.json を書くので、lease が取られていて daemon.json が無い間は起動中である。

| 状況 | CLI の振る舞い |
| --- | --- |
| daemon.json がなく、lease も空いている | 同じ実行ファイルを `serve --root <root>` で起動し、端末から切り離す（新しいセッション）。起動したものが応答せずに終わったら、待たずに daemon.log の最後の行（起動できなかった理由）を示して終える。別の起動に lease を取られたときは、その相手が応答するのを待つ |
| デーモンが応答し、version と build が同じ | 接続する。置き場所が違う同じ build の写しも接続する |
| デーモンが応答し、version か build が違う | 接続しない。相手の version・build・場所・pid と、`prepare-dev stop --root <root>` で止めてから再実行することを示して終える |
| デーモンが停止を受け付けた後で、まだ終わっていない | identity にだけ答え、ほかの要求は 409 で拒む。CLI はその誤りを示して終える（止まってから再実行する） |
| daemon.json はあるが応答せず、lease が空いている | 強制終了したデーモンの残りとみなし、daemon.json を消して起動する。ただし daemon.json を TypeScript 版が書いていて、その版の lease がまだ取られているときは、引き継がずに止め方を示して終える（移行期の対策。§TypeScript 版からの移行） |
| lease が取られているが応答がない（daemon.json の有無によらない） | 起動中かもしれないので、時間（既定 15 秒）まで待つ。それでも応答しなければ、lease ファイルに書かれた pid を示して終える（そのプロセスを止めて再実行する） |

デーモンは、lease を取ってから記録を開き（走査と回復を済ませる）、127.0.0.1 の空いているポートで HTTP を始め、daemon.json（pid、ポート、URL、root、起動時刻、version と build と場所、停止用のトークン）を書く。lease はプロセスの終了とともに OS が外す。停止は `prepare-dev stop` が daemon.json のトークンで `/api/shutdown` を呼ぶ。検証ジョブの実行中は拒否する。デーモンは止めるまでプロジェクトごとに一つ残る。

デーモンを置く理由は三つある。人が回答している間も判断画面をいつでも開けること、回答や検証の完了を画面とエージェントの待機（`q wait`、`verify wait`）へ届けること、検証を非同期に走らせて結果を同じ書き手が記録すること。CLI がその都度ファイルロックを取って直接書く形では、画面と待機のために結局どこかで HTTP を出し続ける必要がある（代替案 no-daemon）。

## 書き手を一つにする

lease が守るのは、一つの root の永続状態（記録、質問、RUN、ジャーナル）を開くプロセスが一つだけであること。ID の採番と回答の適用は、メモリ上の索引とジャーナルを一つの書き手が持つ前提で作っている（SPEC-0001 の前提）。lease のファイルは root の中にあるので、root をどのパスで指してもロックは同じファイルに掛かる。lease を取れない `serve` は記録を開く前に終わる（CLI が lease を確かめるために一瞬ロックするので、取得は 1 秒だけ再試行する）。

lease のファイルを動作中に消されると（`git clean`、`git stash -u` など）、次の CLI は lease が空いていると見て二つ目のデーモンを起動できてしまう。これを防ぐため、デーモンはすべての操作の前に、lease のパスが自分のロックしているファイルと同じものかを確かめ、違えば何も書かずに 503 を返し、2 秒以内に終わる。`init` は `.prepare-dev/.gitignore` に daemon.json・daemon.log・lease などを書き、これらが消されたりコミットされたりしにくくする。

保証は作業コピーごとである。ブランチや worktree の作業コピーはそれぞれのデーモンを持ち、同じ基準から別々に ID を採番するので、記録を書く作業コピーは一つにする（配布物の README と prepare-dev skill に書く）。二つの作業コピーで書いた prepare/ をマージすると、同じ番号の記録とジャーナルが衝突する。これは普通のコンフリクトとして、マージのときに人が直す（DEC-0008）。prepare-dev は自動でまとめず、直し方の手順も持たない。代わりに、直した結果を黙って書き進めないための検査を持つ。

- ジャーナルに衝突の印が残っている: デーモンは起動せず、CLI が待たずにその理由（daemon.log の最後の行）を示す。
- 直した結果に矛盾がある（同じ記録・質問・回答の二度の作成、同じ decision の二つの取引、一つの回答の二つの確定、別の作業コピーで判断に反映した回答や decision が残っている）: デーモンは起動するが、回復も含めて何も書かず、status の problems に示す。
- ブランチの切り替え・stash・reset・pull で Git がジャーナルを置き換えた: 動いているデーモンは、操作の前にジャーナルが開いたときと同じファイル・同じ長さかを確かめ、違えば何も書かずに止まる。次のコマンドが今のジャーナルで起動し直す。

別の名前のファイルが同じ ID を持つ場合（手で写したときなど）は、二つ目を problems に示してどちらも書き換えない。

## データの形式

記録の Markdown（YAML の frontmatter）、質問と RUN の JSON（2 文字の字下げ）、ジャーナル（JSON Lines）の形式は TypeScript 版から変えない。読むだけではファイルを書かないので、記録ファイルの sha256（版として質問・判断・レビュー・RUN が参照する）は、内容を変えない限り変わらず、版の切り替えでファイルが書き換わることもない。

書き方（YAML の引用と順序、JSON の並び）まで TypeScript 版と同じにするのは、runtime が書き直すファイル、つまり記録（`record put` と外部編集の検出）と質問（回答・受領・終了・適用）の差分を、変えた項目だけにするためである。記録は Git に入れて差分で読む。RUN は完了時に一度書くだけ、ジャーナルは追記だけで書き直さないので、書き方の一致は求めず、読んで欠ける項目がないこと（API と回復が使う）だけを求める。

基準は TypeScript 版の最後のコミット（342bc64）が書いたファイルの写し（internal/core/testdata/ts-342bc64）で、テストは写しの記録と質問を読み直して書き出してもバイト列が変わらないこと（`cancelled` の無い古い質問に `cancelled: null` が加わるのは TypeScript 版と同じ）、RUN とジャーナルの行は読んで書き出しても欠ける項目がないこと（書き方は問わない）を確かめる（SPEC-0004 D1）。YAML の書き出しは npm の yaml パッケージに合わせて自前で実装した。書く前に読み戻し、内容が一致しなければ書かない。YAML 1.1 の読み手が改行とみなす文字（U+2028、U+2029、U+0085）と制御文字は、二重引用符の中でエスケープする。

## HTTP API

経路は標準の ServeMux で振り分ける。判断画面と CLI が使う経路は次のとおり。

| 経路 | 用途 |
| --- | --- |
| `GET /api/identity` | pid、root、起動時刻、version・build・場所 |
| `POST /api/shutdown` | 停止（daemon.json のトークンが必要） |
| `GET /api/status` | 未処理の回答、回答待ちの質問、未対処の指摘、適用できない証拠、記録されなかった検証、問題、次の init が skills にすること |
| `GET/POST /api/records`、`GET/PUT /api/records/:id` | 記録の一覧・作成・取得・更新（更新は読んだ版が必要） |
| `GET/POST /api/questions`、`GET /api/questions/:id`、`GET /api/pending` | 質問の一覧・作成・取得、未処理の回答 |
| `POST /api/questions/:id/answers` | 回答（判断画面からだけ） |
| `GET /api/questions/:id/wait` | 回答を待つ |
| `POST /api/questions/:id/answers/:aid/ack`、`.../apply`、`.../close`、`POST /api/questions/:id/cancel` | 受領、判断への適用、終了、取り消し |
| `GET/POST /api/runs`、`GET /api/runs/:id`、`GET /api/runs/:id/wait` | 検証の一覧・開始・取得・待機 |
| `GET /api/trace/:id`、`GET /api/bundle`、`GET /api/plugins` | trace、レビュー資料、プラグイン一覧 |
| `GET /events` | 変更の通知（SSE） |
| `GET /`、`GET /q/:id` | 判断画面 |

Host が `127.0.0.1:<port>` か `localhost:<port>` でない要求と、Origin が自分以外の要求は 403 で拒否する。回答は判断画面の人のものなので、Origin を持たない要求（ブラウザ以外）も拒否し、CLI に回答の操作を置かない。これで防ぐのは、エージェントが手順どおりに CLI で回答することと、ほかのサイトのページからの要求である。同じ利用者のプロセスが Origin を付けて送ることは防がない（受け入れた残りのリスク）。loopback の API に認証は無いので、一人の利用者のホストを前提にする。エラーは `{error, message, details}` の形で返し、500 は daemon.log にも書く。

## CLI

コマンドは `init`、`status`、`ui`、`pending`、`record create|get|put|list`、`q create|list|show|wait|pending|ack|apply|close|cancel`、`verify run|wait|get|list`、`trace`、`bundle`、`serve`、`stop`、`version`。`mcp` と `q answer` は無い。出力は JSON で、`status` は既定で文章（`--json` で JSON）。エージェントが読む `verify` と `trace` は、入力ファイルの一覧を件数に、不一致と実行したテストの一覧を先頭の 5 件と残りの数に縮め、`verify list` は実行ごとの要約にする。`--json` で全体を出す。

## init と skills

`init` は `.prepare-dev/config.json` と `.prepare-dev/.gitignore` がなければ作り（あれば変えない）、skills を `.agents/skills` と `.claude/skills` にコピーし（`--skills-dir` で変更、`--no-skills` で省略）、デーモンを起動する。MCP の設定は書かない。

skills のコピーは、入れた skill の digest を `.prepare-dev/skills.json` に残す。次の `init` では、無い skill を入れ、同じ内容なら何もせず、前に入れたときのまま編集されていない skill は新しい版に置き換える。それ以外の違い（利用者の編集、別の方法で置いたもの）は残して conflicts に示す。`--replace-skills` を付けると、違うものを `.prepare-dev/skills-backup/<時刻>/` に移してから置き換える。root の外、シンボリックリンク、ディレクトリでない配置先は触らずに示す。

status は、init が入れた skills の配置先（skills.json に記録したもの）に対して init を書き込まずに動かし、次の init がすることを示す。入れるもの（この build にあって配置先に無いもの）、置き換えるもの（init が入れて編集されていない、この build と違うもの）、残すもの（編集されたもの、シンボリックリンク、init が入れていないもの。`--replace-skills` はシンボリックリンクでないものを退避して置き換える）。skills.json が無ければ（init で入れていない、`--no-skills`）示さない。

## 判断画面のビルド

ui/ の `pnpm build` が build/index.html、画面に入れた npm パッケージのライセンス（build/THIRD_PARTY_NOTICES.txt）、build/build.json を書く。build.json には、ビルドの元にしたソースの digest と、出力の二つのファイルの sha256 が入る。ソースは ui 直下の index.html・package.json・pnpm-lock.yaml・tsconfig.json・vite.config.ts と、src/ の下のファイル（テストと、`.` で始まる名前を除く）である。Go のテスト（SPEC-0004 B1）とリリースのスクリプトは、今のソースの digest と出力の sha256 を build.json と照合し、ソースを変えてビルドし直していないときも、出力を手で書き換えたときも失敗する。この範囲は、ビルド（ui/vite.config.ts）と Go（internal/uibuild）の二か所に同じ一覧として書き、src/ の外にビルドの入力を足すときは両方を直す。二つの計算が食い違えば B1 が失敗して分かる。Node.js（pnpm・Vite）は画面を直す人だけが使い、prepare-dev のビルドと利用には要らない。

## 検証プラグイン

- lean4: `lake env lean --src-deps` を再帰的に使って入力を集め、`lake build` と `#check`・`#print axioms` で確かめる。Lean はモジュールの名前で import を読むので、ファイルが増えても結果は変わらず、ディレクトリの一覧は記録しない。
- vitest: テスト・追加実装・Vitest の設定から、esbuild のバンドルと同じ規則で import をたどり、esbuild が読み込むファイルを入力にする。拡張子の無い import は Vite の既定の順で探す。node_modules の中のパッケージは manifest と lockfile で代表し、型だけの import は実行時に読まれないので入力にしない。import が読むファイルのディレクトリ（その段だけ）と、impl_files のパターンが探すディレクトリの一覧を記録する（SPEC-0003 V1）。
- gotest: go list が報告するテストのビルドに使うファイル、実行するパッケージの testdata、テストが実行中にビルドするパッケージ（`input_packages`）、そのほかに読むファイル（`impl_files`、`**` を使えるパターン）を入力にし、パッケージ・埋め込み・testdata・パターンのディレクトリの一覧を記録して、`go test -json -count=1` で、テストのキャッシュを使わずに実行する（SPEC-0003 V3。集めるファイルの種類は SPEC-0003 だけに書く）。デーモン自身の環境の `PREPARE_DEV_` で始まる変数はテストに渡さない（ほかの環境変数はデーモンのものが渡る）。テストは RUN ごとのディレクトリ（`PREPARE_DEV_BOUNDS_DIR`）に、流した件数や検査した実行ファイルを書いて scope.bounds に残せる。

runtime は、入力の内容の変更・削除と同じく、記録したディレクトリの一覧が変われば証拠を当てはまらないものにする。どのプラグインも、検証器の有無を project_dir で調べ（elan が project_dir の lean-toolchain の版を選ぶ）、使った道具の場所を RUN の `tool.extra` に残す。検証はデーモンが動かすので、道具の探し方（PATH に `~/.elan/bin`・`~/.cargo/bin`・`~/.local/bin` を足す）と環境変数は、デーモンを起動した CLI のものが使われ続ける。

## 工程の外の記録

工程の記録（DIS・REQ・DEC・DES・SPEC・REV）と検証の結果（RUN）のほかに、工程の外で残すものには記録の種類 record（REC-*）と proposal（PRO-*）を使う。どちらも runtime を通して書く。

- record: 確認記録（用語）と、貼り付けられた引き継ぎの文書の原文のように、工程の外で起きたことの記録。
- proposal: 工程の外で作った案（工程に入る前の具体化案など）。採ったものは工程の記録に引き継ぎ、置き換わったら superseded にする。

### すべての対象プロジェクトに入る規則

skills（prepare-dev の共通規則と prepare-verify の手順）が、すべての対象プロジェクトのエージェントに次を求める。このリポジトリも対象プロジェクトの一つとして従う。

- 工程の記録を runtime の外のファイル（docs/ など）に書かない。
- 書き込みが止まっている間は、確かめたことを人への報告に書き、直った後に確認記録にする。書き込みが止まっているのは、runtime が「Nothing is written until …」の誤りで書き込みを拒む間（マージしたジャーナルの矛盾と、回復できない取引。status の problems にもその理由が出る）と、デーモンが起動しない間（ジャーナルに衝突の印があるときなど）である。status の problems には書き込みを止めないもの（読めない記録のファイル、同じ ID の二つ目のファイル、どの取引も使っていない読めない質問のファイル）も出るので、problems があることだけで記録を控えない。
- 確認記録は、確かめた SPEC・REQ・DES を自分の links.related_to から指し、確かめられる側は確認記録を links にも本文にも書かない。確かめられる側の版が進むと、その版を控えた RUN が当てはまらなくなるので、確認を足すたびに RUN を取り直すことにならないようにするため。どの確認記録が何を確かめたかは trace で引く（trace は links を両方向にたどる）。
- 手の確認は人かエージェントが行い、誰が行ったかを本文に書く。確認は一回ごとに新しい確認記録にし、後から書き足さない。
- frontmatter の checked には、確かめたものを後から特定できる値を書く。commit（確かめたものを作ったソースのコミット）と、成果物や配布物を確かめたならその sha256。確認は変更の無い作業コピーから作ったもので行う。変更のある作業コピーから作ったものを確かめたときは、commit の代わりに base_commit と dirty: true を書き、後から同じものを作れないことを本文に書く。
- 今の版を確かめた確認記録があることは工程の終わりの関門にせず、prepare-verify の報告で、checked の commit から今の HEAD までの差分が、その確認の対象（仕様が手の確認を求める部分）に触れるかを示す。
- 確認記録の添付（画像、出力の JSON）は `<records_dir>/records/<id>/` に置く（records_dir は既定で prepare）。runtime は添付を読まず、記録の版にも含めないので、本文に添付の sha256 を書き、添付を変えたら本文も書き直す。

### このリポジトリでのやり直しの条件

このリポジトリでは、checked の commit の後に次の場所を変えたら、手の確認をやり直す。skills と判断画面の埋め込みは、checkout からビルドした e2e（RUN）が確かめるので、配布物を手で確かめ直すのは、ビルドとリリース、デーモンの起動と識別、判断画面の操作に関わる変更だけでよい。

| 変えた場所 | やり直す確認 |
| --- | --- |
| scripts/release/、cmd/prepare-dev、assets.go の埋め込みの指定 | 配布物を作り、別の場所に置いて e2e を動かす（`PREPARE_DEV_E2E_BINARY`） |
| internal/daemon/（起動、識別、lease、シグナル） | 配布物の e2e、Linux のコンテナでの実行、TypeScript 版との共存の確認 |
| ui/src/ と ui/build/、internal/server/（回答の API と配信） | 配布物で、判断画面をブラウザで操作する |

## 配布と開発

`go run ./scripts/release -version <v>` で macOS と Linux（arm64・amd64）向けの実行ファイルを作り、README と第三者ライセンスとともに tar.gz にまとめ、sha256 を `dist/artifact.json` に残す。画面のビルドが build.json と合わなければ作らない。パッケージ管理サービスへの公開はしない。配布物そのものは、展開した実行ファイルを `PREPARE_DEV_E2E_BINARY` に渡して e2e テストで確かめる。

開発中は checkout で `go run ./cmd/prepare-dev` を使う。ソースを変えると build が変わるので、前のデーモンを `prepare-dev stop` で止めてから使う。

このリポジトリ自身の記録も、§工程の外の記録 のとおりに prepare/ に置く。記録でないものは、それを使う場所か人が決めた場所に置く。配布物の README の元は scripts/release に、構想の段階で参照した資料の一覧は docs/references.md に置く。人が決める置き場（参照元の一覧、guidance）と、記録の規則をすべての対象プロジェクトに求めるかは、判断画面で聞いて判断（DEC）にする（trace DES-0004 で引く）。

検証プラグインごとの主張の書き方（guidance）は、エージェントが仕様と検証の工程で読むものなので、prepare-verify の skill の references/ に置き、skills と一緒に配る。プラグインの規則を説明するので prepare-verify に置き、prepare-specify は同じ親ディレクトリの prepare-verify/references/ を読む（init はすべての skill を並べて入れる）。

更新するときは、デーモンを `prepare-dev stop` で止め、実行ファイルを入れ替え、`prepare-dev init` を実行し直す。init が skills と guidance を新しい版にし、編集した skill は残して status に示す。0.2.0 の skills は `prepare-dev guidance` を実行するよう書いており、0.3.0 の実行ファイルはそれを持たないので、init を実行し直すまで書き方を読めない。

## TypeScript 版からの移行

TypeScript の本体（packages/ の core・runtime・mcp・cli、plugins/、scripts の build.mjs・pack.mjs、ルートの package.json・pnpm・tsconfig・vitest の設定）を消し、画面を packages/ui から ui/ に移す。実プロセスの強制終了からの回復を確かめていた scripts/e2e-crash.sh は Go の e2e テストに移す。このリポジトリの `.mcp.json` と `.codex/config.toml` の登録を消す（DEC-0007）。

切り替えるときは、TypeScript 版のデーモンを `prepare-dev stop` で止め（停止の API は同じ）、エージェントの MCP 設定から `prepare-dev mcp` を消し、`prepare-dev init --replace-skills` で skills を置き換える。戻すときは Go 版のデーモンを止め、commit 342bc64 の checkout で `pnpm install` と `pnpm ui:build` を実行して TypeScript 版を使う。TypeScript 版は Go 版の書いた記録をそのまま読み、Go 版で増えたもの（gotest の RUN、RUN の listings、skills.json）は使わない。

移行期の対策として、止め忘れた相手のデーモンを検出する。TypeScript 版の lease は root から決めた TCP のポートで、Go 版の flock とは互いを排除しない。そこで Go 版は daemon.json と `/api/identity` の識別に TypeScript 版が必須とする root（実行ファイルのディレクトリ）と mode（`package`）も書き、TypeScript 版の CLI が Go 版のデーモンを別の build として拒むようにする。逆向きは、Go 版の CLI と `serve` が TypeScript 版の書いた daemon.json を見つけ、その版の lease のポートが取られていれば、引き継がずに止め方を示す。この検出は相手の daemon.json があるときしか働かない（相手が lease を取ってから daemon.json を書くまでの間、daemon.json が消された後、手で起動した TypeScript 版の `serve`）。そのため、移行中は二つの版を同じ root で同時に使わないことを手順とする。これらは TypeScript 版を使うプロジェクトを切り替え終えるまでの対策で、TypeScript 版を使うプロジェクトが残っていないことを確かめてから外す（版の番号には結びつけない）。外すものは、internal/daemon の TypeScript 版の検出（tsLeasePort、typeScriptDaemon、CheckForeignDaemon と相手の識別の表示）、ToolIdentity の root と mode、cmdServe の検出の呼び出し、e2e の testP3TypeScriptDaemon、SPEC-0004 の P3 と assumptions の該当部分。

移行は、TypeScript の本体が残っていないこと、SPEC-0001・SPEC-0003・SPEC-0004 の主張の RUN が今の版に当てはまること、配布物を別の場所と Linux で動かした確認と版の共存の確認が確認記録に残っていることで完了とした（85477c7 としてコミットする前に、342bc64 と未コミットの変更から作った build で確かめた）。その後の変更で手の確認をやり直す条件は §工程の外の記録 に書く。

## REQ-0009 — 判断に必要な説明・比較・推奨理由を画面で読み、その場で回答できる

## 要求
DES-0002 と DEC-0005 に従い、React で質問データを描画する。背景・判断点・比較表・候補ごとの帰結・推奨理由を読め、選択と自由記述で回答できる。技術的なID・版・ハッシュは補足にまとめる。画面構成JSONは受け取らない。

## 受入条件
- U1: Markdownの段落・箇条書き・比較表を表示し、候補のsummary・reason・recommendedを読める。
- U2: 単一選択・複数選択・自由記述に対応し、送信中の重複操作を抑止。成功・失敗・古い対象版への回答を区別して表示する。確定表示と再接続の契約C6を維持。
- U3: json-render依存、catalog、UI spec APIを除去。古い質問に残るuiデータは表示に使わず、質問・回答・判断の履歴を保持する。

今回の「残ってるUIとCLIの梱包まで進めて、一通り使えるところまで検証して」という指示に基づく実装対象。

## 観点の対応
- users・rationale: 判断する利用者が背景と帰結を読んで回答するための要求。DEC-0005とDES-0002に基づく。
- scenarios_normal: 質問があるとき、説明と候補を読み、単一選択・複数選択・自由記述で送信すると、保存した回答を確認できる。
- scenarios_exception: 初回接続が失敗したときは接続復帰後に再取得する。送信が失敗したときは入力を保持する。対象版が変わったときは回答を再確認対象として表示する。
- terms・data: prompt、options、subjects、answerは既存の質問・回答契約を使う。表示用の内部ID・版・ハッシュは補足で扱う。履歴は既存の保存契約を維持する。
- states・rules: 未回答、送信中、保存済み、反映済み、closed、stale、取消を区別する。保存と判断への反映を混同しない。
- quality・constraints: 空回答・送信中の重複操作を抑止し、HTMLを実行しないMarkdown表示とする。Reactを使い、画面JSONは使わない。表示性能の数値目標を追加する要求ではない。
- priority・acceptance: 今回のUI実装指示に基づくmust。既存のU1〜U3を維持し、SPEC-0004のU1・U2と、実ブラウザでの操作の確認記録（DES-0004 の用語。traceで引く）で確認する。送信中の重複操作の抑止は、画面の部品が送信中に入力とボタンを止める作りで、自動の検査は無い（確認記録で送信中の表示を見た範囲）。

coverageのdecidedは観点の扱いが決まっている意味であり、網羅的な検証済みの意味ではない。検査した版・ケースは、RUNと確認記録（traceで引く）に残る。

## 要求
prepare-dev を OS とアーキテクチャごとの実行ファイル一つで配り、使う人の環境に Node.js などの言語処理系を求めない。検証器（Lean・Vitest・Go など）は、検証する環境に利用者が用意する。エージェントは skills の手順に従って CLI を使う。質問への回答は人が判断画面で行うもので（回答が判断になる手順は REQ-0001）、エージェントが使う CLI には回答の操作を置かず、回答は判断画面からの要求だけを受け付ける。同じ利用者のほかのプロセスが判断画面を装うことまでは防がない。MCP の入口は提供しない（DEC-0007）。

## 用語
- 対象プロジェクト（root）: prepare-dev が記録を置くディレクトリ。パスの書き方が違っても、同じディレクトリなら同じ対象プロジェクト。
- 実行ファイル: OS とアーキテクチャごとの `prepare-dev`。配布物は、それを含む tar.gz。
- build: 実行ファイルの内容。内容が同じなら、置き場所が違っても同じ build。
- 記録を書くもの: 対象プロジェクトの記録・質問・検証の結果（RUN）を書き換えるもの。
- skills の配置先: 対象プロジェクトの `.agents/skills` と `.claude/skills`。利用者は別の場所を指定するか、コピーしないことを選べる。
- 利用者の設定: 対象プロジェクトに既にある prepare-dev の設定（`.prepare-dev/config.json`）と、エージェントの設定ファイル（MCP の設定など）。
- 確認記録: RUN にできない確認（配布物を別の場所で動かす、ブラウザで操作するなど）を手で実行して（人かエージェントが行う）確かめたことの記録（記録の種類 record）。証拠（RUN）の代わりにはならない。P4 はこれで確かめる。

## 受入条件
- P1: 別の場所に置いた実行ファイルだけで help・version、init、status、ui、record、q、trace、bundle、verify が動く。元の checkout を参照せず、Node.js と Go が PATH に無くても動く。verify は、検証器が環境にあるプラグイン（受入では Lean）で確かめる。
- P2: init は skills を配置先にコピーし、MCP の設定を書かず、利用者の設定を変えない。同じ内容なら何も変えない。利用者が編集した skill は上書きせずに差異を報告し、利用者が求めたときだけ退避してから置き換える。prepare-dev が入れて編集されていない skill は、新しい版で更新できる。入れた skills が実行ファイルと違う（古い、無い、編集された）ことを、利用者とエージェントが status で知れる（古い手順のまま検証を進めると、設定や native 参照の書き方を間違えたまま RUN を取ることになるため）。
- P3: 一つの対象プロジェクトに記録を書くものは同時に一つだけ。利用者が手で何かを起動しなくても操作できる。異なる build が黙って記録を書くことはなく、そのときは動いているものと止め方を示す。記録を書くものが異常終了しても、利用者が手で後片付けをせずに次の操作を続けられる。
- P4: 独立したプロジェクトで、要求作成→質問→判断画面で回答→DEC→SPEC→実装→実際の検証器での RUN→trace を通す。パッケージ管理サービスへの公開は対象外。
- P5: 質問への回答は判断画面からだけ受け付け、CLI に回答の操作は無い。MCP の入口も無い。

旧 REQ-0002〜0008（配布と起動の要求。いずれも superseded）の、機械固有のパスを書かない、配布物だけで動く、UI を同梱する、という意図を引き継ぐ。DIS-0001 の案 G（skills を利用者単位の置き場に置き、MCP の登録を軸に段階を分ける案）は採用しない。

## 観点の対応
- users・rationale: 別プロジェクトで prepare-dev を使う利用者と、CLI を呼ぶエージェントのための要求。DEC-0004・DEC-0006・DEC-0007 に基づく。
- scenarios_normal: 実行ファイルを置いて init すると、skills と記録の操作を使える。質問・回答・判断・検証を同じ対象プロジェクトに記録し、trace で追う。
- scenarios_exception: 同時に操作しても、記録を書くものは一つのまま。異なる build のものが動いていれば書かずに止め方を示す。異常終了の後も次の操作で続けられる。利用者が編集した skill は上書きせずに報告する。検証の実行中は停止を拒否する。
- terms・data: 上の用語のとおり。配布方式を変えても、過去の質問・判断・RUN のファイルを書き換えない（読み直しても内容が変わらない）。
- states・rules: 記録を書くものが無い、動いている、異なる build のものが動いている、異常終了の残りがある、を区別する。記録を書くものを一つにし、利用者の設定と skill の編集を守る。
- quality・constraints: checkout・Node.js・Go に依存しない。macOS と Linux（arm64・amd64）、loopback 接続、一人の利用者のホストが前提で、Windows は対象外。記録を書く作業コピーは一つ。ブランチや worktree で並行して書いた prepare/ をマージしたときの衝突は、マージのときに直す（DEC-0008）。直した結果に矛盾があれば、書き込まずにそれを示す。判断画面を直す開発者だけが Node.js を使う。検証器は利用者が用意する。prepare-dev 自体の開発者が配布物を作らずにソースから動かせることは保つ（開発の手順で確かめ、受入条件にはしない）。
- priority・acceptance: must。SPEC-0004 の P1〜P3、A1（P5）、B1・D1 と、配布物による一連の利用の確認記録（P4）で確認する。

coverage の decided は観点の扱いが決まっている意味であり、全ホスト・全 OS での確認済みの意味ではない。実行環境と確認した範囲は確認記録に残す。

## 用語

- 検証の実行（RUN）: `prepare-dev verify run` 一回。結果を `prepare/runs/RUN-NNNN.json` に、検証器の出力（レポートやログ）を同じ名前のディレクトリ `prepare/runs/RUN-NNNN/` に置く。
- targets: `verify run --target` で渡す対象のファイル（テストファイル、証明のファイル）。
- project_dir: 検証器を動かすディレクトリ。ルートからの相対パスで、プラグインの設定（`.prepare-dev/config.json` の `plugins.<名前>`、または `--config-json`）に書く。
- impl_files: import やパッケージの関係からは見つからない入力を、利用者がルートからのパスかパターンで列挙する設定。パターンは `*`・`?`・`[...]` をパスの一段の中で、`**` を任意の段数のディレクトリに使える。`**` は node_modules と `.` で始まるディレクトリに入らず、`.` で始まるファイルはパターンに一致しない。一致するファイルがない書き方は誤り。Vitest ではここからも import をたどる。
- input_packages: Go のテストが実行中にビルドするパッケージ（`go build`、`go run` で作るもの）の一覧。
- ディレクトリの一覧: ディレクトリの下の名前を並べたものの sha256。一覧ごとに、下の段まで含めるかと、どの名前を数えるか（数え方）を決める。数え方は三つある。既定は、通常のファイルの名前で、`.` で始まる名前を除き、下の段では node_modules と `.` で始まるディレクトリに入らない。すべての名前は、`.` で始まるもの、ディレクトリ（`名前/`）、ほかの種類の名前も数え、どのディレクトリにも入る。go:embed の規則は、通常のファイルの名前で、`.` と `_` で始まる名前（ディレクトリならその下も）を除き、ほかのディレクトリには node_modules も含めて入る。数え方とは別に、その段だけの一覧にはパターン（`*`・`?`・`[...]`）を付けて、それに一致する名前だけを数えさせることができる。
- native 参照: 主張と、検証器のテストや定理とを結ぶ参照（主張の `native` の `ref`）。gotest と vitest の形と一致の規則は §結果と主張の対応（V4）に書く。
- 現在の版に当てはまる: RUN が記録した入力・対象・主張の版（内容の sha256）と、記録したディレクトリの一覧が、今のファイルとすべて一致し、RUN を記録したプラグインの版が今の版と同じこと。プラグインの版は、記録するファイルや検証器の出力の読み方を変えたときに上げる。前の版の RUN は今の規則を経ていない。今の runtime に無いプラグインの RUN は、そのプラグインの規則が分からないので、プラグインの版だけは比べない（ほかの条件は同じく比べる。デーモンは gotest・vitest・lean4 を持つ）。

## 契約

検証の結果は、記録した入力が今も同じである限りにおいて現在の版の証拠になる。プラグインは結果を左右するファイルを入力として記録し、ファイルが増えると結果が変わりうるディレクトリの一覧も記録する。runtime は、入力のどれかが変わるか消えたとき、一覧が変わったとき（ファイルの追加・削除）、または RUN を記録したプラグインの版が今の版と違うときに、その RUN を現在の版に当てはまらないものとして扱う。

Vitest（V1）は、テスト、impl_files、Vitest の設定ファイルを起点に、esbuild でバンドルするのと同じ規則（相対パス、package.json の main・exports、tsconfig.json の paths、node_modules にリンクしたワークスペースのパッケージ。拡張子の無い import は Vite の既定の順 .mjs・.js・.mts・.ts・.jsx・.tsx・.json で探す）で import をたどり、esbuild が読み込むファイルを記録する。JavaScript・TypeScript・JSON・CSS 以外の import されたファイルは、記録するが中はたどらない。型だけの import は実行時に読み込まれないので記録しない。node_modules の中に解決されたパッケージは記録せず、入力の上位ディレクトリ（ルートまで）の package.json、pnpm-lock.yaml、package-lock.json、npm-shrinkwrap.json、yarn.lock、bun.lock、bun.lockb、pnpm-workspace.yaml、.npmrc、tsconfig.json で代表する。import が読むファイルのディレクトリ（その段だけ。隣にファイルが増えると解決先が変わりうる）と、impl_files のパターンが探すディレクトリの一覧を記録する。

Go（V3）は次を記録する。集めるファイルの種類はここだけに書き、ほかの記録はここを参照する。

- `go list -deps -test -json` が報告する、テストがビルドするパッケージのソースと埋め込みのファイルすべて（Go のほか cgo・C・C++・Objective-C・Fortran・アセンブリ・ヘッダー・SWIG・syso）。対象はメインモジュール、ローカルのディレクトリへ replace したモジュール、vendor のパッケージ。テストファイルは実行するパッケージのものだけ（依存先のテストはビルドされない）。
- 実行するパッケージの `testdata/` の下のすべてのファイル。
- input_packages のパッケージとその依存先のファイル（上と同じ規則）。
- impl_files のファイル。
- モジュールの定義とロックのファイル（go.mod、go.sum、go.work、go.work.sum、vendor/modules.txt）。
- 一覧: ファイルを記録したパッケージのディレクトリ（その段だけ。既定）、`testdata/`（下の段まで。すべての名前。下のファイルはすべて入力なので）、impl_files のパターンが探すディレクトリ（既定）、go:embed のパターンが探すディレクトリと一致したディレクトリ。go:embed のパターンは、パッケージのものと、実行するパッケージのテストファイル（外部テストパッケージを含む）のもの。

go:embed は、パターンを一段ずつ、ディレクトリの中の名前に `filepath.Match` の規則で当て（`*` は `.` で始まる名前にも一致する）、一致したディレクトリからは、その下のファイルを（`all:` が無ければ `.` と `_` で始まる名前を除いて）すべて取り込む。そこで、ワイルドカードのある段から先は、探す各ディレクトリについて、その段のパターンに一致する名前の一覧（その段だけ。すべての名前。ファイルとディレクトリの両方）を記録し、最後の段で一致したディレクトリ（ワイルドカードの無いディレクトリのパターンを含む）について、その下の一覧（下の段まで。go:embed の規則。`all:` ではすべての名前）を記録する。この一覧は、go:embed が取り込むものの上位集合を数える。取り込むものが変わらない追加のうち、一覧も変わらないのは、`all:` でないディレクトリのパターンの下に `.` や `_` で始まる名前か空のディレクトリを足したときと、ワイルドカードに一致しない名前を足したとき。次の追加では、取り込むものが変わらなくても一覧が変わり、証拠は当てはまらなくなる（安全な側に倒れる）: `all:` の下のディレクトリの名前と、go:embed が `all:` でも取り込まない名前（`.git` など）、go.mod のある下のディレクトリの中。ワイルドカードの段に空のディレクトリを足したときも一覧が変わるが、このとき go:embed はビルドを失敗させる（取り込むファイルの無いディレクトリは誤り）ので、当てはまらなくするのが正しい。`testdata/` もすべての名前を数えるので、`.DS_Store` やエディタの一時ファイルでも当てはまらなくなる（`testdata/` の下のファイルはすべて入力に入るので、これらも次の実行の入力になる）。

`go test -json -count=1` で、キャッシュした結果を使わずに実行する。デーモン自身の環境の `PREPARE_DEV_` で始まる変数（`PREPARE_DEV_E2E_BINARY` など、prepare-dev のテストが何を検査するかを変えるもの）はテストに渡さない。ほかの環境変数（`GOFLAGS`、`CGO_ENABLED` など）はデーモンのものが渡り、RUN には残らない。テストは、RUN ごとのディレクトリ（環境変数 `PREPARE_DEV_BOUNDS_DIR`）に書いた JSON の数値と文字列を RUN の `scope.bounds` に残せる。

Lean（lean4）はモジュールの名前で import を読むので、ファイルが増えても結果は変わらず、ディレクトリの一覧は記録しない。どのプラグインも、検証器の有無を project_dir で調べ、使った検証器の場所を RUN の `tool.extra` に残す。

プラグインの設定は、プラグインが宣言した項目と型だけを受け付ける（V5）。検証を始める前に、`.prepare-dev/config.json` のそのプラグインの設定と、verify run で渡す設定（`--config-json`）を合わせたものを照らし、知らない項目、型の違う値（文字列の配列に文字列を書いたものなど）、config.json の知らないプラグイン名があれば、RUN の番号を取らずに誤りを返す。宣言の無いプラグインはどの項目も受け付けない。書き損じた項目が黙って捨てられると、記録する入力が減り、後でその入力が変わっても RUN が当てはまり続けるため。V5 で設定の読み方を変えたので、プラグインの版を上げ（gotest 0.3.0、vitest 0.4.0、lean4 0.3.0）、V5 より前に取った RUN を当てはまらないものにする（書き損じた設定で取った RUN を後から見分ける手段が無いため）。

主張の今の結果は、その主張を持ち今の版に当てはまる RUN のうち、最も新しいものの結果とする（V6）。より新しい当てはまる RUN が verified でなければ、それより古い verified の RUN を今の証拠にしない。プラグインごとの結果は合わせない（一つの主張を二つのプラグインで確かめるときも、最も新しい RUN の結果を今の結果とする）。

## 結果と主張の対応（V4）

主張は native 参照（`ref`）でテストに対応する。`ref` は `<前半>::<後半>` の形で、前半は、Go ではパッケージのインポートパスの末尾に、Vitest ではテストファイルのパスの末尾に、文字列として一致し（空ならどれにも一致する。パスの区切りでは分けないので、`app` は `example.com/webapp` にも一致する。分けたいときは `/app` と書く）、後半は、テストの名前（Go は `go test -json` の名前で、サブテストは `TestX/名前`。Vitest は describe を含めた名前）に含まれる文字列。前半と後半の両方に一致するテストを、その主張のテストと呼ぶ。

主張の結果は、その主張のテストの結果から決める。すべて成功なら verified、一つでも失敗（終わらなかったものを含む）なら failed、一つも無いか、失敗は無いがスキップが混ざるなら unknown。RUN の結果は、主張の結果のうち最も悪いもの（verified、unknown、failed、timeout、tool_error の順に悪い）。

テストが成功しても、検証器がテストの外での失敗を示したときは verified にしない。テストの外の失敗は、それが起きたパッケージ（Go）かファイル（Vitest）ごとに見分ける。

- Go: パッケージの失敗（`go test -json` のテスト名の無い `fail`）で、次のどれかに当たるもの。そのパッケージに失敗したテストが無い（TestMain が 0 以外で終わる、テストの後の終了）。テストのプログラムが、すべてのテストを走らせる前に終わった。これには三つある。ビルドの失敗やテストを走らせる前の終了で、テストの結果が一つも無い。結果の出なかったテストがある（そのテストの途中で終わった。`go test` は出力をその時に動いていたテストに付けるので、ほかのテストが残した goroutine の panic は、動いていたテストの出力になり、そのテストには結果が出ない）。テストの中で panic した（テスト自身の goroutine の panic は、`go test` がそのテストの失敗にしてからプログラムを終わらせるので、後ろに並ぶテストは走らず、イベントも出ない）。最後に、テストの外の panic がある（パッケージがテストの外で出力した `panic:` か `fatal error:` で始まる行。TestMain の中など）。失敗したテストのあるパッケージで、panic でないテストの外の失敗（TestMain が自分の検査で 0 以外を返すなど）は、テストの失敗と区別できないので対象外とし、そのパッケージで成功したテストの主張は verified のまま残る（失敗したテストを直して実行し直せば、テストの外の失敗として見える）。
- Vitest: ファイル自体の失敗と、未処理の例外。JSON のレポートが示すのは、ファイル直下の hook の例外と読み込みの失敗（ファイルの `status` が `failed` で `message` があるか、失敗したテストが無いもの）だけで、describe の中の hook の例外は `message` に入らず、未処理の例外（テストの後に投げられた例外、拒否された Promise）は出ない（レポートは成功と報告し、Vitest は 1 で終わる）。そこでプラグインは実行のたびに小さな reporter を加え、Vitest から、ファイルとその中の suite（describe）のエラー、未処理の例外と、それが起きたテストファイルとテスト、それぞれの project がテストファイルを分けて動かすか（isolate）を受け取って `vitest-unhandled.json` に書かせる。ファイルや suite のエラーは、ファイルの中のテストが失敗していても、そのファイル自体の失敗とする。未処理の例外は、起きたファイルが分かればそのファイルの失敗とし、isolate が無効の project があるときは、ほかのファイルのテストが残したものでありうるので、起きた場所の分からない失敗とする。globalSetup の後始末の例外は reporter に届かない。0 以外の終了コードとしてだけ見え、同じ実行にほかの失敗があると区別できないので対象外とする。reporter のフックは、Vitest 3 以降は onInit と onTestRunEnd、それより前は onFinished（受け取るファイルのタスクの木から、ファイルと suite のエラーを読む）。実際の Vitest で確かめたのは 5.1.0 の onTestRunEnd だけで、onFinished の経路は Vitest 2 までのタスクの形を模した入力で確かめただけなので、その経路で読んだときは要約にそう書く。

テストの外の失敗は、次の主張を failed にする。

- テストのプログラムが最後まで走ったパッケージやファイルでの失敗: そこにその主張のテストがある主張。
- テストのプログラムがすべてのテストを走らせる前に終わったパッケージ（ビルドの失敗、テストを走らせる前の終了、結果の出なかったテスト、テストの中の panic）と、テストの結果が一つも無いファイル（読み込みの失敗）での失敗: どのテストが走らなかったかが分からないので、`ref` の前半が一致する主張（前半が空ならすべての主張）。
- 起きた場所が分からない失敗（ファイルの分からない未処理の例外と、検証器が 0 以外で終わったのに、失敗したテスト・パッケージ・ファイルと未処理の例外のどれも無いとき）: verified になるはずのすべての主張。このときは主張が無くても RUN の結果を failed にする。

テストの外の失敗は、それに対応しない主張の結果を変えない。RUN の要約には、主張に及んだテストの外の失敗ごとに、パッケージかファイルと理由の一行を残す。理由は、Go のビルドの失敗ではコンパイラの最初のエラー、テストのプログラムが途中で終わったときは、結果の出なかったテストか panic したテストの名前と、その出力の panic の行、ほかの Go の失敗では、テストの外の panic の行か、無ければパッケージがテストの外で最後に出力した行（`go test` 自身の `PASS`・`FAIL`・`ok`・`exit status` の行を除く）。Vitest ではファイルの `message` かファイルと suite のエラーの一行目、未処理の例外の message。どの主張にも及ばない失敗は要約に出ず、検証器の出力（RUN の成果物）に残る。検証器の終了コードは RUN の `tool.extra.exit_code` に残す。Vitest の reporter が何も書かなかったときは、未処理の例外も describe の中の hook の例外も読めないので、0 以外の終了コードの規則だけで扱い、終了コードが 0 以外ならそのことを要約に書く。Vitest はどちらがあっても 1 で終わるので、0 なら読めなくても見逃しは無い（未処理の例外では、設定 `dangerouslyIgnoreUnhandledErrors` を有効にしていないこと）。

## V2: 実行中ジョブの識別

単一 runtime で検証を開始するとき、結果 JSON の完成前に作る RUN のディレクトリを ID の予約として扱う。次の実行と再起動後の採番はその予約を使用済みとして数える。異なるジョブが結果・ログを共有してはならない。結果を書く前にデーモンが止まった RUN は、status の `runs_incomplete` に示す。internal/runtime の [V2] で、非同期の完了を止めたまま二つのジョブを起動し、ID と保存先の分離、および再起動後の非再利用を確かめる。RUN-0006 は二つのジョブが同じ ID を使った実行で、証拠に使わない。

## 根拠

検証の結果が「今の」実装と仕様の証拠であることを、記録した入力の内容とディレクトリの一覧で判断するための契約。DEC-0006 で prepare-dev 本体を Go へ移したため、本体の証拠は gotest で記録する。Vitest の規則（V1）は、判断画面（ui/）と、TypeScript のプロジェクトを検証するときの契約として残す。V4 は、検証器が失敗を示した実行を主張の証拠にしないための規則。テストごとの結果だけを見ると、テストの外の失敗（TestMain の終了コード、hook の例外、未処理の例外）が証拠から漏れる。go:embed の一覧（V3）は、実行ファイルに入るファイルの増加を、go:embed が取り込むものの上位集合として検出するためのもの。
