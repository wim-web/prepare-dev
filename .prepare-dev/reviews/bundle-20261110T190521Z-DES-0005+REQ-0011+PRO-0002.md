## 1. 概要と問題

REQ-0011 の「仕様のページ」を作る設計。prepare-dev を使うどのプロジェクトでも、AI が仕様から中身を生成して ppdev で登録し、判断画面のアプリがそれを描く。

今の判断画面のアプリは質問の画面一つで、図を描く部品も、仕様を試す画面も無い（ui/src）。人は 2026-11-10 に「ずとかもないし、ダイアグラムもない」と指摘した（DEC-0018）。中身は AI に生成させ（DEC-0019、DEC-0022）、形の定義は自前で作る（DEC-0023）。出発点は、DEC-0023 の判断に使ったデモの写し（PRO-0002）である。

```
AI が仕様を書き終える
  │ prepare-specify の references/spec-page.md を読む（書き方の説明。形の定義から書き出したもの）
  │ （AI が中身の JSON を書く）
  │ ppdev page put SPEC-xxxx --file page.json --expected-rev N --expected-sha256 H
  ▼
prepare-dev（デーモン）が検査する
  │ 形の検査（JSON Schema）、つながりの検査、仕様と照らす検査
  │ 合わなければ、何も保存せずに、どこがどう合わないかを返す
  ▼
prepare/pages/SPEC-xxxx.json に保存し、画面に「page」の知らせを出す
  ▼
判断画面のアプリ /spec/SPEC-xxxx が描く
  仕様の中身が変わっていたら「古い」と出す。形が読めなければ、そうと出して仕様の本文を出す
```

## 5. 技術計画

### 5.1 部品と、中身の形

部品は五つ（REQ-0011 の五つ）。ほかに、部品ではない「ページの頭」（題と、何の話かの二〜三文）がある。

部品の並ぶ順は決まっている。中身は、部品ごとの決まった欄を持つ一つのオブジェクトで、並びの配列は持たない。必須の部品の欄が無い中身は、形の検査で断る。

| 欄 | 部品 | 必須か | 中身 |
| - | - | - | - |
| `title`、`lead` | （ページの頭） | 必須 | 題、何の話かの二〜三文 |
| `story` | 例の流れ | 必須 | 2〜5 コマ。コマごとに、誰が何をするか、見せる物（名前と一文）、選択肢（人が選ぶコマだけ）、補足 |
| `promises` | 困ることと約束 | 必須 | 困ること 1〜4 件（困ること、なぜ困るか）。約束は 1〜3 個ずつ（通し番号、言い直した一文、主張の番号） |
| `explorer` | 流れの図と試す画面 | 結果が分かれる決まりがある仕様では必須。無い仕様では使わない | 図 1〜3 枚と、場面 2〜8 個 |
| `quiz` | 理解の確認 | 任意 | 問い 1〜4 個（問い、選択肢、正解の位置、理由、指す場面） |
| `limits` | 扱っていないこと | 必須（DEC-0025） | 仕様の前提、約束していないこと、約束に選ばなかった主張（番号と一文） |

`explorer` が必須か使わないかは、中身を書く AI が仕様を読んで決める。途中で起きることや入力によって結果が分かれる決まりがあれば使う（SPEC-0001、SPEC-0003 は使う）。

言葉の定義。

- 「この仕様の話」のコマ: 例の流れのコマのうち、この仕様が決めている操作が起きるコマ。ページではこのコマに印を付ける。ちょうど一つ。
- 「ふつうの流れ」の場面: 何も変わったことが起きない時の場面。`explorer` を使う時は、ちょうど一つ。ページでは「ふつうはこれ」と印を付ける。
- 場面の結果: 人が場面を選んだ時に出るもの。次の欄で持つ。
  - 結果の見出し（短い文。例: 決定にしなかった）
  - その理由（2〜3 文）
  - 起きたことの並び（出来事ごとに、主語つきの文、補足、確かめた箱ごとの答え、その出来事の終わり方）
  - 後に残るもの（物の名前と状態。あってはならない状態かどうか）
- 箱ごとの答え: 場面の出来事の中で、図の箱を確かめた時の答え（下の四つ）。場面の結果とは別のもの。

流れの図と試す画面の形（PRO-0002 で中身を書いた AI が迷った所を、次のように決める）。

- 図は、名前（図の中で重ならない）を持ち、箱を上から並べた一本道と、横への分かれで描く。箱の名前は、一枚の図の中で重ならない。箱は四種類。
  - 始まり: 図の先頭に一つ。
  - 確かめること: 答えで分かれる箱。分かれる方の答え（はい／いいえ）と、分かれた先の終わり方の箱を持つ。もう一方の答えは、下の箱へ進む。
  - すること: 何かを書く、送るなどの箱。
  - 終わり方: 一本道の最後と、確かめることから分かれた先。
- 図は 3 枚まで持てる。手順の流れと、落ちた後に起動し直した時の流れを、別の図に描ける。
- 場面の「通った道」は、区間の並び。区間は、図の名前と、その図の上で始まりから箱を順にたどった並び。
  - 区間は、終わり方の箱か、止まったすることの箱で終わる。
  - 止まった区間の次には、別の図の区間が続く（例: 書いている途中で落ち、起動し直した時の図へ）。
  - 最後の区間は、終わり方の箱で終わる。
- 箱ごとの答えは四つ。
  - 確かめることの箱: 「分かれずに進んだ」か「分かれた」。
  - することの箱: 「やり終えた」か「止まった」（そこで処理が途中で終わった。プログラムが落ちたなど）。
  - 止まった箱は、その区間の最後の箱と同じ。別の欄には持たない。
- 場面は、その場面がどの約束を見せるかを、約束の番号で持ってよい（任意）。
- 約束に選ぶ主張は、人がその仕様に頼ることを言う主張（例: 一つの回答が決定になるのは一度だけ）。実装と Lean の証明の一致や、テストの範囲だけを言う主張は、扱っていないことの「約束に選ばなかった主張」に入れる。仕様の主張は、すべて約束か「約束に選ばなかった主張」のどちらかに入る。
- 理解の確認は、`explorer` が無い時は、場面を指さない問い（約束についての問い）だけで使ってよい。
- 誰が何をするかが仕様に書かれていない時は、AI は生成の入力の記録（§5.6）から取る。そこにも無ければ「だれかが」と書く。

### 5.2 一つの定義から出すもの

部品と中身の形は、zod で `ui/src/specpage/schema.ts` に一つだけ書く（DEC-0023）。部品ごとの説明、項目ごとの説明、数の上限、選べる値、文の書き方の決まりも、ここに書く。文の書き方の決まりは PRO-0002 の schema.ts の RULES を元にし、AC-5（仕様の内部の言葉と記録の番号を、説明なしに使わない）を含む。

| 出すもの | 置き場所 | どうやって |
| - | - | - |
| 画面の型 | ui/src/specpage | schema.ts の型をそのまま使う |
| JSON Schema | ui/build/spec-page.schema.json | Vite のビルドで z.toJSONSchema から書き出す。assets.go で実行ファイルに埋め込む |
| AI への書き方の説明 | skills/prepare-specify/references/spec-page.md | 同じビルドで、部品の説明、文の書き方の決まり、JSON Schema（字下げなし）から書き出す。PRO-0002 で一回で合ったのと同じく、JSON Schema を入れる |
| 登録の時の検査 | internal/specpage | 埋め込んだ JSON Schema で形を検査し、つながりの検査と仕様と照らす検査を Go で書く |

書き方の説明は、DEC-0011（検証プラグインの書き方は prepare-verify の references/ に置き、専用のコマンドを持たない）と同じく、手順書の references/ に置く。init が手順書と一緒に対象プロジェクトに入れ、status は手順書が古いことを示す（今の仕組み）。手順書が実行ファイルより古いと、説明と検査がずれ、登録が断られて誤りが返る。AI はその誤りで直せる。

二つの書き出しは build.json に載せる。今の `files` は ui/build/ からの名前なので、ui/ の外に書き出す説明は、リポジトリのルートからの名前で載せる欄 `outside` を足す。internal/uibuild の検査は、両方の欄のファイルの sha256 を照らす（今の [B1]、SPEC-0004）。

形の検査には、Go のライブラリ github.com/santhosh-tekuri/jsonschema/v6（Apache-2.0、依存は golang.org/x/text だけ）を使う。

検査の中身。

- つながりの検査（Go の internal/specpage/check.go。PRO-0002 の check.ts を元に、§5.1 に合わせて直す）
  - 「この仕様の話」のコマがちょうど一つ
  - 約束の番号が重ならない
  - 図の名前が重ならない。図ごとに、箱の名前が重ならない、始まりで始まり、一本道の最後が終わり方、確かめることの分かれた先が終わり方
  - 場面の区間が §5.1 の決まりどおり（指す図があり、その図の箱を進める順にたどる。止まった区間の次に別の図の区間がある。最後は終わり方）
  - 箱ごとの答えが箱の種類に合う
  - 「ふつうの流れ」の場面がちょうど一つ（`explorer` がある時）。場面が指す約束の番号がある
  - 問いの正解の位置が選択肢の数の中。問いが指す場面がある（指す時）
- 仕様と照らす検査（Go）
  - 約束と「約束に選ばなかった主張」が指す番号が、仕様の claims にある
  - 仕様の claims が、すべて約束か「約束に選ばなかった主張」のどちらかに入っている

どの検査の誤りも core.Issue（path と message）にし、core.ValidationError で返す（frontmatter の検査と同じ）。

どの操作で、どの検査を行うか。

| 検査 | 登録（put） | 結び直し（rebind） | 読む時 |
| - | - | - | - |
| format がこの prepare-dev の知っている値 | 行う | 行う | 行う |
| 形の検査（JSON Schema） | 行う | 行う | 行う |
| つながりの検査 | 行う | 行う | 行う（メモリの上の検査で軽い） |
| 仕様と照らす検査 | 行う | 行う | 行わない（古い中身では合わなくなりうる。画面は、今の仕様に無い主張を指す約束に「今の仕様に無い主張」と出す） |
| 渡された版が、今の仕様の記録の版と同じ | 行う | 行う | 行わない |

### 5.3 置き場所と状態

中身は `prepare/pages/<SPEC の id>.json` に一つずつ置く。記録の種類（Markdown の記録）にはしない（§6 の record-kind）。

```json
{
  "format": 1,
  "spec": { "id": "SPEC-0001", "rev": 15, "content": "<仕様の中身の digest>" },
  "generated": {
    "at": "2026-11-11T…",
    "rev": 15,
    "claims": { "C1": "<生成した時の主張の文の sha256>", "…": "…" },
    "assumptions": "<生成した時の前提の一覧の sha256>",
    "out_of_scope": "<生成した時の対象外の一覧の sha256>"
  },
  "page": { "title": "…", "lead": "…", "story": { … }, "promises": { … }, "limits": { … } }
}
```

- 仕様の中身の digest: 仕様の記録のうち、ページの元になる所（title、本文、claims の id と文、assumptions、out_of_scope）を決まった形の JSON にしたものの sha256。status、updated、rev、links は入れない。そのため、仕様の status を proposed や accepted に変えても、中身は古くならない。
- AI が書くのは `page` だけ。`spec`、`generated` は、登録の時にデーモンが書く。
- 書くのはデーモンだけ（DES-0004 の書き手を一つにする決まり）。一時ファイルからの rename で書く。
- ジャーナルには書かない。ジャーナルに知らない種類の行があると、前の版の prepare-dev は起動しないからである（internal/core/types.go の行の種類の検査）。中身はジャーナルから戻す必要も無い（AI が生成し直せる）。書いた履歴は Git で追う。
- 記録の書き込みが止まっている間（ジャーナルの矛盾など。store の assertWritable）は、登録と結び直しも断る。
- 登録と結び直しでは、AI は読んだ仕様の記録の版を `--expected-rev` と `--expected-sha256` で渡す（`record put` と同じ）。デーモンは、それが今の記録の版と同じ時だけ受ける。生成している間に仕様が書き換わった中身は断る（AI は読み直して、中身が変わっていなければそのまま、変わっていれば生成し直して出し直す）。遅れて届いた古い中身が、新しい中身を置き換えることも起きない。
- 状態は、無い・今の版・古い・読めないの四つ。
  - 今の版: 中身の `spec.content` が、今の仕様の中身の digest と同じ。
  - 古い: 違う。
  - 読めない: format がこの prepare-dev の知らない値か、形の検査かつながりの検査に合わない（手で書き換えたなど）。
- format は、形を互換でなく変える時だけ上げる。任意の欄を足す時は上げない。新しい prepare-dev は、前の中身を読める。前の prepare-dev は、知らない欄がある中身を、形の検査に合わないので「読めない」と出す（仕様の本文は読める）。読めない中身は、AI が生成し直す。

### 5.4 ppdev と API

| 操作 | CLI | API |
| - | - | - |
| 登録する | `ppdev page put SPEC-xxxx --file page.json --expected-rev N --expected-sha256 H` | `PUT /api/pages/:spec` |
| 今の版に結び直す | `ppdev page rebind SPEC-xxxx --expected-rev N --expected-sha256 H` | `POST /api/pages/:spec/rebind` |
| 見る | `ppdev page get SPEC-xxxx` | `GET /api/pages/:spec` |

- `GET` は、状態、中身、仕様の題・版、今の claims の文と、主張ごとに「生成の後に文が変わったか」を返す。前提と対象外についても、生成の後に変わったかを返す。
- 書き方の説明を出すコマンドと API は持たない（§5.2）。
- 断る時は、今の API と同じく `{error, message, details}` で返し、検査の誤りは `details.issues` に入れる（internal/server の writeError）。CLI は今と同じく誤りを出して終わる。
- 登録と結び直しは、判断画面のアプリからはできない（REQ-0011 の制約）。回答の API と逆に、判断画面の Origin からの要求を断る。
- 中身を書いたら、ストアの Emitter で名前付きの知らせ「page」（spec の id）を SSE に流す（今の「question」「run」「job」と同じ）。
- `status` に `pages` を足す。中身がある仕様のうち、中身が古いか読めないものを挙げる。中身が無い仕様は挙げない（前からある仕様が並ばないように。§5.6）。エージェントは作業の前に status を見る（prepare-dev の手順書の手順 1）ので、これで気付く。

### 5.5 判断画面のアプリ

- 経路 `/spec/:id` を足す。サーバーは、`/` と `/q/:id` と同じく、この経路でも UI の HTML を返す。
- 質問の画面の「関連する記録（補足）」（SubjectRecords）で、種類が spec の記録に「仕様のページを開く」を出す。
- 部品は、PRO-0002 の parts.tsx を移し、§5.1 の形に合わせて直す。文字は React の文字として出し、HTML として解釈しない（dangerouslySetInnerHTML を使わない）。Markdown も使わない。
- ページの上に、中身を結び付けた仕様の版を出す。結び直した中身（生成した版と結び付けた版が違う）では、「中身を作ったのは版 F」も出す。中身が古い時は「古い」を出す。
- 約束の横には、主張の番号と、今の仕様の claims の文を出す。生成の後に文が変わった主張には「生成の後に、仕様の文が変わった」と印を付ける。今の仕様に無い主張には「今の仕様に無い主張」と出す。前提と対象外が生成の後に変わっていたら、扱っていないことの部品に同じ印を付ける。
- 知らせ「page」が来た時と、接続が戻った時は、今の中身を取り直す。取り直した中身が表示中のものと違えば、黙って替えずに「新しい中身がある」と出し、押すと読み込み直す。

### 5.6 いつ、誰が生成するか

- AI が生成する。手順は次の二か所に書く。
  - prepare-specify の SKILL.md: 仕様を書いてレビューを終え、人に確定を頼む質問を作る前に、references/spec-page.md を読み、中身を書いて `ppdev page put` する。仕様の status を proposed にするのと、どちらが先でもよい（status だけの変更では古くならない）。
  - prepare-dev の SKILL.md（すべての工程の共通の決まり）: status の `pages` に仕様が出ていたら、生成し直すか結び直す。仕様の中身は、prepare-specify の外（prepare-verify での名前の直し、外からの編集など）でも変わるため。
- 生成し直すか結び直すかの判断。
  - 材料は、結び付けた版から今の版までの仕様の差。AI は Git の差分（`git log` と `git diff` で、仕様のファイルの、結び付けた版を書いたコミットからの差）で見る。差が取れない時（コミットされていない間に何度も書き換わったなど）は、生成し直す。
  - 差が仕様の決まりを変えている時（DEC-0016 の区別）は、生成し直す。
  - 差が決まりを変えない修正（誤字、言い換え、名前の置き換え）だけの時は、`ppdev page rebind` で今の版に結び直す。結び直しは §5.2 の表の検査を行い、合えば `spec` だけを進める。主張の文、前提、対象外が生成の後に変わっていても断らない。画面がその所に印を付けるので（§5.5）、人が気付ける（DEC-0016 の「変えた箇所を見せるので、人が気付く」と同じ考え）。
- 生成の入力は、仕様の記録の全体と、仕様とつながっている要求・設計・決定の記録。つながりは trace と同じく両向きにたどる（仕様が指す記録と、仕様を指す記録。superseded の記録は除く）。SPEC-0003 のように要求を指さない仕様でも、仕様を指す設計（SPEC-0003 では DES-0004）から、誰が何をするかを取れる。大きな記録は、仕様の言葉が出る節を選んで読む。
- 中身を作る時は、新しく仕様を書いた時と、決まりを変えた時と、人が頼んだ時だけ。前からある仕様（このリポジトリでは SPEC-0004 など）のページを、一度にまとめて作ることはしない。中身の無い仕様は status に挙げない（§5.4）。
- 登録は合わせて 3 回まで試す（最初の 1 回と、誤りを直した出し直し 2 回）。3 回とも断られたら止めて、誤りの一覧を人への報告に書く。書き込みが止まっていて断られた時と、仕様が書き換わって断られた時は、回数に数えない。

### 5.7 生成した中身の確かめ方（DEC-0021。人に聞く）

| 案 | すること | 拾えるもの | 拾えないもの |
| - | - | - | - |
| A | 登録の時の機械の検査（§5.2）と、人がページを見ることだけ | 形の誤り、無い主張を指すこと、主張の落ち、図と場面のつながりの誤り | 例や答えが仕様と食い違うこと |
| B（推奨） | A に加えて、生成した時に、経緯を知らないレビュー役に、生成の入力の記録と中身を読ませて食い違いを挙げさせる | A ＋ 答えや約束の言い直しが仕様と食い違うこと（読んで分かる範囲） | 読み手も見落とす食い違い |
| C | B に加えて、Lean の証明がある仕様では、試す画面の答えを Lean で出した結果と突き合わせるテストを足す | B ＋ Lean の証明がある仕様の、場面の結果の誤り | Lean の証明が無い仕様の答えの誤り |

推奨は B。A では、人は仕様と食い違うページを見ても気付けない。C は、場面の言葉を Lean の操作に対応させる表を仕様ごとに書く必要があり、今 Lean の証明がある仕様は SPEC-0001 だけなので、手間に見合わない。

B の進め方（prepare-review の手順に沿う）。

- 回すのは生成した時（新しく作った時と、決まりを変えた時と、人が頼んで作った時）だけ。結び直しでは回さない（DEC-0016）。
- レビュー役は prepare-review の design_critic の persona を使う。評価基準は渡さない。段階ごとの注記に「見るのは、記録に書かれていることと、ページの中身の食い違いだけ」と書く。
- 渡す資料は、生成の入力の記録を `ppdev bundle` で束ねたものと、ページの中身のファイルの場所。レビュー役は中身のファイルを読む。
- 結果は REV（stage は design_critique）に残す。subjects は仕様の記録の版。中身は記録ではないので、REV の本文に、見た中身のファイルの sha256 を書く（PRO-0002 の添付と同じやり方）。
- 重い指摘を直したら（中身を直して登録し直したら）、一度だけ確かめ直す（DEC-0016 と同じ回数）。

## 7. 非機能要求

- 安全性: 中身は AI が書く。画面は文字を文字として出し、HTML もプログラムも実行しない（REQ-0011 の制約）。登録と結び直しは判断画面の Origin から受けない。
- 大きさ: 判断画面の HTML は、今 404 kB。部品を足すと増える（PRO-0002 の部品は数十 kB）。zod は画面に入れない（型だけを使い、検査はデーモンがする）。実行ファイルには、JSON Schema のライブラリが加わる。
- 互換性: ジャーナルには書かないので、前の版の prepare-dev は `prepare/pages/` を読まずに今までどおり動く。中身の形は format で見分ける（§5.3）。
- 切り戻し: 仕様のページは今の機能から独立している。経路と操作を外し、`prepare/pages/` を消せば元に戻る。
- AI にかかる量（PRO-0002 の実物から見積もる。日本語は 1 字が 3 バイトなので、字とバイトを分けて書く）:

  | 読み書きするもの | バイト | 字 |
  | - | - | - |
  | 書き方の説明（PRO-0002 の guide.md。字下げを外すと減る） | 2.8 万 | 2.4 万 |
  | 仕様（SPEC-0001、SPEC-0003） | 2.6〜3.5 万 | 1.4〜1.5 万 |
  | 入力の記録（SPEC-0003 では、仕様を指す DES-0004 が大きい） | DES-0004 は 5.6 万 | 2.7 万 |
  | 書く中身の JSON | 3.2〜3.4 万 | 2.1〜2.2 万 |

  - 一回の生成で、上の表の読むものを読み、中身を書く。登録を断られると、直して出し直す（合わせて 3 回まで）。
  - B のレビュー役は、入力の記録と中身を読む（SPEC-0003 では合わせて 6 万字ほど）。重い指摘を直したら一度だけ確かめ直す。
  - これが回るのは、新しく仕様を書いた時と、決まりを変えた時と、人が頼んだ時だけ。決まりを変えない修正は結び直しで済み、AI の生成もレビュー役も回らない（主張の文を直した時も、結び直して画面で印を付ける）。前からある仕様をまとめて作ることもしない。
  - 実装の後、SPEC-0001 と SPEC-0003 で実際の量を測り、確認記録に残す。多すぎれば、書き方の説明と入力の記録の読み方を絞る。

## 要求

prepare-dev を使うどのプロジェクトでも、人は、判断画面のアプリで、仕様一つについて「仕様のページ」を見られる。ページの中身は、AI がその仕様の本文から生成する（DEC-0019、DEC-0022）。

ページに出すものは、決めた部品の一覧から選ぶ。最初の一覧は次の五つ。

| 部品 | 人が見るもの |
| - | - |
| 例の流れ | 仕様が扱う場面を、具体的な一件で順に見せる |
| 困ることと約束 | 仕様が無いと何が困るかと、仕様の約束。約束ごとに、元になった仕様の主張を示す |
| 流れの図と試す画面 | 人が場面（途中で起きることや入力の組み合わせ）を選ぶと、仕様の答え（何を確かめ、どう終わり、後に何が残るか）が、流れの図の上で通った道と並んで出る |
| 理解の確認 | 問いに答えると、正誤と理由が出る。問いが扱う場面を、試す画面で開ける |
| 扱っていないこと | 仕様の前提、仕様が約束していないこと、約束に選ばなかった主張 |

試す画面の答えをどう出すか（AI が場面ごとに前もって中身に書くか、prepare-dev に入れた決まった作りが中身のデータから求めるか）と、人が選べる場面の範囲は、設計で決める（§設計で決めること）。どちらの場合も、中身に書かれたプログラムは実行しない（§制約）。

どの部品を使うかは、中身を書く AI が仕様を読んで決める。例の流れ、困ることと約束、扱っていないことは、どの仕様でも使う。途中で起きることや入力によって結果が分かれる決まりが仕様に無い時に、流れの図、試す画面、理解の確認をどうするかは、設計で決める（§設計で決めること）。部品の並ぶ順は上の表の順に決まっていて、どの部品も一つまでしか置かない。部品の中に部品を入れたりはしない。

部品ごとに、中身の形（欄、型、数の上限、欄ごとの説明）を一つの定義に決める。AI への書き方の説明、登録する時の検査、画面の描画は、その定義から出す（DEC-0023）。

```
仕様 ──（AI が本文を読み、決めた形で中身を書く）──→ ppdev で登録する
         登録する時に検査する。合わなければ、何も保存せずに理由を返す（AI が直して出し直す）
         中身は、どの版の仕様に結び付けたかを持つ
     ──→ 判断画面のアプリが描く
         仕様の中身（本文、主張、前提、対象外）が変わったら「古い」と出る。仕様の決まりを変えた時は AI が生成し直し、
         決まりを変えない修正では今の版に結び直す（DEC-0016 と同じ区別）
```

## 根拠

人が 2026-11-10 のチャットで指摘した。「全然pdd-kitのスピリットを感じないんだよね」「ずとかもないし、ダイアグラムもない」「Run a login against the spec　みたいなのもない」。PDD Kit は、prepare-dev が参考にした既存の仕組みである（REC-0001）。今の判断画面のアプリは質問の画面一つで、図を描く部品も、仕様を試す画面も無い（ui/src）。

SPEC-0001 の試作を作り、三つ目の版で「いいんじゃない大枠は」と言われた（DEC-0018）。その後、人は、仕様一つのための画面ではなく道具として作ると決めた。

- 「ここはあくまでtoolなんだからどの仕様じゃなくてもだめだろ」「AIに生成させるしかないとおもうが」（DEC-0019）
- 「仕様からgenerateしないと」（DEC-0022）
- 生成させるものの形は、先に決める。「ある程度決めないと困るぞ」（2026-11-10 のチャット）
- 形の定義は自前で作る（DEC-0023）

デモで確かめたこと（DEC-0023）: 別の AI に、仕様の本文と書き方の説明だけを読ませ、決めた形で中身を書かせた。SPEC-0001 と SPEC-0003 の両方で、一回で検査に合い、画面に描けた。

問題の整理（DIS）は書いていない。この人については、問題が、人の指摘と試作への感想で具体的に分かっているためである。prepare-dev を使うほかの人に同じ問題があるかは、確かめていない。

## シナリオ

通常の場合。

- S1: AI が仕様を書き終え、ページの中身を生成して登録する。検査に合い、保存される。
- S2: 人がその仕様のページを開く。部品が出る。
- S3: 人が、試す画面で場面を選ぶ。仕様の答えと、図の上で通った道が出る。理解の確認の問いに答えると、正誤と理由が出る。

例外の場合。

- X1: AI が登録しようとした中身が、決めた形に合わない（欄が無い、数が上限を超える、図に無い箱を指す）。登録は断られ、何も保存されず、どこがどう合わないかが AI に返る。
- X2: 中身がまだ無い仕様のページを、人が開く。中身が無いことが分かり、仕様の本文は読める。
- X3: 中身を作った後で、仕様の中身（本文、主張、前提、対象外）が変わった。人がそのページを開くと、中身が前の版の仕様に結び付いていて古いことが分かる。仕様の確定の状態を変えただけでは、古くならない。
- X4（中断と再試行）: ページを開いている間に、prepare-dev との接続が切れた。接続が戻ると、人が操作し直さなくても、ページは今の中身を取り直す。

## 受入条件

- AC-1: 次の二つの仕様について、AI が仕様の本文から生成した中身が登録の検査に合い、仕様のページに五つの部品が出る（S1〜S3）。二つとも、途中で起きることや入力で結果が分かれる決まりを持つ。
  - SPEC-0001（回答の適用）: 手順が進んで状態が変わっていく仕様。Lean の証明がある。
  - SPEC-0003（検証入力の追跡と実行記録の対応）: 検証の結果がいつまで証拠になるかを、入力に対して判定する仕様。Lean の証明は無い（主張は Go のテストで確かめる）。対象は仕様の全体。
  - この二つを選んだのは、種類が違い、デモで使ったからである。どちらも、このリポジトリの中で書かれた仕様で、このリポジトリの外の仕様では確かめていない。
- AC-2: 決めた形に合わない中身は、登録が断られ、何も保存されず、どの欄がどう合わないかが返る（X1）。
- AC-3: 仕様のページに、中身がどの版の仕様に結び付いているかと、その後に仕様の中身が変わって古いかが出る（X3）。
- AC-4: 中身が無い時はそうと分かり、仕様の本文は読める（X2）。接続が戻ると取り直す（X4）。
- AC-5: 中身の文は、仕様の内部の言葉と記録の番号を、説明なしに使わない。会話の経緯を知らない読み手に中身の文だけを読ませ、「何の話か」と「約束が無いと何が困るか」を言い直せることを、確認記録に残す。約束に付ける元の主張は、仕様の文を示すもので、ここで言う中身の文には入らない（元の主張が仕様と同じであることの確かめ方は、§設計で決めること）。

## 制約

- 配るのは実行ファイル一つのままにする（REQ-0010）。
- 中身に書かれたプログラムや HTML を、画面で実行しない。中身は AI が書き、質問に答える画面と同じ所に出る。そこでプログラムが動くと、AI の書いたものが、人の代わりに質問に答えられてしまう。
- 画面から、仕様やページの中身を書き換えない。

## 対象外

- わざと間違いを入れた場合に、どの約束が破れるかを見せる機能。後で足す（DEC-0020）。
- AI が部品を自由に組み合わせること、画面に少しずつ出すこと（DEC-0023）。
- 理解の確認の答えを保存すること。
- 表示の速さの数値目標。

## 設計で決めること

- 部品ごとの中身の形の細部。デモで、中身を書いた AI が迷った所がある。
  - 流れの図は、一本道と横への分かれしか描けない。流れが二つある仕様や、落ちた後に起動し直す時の入口を置けない。
  - 場面の中で、途中で止まった所の示し方と、確かめた答えの示し方（はい・いいえ・やり終えた・止まった）の意味が決まっていない。
  - 仕様の主張のうち、どれを約束に選ぶかの基準が無い。
- 試す画面の答えをどう出すか。AI が場面ごとに前もって中身に書くか、prepare-dev に入れた決まった作りが中身のデータ（起きることや入力ごとの効果、分かれ道の表など）から求めるか。前者は、人が選べるのが AI の書いた場面だけになる。後者は、人が選んだどの組み合わせにも答えられるが、仕様の決まりをそのデータで書き切れる場合に限る（状態で答えが変わる仕様では、書き切れるかを確かめていない）。SPEC-0001 の試作は、その仕様の Lean の証明を JavaScript に手で写したもので、どちらの案でもない。どの組み合わせも試せることに価値があったことの根拠にはなる。
- 途中で起きることや入力によって結果が分かれる決まりが仕様に無い時に、流れの図、試す画面、理解の確認をどうするか（流れの図は一本道でも描ける。理解の確認は、約束についての問いなら場面が無くても作れる）。
- 人が選べる場面の範囲。最低限入れる場面（ページに出す仕様が扱う例外の場合それぞれ、など）を決めるか。
- 中身をどこに置くか（記録の一種にするか）。
- いつ、誰が生成するか（手順書のどこに書くか）。生成の入力を仕様の本文だけにするか。登録が断られた時の出し直しを、何回で止めて人に知らせるか。
- 人がどこからページを開くか。

coverage の decided は、観点の扱いが決まっているという意味で、検証済みという意味ではない。
