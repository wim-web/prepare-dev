# prepare-setup（担当の設定）

担当ごとのモデル・思考量・人数を、利用者に確認して「設定の表」に書く。prepare-dev が担当を起動するときは、この表にある値だけを使う。

## 起動する状況

- 別の担当を使うと利用者が決め、起動する段になったが、設定の表がない。
- 利用者が、担当のモデル・思考量・人数を変えたい。
- 「役割の行が設定の表にない」という理由で、担当の起動が止まった。

## 設定の表

一行が一つの役割。pstack の設定の表と同じ書き方をする。

```
設計: gpt-a, gpt-a
仕様レビュー: gpt-a, gpt-b, gpt-b
証明: gpt-b @xhigh
調査: 親と同じ

通常の思考量: high
```

- **人数**：モデルをカンマで並べた数が、同時に動かせる人数になる。違うモデルを並べてもよい。
- **思考量**：モデルの後ろに `@xhigh` のように付ける。付けなければ「通常の思考量」を使う。「通常の思考量」も書かなければ、親と同じ値で起動する。
- **思考量の上げ下げ**：表の値は出発点。進行役は、いちばん難しい作業では一段上げ、判断の作業では一段、定型の作業では二段以上下げる。変えたときは、理由が記録に残る。
- **親と同じ**：モデルを指定せずに起動する。
- 一行に役割を二つ並べてもよい（`実装, 証明: gpt-a`）。

役割の名前：

| 表に書く名前 | 何をする担当か |
|---|---|
| 調査 | 資料やコードを読んで、事実を集める |
| 設計 | 設計案を作る。並べた数だけ、違う案を並行して作れる |
| 設計の評価 | 設計案を、作った担当とは別の目で比べる |
| 実装 | 本番のコードを書く |
| 仕様レビュー | 要求・設計・形式条件を、経緯を知らない立場で読む |
| 実装レビュー | 変更を実際に動かして、不具合を探す |
| 証明 | 証明を書く |
| 説明 | 結果を説明する文や図を作る |

行を書かなかった役割は、担当を起動しない。その作業は進行役が自分で行う。

要るときだけ書く行：

| 行 | 意味 |
|---|---|
| `思考量の調整: 固定` | 仕事に合わせた上げ下げをやめ、表の値だけを使う。書かなければ「自動」 |
| `思考量の引き上げ: xhigh（検証器の時間切れ）` | 「固定」にしたとき、または二段以上上げたいときに使う。この出来事が記録にあるときだけ、その値を使える。出来事は「検証器の時間切れ」「試行の失敗」「試行の終了」 |
| `思考量の段階: low, medium, high, xhigh, max` | 思考量の並び。低いほうから書く。書かなければ、この五つ |
| `禁止する思考量: max` | どの場合も使わない値。上げ下げでも、ここにある値は選ばない |
| `禁止するモデル: ...` | 使わないモデル |
| `代わりに使ってよいモデル: ...` | 役割の行にないが、求められたら使ってよいモデル |
| `起動数の上限: 30` | 作業全体で起動してよい担当の数 |
| `実行環境で止める: on` | 設定に合わない起動を、実行環境の入口で止める（下の「実行環境で止める」） |
| `検証器の制限時間: 120` | 秒 |
| `レビューの回数の上限: 3` | |
| `日本語を整える skill: yomiyasu` | |

「レビューで必ず確かめる観点」は、同じ表の見出しの下に `- 名前: 確かめること` で並べる。書かなければ、既定の五つを使う。

### pstack の表との違い

- 行を消しても、既定のモデルには戻らない。その役割の担当は起動しなくなる。
- 表にない別のモデルへ、自動では切り替えない。
- 思考量を変えたときは、変え方と理由が記録に残る。
- pstack の表とは別のファイルに書く。pstack の表は読まないし、書き換えない。

### 置き場所

| 場所 | 使われ方 |
|---|---|
| `.ppdev/models.md` | このプロジェクトだけの表。あれば、こちらを使う |
| `~/.codex/prepare-dev-models.md`、なければ `~/.claude/prepare-dev-models.md` | どのプロジェクトでも使う表 |

## 手順

1. **今の設定を見る。** `ppdev policy show`
   どの表を読んでいるか、役割ごとの人数、読めなかった行（`warnings`）が返る。
2. **聞く前に調べる。**
   - この実行環境で使えるモデルと思考量の名前。
   - 利用者が既に使っている設定。pstack の設定の表（`~/.codex/pstack-models.md`、`~/.claude/pstack-models.md`）があれば読む。
3. **たたき台を作る。** 調べたモデル名を使い、いま要る役割の行と、通常の思考量を、一つの表にする。使う予定のない役割の行は入れない。
   既にある pstack の設定は、たたき台の材料として使う。そのまま採用したことにはしない。
4. **一回で決めてもらう。** たたき台の表をそのまま見せ、「このままでよいか、変えるところはあるか」を一回だけ聞く。モデル、人数、思考量を、別々に聞かない。
   置き場所は聞かない。このプロジェクトだけの表（`.ppdev/models.md`）に置く。どのプロジェクトでも使いたいと言われたら、そちらに置く。
   思考量の上げ下げは、何も書かなければ pstack と同じ動きになる。上げ下げをやめる、使わない値を決める、起動数に上限を置く、実行環境で止める、といった行は、たたき台では入れずに見せ、「要るなら足せる」と伝える。利用者が求めたら足す。
5. **表を書く。** `ppdev policy template` がひな形を出す。＜＞の部分を、決まった値に書き換える。使わない行は消す。
6. **読めたか確かめる。** `ppdev policy show`
   `warnings` が出ていれば直す。役割ごとの人数と使う値が、決めたとおりかを見る。
7. **できた表を利用者に見せ、決定を残す。**
   `ppdev decide --title "担当の設定を決めた" --source "<利用者の言葉>"`

## 守ること

- モデル・思考量・人数を、AI が選んで決めない。たたき台は提案で、決めるのは利用者。
- 利用者が決めていない値を、表に書かない。
- 表を書き換えるのは、利用者が変えると言ったときだけ。起動が止まったからといって、通るように表を書き換えない。
- 聞くのは一回にまとめる。聞く理由として、skill の決まりを挙げない。選ぶと何が変わるかを言う。
- 依頼の途中で、いま要らない設定を聞かない。
- 「今回だけ」の変更は、表を書き換えない。例外として記録する（`prepare-dev` の「担当を起動するとき」）。

## 実行環境で止める

`実行環境で止める: on` と書いても、それだけでは止まらない。実行環境が担当を起動する直前に `ppdev spawn gate` を呼ぶようにして、初めて止まる。

Claude Code では、`hooks/claude-code.settings.example.json` の内容を、対象プロジェクトの設定に入れる。入れていない間は、制限は手順としての指示でしかない。利用者にそう伝える。

入口が見るのは、依頼文にある起動の札と、起動の要求に含まれるモデル・思考量。実行環境が要求に思考量を含めないなら、思考量は照合できない。

## 参考にした手順

役割ごとにモデル・思考量・人数を一行で書く表と、それを利用者に聞いて作る進め方は、pstack の setup-pstack を参考にしている。表の値を出発点に、仕事に合わせて思考量を上げ下げする決まりは、pstack の poteto-mode と同じにしている。違うのは、行のない役割を起動しないこと、表にないモデルへ切り替えないこと、使わない値や起動数の上限を書けること。
