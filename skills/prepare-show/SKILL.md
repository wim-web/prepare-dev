# prepare-show（見せ方）

図、比較、文章で、利用者が次の四つをたどれるようにする。何を意味するか、なぜ決めたか、何が変わったか、どこまで確認できたか。

目的は、利用者が頭の中で関係を組み立て直す負担を下げること。情報を減らすことではない。

先に `prepare-dev` の「共通の決まり」を読む。

## 起動する状況

- 希望を具体化している途中。条件を考えている途中にも使う。
- 案を比べてもらう。
- 検証やレビューの結果を伝える。
- 変更の前後を見せる。
- 中断のあと、今の状況を伝える。
- 利用者が図の箱や矢印を指して質問・指摘した。

## 見せるのは、HTML のページ

利用者に理解や判断を求めるときは、HTML のページを一枚作り、ブラウザで開いて見せる。チャットの返事に、図のコードや長い説明を貼らない。

1. **雛形を写す。** この skill のフォルダにある `page.html` を、対象プロジェクトの `.ppdev/pages/<名前>-v<版>.html` に写す。名前は英数字で短く付ける（例: `.ppdev/pages/login-v1.html`）。
2. **本文を書く。** 雛形の見た目（`<style>`）はそのまま使い、`<title>` と、`<main>` の中だけを書き換える。少しずつ直さず、まとめて一度に書く。使わない部品は消す。`［ ］` で囲んだ仮の言葉は、すべて中身に置き換える。
3. **確かめる。** 下の「見せる前に確かめる」を通す。
4. **開く。** macOS は `open <ファイル>`、Linux は `xdg-open <ファイル>`。開けない環境では、ファイルの場所を伝える。
5. **チャットには短く書く。**（下の「チャットの返事」）
6. **直すときは、新しい版のファイルを作る**（`-v2`）。見せたあとのページは書き換えない。

守ること：

- ページは説明のための資料で、置き場所は `.ppdev/pages/` だけ。頼まれたものの本体（製品のファイル）は、ここでは作らない。
- 画面を見せるときは、入力もボタンも動かない絵にする。動く見本は作らない。
- 一つのファイルで開けるようにする。外のファイル（スタイル、スクリプト、フォント、画像）を読み込まない。
- 利用者やプロジェクトに決まった見た目があれば、雛形の見た目より優先する。

### ページに載せるもの

依頼をどう理解したかを見せるページは、上から次の順にする。小さな依頼なら、二画面ぶんまで。

| 上から | 中身 |
|---|---|
| 最初の画面 | 作るものの一文と、いちばん大事な図を一枚。ここだけ見れば、何を作るかが分かるようにする |
| 具体例 | 三つから五つ。うまくいく例、断る例、境目の例を入れる。同じ形の小さな絵を、例ごとに一つずつ並べる |
| 流れ | 順番や状態の移り変わりがあるなら、箱と矢印の図 |
| 決めてほしいこと | 利用者が選ぶ点だけ。案を並べ、選ぶと何が変わるかを絵か一行で見せる。おすすめに印と理由を付ける |
| 作らないもの、決まっていないこと | 今回の範囲に入れないもの。まだ確かめていないこと |
| 一番下 | 元にした依頼の言葉、ページの版、作った時点、図の種類 |

案の比較、検証やレビューの結果、変更の前後、再開時の状況を見せるページも、同じ雛形で作る。最初の画面に結論を置き、あとは要る部品だけを使う。

### 図の描き方

- **一つの図で言うことは一つ。** 図は `<figure>` に入れ、`<figcaption>` に、その図が言うことを一文で書く。
- **図が主役で、文章は図の説明。** 図を見れば分かることを、文章でもう一度書かない。
- **名前ではなく、仕組みを描く。** 「入力チェック」という箱を置くのではなく、何を入れると、どこを通って、どうなるかを描く。矢印には、何をすると進むかを書く。
- **違いを描く。** 案を比べるときは、同じ図を並べ、変わる箱や矢印だけを変える。
- **具体例は、同じ形の小さな絵を並べる。** 文だけの箇条書きや表にしない。
- **状態は、形・位置・線の種類・言葉で区別する。** 色だけで表さない。
- **数には絵を添える。** 棒、割合の升目など。
- **見出しは、話題ではなく、言いたいことを書く。** 「入力チェック」ではなく「空欄のままでは、先へ進めない」。
- **箱と矢印には番号を振る。** 箱は `N1`、`N2`、矢印は `E1`、`E2`。利用者が「E2 のところ」と指せる。

| 見せたいもの | 使う図 |
|---|---|
| 画面 | 画面の絵（雛形の `.screen`）。状態ごとに一枚ずつ並べる |
| 順番、状態の移り変わり、データの流れ、変更の前後 | 手描きの SVG（箱と矢印）。雛形の見本を元に、箱と矢印の位置を自分で決める |
| 具体例、うまくいかない場合、選べる案 | 同じ形の小さな絵を並べる（雛形の `.cases`、`.choices`） |
| 行の多い一覧、突き合わせ | 表 |
| 数 | 棒、升目、折れ線 |

Mermaid を使うのは、利用者が頼んだときだけ。下の `ppdev figure generate` が作る図は別。

### 避けること

- 紫系の飾り色、ネオン色、グラデーション、ぼかし、半透明の重ね。
- 絵文字、挿絵、マスコット。
- 全部を中央に寄せる。
- 順番に意味がないのに 01、02、03 と振る。
- 理由なく、雛形の見た目を作り替える。

### 見せる前に確かめる

- `grep -c "［" <ファイル>` が 0。仮の言葉が残っていない。
- 最初の画面だけで、何を作るかが分かる。
- どの図にも、言うことを書いた一文（`<figcaption>`）がある。
- 図の文字が、箱からはみ出したり、重なったりしていない。ページを画像として見られる道具があれば、一度見る。
- 断る例か境目の例が、一つは入っている。

### チャットの返事

ページを開いたら、チャットには次だけを書く。

- 作るものの一文。
- ページの場所。
- 利用者に決めてほしいこと。一つにつき一行か二行。案を選んでもらうときは、案の名前で返してもらう。なければ「これでよいか」だけを聞く。

例：

> ログイン画面を、こう理解しました。ページを開いています。
> `.ppdev/pages/login-v1.html`
>
> 決めてほしいことは一つです。ログインできたあとの行き先を、A「トップへ戻る」と B「元いたページへ戻る」のどちらにするか。おすすめは B です。
>
> 「B で」のように、案の名前で返してください。

返事の最後に、なぜ確認するのかの説明や、skill の決まりを書かない。ページを開けない環境では、作るものの一文と具体例を、文章でも書く。

## 図は二種類ある

| 種類 | 作り方 | 表示 |
|---|---|---|
| 検証対象から作った図 | `ppdev figure generate --frm <FRM> --evidence <EVD>`。受理された検証結果の、検証器に渡した内容から作る | 「検証対象から作った図」 |
| 説明図 | AI が描いた図（上の HTML のページは、これ）、または `--evidence` なしで作った図 | 「説明図」 |

説明図に、検証済みと読める表示を付けない。元の検証結果に成功があっても、図全体が検証済みになるわけではない。確認結果を載せるときは、何について、どの保存内容を確かめた結果かを書く。図の形式（Mermaid か SVG か）で、保証の有無を判断しない。

`ppdev figure generate` は、箱に `N1`、矢印に `E1` のような番号を振り、文書（`.ppdev/figures/<番号>.md`）を作る。同じ状態・同じ動きには、版を重ねても同じ番号が付く。この文書は、今は Markdown と Mermaid で出る。HTML のページに載せるときは、文書の番号と版、元にした内容の版、使った検証結果、作った時点を一緒に載せ、箱と矢印の番号を変えない。

## 見せ方の決まり

- **番号と言葉で区別する。** 状態を色だけで表さない。ラベル、形、位置を併せて使う。
- **いつの、何の図かを載せる。** 図の版、元にした内容の版、使った検証結果、作った時点。結果は「この時点の内容についての結果」として見せ、「現在」とは書かない。
- **確かめていないことを消さない。** 前提、対象外、未検証、反例、未決事項を、図の都合で落とさない。図に合わせて、検証結果の範囲を広げない。
- **畳むときは、中身があることを外に出す。** 畳んだ中に未決事項・反例・前提・未検証があれば、親にもそう表示する。
- **前後の比較は、同じものを同じ位置に置く。** 変わっていない点と、変えた点を見分けられるようにする。比較の元を、見ている途中で差し替えない。
- **頼まれていない要約で情報を削らない。**
- **結果の種類を分ける。** 形式証明、モデル検査、テスト、AI のレビューを、同じ「確認済み」にまとめない（`prepare-verify` の「結果の伝え方」）。
- 同じ内容から図と形式条件を作れても、その内容が利用者の意図どおりかのレビューは別に要る。

## 図への指摘を受け取る

まだ決まっていない段階の、説明のページへの指摘は、記録せずにそのまま受ける。ページを直して、新しい版を見せる。

`ppdev figure generate` で作った図について、利用者が「E3 について」「この矢印」と言ったら、見ていた図の版と、指した番号と一緒に記録する。

`ppdev reply record --figure <FIG@版> --element <番号> --text "<利用者の言葉>" --reply-id <この返答の番号>`

- 記録するだけで、内容には当てない。意味を変える指摘なら `prepare-requirements` へ戻す。
- 「ここ」がどこか決まらないときは、その箇所だけを確かめる。推測で付けない。
- 古い図への指摘は、今の内容との差を確かめてから扱う。そのまま今の内容に当てない。
- 同じ返答を二度受け取っても、二重には記録されない。`--reply-id` は、返答を受け取った側ではなく、返答そのものに付いた番号を使う。なければ、利用者の発言ごとに一つ決める。
- 返答を扱ったら `ppdev resolve <RPL> --to applied`、使わないなら `--to dismissed --reason ...`。

## 図が古くないかを確かめる

`ppdev figure check <FIG[@版]>`

- `current`：図の元になった内容は、今の内容と同じ。
- `unverified-for-current`：現在への適用未確認。理由が返る。

古い図を見せるとき、古い図について答えるときは、先にこれを実行し、結果を一緒に伝える。作ったあとの文書は書き換わらないので、文書自身は「今も正しい」とは言わない。

## 文章

- 日本語の説明は、設定の表の「日本語を整える skill」に書いた skill で整える（`ppdev policy show` の `polish`）。書いていなければ、整えずに出す。
- コード、識別子、数式、形式条件の原文は整えない。
- 整えるときに、意味、条件、否定、確実さ、提案と決定の区別を変えない。
- 日本語以外で説明するときは、その言語のまま出す。

## 状況を伝えるとき

`ppdev status` の内容を、次の順で見せる。

1. 決まったこと（決定と、採用済みの要求・具体例）
2. 利用者の判断を待っていること（差が出る具体例を添える）
3. 済んだことと、どこまで確かめたか（種類を分ける）
4. 済んでいないこと、確かめ直すこと
5. 次の作業
