# prepare-review-spec（仕様レビュー）

要求、具体例、設計案、形式条件を、経緯を知らない新しい文脈の確認役に読ませる。指摘は、どの記録のどの版への指摘かと一緒に残す。

先に `prepare-dev` の「共通の決まり」を読む。

## 起動する状況

利用者が、別の担当によるレビューを使うと決めているときに使う。頼まれていないのに始めない。そのうえで、次のときに起動する。

- 要求・設計案・形式条件を作った、または意味を変えた。
- 設計案を選ぶ前。
- 検証結果の読み方を確かめたい。

誤字の修正、言い回しの調整、名前の変更だけなら起動しない。

## 役の分け方

- **確認役**：新しい文脈で読む担当。会話の経緯を渡さない。渡すのはレビュー文書と、根拠資料の場所だけ。
- **解決役**：経緯を持つ側（進行役）。指摘をまとめ、対応を決める。

同じ会話の続きで読んだ結果を、独立したレビューとして記録しない。新しい文脈を作れない環境では、`--fresh-context` を付けずに記録する。その実行はレビューの完了に数えられない。

## 手順

1. **観点を確かめる。** `ppdev policy show` の `viewpoints` が、必ず確かめる観点。設定の表の「レビューで必ず確かめる観点」に書いたものが入る。書いていなければ、既定の五つ。観点の数と、確認役の人数は別のもの。人数は、設定の表の「仕様レビュー」の行で決まる。
2. **レビュー文書を作る。**
   `ppdev review bundle --target <番号> --target <番号> ...`
   要求、具体例、設計案と代替案、前提、形式条件を、一緒に読ませたいものごとに入れる。返ってきた `bundle`（文書の印）と `path` を控える。
3. **確認役を起動する。** 観点を割り振り、進行役の手順で起動する。
   `ppdev spawn check --role 仕様レビュー --target <番号> --viewpoint <観点の名前> --file <path>`
   依頼文には、下の「確認役への依頼文」と `ticket_line` を入れる。
4. **指摘を記録する。** 確認役が返した指摘を、行番号と一緒に記録する。
   `ppdev review finding --run <実行> --bundle <印> --line 25-31 --title ... --viewpoint ... --problem ... --evidence ... --example ... --impact ... --fix ...`
   行番号から、どの記録のどの版への指摘かが決まる。決まらなければ「対応先なし」として残る。推測で別の記録に付けない。確認役に場所を確かめるか、レビューし直す。
5. **回答を記録する。** `ppdev run answer <実行> --file <確認役の報告> --summary "指摘 N 件"`
   確認役が途中で止まったら `ppdev run fail`。止まった実行は、指摘ゼロとして数えない。
6. **同じ原因の指摘をまとめる。** まとめた先を理由に書いて、重複した側を閉じる。
7. **指摘に対応する。**（下の「指摘の閉じ方」）
8. **完了を確かめる。** `ppdev review status --target <番号>`
   まだ確かめていない観点、閉じていない指摘、数えなかった実行と理由が返る。`complete: true` になるまで、レビュー完了と言わない。

## 確認役への依頼文

```
あなたは、これまでの経緯を知らない読み手としてレビューする。渡した文書だけを根拠にする。
文書：<path>
観点：<観点の説明>

次を探す。
- 要求を落としていないか。未決の条件を、勝手に決めた形で書いていないか。
- 成功してほしい動作も含むか。「常に拒否する」だけで成り立つ弱い条件になっていないか。
- 文章、具体例、図、設計案、形式条件の意味が、互いに合っているか。
- 前提、対象外、外部の部品への信頼、実装との関係は妥当か。

指摘ごとに次を返す。
- 文書の行番号（範囲でもよい）
- 何が問題か
- 根拠
- 差が出る具体例
- 影響（受入条件の成否に関わるか）
- 修正案

直さない。指摘と修正案だけを返す。別の担当を起動しない。
確かめられなかった観点があれば、それも返す。
<ticket_line>
```

## 指摘の閉じ方

| 対応 | コマンド |
|---|---|
| 直した | `ppdev resolve <指摘> --to resolved --reason ... --fix <直した番号@版>` |
| 不採用 | `ppdev resolve <指摘> --to rejected --reason ...` と、下の根拠のどれか |
| 軽微として残す | `ppdev resolve <指摘> --to minor --reason ...` と、下の根拠のどれか |

不採用や軽微にするには、次のどれかが要る。書いた側の判断だけでは閉じられない。

- 反証になる保存内容：`--refutation <番号@版>`
- 新しい文脈の、別の実行による再確認：`--recheck-run <実行>`
- 利用者の決定：`--decision <決定>`

確認役が最初から「受入条件に関わらない」とした指摘（`--minor` で記録したもの）は、理由だけで軽微にできる。

修正の進め方：

- **意味を保つ修正**は、既にある決定の範囲で進める。版を重ね（`ppdev revise`）、その版を `--fix` に渡す。
- **意味を変える修正**は、変更の提案にする。対象の版、変更の前後、影響を示し、`prepare-requirements` へ戻す。
- 確認役がレビュー文書を書き換えて返しても、それは提案。正式な記録の今の版は変わらない。

## 繰り返しと停止

- 修正で版を重ねたら、前の版のレビューは今の版のレビューにならない。必要な範囲をレビューし直す。
- 回数の上限は、設定の表の「レビューの回数の上限」。上限で止めたら、未解決・未実施の範囲を残す。完了にはしない。
- 導入時の設定や既にある決定で決まることを、回ごとに利用者へ聞き直さない。新しい意味の選択、保証範囲の変更、上限を越える許可が要るときだけ確認する。
- 閉じた指摘や不採用の指摘は、新しい根拠か関係する変更があるときに見直す。

## 参考にした手順

新しい文脈の確認役と、経緯を持つ解決役を分ける進め方は、EGM の egm-review-loop を参考にしている。次の点を変えている。対象は一つの文書ファイルではなく、記録から作る文書にした。解決役は対象を直接書き換えず、版を重ねる。まとめて自動で受け入れる選択肢は置いていない。
