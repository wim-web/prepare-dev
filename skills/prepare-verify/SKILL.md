# Build と Verify（実装と検証）

目的は、承認した `SPEC-*` の版を入力に、対象コード・証明・テストを作り、実際のツールで検査して、要求に結びついた証拠（`RUN-*`）を残すこと。

## 入力

- `SPEC-*`（`record_get` で版を控える）、`DES-*` の実装計画、`DEC-*`。
- 検証プラグインごとの主張の書き方: この skill の `references/` にある `lean4.md`、`vitest.md`、`gotest.md`（先頭に、説明しているプラグインの版がある）。読み込んだ SKILL.md の置き場所から解決する（対象プロジェクトに prepare-dev のソースを置く必要はない）。

## 手順

1. `SPEC-*` の各主張について、native 参照が指すもの（定理、テスト、harness）を作るか更新する。参照の名前は仕様と一致させる。
2. 実装は `DES-*` の実装計画の順に進め、各段階でビルドとテストが通る状態を保つ。
3. `verify_run` を呼ぶ。`plugin`、`claims`（`{spec, claim}`）、`targets`（対象ファイル）、必要なら `config`。`verify_wait` で結果を受け取る。`targets`（Go では `config.packages` でもよい）には、主張の native 参照に一致するテストのあるパッケージ（Go）とファイル（Vitest）をすべて入れる。一部だけを走らせた RUN も、そのプラグインの最も新しい RUN として主張の今の結果を決めるので、走らなかったテストは今の結果に入らない。
4. 結果を読む。`result` はツールの実出力から決まる。自分の文章で「検証済み」と書いても記録にはならない。
   - `verified`: 主張ごとの `result`、`assumptions`（公理、前提）、`scope`（境界、実行したケース）を確認し、主張の保証の範囲と一致しているか見る。
   - `failed`: 反例やログ（`artifacts`）を読む。
   - `unknown` / `timeout`: 未解決として扱う。すぐに実装のバグと断定しない。
   - `tool_error` / `unsupported`: 検査自体の失敗。環境を直す。
5. `trace REQ-xxxx` で、要求から主張、証拠までが現在の版に対して `applicable` であることを確認する（主張ごとの今の結果は手順 6）。
6. 要求ごとに人に報告する項目をまとめる。証拠があるもの、未解決のもの、保証の範囲。主張の今の結果は `trace` の `current` で読む。主張が `native` に挙げたプラグインごとに、その主張を持つ最も新しい RUN が今の版に当てはまるときだけ証拠になり、その中で最も悪い結果が今の結果になる。`missing` に挙がったプラグインには今の証拠が無いので、そのプラグインで取り直す。
   要求か仕様が手の確認を求める項目は、確認ごとに、その確認を含む最も新しい確認記録と、その後の変更がやり直しの条件（仕様か設計に書いたもの）に当たるかを示す。変更は、確認記録の `checked.commit` から今の作業コピーまで（`git diff <commit>` と、`git status` に出る追跡していないファイル。コミットしていない変更も含める）。`checked` が `dirty: true` の確認記録と、`commit` も `dirty` も持たない確認記録（この決まりより前に書いたもの）は、確かめたものを特定できず今のものと比べられないので、当たるものとして扱う。確認記録が無い項目、やり直しの条件が書かれていない項目、当たる変更のある項目は、未解決として示す。
7. RUN にできない確認（配布物を別の場所で動かす、ブラウザで操作する、実機で試すなど）を手で実行したら、確認記録（kind `record`、`REC-*`）を `record_put` で新しく作る。確認は一回ごとに新しい確認記録にし、前の確認記録に新しい確認を書き足さない（書いたことの誤りや足りない `links` は直してよく、直したことを本文か `note` に書く）。本文には、何を、どの環境で、誰が（人かエージェントか）確かめたか、確かめていないことを書く。frontmatter の `checked` には、確かめたものを後から特定できる値を書く。
   - `commit`: 確かめたものを作ったソースのコミット。確認は、変更の無い作業コピー（コミットした後）から作ったもので行う。
   - 変更のある作業コピーから作ったものを確かめたときは、`commit` の代わりに `base_commit`（元のコミット）と `dirty: true` を書き、本文に、後から同じものを作れないことを書く。
   - `artifacts`: 確かめた成果物や配布物ごとに `name` と `sha256`（実行ファイルと、それを含む tar.gz は別の項目にする）。

   確かめた `SPEC-*`・`REQ-*`・`DES-*` は確認記録の `links.related_to` から指し、確かめられる側の記録には、自分を確かめた確認記録を書かない（確かめられる側の版が進むと、その版を控えたものが今の版に当てはまらなくなる。RUN は主張の SPEC と REQ の版を、質問は対象の版を、判断は見た記録の版を控える）。添付（画像、出力）は `<records_dir>/records/<id>/`（既定は `prepare/records/<id>/`）に置き、本文にそれぞれの sha256 を書く（runtime は添付を読まず、記録の版にも含めないので、添付を変えたら本文の sha256 も直す）。確認記録は証拠ではないので、主張の `result` は変わらない。

## 二つのループを分ける

| 見つかったこと | 戻る先 |
| - | - |
| 実装、証明、テストの誤り | ここで直して `verify_run` をやり直す |
| 仕様の主張が要求を正しく表していない | `prepare-specify`。主張を直し、`SPEC-*` の版を上げる |
| 設計の前提が成り立たない | `prepare-design`。`DES-*` と `DEC-*` を見直す |
| 要求そのものの誤り、矛盾、実現不能 | `prepare-requirements`。その要求を対象に質問を作り、人の判断を `DEC-*` に残してから直す |

検証に通すために要求や仕様を黙って弱めない。境界を狭める、前提を増やす、対象外を広げる場合は、それ自体を判断として記録する。

## 終了条件

- `SPEC-*` のすべての主張に今の証拠がある（`trace` で、主張の `current` があり、`missing` が空）。
- `verified` でない主張は、未解決として報告され、戻る先が決まっている。
- 証拠の `assumptions` と `scope` が仕様の `assumptions` と矛盾していない。
- 要求か仕様が手の確認を求める項目ごとに、やり直しの条件が仕様か設計に書かれていて、確認記録があり、その後の変更がやり直しの条件に当たらない（`dirty: true` の確認記録は当たるものとして扱う）。当たるものは、変更をコミットした後に、そのコミットから作ったもので確認をやり直す。やり直さずに終えるなら、人に聞いて判断（`DEC-*`）にする。
