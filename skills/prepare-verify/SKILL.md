# prepare-verify（形式化と検証）

採用済みの保証要求に対して、機械向けの条件を書き、検証器にかけ、返ってきた判定を読む。

先に `prepare-dev` の「共通の決まり」を読む。

## 起動する状況

利用者が形式証明を求めたとき、または採用された保証要求があるときに使う。頼まれていないのに始めない。そのうえで、次のときに起動する。

- 必須の性質を確かめる。
- 関係するコード、モデル、前提、検証の設定が変わった。

## 言葉

- **モデル**：「こう動く」というルールを、検証器が読める形に書いたもの。
- **実装**：実際に動かすコード。
- ルールを証明しても、コードがそのルールどおりかは別に確かめる必要がある。

## 手順

### 1. 何を確かめるかを固定する

対象の保証要求（`ppdev show <GRT>`）を読む。採用されていない、または必要な方法が決まっていないなら、ここで止めて `prepare-requirements` へ戻す。必須の保証を、使える検証器に合わせて弱めない。

次を対応づけてから書き始める。

- 守りたいこと
- 成功してほしい例と、拒否すべき例
- 境界になる条件
- 成り立つとして扱う前提
- 調べる部分と、調べない部分

### 2. 機械向けの条件を書く

今の ppdev が実行できる検証器は Lean。ほかの検証器が要る保証要求は、未対応として利用者に伝える。別の方法へ黙って置き換えない。

ファイルを分ける。

| ファイル | 内容 |
|---|---|
| モデル（例: `model/<名前>.lean`） | ルール、主張、前提と対象外の説明、証明、具体例 |
| 書き出しの断片（例: `model/<名前>Export.lean`） | モデルを実行して、図の元になる動きと、コードと突き合わせる結果を書き出す |
| 変種の一覧（例: `model/mutations.json`） | 守る性質に違反するように、ルールを一か所だけ変えたもの |

書き方：

- 主張は、出来事一つ分ではなく「どんな順番のあとでも」成り立つ形にする。一つ分だけの主張は、記録が途中で消える設計でも通ってしまう。
- 成功してほしい側の主張も書く。拒否する側だけだと、「何もしない」ルールでも通る。
- 具体例は、名前の付いた定理として書く。採用済みの具体例と一対一にする。
- 前提と対象外は、ファイルの冒頭に文章で書く。
- 変種は、どの主張が証明できなくなるはずかと組にする。主張と関係のない変更や、意味の変わらない変更は入れない。

リポジトリの `model/CancelRule.lean` が、この形の見本になる。

証明を別の担当に書かせるときの役割は「証明」。思考量の選び方は、`prepare-dev` の「担当を起動するとき」に従う。

### 3. 記録する

```
ppdev frm register --title "<名前>" --grt <GRT> --file <モデル> \
  --claim <主張> ... --example <具体例> ... --def <主張が使う定義> ... \
  --export-file <書き出しの断片> --mutations-file <変種の一覧>
```

主張の文面と定義は、検証器自身が表示したものが保存される。

### 4. レビューに出す

形式条件を `prepare-review-spec` に渡す。形式化で新しい前提や意味を加えたなら、元の要求との差を確かめてもらう。利用者の望む振る舞いや保証範囲を変えるなら、`prepare-requirements` へ戻す。

レビュー前に検証器を試すのは構わない。ただし、レビュー前の条件で得た成功を、要求全体の保証として扱わない。

### 5. 検証する

`ppdev verify lean --frm <FRM>`

返ってくるもの：

| 項目 | 意味 |
|---|---|
| `verdict` | `accepted` 受理、`rejected` 証明が通っていない、`timeout` 時間切れ、`error` 実行できなかった |
| `statement_matches_registered` | 検証した主張と定義が、記録したものと同じか |
| `audit.holes` | 未証明の穴 |
| `audit.unapproved_axioms` | 保証要求が認めていない公理 |
| `audit.flagged` | 検査を弱める書き方や、検証していないコードを信頼させる書き方 |
| `mutations` | わざと壊した変種で、主張が証明できなくなったか |

検証器が受理したことと、求める保証を満たしたことは別。受理されても、穴や認めていない公理があれば証拠にならない。時間切れは、成立とも不成立とも言えない。

主張や定義を変えたら、`ppdev frm register --id <FRM> --base <版> ...` で版を重ねる。前の版のレビューは、今の版のレビューにならない。

### 6. コードとルールを突き合わせる

保証要求が適合テストを求めるなら、モデルを実行した結果と、コードの結果を、出来事の並びすべてについて比べる。リポジトリの `internal/store/conformance_test.go` が見本になる。

```
ppdev verify test --grt <GRT> --method conformance-test --depth <長さ> \
  --cmd "<テストの命令>" --input <モデル> --input <コード> ...
```

`--input` に入れたファイルが変わると、この証拠は「要再確認」になる。結果が依存するファイルを漏らさない。

### 7. 求める保証と照合する

`ppdev guarantee check <GRT>`

- `fulfilled`：求める保証を満たす証拠が揃っている。
- `insufficient`：足りない。何が足りないかが返る。
- `undecided`：保証要求が採用されていない、または必要な方法が決まっていない。

`fulfilled` 以外で、その主張を満たしたと報告しない。

### 8. 図にして見せる

`prepare-show` に渡す。受理された検証結果があれば、そのとき検証器に渡した内容から図を作れる。

## 証明が通らない、反例が出たとき

決めつけずに切り分ける。

| 判定 | 戻り先 |
|---|---|
| 実装で再現する違反 | 手順と影響を残し、`prepare-design` で直して `prepare-review-code` へ |
| 形式条件・モデル・実装との対応の問題 | 合っていない箇所を残し、ここで直して `prepare-review-spec` へ |
| 要求どうしの矛盾、決まっていない意味 | 衝突する期待結果を示し、`prepare-requirements` へ |
| まだ分からない、原因が複数 | 足りない根拠を残し、追加で確かめる |

モデルの反例がコードで再現しないだけで、モデルの誤りとは決めない。モデルが広めに含めた振る舞いかもしれない。再現したことと、推定した原因は分けて残す。

## やってはいけないこと

証明を通すために、次のことをしない。必要なら、保証範囲の変更として提案し、利用者の決定に結び付ける。

- 要求を弱める。前提を強める。
- モデルを粗くする。調べる範囲を縮める。必要な場合を対象外へ出す。
- 信頼する外部の部品や公理を増やす。
- 必須の証明を、テストやモデル検査だけに置き換える。
- モデルを今のコードに合わせる作業を理由に、守る要求そのものを変える。

## 結果の伝え方

何を、どこまで確かめたかを、種類ごとに分けて言う。

| 種類 | 言えること |
|---|---|
| 実装に対する形式証明 | 指定した実装・主張・前提について、検証器が受理した範囲 |
| 動作ルールの形式証明 | ルール上の主張。コードとの対応は別に言う |
| モデル検査 | 設定した範囲の検査結果 |
| 適合テスト、実行テスト | 実行した場合に確認した動作 |
| AI のレビュー、利用者の判断 | 意味・設計・採否についての評価 |

ルールの証明とコードのテストを並べただけで、コード全体を形式証明したと言わない。

今の ppdev は、検証器と同じ実行の中で公理を調べている。別の検査器による再検査はしていない。結果を伝えるとき、これを確認済みに含めない。

## 参考にした手順

対象ごとの検証を作り、わざと壊して検出できることを確かめ、変更のあとに実装とのずれと不具合を分ける進め方は、pstack の create-formal-verification-skill と maintain-formal-verification-skill を参考にしている。検証器の選び方は保証要求から決める形に変え、判定の読み取りと記録は ppdev に寄せている。
