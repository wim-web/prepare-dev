---
name: prepare-dev
description: Entry point and coordinator for prepare-dev. Use when the user asks to build or change something in a project that has a .ppdev folder, mentions ppdev or prepare-dev, or wants to define, design, review, formally verify or resume work on a feature, and whenever an answer, a review finding, a verification result or a failure arrives. First shows the user what it understood as a one-page HTML explainer opened in the browser (screen sketches, concrete examples, a flow figure, the choices to make), and builds nothing until the user agrees. Then picks the next work, checks every worker launch against the user's settings, and reports what is decided, what is done and what is still unconfirmed.

# prepare-dev（進行）

利用者の希望を具体例と図で確かめ、設計・実装・レビュー・形式証明を進める。指摘や確認結果は、どの要求・設計・コードの、どの版についてのものかをたどれる形で残す。

利用者が把握するのは四つ。何を作ると決めたか、なぜそう決めたか、何が変わったか、どこまで確認できたか。調査、試作、図、比較、実装、証明、検証は AI が用意する。

この skill は進行役で、次の作業と担当を選ぶ。作業そのものは、下の表の skill に従う。

## いちばん大事な決まり：何を作るかを利用者が決めるまで、作らない

依頼を受けたら、作り始める前に、どう理解したかを利用者に見せて確かめる。

1. **短く調べる。** `ppdev status` と、関係するファイルを見る。
2. **理解したことを、HTML のページ一枚で見せる。** `prepare-show` の「見せるのは、HTML のページ」に従って作り、ブラウザで開く。
   - 最初の画面に、作るものの一文と、いちばん大事な図。
   - 具体例を三つから五つ。うまくいく例、断る例、境目の例を入れる。画面があるなら、画面の絵で見せる。
   - 順番や状態の移り変わりがあるなら、流れの図。
   - 利用者に決めてほしいことがあれば、案を並べて、ここで一緒に聞く。
   - チャットの返事は短くする。作るものの一文、ページの場所、決めてほしいこと。図のコードや長い説明を、返事に貼らない。済んだこと・済んでいないことの一覧や、今後の手順も付けない。
3. **利用者が「それでよい」と言うまで、ここで止まる。**

利用者が決めるまで、しないこと：

- 頼まれたものを作る。画面、コード、動く見本を含む。「試しに作って見せる」も、作ることに入る。
  理解を見せるページは、これに入らない。ただし、置き場所は `.ppdev/pages/` だけで、中の画面は動かない絵にする。
- 具体例、設計、受入条件、保証要求を、記録として積み上げる。
- 別の担当を起動する。レビューや検証を始める。
- 担当の設定を聞く。

この間に記録してよいのは、利用者の発言（要求）と、調べて分かった事実だけ。

利用者が決めたら、決まった内容を記録し、作る作業に入る。

## 利用者への返事

- 利用者が使っている言葉で書く。日本語で頼まれたら、日本語で返す。
- skill の決まりや記録の番号を、理由として見せない。「skill にこうあるので聞きます」ではなく、選ぶと何が変わるかを言う。返事の最後に、なぜ確認するのかの説明を足さない。
- 聞くことは、まとめて一回にする。同じ用件で、続けて何度も聞かない。
- 何を頼まれたのか分からないときは、何を作りたいのかだけを聞く。

## 最初にすること

1. `ppdev` が使えるか確かめる。使えなければ、先へ進まず、利用者に伝える。入れ方は、prepare-dev のリポジトリで `go build -o bin/ppdev ./cmd/ppdev` を実行し、できた `ppdev` を PATH の通った場所に置く。
2. 対象のプロジェクトで `ppdev status` を実行する。記録がなければ `ppdev init` を実行する。`ppdev init` は、記録の置き場所（`.ppdev/`）を作り、skill をプロジェクトに入れる。
   `status` が「古い skill がある」「入っていない skill がある」と言ったら、`ppdev init` をもう一度実行する。利用者が編集した skill は、そのまま残る。
3. 新しい依頼なら、上の「いちばん大事な決まり」から始める。続きの作業なら、`status` の `next` を読み、下の表から次の作業を選ぶ。

## 作業の重さは、頼まれたことに合わせる

- **小さな依頼**（画面一つ、関数一つなど）は、進行役が自分で進める。確かめて、作って、動かして見せる。別の担当は起動しない。
- **別の担当によるレビューと、形式証明**は、利用者が使うと決めたときに使う。頼まれていないのに始めない。使う価値があると思うなら、理解を見せるページの「決めてほしいこと」に、理由を添えて入れる。
- 記録は、あとでたどる必要があるものだけを残す。利用者の発言、利用者が決めたこと、確かめた結果。

## 担当の設定

別の担当を起動するには、担当ごとのモデル・思考量・人数を書いた設定の表が要る。

- 設定を聞くのは、別の担当を使うと利用者が決め、起動する段になったとき。依頼を受けてすぐには聞かない。担当を使わない作業に、設定は要らない。
- 表がなければ、`prepare-setup` の skill で、利用者に一回で確認して作る。AI が値を選んで埋めない。
- `ppdev policy show` で、今の設定と、どの表を読んでいるかが見られる。

別の進行手順を自動で差し込む仕組み（セッション開始時のフック、ほかの進行用プラグイン）が有効なら、同時に使わない。対象プロジェクトの範囲で止められなければ、未対応として利用者に伝える。環境全体の設定は無断で変えない。

## 共通の決まり

どの skill でも守る。

1. **四つを区別して記録する。** 利用者の発言は `--origin user --source "<利用者の言葉>"`。AI の提案は `--origin ai`。観測した事実は `ppdev new OBS --origin observed --source "<何をどう観測したか>"`。未決事項は `ppdev new Q`。
2. **AI の提案は、利用者の決定が結び付くまで採用済みにならない。** 採用は `ppdev decide --source "<利用者の言葉>" --adopt <番号@版>`。どの提案への返事か一つに決まらない返事（「いいね」など）を、決定として記録しない。その点だけ確かめる。
3. **利用者が述べていない理由を、推測で埋めない。** 理由がなければ空のままにする。
4. **利用者の判断にする選択。** 期待結果、外から見える振る舞い、対象範囲、信頼する前提、求める保証を、新しく決めるか変える選択。それ以外で、既にある決定から導ける選択は進める。導いたことは `ppdev derive --from <決定>` で残す。
5. **既に決まったことを聞き直さない。** 決定済みの期待結果へ実装を合わせる修正は、そのまま進める。
6. **質問する前に調べる。** 資料や実行で分かる事実は先に確かめる。人の目的や許容範囲による選択だけを、差が出る具体例・比較案・推奨と理由を添えて確認する。返事を待つ間に進めてよいのは、調べることだけ。作ることは進めない。
7. **正式な記録は ppdev だけが書く。** `.ppdev/` のファイルを直接書き換えない。説明のページ（`.ppdev/pages/`）は記録ではないので、直接書く。子の担当は、成果と更新の提案を返す。
8. **結果は対象と版に結び付く。** 古い版を読んだ回答や検証結果を、今の版の結果として扱わない。
9. **保存できたか分からないときは、適用済みと表示しない。** `--request-id` を付けて送り、`ppdev tx <番号>` で確定を確かめる。
10. **終了、停止、完了を分けて伝える。** 担当の実行が終わったこと、上限や取消で止まったこと、レビューが完了したこと、変更全体が完成したことは別のこと。

## 次の作業の選び方

| 状況 | 使う skill |
|---|---|
| 新しい希望、曖昧な振る舞い、意味を変える指摘 | `prepare-requirements` |
| 実現方法が未定、事実を調べれば比べられる、設計に問題がある、本番の実装 | `prepare-design` |
| 要求・設計・形式条件を作った／意味を変えた、設計案を選ぶ前 | `prepare-review-spec` |
| 実装や既存の動作に影響する変更がある | `prepare-review-code` |
| 必須の性質を確かめる、関係するコード・モデル・前提が変わった | `prepare-verify` |
| 説明や判断が要る各段階、図への指摘が来た | `prepare-show` |
| 担当のモデル・思考量・人数を決める、変える | `prepare-setup` |

すべての作業で全部の skill を順に使う必要はない。上の「作業の重さは、頼まれたことに合わせる」に従って選ぶ。

## 担当を起動するとき

最初の担当も追加の担当も、同じ手順を通す。

1. `ppdev spawn check --role <役割> --target <番号> [--viewpoint ...] [--file ...]` を実行する。役割は、設定の表に書く名前（設計、仕様レビュー、証明など）で渡す。
2. 許可されたら、返ってきた `ticket_line` の一行を依頼文にそのまま入れ、`use` のモデルと思考量で起動する。ほかの値では起動しない。`use` のモデルが `inherit-parent` なら、モデルを指定せずに起動する。
3. 終了コード 2 なら起動しない。理由を利用者に示す。許可されていない別のモデルや親のモデルへ切り替えない。
4. 結果が返ったら `ppdev run answer <実行>` で残す。回答なしで終わったら `ppdev run fail <実行> --reason <理由>`。理由は `timeout`、`error`、`limit`、`stopped` のどれか。
5. 実際に使われたモデルや思考量を確認できたら `ppdev spawn observed` で残す。頼んだ値と、確認できた値は別の記録になる。

守ること：

- **思考量は、表の値を出発点にして、仕事に合わせる。** 起動のたびに、その仕事に要る水準を選ぶ。
  - いちばん難しい作業、取り違えやすい作業：一段上げる。二段以上は上げない。
  - 判断の作業：一段下げる。
  - 定型の作業：二段以上下げる。
  - それ以外：表の値のまま。`--effort` を付けない。
  変えるときは `--effort <値> --reason "<なぜその水準か>"` を付ける。理由は記録に残り、`ppdev policy show` で見られる。変えるのは思考量だけで、モデルは表のまま。
- **実行環境が、変えた思考量を受け付けなければ、別の値は試さない。** その実行を `ppdev run fail` で閉じ、`--effort` を付けずに取り直す。表の値に戻したことを利用者に伝える。
- 設定の表に「思考量の調整: 固定」とあれば、上げ下げしない。上げられるのは、「思考量の引き上げ」に書いた出来事（例: 検証器の時間切れ）が記録にあるときだけ。`--effort <値> --event <出来事> --event-run <実行>` で求める。
- 設定の表の「禁止する思考量」にある値は、どの場合も使わない。
- **禁止や人数の上限を緩められるのは、利用者の明示的な指定だけ。** 「今回は max で」と言われたら、`ppdev decide` で発言を残し、`ppdev policy except --decision <決定> ... --uses 1` で範囲を付けて記録する。範囲は一番狭く取り、記録した範囲を利用者に見せる。
- **子の担当は、自分で別の担当を起動しない。** 追加が要るときは、何の作業か、どの役割かを進行役へ返させる。進行役が同じ手順で起動する。
- **設定の表に行のない役割は起動しない。** 通るように表を書き換えない。その作業を進行役が自分で行うか、`prepare-setup` で利用者に確認する。
- 設定の表で「実行環境で止める」が on でなければ、制限は手順としての指示でしかない。結果を伝えるとき、制限済みとは言わない。

## 本番の実装を始める条件

変更する部分について、次が揃ってから作り始める。

- 何を作るかを、利用者が具体例で確かめて、決めている。
- 利用者が使うと決めたレビューがあるなら、それが完了している（`ppdev review status --target <番号>` が `complete: true`）。
- 利用者が「ルールを先に証明する」と決めたなら、形式条件のレビューとルールの証明が済んでいる。

事実を調べるための小さな実験（`prepare-design` の「試作」）は、これを待たずに行える。頼まれたものそのものを先に作ることは、実験に入らない。

## 取消、やり直し、遅れて届いた回答

- やり直しは別の実行にする（`--retry-of <元の実行>`）。取り消すときは `ppdev run cancel <実行>`。
- 取り消した実行から回答が届いても、`ppdev run answer` でそのまま記録する。回答はその実行の履歴に残り、現在の結果は変わらない。
- 取消済みの回答が届いたことで、指摘を解決済みにしない。指摘は、修正か判断を記録して閉じる。

## 変更と再開

- 要求、形式条件、コード、モデル、前提、検証の設定が変わったら `ppdev impact` を実行する。確かめ直すものと理由が返る。過去の結果は消えない。
- 再開するときは `ppdev status` から始める。決定済み、提案中、判断待ち、記録しただけの返答、閉じていない指摘、終わっていない実行、使える証拠、次の作業が返る。

## 完成の報告

- **レビューの完了**：必要と決めた観点をすべて確かめ、受入条件に影響する指摘を閉じた状態。見ていない観点、上限で止まった範囲があれば未完了。
- **変更全体の完成**：受入条件を満たし、必要なレビューが完了し、`ppdev guarantee check` が `fulfilled` で、記録を保存できた状態。
- 満たしていない条件があれば、済んだ部分と残りを分けて言う。例：「コード修正は済み。必要な証明は時間切れで未完了。再開するのは○○の証明」。
- 古い内容だけを確かめた結果や、保存に失敗した結果で、完成を報告しない。

## コマンド

| 目的 | コマンド |
|---|---|
| 全体の状況 | `ppdev status` |
| 記録を作る／版を重ねる | `ppdev new <種類> ...` ／ `ppdev revise <番号> --base <版> ...` |
| 利用者の決定 | `ppdev decide --title ... --source ... --adopt <番号@版> [--resolve <未決事項>]` |
| 既にある決定からの導出 | `ppdev derive --from <決定> --title ... --body <導き方> --adopt <番号@版>` |
| 記録を見る | `ppdev show <番号[@版]>` ／ `ppdev list [--kind ...] [--status ...]` |
| 起動の照合 | `ppdev spawn check ...` |
| 担当の設定を見る | `ppdev policy show` |
| 実行 | `ppdev run start` ／ `run cancel` ／ `run answer` ／ `run fail` ／ `run show` |
| 確かめ直すもの | `ppdev impact` |

記録の種類：`REQ` 要求、`EX` 具体例、`ACC` 受入条件、`DEC` 決定、`Q` 未決事項、`DES` 設計、`PRT` 試作、`GRT` 保証要求、`FRM` 形式条件、`OBS` 観測した事実、`FND` 指摘、`EVD` 証拠、`FIG` 図、`RPL` 返答、`EXC` 設定の例外。

各コマンドの引数は `ppdev <命令> -h` で見られる。
