## 現行要求への置き換え（2026-11-09）

DEC-0004と、UI・CLI配布まで実装・検証する指示に基づき、この旧案の要求を置き換えた。現行の要求はREQ-0010、設計はDES-0003、受入仕様はSPEC-0004。本記録の残りは変更前の案と検討理由を保存する履歴であり、現行実装への追加要件にはしない。

配布物の版・build・配置先の不一致検出はREQ-0010/P3とDES-0003へ引き継ぐ。

## 要求

入口とデーモンは、自分がどの checkout または配布物から動いているかを `daemon.json` と `status` に出す。ソースとビルドの二系統を持つ案（C、D）では、さらにビルド成果物（C では `dist/`、D では束ねたファイル）の内容ハッシュを識別子として持ち、入口は接続時に自分の識別子とデーモンの識別子を照合して、不一致なら失敗するか、古いデーモンを止めて起動し直す（どちらにするかは設計）。識別子の無い `daemon.json`（版の報告を入れる前のデーモン）は不一致として扱う。段階 1 の案（G、B）では `daemon.json` に道具リポジトリの位置を一項目足す最小形でよい。

識別子に git sha は使わない（未コミットの編集を検出できない）。

`coverage.self` は、この要求の優先度（段階 1 で should か must か）が Q-0003 の判断であることを示す。用語は DIS-0001 の「用語」に従う。

## 根拠

- 現在は入口にもデーモンにも版・経路・checkout を報告する仕組みが無く、`daemon.json` は pid、port、url、root、started_at だけ（DIS-0001 §現状）。
- 二系統を持つと、再ビルド後の古いデーモンが黙って動く。エージェントは `status` を習慣的に呼ばないので、検出は接続時に入口側で行う必要がある（REV-0009 design_critic-3-3）。
- 版の報告を入れた直後に必ず起きるのは「識別子の無い旧デーモンが残っている」状態なので、「不明」を一致とみなすと検出の目的を失う。
- 機械で一つの指し先（PATH、利用者単位の登録）と複数の checkout の組み合わせでは、どの checkout が動いているかを見られないと食い違いに気付けない（DIS-0001 §制約）。
- 「ソースを直したが再ビルドしていない」状態は、ビルドから動く入口には知りようがない。開発のループはソース経路で守る（REQ-0007）。

## シナリオ

- 通常: Given デーモンが動いている、When `status` を呼ぶ、Then 道具リポジトリ（または配布物）の位置が表示される。C、D では識別子と経路も表示される。
- 通常（C、D）: Given 入口とデーモンの識別子が同じ、When 入口が接続する、Then そのまま動く。
- 例外（C、D）: Given 再ビルド後に古いデーモンが残っている、When 入口が接続する、Then 不一致を検出して失敗するか、古いデーモンを止めて起動し直す。
- 例外（C、D）: Given 識別子の項目が無い古い `daemon.json`、When 入口が読む、Then 不一致として扱い（落ちない）、上と同じ振る舞いをする。
- 例外（中断と再試行）: Given 再起動の途中で入口が止まった、When もう一度起動する、Then 二つ目のデーモンが立たず、`daemon.json` は一つの生きているデーモンを指す（REQ-0003 AC-6 と同じ仕組み）。

## 受入条件

- AC-1: `daemon.json` と `status` に道具リポジトリ（または配布物）の位置が出る。
- AC-2（C、D）: `daemon.json` と `status` にビルド成果物の内容ハッシュと経路（ソース／ビルド）が出る。
- AC-3（C、D）: 再ビルド後に古いデーモンが残っている状態で入口を起動すると、入口が失敗するか再起動し、古いデーモンがツールを提供し続けない。
- AC-4（C、D）: 識別子の項目の無い `daemon.json` を読んでも入口は落ちず、不一致として AC-3 と同じ振る舞いをする。

## 対象外

- デーモンの複数版共存と自動更新（DIS-0001 非目標）。
- ソース経路で動くデーモンが、起動後のソースの変更を検出すること（REQ-0007 の対象外と同じ。デーモンは `stop` で止めて起動し直す）。
