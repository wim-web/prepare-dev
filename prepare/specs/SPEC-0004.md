## 受入範囲
REQ-0009 の判断画面と REQ-0010 の配布物を検査する。画面は既存の prompt/options を使い、背景・候補の帰結・推奨理由と比較表を読めることを確かめる。単一選択・複数選択・自由記述、送信中・完了・失敗・stale の表示は実ブラウザでも操作する。回答は判断画面からだけ受け付ける（A1）。

配布物の検査（P1〜P3）は、実行ファイルを別の場所に置き、PATH を `/usr/bin:/bin` にして（そこに Node.js・npm・pnpm・Go が無いことを確かめて）行う。init、skills のコピーと更新、同時起動、識別、停止、強制終了の後の再起動、シンボリックリンク経由の root、lease ファイルを消されたデーモンとジャーナルを置き換えられたデーモンの停止、マージしたジャーナルの扱い、TypeScript 版の残したデーモンの検出、質問・回答・判断・trace・bundle・ui、MCP の入口が無いことを確かめる。別プロジェクトで実際の Lean の実行も行い、証拠の対象版を確かめる。

主張の証拠（RUN）は、checkout からビルドした実行ファイルで動かすテストの結果である。Go のテストの検証実行は `.prepare-dev/config.json` の `plugins.gotest` を使い、テストが実行中にビルドする `./cmd/prepare-dev`（input_packages）と、読むファイル（`model/**`、`ui/**` を impl_files、各パッケージの testdata は自動）を入力に含める。e2e は検査した実行ファイル（checkout からのビルドか、その sha256）を RUN の `scope.bounds` に残し、デーモンの環境の `PREPARE_DEV_E2E_BINARY` は検証実行に渡らない。次は手で実行して（人かエージェントが行い、誰が行ったかを書いて）確認記録に残す（RUN ではない）。それぞれをどの変更でやり直すか（やり直しの条件）は DES-0004 §このリポジトリでのやり直しの条件 にある（設計に置くので、条件を直してもこの仕様の版は進まない）。

- 配布物の e2e: `go run ./scripts/release` で配布物を作り、darwin/arm64 と darwin/amd64 の tar.gz から取り出した実行ファイルを、それぞれ `PREPARE_DEV_E2E_BINARY` に渡して `go test ./internal/e2e -count=1` を動かす（amd64 は Rosetta で動かす。Rosetta が無ければ arm64 だけで行い、そう書く）。
- Linux のコンテナでの実行: linux/arm64 と linux/amd64（エミュレーション）の実行ファイルを、ネットワークの無い Linux のコンテナで、PATH を `/usr/bin:/bin` にして（go・node・npm・pnpm が無いことを確かめて）動かす。行う操作は、`version --json`、`init`（skills をコピーし、MCP の設定を作らない）、`record create`、`q create`、判断画面の配信、Origin の無い回答の拒否と Origin のある回答、`q answer` が無いこと、`q wait`・`ack`・`apply` による判断、`trace`・`ui`・`bundle`、二つ目の `serve` が lease で拒まれること、`kill -9` で止めたデーモンの後の `status` が起動し直すこと、lease と daemon.json を消したデーモンが終わり、次の `status` で新しく起動すること。検証（verify）は、コンテナに検証器が無いので含めない（DES-0004 §リスクと対策）。
- TypeScript 版（342bc64）との共存と戻し方: 342bc64 を作業用の場所に展開して `pnpm install --offline` と `pnpm ui:build` を実行する。Go 版のデーモンが動いている root で、TypeScript 版の CLI の `status` が別の build として拒み、デーモンを起動しないこと。TypeScript 版のデーモンが動いている root で、Go 版の CLI の `status` と `serve` が相手を示して拒み、serve のプロセスが一つのままであること。今の prepare/ の写しを TypeScript 版で開き、記録・質問・RUN を読め、TypeScript 版がファイルを書き換えないこと。
- ブラウザでの操作: 配布物の実行ファイルで作った一時的なプロジェクトで、単一選択・複数選択・自由記述の回答、送信中の表示、完了、送信の失敗（画面を開いた後にデーモンを止める）、stale（質問の後に対象を書き換える）の表示を、実際のブラウザで確かめる。
- REQ-0010 P4 の一連の利用: 配布物の実行ファイルで空のディレクトリに init し、要求の作成、質問、判断画面での回答、`q apply` による判断、仕様と実装（Lean のモデル）、実際の検証器での `verify run`、trace までを一つのプロジェクトで通す。

画面の表示（U1）は React の部品のテストを Vitest で確かめる（`ui/` を project_dir にする）。埋め込むビルドがそのソースから作られ、その後に書き換えられていないこと（B1）と、それ以外の主張は Go のテストで確かめる。

ブラウザでの確認は実操作の記録として残す。自動テストの RUN を、画面の全操作を検証した証拠とは扱わない。
