# 回答の適用

本仕様は、人間の回答を判断（decision）として確定する手順と、中断からの回復を定める。対象は runtime の永続状態であり、プロセス内の一時状態は含めない。中断後に残るのは永続状態だけだからである。

## 1. 永続状態

| 要素 | 内容 |
| - | - |
| `records` | 記録 id → 現在の版 `{rev, sha256}`。質問の対象になる要求・仕様など |
| `questions` | 質問 id → `{subjects, answers}`。`subjects` は作成時に写した対象の版の一覧 `[{id, rev, sha256}]` |
| `answers` | 回答 id → `{question, subjects_at_answer, stale, received, closed, applied_as}`。`subjects_at_answer` は回答を保存したときの対象の現在の版の写しで、`stale` の判定の根拠として残す。`applied_as` はファイル上の適用印で、確定の写し |
| `decisions` | 存在する decision ファイルの集合。各 decision は `{id, txid}` を持つ |
| `journal` | 追記のみの列。要素は `intent {txid, answer, decision_id, subjects}`、`commit {txid}`、`abort {txid}`。実装のジャーナル（`prepare/events.jsonl`）ではそれぞれ `apply.intent`、`apply.commit`、`apply.abort` の行 |

実装では、記録は `prepare/<種類>/<id>.md`、質問と回答は `prepare/questions/<id>.json`、decision は `prepare/decisions/<id>.md` にある。ジャーナルには記録の書き込みや削除（`record.write`、`record.remove`）などの行もあるが、この仕様の状態には含めない。`.prepare-dev/index.json` は起動を速くするための補助で、無くても再構成できる。

導出する状態。

- `committed(a)`: `intent(tx, a)` と `commit(tx)` が存在する。
- `inflight`: `commit` も `abort` もない `intent` が存在する。
- `recovery_pending`: `inflight`、または abort 済み取引の仮 decision・仮適用印・未更新の stale 状態が残っている。`inflight = false` だけでは回復完了を意味しない。
- `public_decisions`: `decisions` のうち `txid` が commit 済みのもの。
- `pending`: 保存済みの回答のうち、`committed` でも `closed` でもないもの。`received` や `stale` は条件に含めない。

## 2. 操作

通常の操作は `recovery_pending = false` のときだけ受け付ける。回復が必要なときは先に `recover` を完了する。API の質問取得・未処理回答・変更の通知（SSE）は journal から確定を判定し、未確定の `applied_as` を公開しない。質問全体に別の確定済み回答があっても、各回答を個別に判定する。

| 操作 | 前提 | 効果 |
| - | - | - |
| `create_question(q, subjects)` | 対象の記録が存在 | 対象の現在の版を写して質問を保存 |
| `edit(r)` | デーモン停止中、または操作と操作の間 | 記録 `r` の `rev` を 1 増やし `sha256` を変える（外部編集） |
| `save_answer(q, a)` | 質問が存在 | 回答を保存し、対象の現在の版を `subjects_at_answer` に写す。そのいずれかが `q.subjects` と異なれば `stale = true` |
| `ack(a)` | 回答が存在 | `received = true`。`pending` には影響しない |
| `close(a)` | `¬committed(a)` | `closed = true` |
| `apply(a)` | 下記 | 下記 |
| `recover()` | なし | 下記 |

### 2.1 `apply(a)`

1. `committed(a)` なら、その `decision_id` を返して終わる（再試行は同じ結果）。
2. `closed(a)` なら拒否する。
3. `a.stale` であるか、`q.subjects` のいずれかが現在の版（`rev` と `sha256` の両方）と一致しなければ、`a.stale = true` にして拒否する。
4. 段階 a: `decision_id` を採番し、`intent {txid, a, decision_id, subjects = q.subjects}` を journal に追記する。
5. 段階 b: decision ファイル `{decision_id, txid}` を書く。
6. 段階 c: 回答に `applied_as = decision_id` を書く。
7. 段階 d: `commit {txid}` を journal に追記する。

段階の名前は実装の中断点でも使う: 段階 a が `intent`、b が `decision`、c が `question`、d が `commit`。適合テストの操作列の `crash_after` と、試験用に `prepare-dev serve --crash-after <段階>`（または環境変数 `PREPARE_DEV_CRASH_AFTER`）で起動したデーモンは、その段階を書いた直後に中断する。段階 a の追記以降、どの段階の後でも中断（crash）が起こりうる。中断後は `inflight` となり、`recover` が完了するまで通常の操作は受け付けない。

### 2.2 `recover()`

`inflight` の `intent` について、

- `intent.subjects` のすべてが現在の版（`rev` と `sha256`）と一致すれば、同じ `decision_id` で段階 b、c、d のうち未完了のものを順に行う（ロールフォワード）。
- 一致しなければ (1) `abort {txid}` を追記、(2) 仮 decision ファイルを削除、(3) 回答の `applied_as` を外して `stale = true` を保存する。各書き込みの後に再中断できる。`abort` 後は `inflight = false` になるが、清掃が終わるまで `recovery_pending = true` とする。
- 起動時には abort 済み取引も走査し、残存する仮 decision と回答を再清掃する。既に済んだ書き込みは繰り返しても結果を変えない。再中断は保存状態をそのまま残し、次の起動も同じディスク状態から再開する。

確定済み（commit 済み）の取引は、その後に対象の版が変わっても abort しない。

## 3. 主張

| 主張 | 内容 |
| - | - |
| C1 | 任意の到達可能な状態で、各回答について commit 済みの `intent` は高々一つ。`public_decisions` の各要素は commit 済みの `intent` と一対一に対応する |
| C2 | commit 済みの各取引について、`intent.subjects` は質問の `subjects` と一致し、その回答は `stale` ではない。commit は、現在の版が `intent.subjects` と一致する状態でのみ起こる |
| C3 | 保存済み回答はすべての遷移で保持される。`recovery_pending = false` の状態で、(i) 保存済みの回答は存在し続ける、(ii) `applied_as` が付いている ⟺ `committed`、(iii) decision ファイルが存在する ⟺ その `txid` が commit 済み、(iv) `pending` はファイルから計算しても journal から計算しても同じ集合になる |
| C4 | 第4節の形式でモデルが生成した操作列を Go 実装に流したとき、各段階の観測結果がモデルと一致する |

C1 から C3 は操作単位の Lean モデルで証明する。C3 の実装側は、`internal/runtime` のテストに加え、`internal/e2e` の `[C3]` が実プロセスで確かめる。段階 c と d の後にデーモンのプロセスを終わらせ、停止中に対象を編集してから起動し直し、取り消しと確定の維持を見る（C3 の native 参照がパッケージを限らない `::[C3]` なのはこのため）。`internal/store` の `[C3]` は、前提を崩すジャーナル（二つの作業コピーのマージ）を起動時に検出し、何も書かないことを確かめる（一人の書き手が書いたジャーナルの例として、TypeScript 版のジャーナルの写し `internal/store/testdata` を使う）。C2 は `committed_safety` が状態と確定時の版照合をまとめ、C3 は `quiescent_with_answers` が回答保持と整合性をまとめる。モデルは `apply` の段階 a〜d と中断を含むが、`recover` の内部は一操作に抽象化している。その内部の取り消し清掃は C5 のモデルで別に扱う。操作単位のモデルの `inflight = false` は清掃完了後の状態に対応し、実ディスク上の清掃途中を含めない。

### C5: 回復途中の再中断

`model/PrepareDev/Spec/Recovery.lean` は、対象版が変わった未確定取引一件の abort 記録、decision の有無、適用印、stale 状態、保存した回答をモデルにする。`resume` は次の一つの保存段階、`crash` は保存状態を変えない中断。任意の有限な操作列で回答を保持し、続けて三回 resume すれば清掃が完了し、完了状態は再回復で変わらないことを `PrepareDev.Recovery.recovery_safe` で証明する。中断が永久に続く場合の進行は保証しない。段階は abort ログ、仮 decision の削除、回答 JSON の更新という三つの状態変更であり、補助的な index や record.remove ログの更新回数は数えない。

`lake exe prepare-model recovery` が生成する 48 本の操作列（`model/traces/recovery.jsonl`）を `internal/runtime/recovery_test.go` で実装へ流す。48 本は、apply の三つの中断点（段階 a・b・c の後。その後に対象を編集して取り消しの回復に入る）ごとに、最初の四手を `resume`（次の保存段階を一つ行う）か `crash`（何も保存せずに中断する）にした 16 通りで、その後に `resume` を四回続ける。形式は第4節の終わりに書く。各保存段階の後に中断し、実ファイルの状態、回答保持、回復待ち中の通常操作拒否、未確定印の非公開を比較する。モデル上の証明と、実装について実行した trace の範囲の適合テストを区別する。

### C6: 公開する確定状態と回復待ち

API の質問取得・未処理回答・通知は `apply.commit` を根拠に各回答の `applied_as` を組み立てる。保存途中の仮適用印は公開しない。通常の質問操作は清掃中も拒否する。`internal/runtime` の `questions_test.go` と `recovery_test.go` の `[C6]` を同じ検証実行に含める。C6 は実装テストによる保証であり、C5 の Lean 定理が API や UI を証明するという意味ではない。

## 4. 適合テストの操作列の形式（C4 用）

モデルの実行可能定義が操作列を列挙し、各段階の後の観測を JSON Lines で出力する。Go 側は同じ操作を実装に対して行い、観測を比較する。ここでの操作列（trace）は、記録のつながりを表示する `prepare-dev trace` とは別のもの。

生成は `cd model && lake exe prepare-model gen --depth N [--max-traces M] [--seed S]`。記録 R1・R2、質問 Q1（対象 R1）・Q2（対象 R1 と R2）、回答 A1（Q1 への回答）・A2（Q2 への回答）の上で、ちょうど N 手の操作列を決定的な深さ優先で列挙し、M 本（既定 2,000）で打ち切る。`--seed` は候補の操作を試す順を回す（既定 0）。打ち切ったときにどの操作列が入るかは、この順で決まる。`model/traces/depth-4.jsonl` は depth 4 の全 165 本、`model/traces/depth-6.jsonl` は seed 0 の depth 6 の先頭 2,000 本。`model/bin/test` は両方とリカバリーの操作列をモデルから作り直し、保存しているファイルと一致することを確かめる。

`internal/runtime/conformance_test.go` は環境変数 `PREPARE_DEV_TRACES`（リポジトリのルートからのパス）のファイルを、無ければ depth-4 を流し、流したファイルと本数・手数・不一致の数を、gotest プラグインが RUN ごとに用意するディレクトリ（`PREPARE_DEV_BOUNDS_DIR`）に書いて RUN の `scope.bounds` に残す。このリポジトリの検証実行は `.prepare-dev/config.json` の `plugins.gotest` の `env` で depth-6 を指定する。

操作列がモデルの生成したものであることは、次の二つで結び付ける。`model/bin/test` は操作列を作り直して保存しているファイルと一致したときだけ、モデルのソース（Lean のファイル、lakefile.toml、lean-toolchain、lake-manifest.json）の digest を `model/traces/model.sha256` に書く。`internal/runtime` の `[C4][C5]` のテストは、今のモデルの digest をこれと照合し、違えば失敗する（モデルを変えたのに照合し直していない）。モデルのソースと操作列のファイル（`model/**`）は `impl_files` で入力に記録するので、どちらかが変われば C4・C5 の RUN は当てはまらなくなる。

一行の形式。

```json
{"trace": 12, "step": 3, "action": {"type": "apply", "answer": "A1", "crash_after": "question"}, "observe": {"inflight": true, "pending": ["A1"], "committed": {}, "closed": [], "stale": [], "public_decisions": [], "result": "crashed"}}
```

`action.type` と引数。

| type | 引数 | 意味 |
| - | - | - |
| `create_question` | `question`, `subjects: [record]` | 2章の `create_question` |
| `edit` | `record` | 外部編集 |
| `save_answer` | `question`, `answer` | 回答の保存 |
| `ack` | `answer` | 受領 |
| `close` | `answer` | 終了 |
| `apply` | `answer`, `crash_after: null \| "intent" \| "decision" \| "question"` | 適用。`crash_after` があれば、その段階まで行って中断する |
| `recover` | なし | 回復 |

記録 id は `R1`、質問は `Q1`、回答は `A1`、decision は採番順に `D1`、`D2` … とする。実装側は自分の id 体系へ対応づける。

`observe` の項目。

| 項目 | 内容 |
| - | - |
| `inflight` | 進行中の取引があるか |
| `pending` | `pending` に含まれる回答 id の昇順一覧 |
| `committed` | 回答 id → decision id |
| `closed` | `closed` の回答 id の一覧 |
| `stale` | `stale` の回答 id の一覧 |
| `public_decisions` | 公開される decision id の一覧 |
| `result` | 直前の操作の結果。`ok`、`applied`、`already_applied`、`rejected_stale`、`rejected_closed`、`rejected_inflight`、`crashed`、`recovered_forward`、`recovered_abort`、`noop` |

操作列の生成は決定的で、同じ入力から同じ出力を得る。中断後は `edit` と `recover` だけを生成し、`recover` の後に通常の操作へ戻る。

### 回復の操作列（C5 用）

一行が一本の操作列で、`{"stage": "intent"|"decision"|"question", "initial": 観測, "steps": [{"action": "resume"|"crash", "observe": 観測}]}` の形。`stage` はどの段階の後に中断したか。観測は `answer`（保存されている回答の数）、`aborted`（abort が記録済み）、`decision`（仮 decision のファイルがある）、`applied`（回答に適用印がある）、`stale`、`ready`（清掃が完了し `recovery_pending = false`）。
