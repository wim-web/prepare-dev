## 契約

具体化案 §2.5 の入力版追跡を検査する。テストだけでなく impl_files と Vitest 設定も import の探索開始点にする。入力の上位ディレクトリ（対象 root まで）の package.json、pnpm-lock.yaml、package-lock.json、npm-shrinkwrap.json、yarn.lock、bun.lock、bun.lockb、pnpm-workspace.yaml、.npmrc、tsconfig.json と、workspace 解決に用いる package.json を含める。

静的な文字列 import から得られない入力は impl_files へ明示する。依存パッケージの内容は manifest・lockfile に従って導入されたことを前提にする。ファイル版の比較は内容の sha256 で行い、変更・削除時は現在版への適用を未確認に戻す。

## 検証

plugins/vitest/src/index.test.ts の [V1] で入力収集と推移的依存・metadata の変更を検査し、packages/runtime/src/runs.test.ts の [V1] で記録済み入力の変更・削除による適用可否を検査する。二つのファイルを同じ verify_run の targets に含める。これは実行したケースの範囲のテストであり、任意の動的依存を自動発見する証明ではない。

## 根拠

REV-0035/f3 の修正。2026-11-09 の「その6件全部直して、検証までやって」という指示に基づく。既存の入力追跡契約を具体化し、未収集入力の責任範囲を明記した。

## V2: 実行中ジョブの識別

単一runtimeで検証を開始するとき、結果JSONの完成前に作る実行artifactディレクトリをIDの予約として扱う。次の実行と再起動後の採番はその予約を使用済みとして数える。異なるジョブが結果・ログを共有してはならない。runs.test.ts の [V2] で非同期の完了を止めたまま二つのジョブを起動し、IDと保存先の分離、および再起動後の非再利用を確かめる。

この問題は6件の修正後の検証実行で追加発見した。RUN-0006 は二つのジョブが同じIDを使ったため、今回の完了証拠には使用せず、新しいIDで実行し直す。
