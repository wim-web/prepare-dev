## 実装側の証拠（vitest プラグイン）

`SPEC-0001` の C1〜C3 には Lean の定理に加えて vitest の参照（`questions.test.ts::[C1]` など）を付けた。`RUN-0002` は vitest プラグインがテストファイルの推移的 import（core と runtime の 14 ファイル）を `inputs.files` に記録して `verified` になった。

適用可否の確認: `packages/runtime/src/questions.ts` に1行加えると `status` は `runs current: 0, not applicable: 1`、`trace REQ-0001` の C1〜C3 は「現在の証拠なし」になり、元に戻すと `runs current: 1` に戻った。

## Lean（lean4 プラグイン）

`model/` は SPEC-0001 の状態機械の Lean 4.35 モデル（core Lean のみ、Mathlib なし）。`step : State → Action → State × Result` が §2 の操作を段階 a〜d と中断・回復込みで実行可能に定義し、`Reachable` 上の不変条件 `Inv`（13項目）を全遷移で保存することから、`applied_at_most_once`（C1）、`committed_matches_snapshot`（C2）、`quiescent_consistent`（C3）に加えて `step_commit_guard`（commit は現在の版が intent の版と一致するときだけ）と `answers_monotone`（回答は消えない）を証明している。`model/bin/test` は `sorry` 等の走査、`lake build`、`#print axioms`（propext / Classical.choice / Quot.sound のみ）、生成器の煙テストを行う。

`RUN-0003`（`pnpm cli verify run --plugin lean4 --claim SPEC-0001/C1 --claim SPEC-0001/C2 --claim SPEC-0001/C3 --target model/PrepareDev/Spec/Theorems.lean`）は `verified` / `proof`。記録には各定理の仮定を含む完全な命題（`#check`）、公理一覧、対象と推移的依存（`Invariant`、`Lemmas`、`Reachable`、`State`、`Step`、`lean-toolchain`、`lakefile.toml`、`lake-manifest.json`）の sha256、`SPEC-0001@rev2` と `REQ-0001@rev1` の参照が残る。

適用可否の確認（条件13）: `Theorems.lean` から二段先の `Lemmas.lean`（`Theorems → Invariant → Lemmas`）に1行加えると `status` は `not applicable: 1`、`trace` の C1〜C3 は `RUN-0003 applicable=false (input model/PrepareDev/Spec/Lemmas.lean)` になり、戻すと `runs current: 2` に戻った。仕様・要求・対象ファイルの変更で適用不可になることは `packages/runtime/src/runs.test.ts` で自動確認している。

## C4（適合テスト）

`lake exe prepare-model gen` が SPEC-0001 §4 の形式で操作列と観測を列挙する（`model/traces/depth-4.jsonl`: 165 trace・660 step、`depth-6.jsonl`: 2000 trace・12000 step）。`packages/runtime/src/conformance.test.ts` は各 trace を一時ディレクトリの runtime に流し、中断は `SimulatedCrash` フック、回復は `Runtime.open` で再現して、`inflight`・`pending`・`committed`・`closed`・`stale`・`public_decisions` と apply/recover の結果を比較する。

- `pnpm test` は depth-4 を再生する（約20秒）。
- `RUN-0005` は vitest プラグイン経由で depth-6 を再生し `verified`（`bounds: {traces: 2000, steps: 12000, failures: 0}`、約5分）。入力には test の import 閉包に加え、trace ファイル、Lean の生成器と意味論（`Main.lean`、`Gen/*.lean`、`Spec/State.lean`、`Spec/Step.lean`）、`lean-toolchain` を記録した。
- `RUN-0004` は同じ内容で `failed`。原因は vitest の既定 60 秒タイムアウトで、適合の不一致ではない（artifact の `vitest.json` に "Test timed out in 60000ms"）。結果は実出力から決まるので、記録はそのまま残している。
- 開発中に見つけた不一致は4件あり、いずれも比較側のバグ（`committed` のキー順）だった。モデルと実装の意味的な差は見つかっていない。

C4 が示すのは「生成した trace の範囲で観測が一致する」ことであり、実装の証明ではない。

## UI

`packages/ui` は React 19＋json-render 0.22（`defineCatalog`、`defineRegistry`、`Renderer`、`JSONUIProvider`、`useBoundProp`）で、`vite-plugin-singlefile` により 1 ファイル（約 392 KB）にビルドし、デーモンが `/` と `/q/:id` で配信する。spec は runtime の `ui-spec.ts` が質問 JSON から生成し、UI 側で変更は不要だった。

条件1・2の確認: このリポジトリで `Q-0001`（対象 `REQ-0001@1`、`SPEC-0001@2`）を作り、`pnpm cli q wait Q-0001` を待機させた状態でブラウザ（`/q/Q-0001`）から推奨案 `hold` と補足を送信した。待機中の呼び出しは `status: answered` で `ANS-0001-1` を受け取り、`question_pending` → `question_ack`（未処理のまま）→ `question_apply` で `DEC-0001` が確定した。`trace REQ-0001` は `Q-0001 applied`、`DEC-0001 committed=true reviewed_current=true`、C1〜C3 の現在の証拠 `RUN-0003`（proof）と `RUN-0002`（test）、C4 の `RUN-0005` を返す。

## 記録の注記

- `RUN-0001` は daemon が設定ファイルを読む前に実行され、入力に実装ファイルが含まれなかったため、ファイルを削除した。journal の `run.record` は残っており、id は再利用されない。
- `.prepare-dev/index.json` と `daemon.json` はキャッシュと実行時情報で、Git 管理しない。

## dogfooding

このリポジトリ自身を対象に `pnpm cli init --root .` を実行し、`.mcp.json`、`.codex/config.toml`、`.agents/skills/prepare-dev` を用意した。`SPEC-0001` は直接書いたファイルを runtime が発見し（`record.discover`）、その後の編集は `external_change` として rev 2 に上がった。`REQ-0001` は `record create` で runtime 経由で作成した。
