# マイルストーン2の検証記録

[具体化案](../proposals/PRO-0001.md) 6章のマイルストーン2の完了条件を、どう確かめたかの記録。題材は「prepare-dev の配布と起動（CLI のビルド配布）」。具体例の実行はすべて、この checkout のデーモン（`pnpm cli serve --root .`）に対して CLI 経由で行い、レビュー役は Claude Code の `Agent` tool で会話履歴なしのサブエージェントとして起動した。工程を進める側は、Discover と Requirements をサブエージェント E1、Design と Specify の前半をサブエージェント E2 が、skills を読んで行った。E2 は SPEC-0002 rev 2 まで進めたところでモデルの利用上限で止まった。Specify の残り（再確認、rev 3、質問）は親のセッションが同じ skills に従って行った。その後、人がレビューを続けるよう指示したので（DEC-0002、DEC-0003）、DES-0001 と SPEC-0002 の両方で `prepare-review` の上限（工程ごとに四 round）まで round 3 と round 4 を行い、rev 5 まで直した（下の「レビューを上限まで続けた経緯」）。

## 具体例の経緯（Discover と Requirements）

実行はサブエージェント一つ（E1）が skills を読んで CLI で行った。人の回答はまだない。

- `DIS-0001`（rev 5）: 問題、現状、関係者、価値、代替案、制約、費用と期間、仮説（H1〜H8）、非目標、リスク、成功、用語。調査で前提が変わった: tsx の起動は 0.25 秒で問題ではない、`tsc -b` の出力は `exports` が `src/*.ts` を指すので今は動かない、`--root` 自体が三つ目の絶対パスである。レビュー役が「コードを書かない案」（利用者単位の MCP 登録と `~/.agents/skills`）と esbuild の案を加えた。
- `REQ-0002`〜`REQ-0008`（rev 2、`links.derived_from: [DIS-0001]`）: 絶対パスを書かない（must）、入口が位置と root を設定なしで決め対象外では副作用を出さない（must）、版・経路・checkout の報告と接続時の照合（should）、skills の解決と切れ・古さの検出（must）、UI の配信（must）、開発のソース直実行とテスト（should）、配布物だけで動く段階 2（could）。
- `REV-0001`〜`REV-0009`: DIS の round 1〜3 × {zoom_out BRAINSTORM、comprehension REVIEW、design_critic BRAINSTORM + heilmeier}。`REV-0010`/`0011`: REQ × {comprehension、design_critic + feature-spec}。合計 Blocker 0、Major 47、Nit 43。Major は一件（`REV-0005` の design_critic-1-3、PATH 依存）を質問に回したほかは直した。declined は二件。
- `Q-0002`（対象 DIS-0001@5）: 問題の範囲と案（作らない / 段階 1 を G、B、C / 段階 2 を D）、skills の置き方、PATH 依存への備え。`Q-0003`（対象 REQ-0002〜0008@2）: REQ-0004 と REQ-0008 の優先度、起動時間の目標、対象外のときの振る舞い、既存登録の移行。どちらも UI（`/q/Q-0002`、`/q/Q-0003`）で未回答。
- 収束は到達しなかった。BRAINSTORM の persona は round ごとに三〜四件の新しい Major を出し、前の指摘を再開することはなかった。費用（persona 一つの round で十万 token 前後）から DIS は三 round、REQ は一 round で止め、経緯を `DIS-0001` の「レビューの経緯」に書いた。

## 具体例の経緯（Design と Specify）

一巡目のあとに直した skills で行った。人の回答はまだないので、前段の質問は推奨案を前提にし、その前提を `DES-0001` の「未決事項」と `SPEC-0002` の `assumptions` に書いた。

- `DES-0001`（rev 3、proposed、`links.derived_from: [REQ-0002〜0008]`）: 案 G（利用者単位の登録）の設計。決定点 1〜7、検討した代替案、実装計画（フェーズ 0〜5）、検証計画、前段との照合。
- `REV-0012`〜`0016`: DES の round 1 {zoom_out BRAINSTORM、comprehension REVIEW、design_critic BRAINSTORM}、round 2 {zoom_out と design_critic の REVIEW による再確認}。Major 15 件はすべて直し、Nit 2 件を棄却した。round 2 の Major 2 件は round 1 の修正で入ったもので、rev 3 で直したが再確認はしていない。
- `Q-0004`〜`Q-0009`（対象 DES-0001@3 と関係する REQ）: 入口コマンドの形、dogfooding の登録を git 管理に入れるか、自動起動の同意の関門、`--migrate` が古い symlink を消すか、REQ-0006 の読み方、DES のレビューを再確認せずに進むか。独立した判断ごとに一つの質問になった。
- `SPEC-0002`（rev 3、proposed、主張 27 件、すべて vitest）: REQ-0002〜0007 の受入条件 27 件のうち 18 件に主張があり、9 件は理由つきで対象外。REQ-0008（段階 2）は対象外。
- `REV-0017`〜`0021`: SPEC の round 1 {comprehension REVIEW、design_critic BRAINSTORM、implementation_readiness BRAINSTORM}、round 2 {design_critic と implementation_readiness の REVIEW による再確認}。Major 25 件、Nit 35 件をすべて直した。

Specify の段階で設計の欠陥が見つかった。DES-0001 決定点 2 は、古い `daemon.lock` を `rename` で引き取る手順を「`rename` は同じ元ファイルに一つしか成功しない」として採用していた。しかし `rename` はその時点のパスに効くので、先に引き取ったプロセスが作り直した生きた lock を、後のプロセスが奪える。DES-0001 が別案を棄てた理由と同じ競合である。SPEC-0002 の決定的テストの場合分けは、この誤った前提をそのまま主張に写していた。作者と二つのレビュー役が独立に見つけた。skills の規則どおり、DES-0001（質問の対象）は直さずに、推奨する直し方を前提に SPEC-0002 を書き直し、DES に書き戻す内容を本文に残し、直し方を質問 Q-0010 にした。あわせて、場合分けのテストから漏れる競合を見つけるための状態探索（C27）を足すかを Q-0011 にした。

入口の費用の実測も前提を変えた。待機する入口は tsx のラッパーと子の二プロセスで、RSS の和は約 170 MB だった（DES-0001 §7 は約 95 MB としていた）。十セッションで約 1.7 GB になり、Q-0003 の「非対象で待つか終わるか」の判断材料に関わる。SPEC-0002 の「DES-0001 に反映すべき事項」と Q-0012 に書いた。

## レビューを上限まで続けた経緯

人は「全部つづけて」と答えた（チャット。Q-0009 と Q-0015 の回答として保存し、DEC-0002、DEC-0003 に確定した）。作者が置いていた「工程ごとにレビュー役を五回まで」は費用から置いた予算で、`prepare-review` の上限ではなかった。そこで DES-0001 と SPEC-0002 の両方で、三つの観点（DES は zoom_out、comprehension、design_critic、SPEC は comprehension、design_critic、implementation_readiness）を REVIEW mode で round 3、round 4 と回した。

- round 3（REV-0022〜0027。DES-0001 rev 3、SPEC-0002 rev 3 を読んだ）: Major は DES 7 件、SPEC 8 件。`init` が排他を通らずに回復処理を走らせて二つ目の書き手になる経路、停止が `daemon.json` を先に消すので停止中に二つ目の書き手が立つ経路、`daemon.lock.break` の保持者を待つ輪に上限が無い、保持者が正常に終わった後に存在しない `daemon.lock.break` を消せと案内する誤判定、Codex のタイムアウトが利用者単位の登録で落ちる、サブディレクトリでツールが消える、フェーズ 0 の掃除の手順がこのリポジトリの未コミットの記録を消しうる、など。DES-0001 rev 4 は排他の性質 P1〜P7 だけを持ち、手順を SPEC-0002 に委ね、レビューの経緯を本文から外した（round ごとに版が進んで質問が古くなるのを避けるため）。SPEC-0002 rev 4 は起動手順を状態を明示した遷移関数にした。
- round 4（REV-0028〜0033。rev 4 を読んだ）: Major は DES 3 件、SPEC 5 件。設計に未決の手順のファイル名が残っていた、`daemon.json` の生存判定が EPERM を生存とし再起動の後の pid の再利用に弱い、新しい停止の順序が人の回答を待つ長い要求の終わりを待って最長 1 時間かかる、書き手の境界の定義が箇所ごとに違う、状態探索の規模（`serve` 三つで約 1,600 万状態）。rev 5 で直した。
- 上限に達したので、rev 5 は読み直していない。続けるか、受容して実装へ進むか、要求へ戻るかを質問 Q-0025 にした。
- 版が進んだ記録を対象にした未回答の質問は、新しい版で作り直し（Q-0016〜Q-0024）、古い質問（Q-0004〜Q-0008、Q-0010〜Q-0014）を `question_cancel` で取り消した。SPEC が固めた契約の扱いを聞いていた Q-0013 は、DES-0001 rev 4 が手順と形を SPEC に委ねて問いが無くなったので、置き換えずに取り消した。

傾向: Major の数は減りきらなかったが、中身は「設計の誤り」から「直した仕組みの細部」へ移った。round 3 と 4 はどちらも、直前の修正が新しい Major を持ち込んでいた（停止の順序を直すと長い待ちの問題が生じた、など）。同じ指摘に二つ以上のレビュー役が独立に行き着くことが多く（round 3 の排他の待ち、round 4 の書き手の境界と停止）、会話を持たないレビュー役の指摘の再現性は高い。費用はレビュー役一回あたり約 16 万〜25 万 token。

## 残している課題

- 質問一つに複数の独立した判断をまとめて出す UI（選択肢の群）は作っていない。
- finding 一件だけを更新する操作（`findings` 配列全体の再送以外）はない。
- 要求専用の評価基準（EGM にはない）は書いていない。
- Codex のサブエージェントでレビュー役を起動する手順は書いたが、実行していない。Codex の実セッションでの MCP 接続も未確認。
- DES-0001 rev 5 と SPEC-0002 rev 5 の修正は、どのレビュー役も読んでいない。`prepare-review` の上限に達したので、続けるかどうかは Q-0025 で人が決める。
- この例で回答から作った判断は DEC-0002 と DEC-0003 だけで、どちらも人がチャットで答えたものを作者が回答として保存した。UI から回答して判断を作る流れは M1 の Q-0001 → DEC-0001 で確かめたが、この例ではまだ通っていない（設計と仕様の質問はすべて未回答）。
