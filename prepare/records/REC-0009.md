## 配布物の e2e

darwin/arm64 と darwin/amd64（Rosetta）の実行ファイルを、それぞれ `PREPARE_DEV_E2E_BINARY` に渡して `go test ./internal/e2e -count=1 -v` を動かした。どちらも全部通った（TestDistribution の 8 つの場面と TestCrashRecovery の 2 つ。arm64 は 14.3 秒、amd64 は 32.6 秒）。出力は添付の e2e-darwin-arm64.txt と e2e-darwin-amd64.txt。

## Linux のコンテナでの実行

linux/arm64 と linux/amd64 の実行ファイルを、redis:7-alpine のコンテナで動かした。ネットワークは無く、PATH は `/usr/bin:/bin` で、go・node・npm・pnpm が無いことを確かめた。添付の linux-check.sh が SPEC-0004 §受入範囲 の操作の並びを流し、両方で全部通った（添付の linux-arm64.txt と linux-amd64.txt）。

- `version --json`: build は上の実行ファイルの sha256 と同じだった。
- `init`: skills を .agents/skills と .claude/skills に 7 つずつコピーし、MCP の設定を作らない。
- 記録と質問: `record create`、`q create`、判断画面の配信（404,249 バイトの HTML）。
- 回答の経路: Origin の無い回答は 403 で拒み、ページの Origin のある回答は受け付ける。`q answer` は「questions are answered in the decision UI」で拒む。
- 判断と一覧: `q wait`・`ack`・`apply` で DEC-0001 ができ、`trace` がそれを示す。`bundle` と `ui --no-open` も動いた。
- 書き手を一つにすること:
  - 二つ目の `serve` は「another daemon holds the lease」で終わる。
  - `kill -9` したデーモンの後の `status` は、新しいデーモンを起動する。
  - lease と daemon.json を消したデーモンは、1.8〜1.9 秒で終わり、次の `status` で新しいデーモンが起動する。

検証（verify）は、コンテナに検証器が無いので含めていない。

## ブラウザでの操作

darwin/arm64 の実行ファイルで一時的なプロジェクトを作り（`init --no-skills`、PATH は `/usr/bin:/bin`）、要求一つと質問五つを置いた。それを Claude Code のアプリ内のブラウザで操作した。

| 質問 | 操作 | 画面の表示 | 記録された回答 |
| - | - | - | - |
| 単一選択 | 推奨の「受け付けない」を選んで送信 | 「回答済み」「回答を保存しました。エージェントが続きの作業を進めます。」、回答の中身と「エージェント処理待ち」 | choice reject、stale false |
| 複数選択 | 「メール」と「アプリの通知」を選んで送信 | 送信の直後に「保存しています…」、その後に回答済みと「メール、アプリの通知」 | choice mail・push |
| 自由記述 | 文を書いて送信 | 送信の直後に「保存しています…」、その後に回答済みと、「自由記述」と書いた文 | 文だけ（choice は空） |
| stale | 質問の後に対象の要求を書き換え（status が subjects changed since asked を示した）、「はい」で送信 | 「資料が更新されています。回答は保存されますが、自動では判断に反映されません。エージェントによる再確認が必要です。」、送信中の表示、回答に「対象が更新済み」 | choice yes、stale true |
| 失敗 | 画面を開いた後にデーモンを止め、「はい」で送信 | 「回答を保存できませんでした。Failed to fetch 入力は残っています。接続を確認して再送してください。」。選んだものは残った（添付の browser-failure.jpg） | 記録されず、質問は回答待ちのまま |

## REQ-0010 P4 の一連の利用

darwin/arm64 の実行ファイルを別の場所に置き、PATH を `/usr/bin:/bin` にした。空のディレクトリで、次を一つのプロジェクトで通した。

1. `init` で skills を 14 か所（7 つずつ二つの配置先）にコピーした。
2. `record create` で REQ-0001（受付人数は定員以下）を作った。
3. `q create` で、比較表と推奨つきの質問 Q-0001 を作った。判断画面で、背景・比較表・人に尋ねる理由・推奨と理由が読めることを見た（添付の browser-question.jpg）。推奨の「受け付けない」を選んで回答した。
4. `q wait`（answered）、`q ack`、`q apply` で DEC-0001 を作った。
5. DEC-0001 を根拠にした SPEC-0001 と Lean のモデル（受け付ける人数は申し込みの数と定員の小さい方）を書き、`verify run --plugin lean4` で RUN-0001 が verified（proof）になった。公理は propext だけで、今の版に当てはまった（添付の p4-run.json）。
6. `trace REQ-0001` が、DEC-0001 と、SPEC-0001 の C1 の今の証拠 RUN-0001 をつないだ（missing は空）。`status` は未処理の回答 0、古い判断 0。

## 実際の Vitest での確認（SPEC-0003 §検証）

ui/node_modules の Vitest 5.1.0 を、リポジトリの外の一時ディレクトリで動かした。node_modules はそこへのシンボリックリンク。テストのファイルは添付の vitest-cases.txt、結果は添付の vitest-results.json にある。

- Vitest をそのまま動かしたときのレポート:
  - afterAll が例外を投げたファイル: レポートのファイルは status が failed で、message にその例外、テストはすべて passed。同じファイルのテストが失敗していても、message は残る。
  - 存在しないモジュールを import するファイル: status が failed、message は「Cannot find module …」、assertionResults は空。
  - テストの後に setTimeout から例外を投げるファイル（後ろに待つテストがあり、ファイルの実行中に例外が起きる）:
    - そのファイルだけなら、終了コードは 1 で、レポートは success: true、失敗したテストもファイルも無い。
    - ほかのファイルのテストが失敗する実行では、終了コードは 1 で、未処理の例外はレポートにも標準出力にも出ない。
  - describe の中の afterAll の例外は、同じファイルのほかのテストが失敗すると、レポートのファイルの message が空になる。
  - globalSetup が返した後始末が例外を投げると、終了コードは 1 で、例外は標準出力にだけ出て、JSON のレポートには入らない。
- 配布物の実行ファイルの vitest プラグインを通した結果（verify run を三回）:
  - 一回目: afterAll の例外、テストの失敗と afterAll の例外が同居するファイル、読み込めないファイル、未処理の例外、describe の中の afterAll の例外、参照の前半が空の主張を、一度に流した。
    - 参照の前半が空の主張は、読み込めないファイルのために failed になった。ほかのファイルの主張（ok）だけが verified、それ以外の主張は failed だった。
    - 要約に、それぞれの理由（「teardown broke」「Cannot find module …」「unhandled error: late failure」「nested teardown broke」）が残った。tool.extra.exit_code は 1。
    - reporter は onTestRunEnd で呼ばれ、未処理の例外は起きたテストファイルとテストを持っていた。describe の中の afterAll の例外も、ファイルのエラーとして書き出された。
  - 二回目: `isolate: false` を書いた project では、reporter の isolate が false になった。未処理の例外は起きた場所の分からないものとして扱われ、どの主張も verified にならなかった（要約に「test files are not isolated」）。
  - 三回目: globalSetup の後始末の例外は、reporter の未処理の例外にもファイルのエラーにも入らなかった。ほかのファイルのテストが失敗する実行では、成功したテストの主張は verified のままだった（仕様の対象外のとおり）。
- onFinished の経路: Vitest 2 までのファイルのタスクの形（filepath、tasks、result.errors）を模した入力を、node で reporter（プラグインのソースから組み立てたもの）に与えた。ファイルのエラー、二段の describe のエラー、未処理の例外とそのファイル・テストが書き出され、hook は onFinished だった。

## 気付いたこと（この確認の範囲の外）

- vitest プラグインは、targets を Vitest にファイルの絞り込みとして渡す。しかし Vitest は名前の部分一致で絞り込むので、渡していないファイルも走った。
  - 今回、一回目の実行では、iso/ok.test.js・iso/late.test.js・gs/ok.test.js が加わった。
  - 走ったファイルは RUN の targets にも入力にも入らない。そのため、そのファイルの結果（未処理の例外など）が主張の結果に響いても、そのファイルを変えたときに RUN が当てはまらなくならない。
  - このリポジトリの vitest の RUN（ui/src/QuestionView.test.tsx だけを渡す U1）では、同じ文字列を名前に含むファイルが無いので起きない。
  - 別の作業で直す。
- 前の確認（REC-0007）の「テストの後に setTimeout から例外を投げる」を、テストの中で 0 ミリ秒の setTimeout を置いてすぐ終わる形で試すと、ファイルの実行が先に終わった。例外は出ず、終了コードは 0 だった。前の確認と同じ結果は、後ろに待つテストを置く形で得た。
