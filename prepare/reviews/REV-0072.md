### この文書が提案していること
prepare-dev の本体（記録を書くデーモン、CLI、検証プラグイン）を Go で書き直す。React で作った判断画面のビルドと skills を埋め込み、OS・アーキテクチャごとの実行ファイル一つで配る（DES-0004、REQ-0010）。エージェントは skills の手順に従って CLI だけを使う（MCP の入口は無い）。人は判断画面で説明・比較・推奨理由を読んで回答し、回答の API は同じ Origin のブラウザからの要求だけを受け付ける（REQ-0009、DES-0002、SPEC-0004）。RUN が現在の版の証拠になるのは、記録した入力・ディレクトリの一覧・プラグインの版が今と一致する間だけで、テストの外で失敗があれば verified にしない（SPEC-0003）。今回の変更は三つ。docs/ にあった prepare-dev 自身の文書を runtime 経由の記録（REC-0001〜0007、PRO-0001）に移して参照を ID に置き換えた。手で確かめたことは kind record の「確認記録」に書くことにした。guidance を prepare-verify の skill の references/ に移し、`prepare-dev guidance` を無くした。

### この文書によると既存の仕組みはどう動くか
CLI は `.prepare-dev/daemon.json` と `/api/identity` を見て、version と build が同じデーモンにだけ接続する。デーモンがいなければ、同じ実行ファイルを `serve` で端末から切り離して起動する。デーモンは `<root>/.prepare-dev/lease` の flock で書き手を一つにし、記録・質問・RUN・ジャーナルを TypeScript 版と同じ形式で書く。操作の前には、lease とジャーナルが開いたときのままかを確かめる。init は skills を `.agents/skills` と `.claude/skills` にコピーし、skills.json の digest を見て、編集されていない skill だけを更新する。検証はデーモンが lean4・vitest・gotest で走らせ、入力とディレクトリの一覧を RUN に残す。一方 DIS-0001 は、時点を書かないまま TypeScript 版を「現状」として書いている。そこでは tsx でソースを動かし、init が機械ごとの絶対パスで MCP の登録と skills の symlink を書く。これは上の仕組みと食い違う。
