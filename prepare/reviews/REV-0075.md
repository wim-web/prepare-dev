### 指摘 1
- **severity:** Major
- **scope:** DES-0004 §工程の外の記録（checked の項目と、確かめた build と今の build の比較）、skills/prepare-verify 手順 6・7、REC-0008 の checked。REV-0071 f2・REV-0073 f2・REV-0074 f3 の処理。

- **rationale:**

### 指摘 2
- **severity:** Major
- **scope:** DES-0004 §工程の外の記録（製品の規則と、このリポジトリのやり直しの条件が同じ節に混ざっている）、skills/prepare-verify 手順 6・7。
- **summary:** すべての対象プロジェクトに配る prepare-verify の手順に、prepare-dev 自身の配布物の確かめ方が入った。具体的には、実行ファイルの version と build、それに用語の build である。多くの対象プロジェクトにはこれに当たるものが無く、skill の中で build も定義されていない。
- **rationale:**
  - **一つの節の中で区別されていない。** §工程の外の記録 は「これは製品の規則で、skills … がすべての対象プロジェクトのエージェントに求める」と書いた後、同じ節で次の二つを続けて書いている。
    - checked の項目（実行ファイルの version と build と commit）
    - やり直しの条件（埋め込み、リリースのスクリプト、デーモンの起動と識別、`PREPARE_DEV_E2E_BINARY`）
    やり直しの条件はこのリポジトリにしか当てはまらないが、節の中で製品の規則と区別されていない。
  - **skill に prepare-dev 固有の概念が入った。**
    - prepare-verify の手順 7 は「checked に確かめた実行ファイルの version と build（sha256）と commit を書く」と求めている。
    - 手順 6 は「どの build を確かめた確認記録があるか、それが今の build と違うか」を求めている。
    - build は DES-0004 の用語（prepare-dev の実行ファイルの sha256）で、skill を読む対象プロジェクトのエージェントには定義が無い。
  - **記録の形がばらつく。** ライブラリ、Web アプリ、Lean のプロジェクトでは、何を version・build と書くのかが決まらない。prepare-dev の版を書くのか、自分の成果物の値を書くのかが分からないからである。このリポジトリの中でも、checked の形はすでに三通りある。
    - REC-0006: version・artifact・sha256
    - REC-0007: commit・version・build・build_of
    - REC-0008: version・build・build_of・artifact_sha256・base_commit・worktree
  - **提案:** 製品の規則は「確かめたものを後から特定できること」に留める（commit と、配布物を確かめたならその sha256）。version・build とやり直しの条件は、このリポジトリの手順として DES-0004 の中で分けて書く。
  - 照らした項目: §3（置き場所: 製品の層とこのリポジトリの使い方を分ける）、§1（プロジェクトの方針との整合）。

### 指摘 4

- **scope:** DES-0004 new_decisions（プラグインが設定の項目と型を Capabilities で宣言する）、SPEC-0003 V5、internal/plugin の configKeys と CheckConfig。REV-0073 f5 の処理。
- **summary:** 設定の項目と型の宣言（configKeys）が、各プラグインの cfg とは別の一覧になった。あわせて、独自の型の名前（string・strings・int・env）と、それを確かめる検査が新しくできた。
- **rationale:**

  - **既存の関数も黙って捨てる。** ConfigString・ConfigStrings・ConfigInt は、型が違うと黙って既定値にするか、要素を捨てる。
  - **提案:** 読む側を厳しくすれば、規則は一つで済む。たとえば Go 標準の encoding/json を使い、プラグインごとの設定の構造体へ DisallowUnknownFields で読む。こうすると知らない項目も型の違いも同じ誤りになり、宣言と読み込みが一か所にまとまる。runtime は RUN の番号を取る前に、この読み込みを呼べばよい。
  - **宣言が無いと保証も無い。** Config が nil のプラグインはどんな設定も受け付けるので、V5 の保証は宣言がある場合に限られる。
  - 照らした項目: §4（標準の仕組みの利用）、§2（単純さ）。
