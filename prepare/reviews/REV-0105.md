paraphrase: "提案: どのプロジェクトでも、AI が仕様を書き終えたら、仕様と、それにつながる要求・設計・決定（仕様が指すものと仕様を指すもの）と、zod の一つの定義から書き出した references/spec-page.md（JSON Schema を含む）を読み、部品ごとに決まった欄を持つ JSON（ページの頭、例の流れ、困ることと約束、流れの図と試す画面、理解の確認、扱っていないこと）を書いて、読んだ仕様の記録の版と一緒に ppdev page put で渡す。デーモンは format、JSON Schema による形、Go のつながり、claims との照合、版の一致を検査し、合えば spec（結び付けた版と仕様の中身の digest）と generated（生成した時の版と、主張・前提・対象外ごとの sha256）を足して prepare/pages/<SPEC>.json に書き、SSE で page を知らせる。ジャーナルには書かない。判断画面は /spec/:id に部品と状態（無い・今の版・古い・読めない）を出す。古いかは status などを除いた仕様の中身の digest で決め、生成の後に文が変わった所に印を付ける。仕様が変わったら、AI が Git の差分で決まりが変わったかを判断し、変わっていれば生成し直し、変わっていなければ rebind で結び直す。古いか読めない中身は status の pages に出る。食い違いの確かめ方は推奨の B を人に聞く。既存の仕組み: 判断画面は質問の画面一つで、対象の記録を『関連する記録（補足）』に出す。書き手はデーモンだけで、記録は rev と sha256 の版を持ち、status だけを変えても版が進み、更新には読んだ版を渡す。ジャーナルに知らない種類の行があると前の版は起動しない。書き込みはジャーナルの矛盾などで止まる。Emitter は question・run・job を SSE に流す。手順書は init が入れ、古いと status が示す。ビルドで書き出したものは build.json と uibuild の検査で照らす。回答の API は判断画面の Origin だけを受け、誤りは error・message・details で返す。trace は links を両向きにたどる。"
