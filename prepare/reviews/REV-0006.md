## 言い直し

**この文書が提案していること**
prepare-dev の入口（CLI と MCP）が「自分がどこに置かれ、どう起動されるか」をソースの置き場所に頼って決めているため、対象リポジトリに書かれる MCP 登録と skills 参照が機械固有の絶対パスを四つ含む。これを PATH 上の `prepare-dev` という一つの名前に間接化し、root は cwd か環境変数で渡すことで、登録と skills 参照を git で共有できる形にする（段階 1）。道具リポジトリの checkout と `node_modules` なしで動く配布（段階 2）まで含めるかは人の判断（質問 1）に委ね、段階 1 なら tsx でソースを実行する起動シム（案 B）、段階 2 なら esbuild で単一 JS に束ねる（案 D）を推奨する。`tsc -b` ビルド（案 C）は B より手間が多く段階 2 に届かないので推奨しない。付随して、版・経路の報告の新設、UI HTML の解決方法、skills の置き方、PATH 依存を受け入れるかを論点として挙げている。

**この文書によると既存の仕組みはどう動くか**
開発では `pnpm cli`（tsx）でソースを直接実行し、各 package の `exports` が `src/index.ts` を指すため、`tsc -b` の出力を `node` で起動すると失敗する。`init` は `toolRepoRoot()` で求めた tsx と CLI ソースの絶対パス、および対象リポジトリの絶対パス（`--root`）を `.mcp.json` と `.codex/config.toml` に書き、skills は道具リポジトリへの絶対 symlink で `.agents/skills/` に置く。入口は `.prepare-dev/daemon.json` でデーモンを探し、無ければ同じ絶対パスで `serve` を detached 起動する。デーモンは `packages/ui/dist/index.html`（約 392 KB）を読んで UI を配信し、無ければ簡易フォームに落ちる。入口にもデーモンにも版や実行経路を報告する仕組みはない。

（確認した事実: `toolRepoRoot()`／`ensureDaemon`／`cmdInit`／`rootOf()`／`uiHtmlPath()` と `Server.ui()`／`vitest.config.ts`／`node packages/cli/dist/index.js` の失敗（再現）／tsx 経由 0.27 秒・`node` 単体 0.03 秒（再現）／esbuild 0.28.2／UI HTML 391,843 バイト／MCP version 固定／`daemon.json` の項目／Codex `startup_timeout_sec = 30`／Node >= 26／`exports` を持つ 6 package／具体化案 §1.7。いずれも記述と一致。）

## 指摘

**1.** Major — DIS-0001 §仮説 H1 / §代替案 B・C・D / §費用と期間
推奨案 B・C・D はすべて H1（`args` に絶対パスなしで両ホストが接続できる）に依存するが、H1 は未検証のまま費用表と推奨が組まれており、H1 が片方のホストで偽だったときの代替が書かれていない。
根拠: persona「Faulty Assumptions」「Architectural Bottlenecks」。Heilmeier「Risks」「Timeline」。緩和要件: H1 の検証を案の選択より前の工程として費用表の先頭に置き、偽だった場合の逃げ道を明記する。

**2.** Major — DIS-0001 §関係者（dogfooding）/ §代替案 B・C・D / §リスク
PATH 上の `prepare-dev` は機械で一つの大域状態であり、道具リポジトリの checkout が複数ある場合（worktree、別ブランチの clone、対象＝道具リポジトリ）に、編集中の checkout と実行される checkout が黙って食い違うリスクが挙げられていない。
根拠: persona「Unmitigated Risks（unscalable state management）」。緩和要件: 対象＝道具リポジトリのときは自分のソースを優先する規則か明示の上書きを設計要件にし、§成功に別 checkout での確認を加える。

**3.** Major — DIS-0001 §成功 vs §制約・§リスク（版・経路の報告）
C・D では「版・経路の報告を新設しないと検出できない」と制約に書いているのに、§成功にその検出を確かめる項目がなく、「Node の版を切り替えた後の挙動を確認する」にも合否基準がない。
根拠: Heilmeier「Metrics & Exams」、persona「Standard Compliance Gaps」。

**4.** Major — DIS-0001 §仮説 H4 vs §代替案 D / §用語「束ねる」
D は「単一ファイル」に「UI HTML を同梱する」と書くが、H4 は `server.ts` がパスを受け取る前提に立っており、HTML を JS に埋め込むならこの前提は成り立たず、別ファイルで添えるなら D は単一ファイルではない。
根拠: persona「Faulty Assumptions」「Stress-Test Assumptions」。`Server` の `uiHtml` はパスで、`ui()` はリクエストごとに `fs.readFileSync` する。

**5.** Nit — DIS-0001 §代替案（skills の置き方 (iii)）
コピー方式の更新は「`init` の再実行が要る」とあるが、現在の `init` は既存の項目があれば必ず飛ばすため、再実行しても更新されない。

**6.** Nit — DIS-0001 §代替案 D / §仮説 H6 / §用語
「guidance 文書」が未定義で、誰が・何を基準に解決して読むのかが書かれていない。現在それを読む側は存在しない。

**7.** Nit — DIS-0001 §現状（登録）/ §価値（段階 1）
既存の対象リポジトリに残る絶対パス登録からの移行手順（`init` が既存ファイルを上書きしない点）が触れられていない。

**8.** Nit — DIS-0001 §価値（起動時間）/ §代替案 D
D の成果物の大きさと起動時間（「推定 0.05 秒」）が未計測で、根拠がない。

- 2（Major）: 制約とリスクに複数 checkout の食い違いを加え、優先規則か明示の上書きを設計要件とし、成功に worktree での確認を加えた（rev 3）。
