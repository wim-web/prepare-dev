## 言い直し

**この文書が提案していること**
prepare-dev の入口（CLI と MCP）が「自分の置き場所をソースの位置から逆算する」構造をやめ、`tsc -b` の `dist/` を実行形にして各 package の `exports` と `bin`（`prepare-dev`）を `dist/` に向け、`pnpm link --global` で `prepare-dev` コマンドを PATH に置く（案 C）。`init` は `command: "prepare-dev"` という機械に依存しない登録を書き、UI の HTML はパッケージ内の相対位置で解決する。これで `.mcp.json` と `.codex/config.toml` を git 管理に戻し、道具リポジトリの移動や再インストールが対象リポジトリに波及しないようにする。単一ファイル化（D）と npm 公開（F）は後続とし、C はそれらを妨げない形にする。費用は所有者一人で半日程度（仮説）。

**この文書によると既存の仕組みはどう動くか**
入口は `pnpm cli`（`tsx packages/cli/src/index.ts`）で動き、各 package の `exports` は `./src/index.ts` を指すため、`tsc -b` の出力を `node` で起動すると `@prepare-dev/runtime` が `src/index.ts` に解決され `./errors.js` が見つからず失敗する。`init` は `toolRepoRoot()` で道具リポジトリを求め、`node_modules/.bin/tsx` と CLI ソースの絶対パスを `.mcp.json` と `.codex/config.toml` に書く（機械固有なので gitignore）。入口の `ensureDaemon` は `.prepare-dev/daemon.json` で稼働中デーモンを探し、無ければ同じ絶対パスで `serve` を detached 起動する。デーモンは `packages/ui/dist/index.html`（約 392 KB）を読んで UI を配信し、無ければ簡易フォームに落ちる。skills は道具リポジトリの `skills/*` を対象の `.agents/skills/` に絶対パスで symlink する。

（リポジトリで確認した事実: 上記の記述はコードと一致。`node packages/cli/dist/index.js` は記録どおり `ERR_MODULE_NOT_FOUND` で落ちる。`daemon.json` に版情報はない。「具体化案 1.7」は `docs/2026-11-08-concretization-proposal.md` §1.7 に実在。）

## 指摘

**1.** Major — DIS-0001 §問題 / §成功（中間） / §用語「可搬な登録」 / H1
現在の登録には道具リポジトリだけでなく対象リポジトリの絶対パス（`--root <root>`）も入っており、提案はこれを症状にも成功基準にも含めていないため、案 C を完遂しても「登録を git で共有できる」という価値は成立しない。
根拠: `cmdInit` は `args: [cli, "mcp", "--root", root, ...]` を書く。`rootOf()` は `--root` 省略時に `PREPARE_DEV_ROOT` → `process.cwd()` に落ちるので解決自体は可能だが、「ホストが MCP サーバをプロジェクト直下の cwd で起動する」という前提は Codex と Claude Code のどちらについても未検証で、H1 に含まれていない（Faulty Assumptions / Metrics）。緩和: H1 を「args に絶対パスを一つも含まない登録で両ホストが接続し、root を cwd（または環境変数）から正しく決める」に書き換え、中間試験を「`init` の出力に絶対パスが一切含まれない」にする。

**2.** Major — DIS-0001 §制約（二系統・古いデーモン） / §リスク（やる場合） / H6
ソース直実行と dist 実行の乖離、および再ビルド後も古いデーモンが動き続けるリスクを、記録は認識しながら緩和を H6（証拠なし）に丸投げしており、現状の仕組みでは H6 は成立しない。
根拠: `daemon.json` は版情報を持たない。`McpServer` の version は `"0.0.1"` 固定、CLI に版表示コマンドはない。さらに `exports` を `dist/` に向けると、`vitest.config.ts`（alias なし）のテストも `@prepare-dev/runtime` を `dist/` に解決するため、ソースを直しても古い dist を検査して通る経路が生まれる（Unmitigated Risks）。緩和: (a) `daemon.json` と `status` にビルド識別子を入れ、入口が比較して警告または再起動する。(b) 開発経路（tsx と vitest）が常に `src` を見るよう、条件付き exports か vitest alias を設計で確定する。(c) H6 を「決定」に上げる前に二系統を同時に動かす実験を一度行う。

**3.** Major — DIS-0001 §制約（ホストの PATH） / §リスク（やる場合） / H1 / §成功（最終）
`command: "prepare-dev"` だけの登録は「ホストの PATH にグローバル bin があるか」に全面的に依存し、記録自身がその失敗様式を列挙しながら、緩和も最終試験への組み込みもしていない。
根拠: 既存の単一障害点を PATH と Node 版ごとの global 領域という別の単一点に移し替えているだけで、「黙って壊れる」性質は変わらない（Unmitigated Risks: single points of failure）。緩和: 最終試験に「GUI から起動した Claude Code と Codex で接続できる」と「Node 版を切り替えた後の挙動」を明記する。設計では、解決済み bin の絶対パスを書く fallback、`node` + パッケージ相対パスで起動する形、起動失敗を対象リポジトリ側に残す仕組みのどれを採るかを決める。

**4.** Major — DIS-0001 §代替案 C / §非目標（skills の置き方は扱う） / §成功（最終）
案 C は MCP コマンドの可搬化だけを扱い、記録が「扱う」と宣言した skills の置き方に何も答えていないため、最終試験は skills が dangling になっても合格してしまう。
根拠: `cmdInit` は道具リポジトリへの絶対 symlink を書く。A〜F のどの案にも skills の扱いがなく、成功基準にも出てこない（Standard Compliance Gaps: New Approach が問題の一部に答えていない）。緩和: C に skills の配置方式を書き、最終試験に「移動後も skills が解決される」を加える。

**5.** Nit — DIS-0001 §制約（費用）/ Heilmeier: Cost, Timeline
費用「半日程度（仮説）」が §制約に一行あるだけで、Timeline は独立に答えておらず、C が所有者以外には配布問題を解かないことと費用対効果の関係も明示されていない。

**6.** Nit — DIS-0001 §現状（方針）/ H5 / §成功（最終）/ §用語
「具体化案 1.7」「`question_apply`」「検証プラグイン」はこのプロジェクト固有の語で、用語表に定義も参照先もない。

**7.** Nit — DIS-0001 §代替案 C / H3 / §非目標
`tsc -b` は `include: ["src"]` のため `*.test.ts` も `dist/` に出力しており、ビルド成果物に vitest 依存のファイルが混ざる。C の段階で `exclude` を決めておくと「F を妨げない」方針と整合する。

（経済性の確認: ローカル CLI の配布形態であり、定量コストは閾値には遠い。）
