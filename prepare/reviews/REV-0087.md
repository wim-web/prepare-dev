## 言い直し

**この文書が提案していること**

prepare-dev の判断画面のアプリ（人が質問に答えるブラウザの画面）に、仕様一つを人が理解するための「仕様のページ」を足す。ページには次の四つが出る。(1) 具体的な一件を順にたどる例、(2) 仕様の約束と、それが無いと困ること、(3) 人が「途中で起きること」を選ぶと、仕様の答え（何を確かめ、どう終わり、何が残るか）が流れの図と並んで出る試せる画面、(4) 答えると正誤と理由が出る理解の確認。ページの中身（説明）は仕様の本文とは別に用意する。求めているのは、内部の言葉や記録の番号を知らなくても読めること、試せる画面の結果がモデルの結果と同じだと検証の実行（RUN）で確かめられること、説明が無い・古い・読めない・接続が切れた時にもそうと分かって画面が止まらないこと。説明を最初に用意するのは SPEC-0001 だけで、仕組みをどのプロジェクトの仕様にも使えるものにするか SPEC-0001 専用にするかは未決（設計の前に人に聞く）。優先度は仮の should で、作るかどうかは設計を人が確認した後に決まる。

本文に明記が無く、推測で読んだ所が二つある。「約束」は仕様の主張を平易に言い直したもの、理解の確認の答えは保存しない、と読んだ。

**この文書によると既存の仕組みはどう動くか**

今の判断画面のアプリは質問の画面一つで、人が見られるのは質問の文章と表、対象の記録の本文だけ。図を描く部品も、仕様を試す画面も無い。Markdown は HTML を実行せずに表示し（REQ-0009）、prepare-dev は実行ファイル一つで配る（REQ-0010）。SPEC-0001 には Lean のモデルがあり、本体の外に作った試作では、それを AI が JavaScript に手で写して、Lean が出した操作列 2,000 本と照合した。試作は三つの版があり、画面の形は最初から方向が合っていて、直したのは例と文言だった。

この節の事実はリポジトリと合っていた（ui/src は質問の画面一つで Markdown は skipHtml、depth-6.jsonl は 2,000 本、REQ-0009 の引用句と REQ-0010 の制約は本文にある、SPEC-0001 の C5 は回復途中の再中断）。
