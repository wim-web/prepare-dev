### 2. 「現在の版を確かめた確認記録」の版が決まっておらず、DES-0004 の完了条件と合わない
- **severity:** Major
- **scope:** DES-0004 §用語「確認記録」・§TypeScript 版からの移行（完了条件）。skills/prepare-verify の終了条件の四つ目
- **summary:** 新しい終了条件「現在の版を確かめた確認記録がある」の「現在の版」は、確認記録については定義が無い。DES-0004 の移行の完了条件（確認記録に残っていること）とも、REC-0007 の実態（配布物・Linux・TypeScript 版との共存の確認は 85477c7 の時点）とも合わない。
- **rationale:**
  - **定義が無い:**
    - RUN についての「現在の版に当てはまる」は SPEC-0003 に定義があり、入力の sha256 で判定できる。
    - 確認記録には、何の版を確かめたかを控える決まった場所も定義も無い。候補は、記録の rev・sha256、実行ファイルの version、build の sha256、commit のどれか。DES-0004 の用語でも「版」は二つの意味で使い分けている。
  - **今どちらとも読める:**
    - この条件をそのまま当てると、このリポジトリの SPEC-0004（§受入範囲が人の確認を求める四項目）は今、終了条件を満たさない。REC-0007 自身が、配布物・Linux・TypeScript 版との共存の確認は「85477c7 の時点のもので、この修正の後に配布物は作り直していない」と書いている。
    - 一方 DES-0004 §TypeScript 版からの移行は、RUN には「今の版に当てはまる」を求め、確認記録には「残っていること」しか求めていない。こちらで読めば移行は完了している。
    - どちらが意図なのか、記録からは決められない。
  - **やりすぎ（YAGNI）:** 手で行う確認を変更のたびにやり直させる関門は重く、作者自身も守れていない。根の問題は「人が確かめたことを記録に残し、追えるようにする」ことで、関門は要らない。
  - **代わりの案:**
    - 最も単純なのは、関門ではなく報告にすること。確認記録には、確かめた build（実行ファイルの sha256 か commit）と、その後に確かめ直していないことを書く。手順 6 の報告で、今の build との差を人に示す。
    - どうしても関門にするなら、新しい仕組みは作らない。今ある識別（version と build の sha256。REC-0007 も配布物の sha256 を載せている）で確かめた build を書き、今の build と比べる、と一文で定義する。
    - 確認を一回するごとに新しい REC を作る（RUN と同じく後から書き足さない）なら、REC ごとに版が一つに決まり、比べ方も簡単になる。
  - **照らした項目:** persona の YAGNI と Context Insufficiency、Zoom-Out Standard §1 Root Problem Focus。このプロジェクト固有で定義されていない言葉（確認記録についての「現在の版」）。
