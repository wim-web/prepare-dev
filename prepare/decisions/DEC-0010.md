## 決定

docs/ と guidance/ を片付けた変更を、prepare-review の手順書どおりにレビューする。変更は次の四つ。

1. docs/ にあった記録を REC-0001〜0007・PRO-0001 として prepare/ に移し、八つの記録（DIS-0001、DES-0002・0003・0004、REQ-0009・0010、SPEC-0003・0004）にあった docs/ のパスを記録の ID に置き換えた。
2. DES-0004 で、確認記録の置き場を prepare/ の記録に変え、記録でないものの置き場（配布物の README は scripts/release、構想で参照した資料の一覧は docs/references.md）と理由を書いた。
3. skills（prepare-dev、prepare-verify）に、人が確かめたことは REC に書き、工程の記録を docs/ などに書かない規則を足した。
4. 検証プラグインの書き方の説明（guidance）を prepare-verify の skill の references/ に移し、`prepare-dev guidance` コマンドを無くした。

版の進んだ記録の種類に応じた段階（問題の整理・設計・要求・仕様のそれぞれに手順書が定める段階）を、会話履歴の無いレビュー役で回す。各段階の最初は BRAINSTORM、直した後の再確認は REVIEW、上限は段階ごとに四回とする。

## 代替案

- 二人で見る（質問で推奨した案）: 中身のある変更（2〜4）と置き換えの一覧を一つの資料にまとめ、全体の妥当さを見る役と読んで分かるかを見る役に一回ずつ見せる。採らない。
- レビューしない: 省いたことと理由を記録に残して完了とする。採らない。

## 理由

人が判断画面の Q-0031 で「手順どおり」を選んだ。質問には、手順どおりに回すと 100 万 token を超えること、範囲を絞ると手順の一部を省くことになることを示していた。
