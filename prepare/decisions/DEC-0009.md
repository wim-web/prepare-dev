## 判断

三回目のレビュー（REV-0068〜0070）で残った四つの穴を直し、実際に動かすテストで確かめてから証拠の RUN を取り直し、コミットの確認に進む。直した箇所は、会話履歴の無いレビュー役には見せない（上限を超えた再確認はしない）。

## 残っていた四つ

1. Go: テストが自分で panic するとテストのプログラムが終わり、後ろのテストが走らない。後ろのテストを含む主張が、前のテストだけで verified になる（REV-0068 f1、REV-0070 f1）。
2. 質問のファイルが無いときに止まる処理が、取り消しの経路と、回答が入る前の版のファイルを戻した場合に効かない。status も失敗する（REV-0068 f2、REV-0070 f2、REV-0069 f2）。
3. git clean で消えた質問のファイルは戻せず、デーモンがそのプロジェクトで二度と起動しない（REV-0068 f3、REV-0069 f1）。
4. Vitest 3 より前の版では、describe の中の afterAll の例外を書き出せない（REV-0070 f3、REV-0068 f6、REV-0069 f5）。

## 代替案

- 直してもう一回レビュー: 四つを直し、上限を超えて三人でもう一回見る（約 45 分、約 100 万 token）。それでも穴が出たら、また聞く。
- 直さずに限界として書く: 四つを直さず、仕様に既知の限界として書く。いちばん速いが、穴が残る（一つ目は「古い成功を今も有効と言わない」という目的に直結する穴）。

## 理由

四つとも直し方がはっきりしていて、実際に go test と Vitest を動かすテストで確かめられる。レビューは回すたびに前より細かい穴を出していて（Major 以上が 10、9、4）、もう一回回しても新しい穴が出る見込みが高い。人が判断画面の Q-0029 で、推奨どおり「直して完了へ」を選んだ。
