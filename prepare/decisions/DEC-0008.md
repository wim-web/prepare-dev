## 判断（チャットでの人の回答）

2026-11-09、会話履歴なしのレビューが上限（4 回）に達した時点で、二つのブランチや worktree で記録を書いてマージしたときの扱いについて、人が「あったところでなんなの？ ただのコンフリクトじゃん マージ時に修正するだけでは？」と答えた。エージェントが、直し方の手順は細かく書かず、壊れたジャーナルを書き込まずに status に示す検査と、ジャーナルが置き換わったらデーモンが止まる検査だけを残す方針を示し、人が「じゃあそれでいいよ」と答えた。

## 読み取ったこと

- 二つの作業コピーで書いた prepare/ のマージで起きる衝突は、普通のコンフリクトとしてマージのときに人が直す。prepare-dev は自動でまとめず、直し方の手順も書かない。
- 直した結果のジャーナルに矛盾があるか、別の作業コピーで判断に反映した回答や判断が残っていれば、デーモンは書き込まずに status の problems に示す。ブランチの切り替えなどで Git がジャーナルを置き換えたら、動いているデーモンは書かずに止まる。
- 配布物の README と prepare-dev skill には、記録は一つの作業コピーで書くこと、マージで衝突したら直すこと、直した結果がおかしければ status に出ることだけを書く。
- レビュー（REV-0060・REV-0061）の残りの指摘は、記録が実装と食い違う箇所と危険な箇所だけを直し、ほかはこの判断で閉じる。

## 棄却した案

- 直し方の手順（片方の prepare/ を丸ごと採る git のコマンド、相手側で作ったものの一覧の出し方）を書き、e2e で実際のマージを確かめる: 普通のコンフリクトとして直せば済み、手順を書き込むほどの必要がない。
- 検査も外す: 両方の行を残して解いたジャーナルで、一つの回答から判断が二つできるような状態を黙って書き進めないため、検査は残す。

## 影響

- DES-0004・SPEC-0001・SPEC-0004・REQ-0010 のマージの扱いの記述を短くする。配布物の README と prepare-dev skill の手順を短くする。
